## 代理残留清理（用户："检查一下网关层…上次关机前开了一个代理但没刷新"）

早上那条 pip `ProxyError` 的**同一陷阱再次复现**（这次是关机前开了代理又没关，代理进程随关机消失）。完整排查了 6 个可能藏代理的层：

| 层 | 排查结果 | 处置 |
|---|---|---|
| WinINet 系统代理（注册表） | `ProxyEnable=1` + `ProxyServer=127.0.0.1:7890` ← **残留** | `ProxyEnable` 置 0（**保留 ProxyServer 值**，下次开代理免填） |
| 代理进程 / 端口 | 无 clash/xray 类进程；7890 未 LISTEN；TCP 探测 False | 确认是死代理，非误判 |
| git 全局（`~/.gitconfig`） | `http.proxy` + `https.proxy` = `http://127.0.0.1:7890` ← **残留** | 两条 `--unset` 清除（git 不读系统代理，必须单独清） |
| WinHTTP | Direct access（无代理） | 无需动 |
| 代理环境变量 | 全无 | 无需动 |
| pip 配置 / npm | `pip config list` 空、npm proxy null | 无需动 |

**刷新**：改完注册表补发 WinINet 通知（`InternetSetOption` `SETTINGS_CHANGED=39` + `REFRESH=37`），让已运行进程不用重启就感知（Add-Type 内联 P/Invoke，非必需但避免"改了没生效"）。

**验证**：`api.minimax.chat` HTTP 200、`dashscope.aliyuncs.com` HTTP 404（服务可达即通）。项目侧无残留：`.env`/`.env.example` 无 PROXY 项，`nginx.conf` 的 `proxy_pass` 是正常反向代理 upstream。

**结论（下次复用）**：本机"代理层"要清的一共 **2 处**——① 注册表 `ProxyEnable`；② `git config --global http(s).proxy`。其余层默认干净。

## 修复：启动脚本「启动完成后服务莫名全关」（用户确认后改造 start.ps1）

**现象**：双击 `start.ps1` → 提示"启动完成" → 约 30 秒内后端+前端一起被关掉。

**根因（源码级定位，不是猜）**：`uvicorn/supervisors/basereload.py:87-95`
```python
def restart(self) -> None:
    if sys.platform == "win32":
        self.is_restarting = True
        os.kill(self.process.pid, signal.CTRL_C_EVENT)   # ← 元凶
```
Windows 上 `CTRL_C_EVENT` **广播给同一控制台的所有进程**。reloader 自己有 `is_restarting` 标志忽略它，**但共享控制台的启动脚本没有** → `Start-Sleep` 被 Ctrl+C 打断 → `$ErrorActionPreference="Stop"` 让脚本终止 → `finally` 把前端一起关掉。

**关键判别点（很好用）**：日志里**从来没有** `[WARN] 后端进程已退出 (code: ...)` 那行 —— 说明不是"检测到子进程退出后 break"，而是**脚本自己被信号打死**。修好后这条 `[WARN]` 就正常出现了。

**实测排除掉的方案**：
- `[Console]::CancelKeyPress += {$e.Cancel=$true}` 吞信号 → 只多活一两拍，仍死（PowerShell 管道中止独立于 .NET Console handler）。
- `--reload-include/--reload-exclude` → uvicorn 源码明写：**缺 watchfiles 时它们无效**（`statreload.py:25` 有 warning）。

**最终修法（`start.ps1` 4 处，+50/-9 行）**：
1. **后端必须在独立控制台**：去掉 `-NoNewWindow`，改 `-WindowStyle Hidden` + `-RedirectStandardError logs\uvicorn-dev.log`（`logs/` 已在 .gitignore）。信号源隔离后，脚本与 vite 都不再被广播误伤。代价：后端日志改到文件，启动横幅已提示路径。
2. `--reload-dir app`（本机 StatReload 会 `rglob` 整个 backend 目录，跑测试/写临时文件都触发重载）。
3. `--no-use-colors`（日志文件里不再有 ANSI 转义码）。
4. 启动前清理残留（`cmdline -match 'uvicorn|spawn_main|vite'` 的 python/node/cmd → `taskkill /PID x /T /F`，再按端口 8000/5173 兜底）+ `finally` 改 `taskkill /T /F` 杀整棵进程树（原来只 `Stop-Process` 单个 PID，留下的 spawn worker 会变孤儿继续占 8000）。

**验收（端到端实测，全部通过）**：① 人为制造孤儿占 8000 → 脚本自动清理并 `health=200`；② **触发热重载后脚本仍 `alive=True`、`5173=1`（旧版这里脚本和前端都会死）**；③ 收尾后 `8000=0 5173=0 residual=[]`。

**附带环境事实**：venv 里 `uvicorn[standard]` 的额外依赖（watchfiles/websockets/httptools）**全都没装** —— requirements 声明了 `[standard]`，属环境漂移；不装不影响正确性（降级 StatReload），要补跑 `pip install -r requirements.txt`。

**未提交**（用户未让 commit；本轮仅 `start.ps1` 一个文件）。

```
com.docker.backend.exe  Direction=Inbound  Action=Allow  Profile=Public
  TCP: LocalPort=Any  RemoteAddr=Any  Program=...\DockerDesktop\resources\com.docker.backend.exe
```
即 **8080 天然对局域网放行**（端口发布正是由 com.docker.backend.exe 转发）。曾试 `Start-Process -Verb RunAs` 加 `New-NetFirewallRule` 但 UAC 未被批准，事后发现**根本不需要**——先查 `Get-NetFirewallRule | Where DisplayName -match 'Docker'` 再决定是否提权。
