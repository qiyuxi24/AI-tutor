### ① Collector 遗留债 #1 — MediaWiki 地区词标记 `-{…}-` 清理

- `-{zh-cn:堆叠; zh-tw:堆棧;}-` → 取第一个变体值 `堆叠`（`split(";")[0]` → `split(":",1)[-1]`）

- `-{A|B}-` → 取前者，但 `if "[[" not in inner` 保护，不切坏 `[[链接|文字]]`
- `-{}-` / 无冒号裸文本 → 原样/空
- 嵌套用 `while "-{" in text` + `re.subn`（n==0 即 break，不会死循环）

## 知识图谱论文与开源实现调研（用户"继续调研"，产出 `docs/知识图谱_论文与开源实现调研.md`）

**顺带**：MEMORY.md 超注入上限，已按提示压缩重写（细节全部转为 §文档索引 的指针，文件从"48 行超长段落"改为结构化 + 文档索引表）。

**核心框架（自建）：业界三种"图谱怎么用"，本项目属第二种且是少数派**
| 路线 | 图是什么 | 代表 | 图的来源 | 每轮 |
|---|---|---|---|---|
| A 检索索引 | 索引 | Microsoft GraphRAG / LightRAG / HippoRAG | 从文本自动抽 | 命中才用 |
| **B 教学参照系** | **教学可行域** | **本项目**；MDPI 智能导学 2025 | 人工/AI 辅建/教材生成 | **每次注入** |
| C Agent 记忆 | 长期记忆 | Zep/Graphiti、Mem0、MemGPT | 交互累积 | 按需召回 |

**关键结论**
1. **GraphRAG 家族不能直接搬**（图从文本抽、服务检索）；唯一可复用是"图遍历扩跳"手法。我们**不需要社区摘要 → 规避了 GraphRAG 系最大的 LLM 成本坑**（这是"图不来自文本"的架构红利）。
2. **最大缺口 = 先修关系无量化能力**。学术界这条线很成熟：**arXiv:2509.05393（Alatrash/Chatti, IJCKG 2025）**——**无监督**、基于文档/维基链接/图/文本四类特征定义 **10 项准则 + 投票融合**，条件与我们（无标注数据）完全匹配；**MOOCCubeX（THU-KEG, CIKM 2021）含数学/心理学/CS 三科先修关系（含人工标注）**，可作**外部评测集**把"图谱很准"从自证变成外部可比。另有 DGCPL（IJCAI 2025）双图蒸馏。
3. **知识追踪（KT）= 我们"掌握度"的学术对应物**。pyKT 工具包（30+ 模型 × 7 数据集）；**NTKT**（arXiv:2511.02599，把 KT 重构为 next-token 预测）与我们 LLM 栈最契合。**明确不采纳 DKT/AKT**（需长交互序列，我们是冷启动单用户）。
4. **KG 抑幻觉有权威引证**：*Can Knowledge Graphs Reduce Hallucinations in LLMs? A Survey*（NAACL 2024, arXiv:2311.07914）—— 答辩问"为什么必须注入图谱"时最硬的一篇。
5. **印证"始终注入"非孤例**：ChatGPT 与 Claude 的记忆哲学相反（始终注入 vs 按需检索）；且 Claude Code/Codex/Gemini CLI 的记忆就是**朴素滑动窗口**（无 RAG 无图谱）→ 图谱非记忆必需品，用不用取决于是否需要结构化约束与可审计。
6. **新对标项目 `098765d/AI_Tutor`（KG-RAG AI tutor，配 ICEIT 2025 论文）**：双路检索（向量 + **图谱遍历 `kg_hop_depth`**）、三元组抽到 **Excel**、含"KG-RAG vs 纯 RAG"**模式切换对照**。→ 暴露两点：①同类学术实现比我们简单得多（我们的用户隔离/两级切片/SSE 是相对优势）；②**我们没有"沿先修边扩跳"能力**；③**它的 A-B 对照设计值得我们照做**。

**给的借鉴优先级**：P0 = 多准则先修推断 + MOOCCubeX 外部评测；P1 = `rag_search(source=graph)` 加扩跳 + **图谱开/关 A-B 对照实验**（AIC 赛道最好写的量化证据）；P2 = 掌握度时序（Graphiti 式）、PPR 多跳、查证《基础教育知识图谱标准》(CELTSC 2025-06) 是否与 subject/board/tags 冲突。

### 多资料（多教材）维护调研（新文档）
- **五件事分解**：`溯源 → 对齐 → 补全 → 冲突 → 增量`；**溯源是前四者前提**（没"来自哪本书哪一章"则对齐无法复核、冲突无法裁决、覆盖度无法度量）。
- **现状两个最大缺口**：节点/边**零来源字段**；语义去重只在**单次生成内**生效（`_find_dedup_candidates`），跨 run 不合并。
- **业界映射**：融合分 **schema 层 + instance 层**（arXiv:2510.20345）；教育域对口 **arXiv:2305.04567（北邮，教材/课件/大纲三源）** 四步融合可借鉴 —— 名称匹配三路并用 / 融合后取**最粗粒度** / 属性**取并集**（除 url）/ **保留原始边**；其"三源交集=最有价值知识点"可作我们的 support count。**它的反面教训：全篇无 P/R/F1、无金标准、无消融** → 我们评测口径必须更严。
- 其他可借鉴：**KARMA**（arXiv:2502.06472, NeurIPS 2025，冲突消解是独立角色，非抽取副产物）、**In-context Clustering ER**（arXiv:2506.02509，批量聚类把 O(n₁×n₂) 降到 O(n/k)）、**iText2KG**（增量、schema 驱动）、**LightRAG**（arXiv:2410.05779，增量避免全量重建）。引用复核状态已在文档 §7 逐条标注（iText2KG 未核到编号故不写编号）。
- **落地分层设计**：L0 溯源（`sources` JSON：doc_id/doc_name/chunk_id/span）→ L1 跨源对齐（三路粗筛 + 批量聚类 + 二阶段仲裁 + `merge_decisions` 表可回滚）→ L2 冲突队列（**复用 `prerequisite.py` 的多准则+证据链骨架**，detect-then-resolve，AI 不改人类内容）→ L3 按资料增量（幂等键 `(doc_id,chunk_id,span)`，成本 ∝ 新书）→ L4 覆盖度度量（support/coverage/对齐率/冲突率/冗余率）。
- **关键约束**：多源融合前必须**先收敛写路径**（现 4 套并行实现，否则融合逻辑写 4 遍）；`update_node_content` 是**覆盖**语义，与多源"合并"语义冲突。

## 排查：启动异常根因 —— uvicorn `--reload` 孤儿 worker 占用 8000（未改代码，纯诊断）

**用户报"启动有问题"。实测结论：代码本身没问题，是"僵尸进程 + 端口占用"的环境问题。**

### 根因链（已实证，非推测）
1. `uvicorn --reload` 是**双层进程**：reloader（父，`python -m uvicorn`）+ worker（子，Windows 下 cmdline 形如 `-c "from multiprocessing.spawn import spawn_main; ..."`）。
2. `start.ps1` 的 finally 只 `Stop-Process -Id $backendProcess.Id -Force` —— **只杀得掉一个 PID**，worker 子进程逃脱变成**孤儿进程，继续 Listen 8000**。
3. 下次启动：新 uvicorn 绑定 8000 → **`ERROR: [Errno 10048] error while attempting to bind on address ('127.0.0.1', 8000)`**（已抓日志）。
4. 但孤儿 worker **仍在响应 `GET /api/health` → 200** → `start.ps1` 的健康检查被"骗过"，打印"[后端] 服务已就绪!"。
5. 新后端因绑定失败退出 → `$backendProcess.HasExited = true` → 监控循环 `break` → finally **把前端也一起杀掉**。
6. 用户可见现象：①"启动完成"后服务莫名全关；②前端能打开但接口连到旧代码实例；③8000 上同时多个 LISTENING（Windows `SO_REUSEADDR` 允许多实例绑同端口）。

### 实测证据（可复现）
- 抓到 4 个孤儿：`spawn_main(parent_pid=41372/30944/37572/41428)`，parent 全已死，孤儿仍活并占 8000。
- `Get-NetTCPConnection -LocalPort 8000 -State Listen` → `owner=37572` 但 `Get-CimInstance ProcessId=37572` = not found（孤儿 socket）。
- 干净环境（端口全空）复跑 `start.ps1` → **稳定运行 30s+、health 200、无自动退出**（证明代码无问题）。
- 前两次复现自动退出时，日志均有 `StatReload detected changes in '...'`（外部会话在跑 `scripts/eval_graph_injection.py` 写 backend 目录文件 → 触发 reload）。

### 止血命令（Windows）
先按端口找 owner 再杀，**不要只杀 Start-Process 的 PID**：
```powershell
Get-CimInstance Win32_Process -Filter "Name='python.exe'" |
  Where-Object { $_.CommandLine -like "*spawn_main*" -or $_.CommandLine -like "*uvicorn*" } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```
注意别误杀 `lsp_server.py`（IDE）与 `scripts/eval_*.py`（另一会话在跑）。

### 待修（本次未动代码，等用户拍板）
1. `start.ps1` 启动前**端口预检**（8000/5173 被占用则清理或报错退出），而非盲目启动。
2. `start.ps1` 关闭时杀**整个进程树**（`taskkill /PID x /T /F` 或按端口找 owner），而非单个 PID。
3. venv **缺 `watchfiles`** → uvicorn 降级 `StatReload`（监视**整个 backend 目录**，`tests/`、data、临时 py 变动都触发重载）→ 建议 `pip install watchfiles` + `--reload-dir app` 限定目录。

### P1-1 图谱检索沿先修边扩跳
- `core/rag/manager.py::search(hops=0)` 新增 `_expand_prerequisites()`：反向邻接 `to→[from]` BFS，`score = 初检最高分 × 0.6^depth`，补充条数 ≤ `top_k`；**默认 `hops=0` → 零回归**；LLM 可在 `rag_search` 按需传 1~2（工具描述已写明"学生卡住/需牵扯前置概念时使用"）。
- 全链路贯通：`agent_tools` 的 `rag_search` spec+handler → `rag_tool.rag_search(hops)` → `RagContext.metadata["graph_hops"]` → `GraphRagSource.retrieve` → `rag_manager.search(hops=)`；`chat_service._build_retrieval_context(graph_hops=)` 供实验控变量。

### 顺手修的方向 bug（意外高价值产出）
- `knowledge_graph.get_prerequisites` 递归 CTE 方向反了（沿 `from_node=?` 取 `to_node` = **后继**）。实测 `get_prerequisites("递归定义")` 返回 `[AI创建测试, 计算机操作系统]`，真前置 `递归终止条件`/`分治算法` 查不到。
- 全库统一语义 = **`A → B (prerequisite)` 表示 A 是 B 的前置（先学 A）**（与 `add_edge`/`topological_sort`/`knowledge_writer`/generator prompt 一致，并用真实库 30 条边交叉验证）。修复 = 递归 CTE 里 `from_node`/`to_node` 对调 + docstring 写准方向。
- 影响 4 个调用点（3 个受影响）：`get_next_to_learn()`（把**进阶内容**当"该巩固的先修"推荐）、`get_learning_path(target)`（目标前置链全丢）、`GET /knowledge/node/{id}`（详情页"前置依赖"显的是后继）。**静默错误**——不报错，只是答案反了。

### P1-2 A/B 对照实验（单变量：仅"图谱注入与否"）
- 脚本 `backend/scripts/eval_graph_injection.py` + 数据集 `backend/eval_data/graph_injection_cases.json`（自包含图谱 7 节点/6 边，5 用例 = 2 `general` + 3 `graph_dependent`；测试用户 9902 / 节点前缀 `ab_`，**不碰真实用户数据**）+ 原始结果 `graph_injection_report.json`。
- 关闭组 = 不注入图谱摘要 + `pipeline.unregister("graph")`（检索也拿不到图谱）；其余（模型/温度/画像/工具集）全同。指标全规则计算，零额外 LLM 调用。
- **结果：总命中 25.0% → 62.5%（Δ+37.5pp）；`graph_dependent` 30.0% → 80.0%（2.7 倍）；token +6%（回答更长 261→305 字）**。`general` 也从 16.7%→33.3% → 注入图谱**没有"超纲拒答"副作用**，反而帮它挑对讲解层次。
- 关闭组核心失败模式：3 道依赖图谱题共检索 **22 次**（d2 达 9 次）仍徒劳，并断言**"你目前的知识图谱可能还是空的"**（实际 7 节点）= 对学生个人数据的确定性幻觉，比"答不出"更有害。同一道 DP 题对照：关闭组 7 次检索 / 8 轮 / 21295 tokens / 命中 1-3 vs 开启组 3 轮 / 13552 tokens / 命中 3-3。

### 实验暴露三项（已写进文档 §5，等用户拍板）
1. **嵌入 API 欠费**（`text-embedding-v4` 返 `Arrearage`）→ 生产图谱 RAG / KB 混合检索的向量部分静默降级为 BM25 / 空结果，**建议优先处理**（充值或换 key）；
2. 检索为空时 LLM 会向学生断言"图谱是空的"（需区分"图谱为空"与"本次检索未命中"，并禁止向学生断言图谱状态）；
3. LLM 拿节点名当 `node_id` 调工具（`E-LLM-007 节点不存在：递归`）→ 参数描述强调传 id，或工具内按名称回退解析。
