## 完成：学科知识图谱生成（书籍→学科图谱）+ 语义去重优化

### 调研结论（外部论文/开源）
用户要求调研"书籍→学科知识图谱"的可借鉴方案。调研发现：
- **《LLM-Empowered Knowledge Graph Construction: A Survey》**（arXiv:2510.20345）：教材场景推荐混合范式（Top-down 模式构建 + Bottom-up 实例抽取 + 去重融合）
- **Tree-KG**（清华，ACL2025）：教科书双层知识图谱（显式章节层级 + 隐式跨章节实体关系），5 操作符（上下文卷积/实体聚合/节点嵌入/实体去重/边预测）
- **KGGen**（NeurIPS'25）：两阶段抽取（先实体检测后关系生成）+ LLM 语义去重聚类（entity/edge_clusters）
- **开源**：CourseGraph（CPU-DS，MIT，Neo4j+Rust 较重）、TreeKG（lzl8800）、kg-gen（stair-lab，LiteLLM+DSPy）

### 用户选择
- 只实施「语义去重（合并同义概念）」
- 嵌入方案倾向本地 embedding，但因 torch 依赖重（sentence-transformers 2GB+）与项目轻量定位冲突，最终采用**可插拔设计**：text-embedding-v4 API 优先（效果最好、零新依赖）→ sentence-transformers（可选离线）→ 内置 numpy 哈希嵌入（零依赖兜底）

### 后端改动
1. **新增 `app/core/kb/embedder.py`**：可插拔嵌入层
   - `BaseEmbedder` 基类 + `similarity()`（余弦）
   - `ApiEmbedder`（text-embedding-v4，同步 OpenAI 客户端，默认首选）
   - `SentenceTransformerEmbedder`（可选，paraphrase-multilingual-MiniLM-L12-v2，需安装）
   - `HashEmbedder`（内置 numpy 哈希：字符 n-gram feature hashing + TF 加权，零依赖离线兜底）
   - `get_embedder()`：API→本地→哈希 优先级，单例缓存

2. **`app/core/kb/graph_generator.py`** 新增语义去重：
   - `_node_signature()`：节点判重签名（name + summary）
   - `_find_dedup_candidates()`：嵌入相似度候选粗筛，返回 `{new_idx: [(exist_idx, sim)]}`，阈值 0.78
   - `_confirm_synonyms()` / `_confirm_one_pair()`：LLM 二次确认同义（'merge'/'keep'）；**LLM 失败时降级**：相似度 >= 0.90 才保守合并
   - `_write_to_graph()` 集成去重：确认同义的新节点 → 合并（不新建，边指向已有节点），记入 `merged_nodes`
   - `generate_subject_graph`/`generate_section_graph` 传入 `existing_nodes` 并聚合 `merged_nodes`

## 完成：RAG 去耦合 + 目录级检索调研 — docs/RAG_去耦合与目录检索调研.md

用户提出两个架构问题：(1) RAG 是否去耦合、是否需要中间件（LLM 问什么再查什么）；(2) 知识库按目录组织，是否"先检索目录→再检索文档"。

调研素材：Agentic RAG 综述（arXiv:2501.09136）、RAPTOR（arXiv:2401.18059）、Adaptive-RAG（arXiv:2403.14403）、LangChain ParentDocumentRetriever/RecursiveRetriever、RAGFlow、卡码笔记《长文档与代码RAG检索》、掘金《Parent-Child 高级分块》。

核心结论（已写入 TODO P1.5 小节）：
1. **去耦合**用"RAG 路由器（可插拔 RagSource 数据源）+ 按需检索开关"，而非一步到位纯工具调用（避免每轮额外 LLM 往返）
2. **目录级检索**用"元数据过滤 + Parent-Child 父级回溯"，**不做"先目录后文档"顺序流程**（目录名语义信息少，先粗筛会冲淡信号）
3. 两条铁律：①先在小块上排序再向父级扩展 ②父级扩展是预算决策（按 token 决定返回章节/标题路径/完整文档），非固定动作

推荐落地顺序：P0 RAG 路由器解耦（新增 rag_pipeline 包）→ P1 按需检索开关（规则启发式零 LLM 成本）→ P1 chunk 加 path 元数据 → P2 父级扩展 → P3 RAG 检索作 function calling 工具。

当前耦合点：`chat_service._build_system_prompt()` 硬编码调用 `_build_rag_context()`（图谱 RAG 无条件）+ `_build_kb_context()`（知识库，仅用户勾选目录时）。目录目前只作 node_ids 范围过滤，不参与排序。
- 注：whoosh/python-pptx/Pillow/onnxruntime/rapidocr 已装进 venv；DASHSCOPE 假 key 导致 embedding 401 不影响解析链路

- `pipeline.py`: `RagPipeline` 路由编排——`register/unregister/sources/run`；run 流程：空查询→按需开关→收集 active 源→`asyncio.gather(return_exceptions=True)` 并行→单源 8s 超时/异常隔离→`_fuse` 按 content 去重+分数降序。全局单例 `pipeline` 已注册 graph+kb 两源。

### chat_service 改动
- `_build_rag_context` + `_build_kb_context` 两个独立函数 **删除**，合并为 `_build_retrieval_context(student_message, user_id, kb=None)`
- 内部一次 `pipeline.run(RagContext(...))`，按 source 分组生成"图谱区块 + 知识库区块"，避免同一 query 重复 embedding
- `_build_system_prompt` 中两处硬编码调用替换为一次 `_build_retrieval_context`

### 鲁棒性关键设计（重要）
- `asyncio.gather` 必须用 `return_exceptions=True` + 结果归一化，否则任一源异常会传播导致整个 run 抛错（踩过坑）
- 单源超时 `_SOURCE_TIMEOUT=8s`；所有异常在 `_safe_retrieve` 内捕获返回 `[]`，绝不外抛
- 验证：14 项单测通过（按需开关/跨源融合去重/单源异常隔离/单源超时隔离/全源失败不抛错/注册注销）；真实调用验证 API 401 挂掉时 `_build_retrieval_context` 静默返回空不抛错
