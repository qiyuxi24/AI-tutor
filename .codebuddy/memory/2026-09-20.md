## 查「刚生成知识图谱消耗多少 token」——结论：无落盘记录，只有估算
- 本次建图实据（本地库 `data/knowledge/knowledge.db`）：user **5**，2026-09-20 **20:06:39→20:21:15**（约 15 分钟），新增 **282 节点**（added_by=ai、board 空、subject 强化学习类，如 `rl_history.md`）；源文档 kb/5 里 **2 个文件共 198,448 字符**；用项目自身 `kb_manager.chunk_text(chunk_size=3000)` 实切 = **335 块、平均仅 570 字符/块**（按标题/段落边界切，远没填满 3000）；产出节点 MD 301 个文件 **178,184 字节**。
- **没有 token 报告的三个原因**：① 图谱生成走 `call_llm`（`kb/graph_generator`），token 只 `logger.info` 打控制台、**不落盘**；② 它不走 agent loop → `debug_log.db`(`agent_debug_logs`) 无记录（最近一条 9/19 22:40）；③ 本地 `backend/logs/tutor.log`(末 9/19 22:23) 与 `logs/tutor.log`(末 9/19 22:48)、远端容器 `/app/backend/logs/tutor.log`(末 9/19 22:08) 都早于本次 → 这次多半是被脚本直调（未配 logging → INFO 不输出）。本地无 python/docker 进程在跑。
- **估算（非实测）**：输入 ≈ 335×(system ~1.1K + chunk 0.57K + 「已有节点」清单均值 ~1.5K) ≈ **1.0M**；输出 ≈ 178KB 中文 + JSON 开销 ≈ **0.13–0.16M** → 合计 **约 1.0–1.2M token**。
- **成本大头/可优化点**：①「已有节点」清单每块全量注入且线性增长（0→282），约占总输入一半，是 O(n²)；② 335 块平均只有 570 字符（上限 3000），固定开销被摊薄 5 倍 → 块切大可省数倍；③ `_confirm_synonyms` 去重小调用次数未记录。
- 待办（未做，等用户点头）：给 `graph_generator` 加 usage 累计并落盘（复用 `token_counter.extract_usage`，写进 aggregate + 一份报告文件）。 → **已按通用方案落地，见下节。**

## 记录库底座收敛（core/records.py）—— 回答"要不要专门维护一个模块建表"
- 背景：三张记录表分属三处 —— `agent/store.py` 的 `agent_runs`、`agent/debug_log.py` 的 `agent_debug_logs`、`llm/usage.py` 的 `llm_usage`，各抄一份 `_connect`（connect + Row 工厂 + WAL + executescript）、各算各的路径；于是 `llm/usage.py` 只能**延迟导入** `agent.store.default_db_dir` 来躲循环导入。

## 图谱质量调研 + 新建 `TODO_Graph_Quality.md`（用户要求先调研再开 TODO）
用户三个问题：① 节点该多深 ② 重复生成怎么办 ③ 如何保证质量。产出 `TODO_Graph_Quality.md`（活清单，GQ-1…GQ-13 + 3 个待拍板项）。核心调研结论：
- **Q1 深度**：现状中位 241 字的根因**不是模型能力，是 prompt 自己写的硬限** —— `GRAPH_GENERATOR_SYSTEM_PROMPT` L101「每次最多 8 个知识点；每个 content 控制在 300 字以内，不要展开长篇示例与推导」。叠加 `GRAPH_CHUNK_CHARS=3000` 但 `chunk_text` 实测均只填 **570 字符/块**，上下文撑不起深度。建议：content **600–1000 字**（下限 400）、五段式（定义/要点3-5条/示例**必须含数值或代码**/易错点/与前后置关系）、每次 4–5 个节点（不是 8）、节点总规模 100–150（现 311，≈640 字符/节点）。判据=用途倒推三用（出题单元/讲解单元/检索单元）+ 可出题性 + `estimated_minutes` 5–25 + 禁「摘要/回顾/复习/小结」类碎片节点。成本对冲：块变大→块数 335→~100，"已有节点清单"O(n²) 注入成本反而大降。
- **Q2 重复根因链（4 层，已拿硬证据）**：① **嵌入 `text-embedding-v4` 返回 400 `Arrearage`（账号欠费）→ `ApiEmbedder.embed()` 返回空 → `_find_dedup_candidates` 直接 `return {}` → 语义去重整条链路静默失效、不报错不告警**（实测脚本验证）；② **缺 Neo4j 三档里的第一档"精确同名匹配"**（`SinglePropertyExactMatchResolver` 是默认档、零误判、不需嵌入），而漏掉的 18 组恰恰全是精确同名（`bar_reward_function` vs `bar_reward_function_extended`）；③ 只比"新↔已有"，不比"批次内新↔新"；④ 写入层 `add_node` 只校验 id 唯一，精确同名并轨只在 `knowledge_writer._find_same_name`（agent 路径），**建图走 `create_node_with_content` 绕过**。修法=三层护栏 L1 精确（下沉到写入层）→ L2 字符串模糊（去 `_extended`/`_review`/「（复习）」尾缀）→ L3 语义（先修嵌入 + 失败必须告警，不得静默）。
- **Q3 质量保证四层**：生成前约束 / 生成中护栏（去重+400 字下限+噪声拦截+写 confidence）/ **生成后体检（当前完全缺失，最该补 → 固化成本次手工审计的 `backend/scripts/inspect_graph_quality.py`，可选 `--fix-dupes`）/ 可观测（token 落盘、aggregate 暴露合并数）**。
