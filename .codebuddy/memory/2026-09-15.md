## 上下文预算框架（先定框架，不动代码）

用户指令：先定框架 —— 各部分占比多少、给弹性界限、以 128K 为界、含 skill/历史/提示词等段。

**关键诚实点（必须先说）**：**没有任何论文给出"各段占百分之几"的配额表**。找到的文献给的是**每段的边际收益曲线与失效机制**，配额只能由「曲线形状 + 本项目实测基线 + 工程判断」反推。所以文档里每行都标了 `【论文】/【实测】/【判断】`。

**两级窗口（框架核心）**：H = 128K（记账墙，越线是事故）/ **E = 64K = 50%×H（常态设计目标线）**。

**E 的依据**：arXiv **2410.18745**（RULER 128K 实测）—— **多数开源模型有效上下文 < 声称长度的 50%**（Llama3.1-70B / Qwen2-72B / GPT-4-1106 = 50%，Llama3.1-8B = 25%，GLM4 在 1M 上仅 6.4%）；机制是位置频率左偏。

**检索段是唯一"越多越差"的段**：Databricks arXiv **2411.03538**（20 模型×3 数据集×2000+ 实验）—— 正确率峰值在 **8–32K**（"多数 LLM 只在 16–32K 内表现出 RAG 性能提升"），召回单调升但正确率不升，8K→128K 成本 **16×**，64K 后边际对 GPT-4o = 0、对 o1-preview = 负；OP-RAG（arXiv **2409.01666**）检索块数与质量呈**倒 U**；Lost in the Middle（arXiv **2307.03172**）>20 篇文档边际仅 ~1.5%。→ 规则：**窗口放大时检索段不涨，全给历史**。

**位置规则**：Lost in the Middle 实测中间位 52.9% **低于闭卷 56.1%**；**query-aware 双端放置**（当前问题放数据前后）在 KV 任务上 45.6%→**100%** ← 本项目唯一"低成本高确定性"的未做收益点（约 50 token）。另：Chroma 实测**打乱的干草堆一致优于结构化的** → 不许为排版重排注入顺序。

**本项目实测基线**（`reports/probe_context_budget.py`，新增）：

| 工具指南 2017 + 策略 672 + **schema 2661** | **5350** | 4.2% | 8.4% |
| 图谱注入（120 节点，降级后） | 5218 | 4.1% | 8.2% |
| 检索注入（5×500 字符） | 2500 | 2.0% | 3.9% |
| **固定成本合计** | **13,984** | 10.9% | **21.9%** |

→ 固定段已占 25%E 告警线的 **87.4%**；**历史段可用余量 = E − 固定 − 输出预留 = 42,016 token**（远超框架给历史的 30K 目标）→ 说明**当前瓶颈是窗口预算设小了（`LLM_CTX_BUDGET=32000`），不是没地方放**。

**八段配额**（下限/目标/上限，K token）：输出预留 2/**8**/20、静态指令 0.8/**0.9**/1.5、工具技能 3/**5.4**/8、图谱 3/**5.2**/8、画像 0.3/**0.8**/2、检索 1.5/**2.5**/8、历史 8/**30**/48、当前轮+工具回填 2/**7**/20 → 合计 ≈18/**60**/**115**（目标 ≈94%E，上限 = 90%H 留抖动）。**让位顺序：历史 → 检索 → 图谱 → 画像**；不可压三段（输出预留/静态指令/当前轮）无外部还原源。

| 指标 | A 无 skill | B 有 skill | 差 |

**关键量化发现（值得长期记住）**：
- ponytail 的机制是**压缩 diff**，而它自己有**固定 2,005 token 加载成本/任务**。回本阈值 ≈「不省则要多写的代码 > 2K token（约 200+ 行）」——
  本任务（小改动）**净亏 token**；只有中大型改动（多文件/重复实现/加依赖类）才可能净赚。
- 它真正的收益不在 token 而在**维护面**：少改模板、少引入命名/文案漂移、把"要不要序号/要不要去描边"这类审美决策**退回给用户**（而非擅自加）。
- 代价：用户若想要 A 的观感，得再补一句"工具行去掉描边并加序号" → **多一轮往返**。小任务里这轮往返的成本 > 它省下的 805 token。

**实验局限（诚实标注）**：B 在同一会话内进行，复用了 A 的探查结果（无需重读文件），因此 B 的耗时/token 是**下界**；真正的可控差异是 diff 体量与是否加载技能。另：实验装置（harness 两文件 + 5199 dev server + 无头 Edge 截图）为共享装置，成本单列，不计入任一 run。

**产物**：`reports/ponytail_ab/`（baseline.png / runA_no_skill.png / runB_ponytail.png / runA.patch / runB.patch / buildA.log / buildB.log）。**当前工作区保留的是 B 版**（`MessageBubble.vue` 纯 CSS 改动，未提交）。

## 嵌入 API 双源收口（用户追问"那个 API 写了两次的问题"后修）

**事实澄清（先查代码再下结论）**：`text-embedding-v4` 确实有两份调用实现 ——
- **检索侧** `llm/embed.py::embed_texts`（async + AsyncOpenAI 单例，无兜底）；
- **语义去重侧** `kb/embedder.py::ApiEmbedder.embed`（同步 + 懒加载 OpenAI，hash/sentence-transformers 兜底），服务 `graph_generator`（同义节点合并）与 `prerequisite`（C5）+ `api/v1/knowledge.py`。

两者**各自硬编码**模型名（`EMBEDDING_MODEL` vs 字面量 `"text-embedding-v4"`）、批大小（`EMBED_BATCH_SIZE` vs `BATCH_SIZE`），且失败语义不同（前者"不齐→整批 []"，后者"过滤 None→返回短列表"）。

**历史成因**：`embed.py` 是 2026-09-12 收敛"kb_manager / rag_manager 两份 `_embed()`"时抽出的，**只覆盖检索侧**；去重侧更早（"the RAG part"）且没被那次收敛碰到 → 真实账是 **3 处收敛成 2 处**。

**危害（如实修正我先前的猜测）**：**不会错位** —— 两个调用方（`prerequisite._build_vectors` / `graph_generator._dedup_candidates`）都有 `len(vectors) != len(texts)` 校验，行为是静默降级。真实危害 = **配置双源**（换模型要改两处，漏一处只有去重那条线悄悄用旧模型）+ **文档把"唯一出口"写成了全库级**（`llm/__init__.py`、`llm/README.md`、记忆都这么写，误导排查）。

**收口方案（最小，不合并调用路径）**：`ApiEmbedder` 的 `name` / `BATCH_SIZE` 改为引用 `EMBEDDING_MODEL` / `EMBED_BATCH_SIZE`，补 `t[:MAX_EMBED_CHARS]` 截断（此前不截断，超长会 400 整批失败），失败语义改为"条数不齐 → 整批 []"（去掉 None 过滤）；顺带删掉 `embedder.py` 未使用的 `import math`。
**没做**（明确记录）：不做同步桥让 ApiEmbedder 完全委托 embed_texts —— 在 FastAPI 同步上下文里跑新事件循环会踩"AsyncOpenAI 单例跨 loop → Event loop is closed"（项目已实测），收益（少 ~20 行）不抵成本。

**文档措辞修正**：`llm/embed.py` 头部 / `llm/__init__.py` / `llm/README.md`（§ 模块表、调用链图里的"其他任何地方都不应出现 embeddings.create"、§3.3 标题与末条）/ `AGENTS.md` 单一事实源行 —— 全部改为"**检索侧**唯一出口 + 语义去重侧共用常量"。
