## 完成：P2 父级扩展（相邻块拼接，预算决策）

用户选定：父块粒度=相邻块拼接（滑窗），预算=固定预算。已实现知识库的父级扩展。

### 调研：论文推荐 chunk size
- 子块（检索用）：256~512 token（约 500~1000 中文字符）——当前 `CHUNK_SIZE=500` 字符（≈250 token）已在推荐区间
- 父块（返回用）：1024~2048 token（约 2000~4000 字符）
- 反直觉结论：512 token chunk 比 1024 的 MRR 高 12-18%（大 chunk 语义噪声拉低排序）→ 检索用小块、返回用大块

### 改动
1. **`doc_vector_store.py` 新增 `get_node_chunks(user_id, node_id)`**：按文件取全部块（chunk_index 升序），供父级扩展回溯相邻块。
2. **`kb_manager.py`**：
   - 常量：`PARENT_EXPAND_CHARS=1500`（每命中块追加预算）、`PARENT_MAX_BLOCKS=8`（最多拼接块数）
   - `search()` 在 `_attach_paths` 后调 `_expand_parents`：原地替换命中项 content 为父级扩展文本
   - `_expand_parents`：按 node_id 缓存取 chunks（同文件多次命中避免重复查）
   - `_expand_one`：命中块居中，左右交替扩展相邻块，预算+块数双重约束，超即截断；首/尾/单块安全

### 设计要点
- 对齐铁律：先在小块上排序（命中即已排序），再向父级扩展；父级扩展是预算决策非固定动作
- 仅扩展后有增益才替换（扩展后必比原命中块长），单块文件保持原文
- `_expand_one` 是纯函数，独立可测；`_expand_parents` 依赖 get_node_chunks（同步，无 embedding 调用）

### 验证
- `_expand_one` 8 项：中间/首/尾块扩展、预算约束、块数上限(8)、单块无扩展、不连续 chunk_index 定位
- `_expand_parents` 集成 6 项：get_node_chunks 查询/排序、命中块替换、含相邻块、同文件缓存一致、单块不报错
- 全部通过，临时测试已清理；编译+linter 零错误

## 完成：宽召回 + RRF 融合（召回率优化，路线0+1）

用户选定：路线0+1（宽召回 + 融合升级 RRF），候选池 Top-30。产出调研 `docs/RAG_召回与重排优化调研.md`。

### 调研结论（召回率）
- 业界标准：**宽召回 Top-30~50 → RRF 融合 → 精排 Top-3~5**。当前 search 直接 top_k=5 太窄漏召回
- 提升召回率论文：HyDE（arXiv 2312.04467，零样本 +15-25%）、RAG-Fusion Multi-Query+RRF（arXiv 2402.03367，+10-15%）、Cross-Encoder Rerank（需模型）
- 用户问的"两种搜索方式同时加权"= 现有 Hybrid Search（向量+BM25），缺的是"宽召回+精排"流程

### 改动
1. **`hybrid_search/fusion.py` 新增 `rrf_fuse(result_lists, k=60, min_score)`**：Reciprocal Rank Fusion
   - 基于排名 `1/(k+rank+1)` 累加（rank 从 0 起），不依赖分数值 → 对权重/分数尺度不敏感
   - 多路任意数量，chunk_id 主键聚合，同 doc 多路累加，优先保留首次元数据
   - 归一化到 (0,1]：除以理论最大分 `n_lists/(k+1)`，与 MIN_SCORE=0.25 过滤对齐
   - 保留原 `fuse`（线性加权）不删（hybrid_search/__init__ 仍在导出）
2. **`kb_manager.py`**：`search` 改宽召回 + RRF
   - 新增 `RECALL_TOP_K=30`；向量/BM25 各取 30（原为 top_k=5）
   - `rrf_fuse([vec_results, sparse_results], min_score=MIN_SCORE)` 替代原 `fuse`
   - 取 `fused[:top_k]`（精排后进 LLM），后续 _attach_paths/_expand_parents 不变
   - 移除不再用的 `fuse`/`DEFAULT_ALPHA` import 和 `VEC_WEIGHT` 常量

### 验证
- `rrf_fuse` 9 项：多路命中优先（B>C>A>D）、归一化、权重不敏感（分数尺度无关）、min_score 过滤、空输入、极端高分不主导（RRF 选 B 两路都靠前，线性加权被单路高分 X 主导）
- `search` 集成 5 项：各取 RECALL_TOP_K=30、返回 top_k=5、重叠命中排前、归一化

## 完成：主题切换组件重构（解决部分输入框不随主题切换的问题）

当前项目原来用 `data-theme` 属性 + `--color-*` 变量，存在三个断层导致部分输入框切换不了主题：

### 重构方案（对齐业界标准）

- **`style.css`**：主题变量选择器从 `[data-theme=dark]`/`[data-theme=light]` 统一为 `html.dark`/`:root`（:root=浅色默认），并为深/浅两块补充 `--el-*` 变量覆盖（对齐自定义配色，让 EP 控件与自定义变量一致）
- **`main.js`**：在 `element-plus/dist/index.css` 之后、`./style.css` 之前引入 `element-plus/theme-chalk/dark/css-vars.css`
- **修复硬编码组件**：InputArea / NodeDetail / MessageBubble / ChatArea 全部改为 `var(--color-*)`

## 完成：P1 LLM 请求重试机制（llm_client.py，健壮性/体验优化，第2项）

### 改动（backend/app/core/llm_client.py）
- 新增 `random` import
- **`_is_retryable(e)`**：只重试瞬时错误——`APITimeoutError`/`APIConnectionError`/`RateLimitError`（isinstance 命中）+ `APIStatusError` 的 429 或 5xx；**不重试** `AuthenticationError`（认证错）、400 等业务错

- **应用 5 处 `create()` 调用**：`call_llm` 首次 + 第二次（工具确认）、`call_llm_stream` 首次（只重试"发起请求"不重消费生成器）、`call_llm_tools` 首次 + 第二次。`_with_retry` 是内部新增，**无公开 API 签名变化**，其他调用方零改动

- `py_compile` 编译 OK，模块导入 OK
- `_is_retryable` 判定：timeout/conn/ratelimit/500/429 → True；401(auth)/400 → False
- `_with_retry` 行为：500 连续 2 次失败后第 3 次成功（指数退避 1.4s→2.4s 含抖动，调用 3 次）；400 只调用 1 次即抛出
- lint 零错误

- **只对瞬时错误重试**是核心：认证错重试无意义，业务 4xx 重试也白费
- 后台 `call_llm_tools` 也加重试（提高图谱更新成功率），最坏多等几秒，后台任务本就不阻塞主流程，可接受
