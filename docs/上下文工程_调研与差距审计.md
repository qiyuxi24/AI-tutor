## 一、结论先行

1. **前提要更正：不是「没做」，是「做了一半且没分层」。** 对话侧已有四个真实组件在跑：`agent_context.py`（上下文唯一写入点）、`context_guard.py`（发送前预算守卫）、`token_estimator.py`（三层预估）、`agent_run_store.prune(30,180)`（分层保留）。图谱生成侧也不是「完全一次性生成」——`graph_generator._split_text(5000)` + 逐块 LLM + 增量写库 + 事后语义去重，**这已经是一个 Map 阶段**。所以本任务的正确形态是**差距审计 + 补齐机制**，不是推倒重来。

2. **两个场景的性质根本不同，不能用同一套机制。** 这是本报告最重要的判断：
   | | 场景 A：对话上下文 | 场景 B：超窗产物生成（图谱文件） |
   |---|---|---|
   | 状态性 | **有状态**，跨轮增量追加 | **无状态**，批次之间只靠产物通信 |
   | 核心约束 | 保**连续性**（不能忘、不能乱） | 保**全局一致性**（同义不重、粒度一致、跨块关系不漏） |
   | 失败形态 | 忘事、跑偏、成本线性膨胀 | 静默丢批、粒度漂移、跨章节边永远抽不到 |
   | 业界对应主线 | Anthropic 长时任务三技术 / Manus 六原则 / LangChain 四策略 | GraphRAG 层次化 map-reduce / LongWriter·DOC plan-then-expand / iText2KG 增量一致性 |
   
   **混用会两头失手**：把「丢最旧」用在图谱生成上等于丢内容；把「全局归一化」用在对话上等于每轮重算。

3. **最严重的问题不是「窗口不够」，是「输出被静默截断」。** ~~`call_llm` 硬编码 `max_tokens=2000`（`core/llm/call.py:41`），而图谱生成的系统提示词要求**每个节点输出完整 Markdown 讲解**（`GRAPH_GENERATOR_SYSTEM_PROMPT`）。截断 → JSON 不完整 → `_parse_json` 三策略全失败 → `graph_generator.py:526-527` 的 `if not result: continue` → **整块 chunk 静默丢弃，无任何用户可见报错**。~~ **✅ 2026-09-13 已在 Docker 日志中实证并修复**（详见 §2.3 #1/#2 与 §10 实施记录）。

4. **「不能在一次上下文窗口内生成」是两个不同约束的叠加，要分开对症。**
   - **(i) 输出上限**：与输入窗口无关，是独立的硬墙。LongWriter 论文（arXiv 2408.07055）的核心发现正是：模型能读 10 万 token 输入，**却写不过 2000 词**，根因是 SFT 数据里缺长输出样本。
   - **(ii) 全局视野**：跨块一致性需要「看到全局」，但全局塞不进窗口。
   
   对应两条独立的学术主线：**plan-then-expand**（Plan-and-Write → Re3 → DOC → LongWriter/AgentWrite）解 (i)；**层次化 map-reduce + 预生成摘要**（GraphRAG、RAPTOR）解 (ii)。

5. **本项目有一个已经可计算的硬失效点（主对话热路径）**：`chat_service` 主路径 `inject_tools=True` → `build_graph_context(detailed=True)` 对**每个节点**注入 `content[:200]`（`graph_analyzer.py:150-153`）。算式 ≈ `260 字符/节点`：**约 200 个节点时 system prompt 自身就顶穿 32K 预算**，而 `context_guard` 对此明确写着「照发并记 warning」（`:86-88`）——即**静默失效**。详见 §2.4。

6. **成本视角：真正的收益在「每轮重发历史」的线性成本与注意力稀释，不在「能不能答」。** Manus 实测输入:输出 ≈ **100:1**，缓存与未缓存输入价差 **10 倍**（$0.30 vs $3.00/MTok）。本项目同构：MiniMax-M3 有 1M 窗口，对话几乎不会溢出，但每轮重发全量历史 + 全量图谱摘要是**按输入计费的线性烧钱**，且 Chroma 的实测（18 个模型、194,480 次调用）表明**上下文越长性能持续退化**，不是断崖而是梯度。

7. **落地顺序：先修 bug，再补机制，最后做优化。** P0 只做三件事（`max_tokens` 参数化 + 截断检测 + system prompt 预算化），零架构变更、当天可验；P1 才做图谱生成三段式；P2 做对话侧摘要分层与 tool result clearing；P3 才是前缀缓存与可观测面板。

### 2.2 两个场景的对照（决定后续所有设计）

| 维度 | 场景 A：对话上下文 | 场景 B：图谱文件生成 |
|---|---|---|
| **要保的东西** | 教学连续性：学生之前说过什么、讲到哪了 | 产物一致性：同一概念只有一个节点、粒度一致、关系完整 |
| **可接受的损失** | 早期闲聊可丢（已被图谱/画像/记录沉淀） | **任何内容都不能丢**（丢的是知识资产） |
| **压缩必须可逆吗** | 不必（已有外部沉淀） | **必须可逆或可重放**（丢了就要重跑 LLM 花钱） |
| **主要成本项** | 每轮重发全量历史 + 全量图谱 | 多次调用的输出 token（内容写作） |
| **失败要能重试吗** | 不需要（对话是一次性的） | **必须能断点续跑**（一个学科 100+ 块） |
| **对应业界主线** | Anthropic 三技术 / Manus 六原则 | GraphRAG / LongWriter / iText2KG |
| **明确不应采用** | 全局 map-reduce（每轮重算太贵） | 「丢最旧」（丢的是知识） |

### 2.4 一个已可计算的硬失效点（请重点看这条）

**主对话路径的 system prompt 无上限，且守卫无法救它。**

链路：

```
chat_stream → _build_system_prompt(inject_tools=True)
            → _build_graph_summary(kg, detailed=True)          chat_service.py:138
            → build_graph_context(kg, detailed=True)           graph_analyzer.py:126
            → 对【每个节点】注入 content[:200]                 graph_analyzer.py:150-153
+ 全部边（edge_list）
+ 用户画像 get_summary()
+ RAG 检索上下文（rag_pipeline）
+ TOOL_CAPABILITY_PROMPT
```

单个节点的注入成本 ≈ `"  [id] name (掌握度:x, 难度:y, 预计:z分)"`（约 60 字符）+ `"    摘要: " + content[:200]` ≈ **260 字符**。

| 节点数 | 图谱摘要字符数 | 约合 token（中文 ≈0.7 tok/char） | 与 32K 预算（扣 2000 输出预留 = 30K）的关系 |
|---|---|---|---|
| 50 | ≈ 13,000 | ≈ 9,100 | 安全 |
| 100 | ≈ 26,000 | ≈ 18,200 | 占 60%，剩余历史空间被压缩 |
| **200** | ≈ 52,000 | **≈ 36,400** | **system prompt 自身顶穿预算** |
| 300 | ≈ 78,000 | ≈ 54,600 | 严重超出 |

顶穿之后会发生什么？看 `context_guard.py:86-88`：

```python
else:
    # system_prompt 自身已超预算：无可裁余地，退化为只剩当前消息（软目标，1M 窗口兜底照发）
    drop = hi
```

→ 裁剪到只剩当前消息，**然后照发**（只有一行 `logger.info`），1M 窗口不会拒绝请求，所以**表面上一切正常**，但：

- 每轮输入包含 5 万+ token 的图谱摘要（按输入计费，线性烧钱）；
- 这是 Attention Budget 最糟糕的用法——Chroma 的实测表明上下文越长性能持续退化；
- 且图谱每轮都在变（掌握度、节点增删）→ 前缀不稳定 → 缓存永不命中。

**这不是理论风险，是随图谱自然增长必然发生的**（一个学科教材生成 100–300 个节点是常态）。修复代价很低（§5.1 A1，且切片能力已存在）。

## 三、调研 A：对话上下文的业界与学术做法

### 3.1 认知基础：Context Rot 与 Attention Budget

**Anthropic《Effective context engineering for AI agents》**（官方工程博客，2025-09-29，作者 Prithvi Rajasekaran 等）把上下文工程定义为「在推理过程中**策划并维护最优 token 集合**」，总纲一句话：

> 好的上下文工程 = 找到**最小的一组高信号 token**，最大化期望结果出现的概率。

它给出的理论解释（为什么长上下文会退化）：
- Transformer 让每个 token 关注所有其他 token → **n 个 token 产生 n² 组配对**，上下文越长配对越被「摊薄」；
- 训练数据分布中**短序列远比长序列常见**，模型对长程依赖的经验更少；
- 位置编码插值能让模型处理更长序列，但**降低位置理解精度**；
- 因此这是**性能梯度而非断崖**——长上下文仍可用，但检索精度与长程推理相对下降。

**Chroma《Context Rot》技术报告**（2025-07-14，Kelly Hong / Anton Troynikov / Jeff Huber）是这个问题最系统的实测：

| 项目 | 规模 |
|---|---|
| 模型数 | **18 个**（Claude Opus 4 / Sonnet 4 / 3.7 / 3.5 / Haiku 3.5；o3 / GPT-4.1 / 4.1-mini / 4.1-nano / 4o / 4 Turbo / 3.5 Turbo；Gemini 2.5 Pro / 2.5 Flash / 2.0 Flash；Qwen3-235B / 32B / 8B） |
| 实验矩阵 | 8 种输入长度 × 11 个针插入位置 |
| 总调用量 | **194,480 次**（拒绝 69 次，0.035%） |

关键结论（对工程设计有直接影响的几条）：

1. **性能随输入长度持续退化**，即使任务极简、难度恒定。
2. **仅 1 个干扰项就使性能低于基准**，4 个干扰项进一步加剧——即**无关内容不是"中性的"，是主动有害的**。这条直接支持「不要全量注入图谱」。
3. **反直觉**：在全部 18 个模型、所有配置中，**打乱的干草堆一致优于逻辑结构化的干草堆**（作者推测与注意力机制如何作用于输入结构有关，属未解机制）。→ 提示「结构连贯性」本身不保证增益，不要迷信排版。
4. **LongMemEval 实测**：长提示平均约 **11.3 万 token** vs 聚焦提示平均约 **300 token**，所有模型在聚焦提示上显著更优；Claude 家族差距最大（模糊情境下倾向弃权）。思考模式能提升两者，但**差距依然存在**。
5. **上下文工程至关重要**：信息"是否在上下文中"不是全部，**如何呈现**（位置、结构、相似度、干扰项）同样强烈影响性能。

> **对本项目的直接推论**：把 300 个节点全量注入 system prompt，属于「大量低相似度内容 + 潜在干扰项」的最差组合。聚焦提示（只给当前话题相关的子图切片）预期显著更优。

**长上下文失效的四类模式**（Drew Breunig，LangChain 博文引用）：
- **Poisoning**（污染）：幻觉进入上下文，并被后续轮次反复引用固化
- **Distraction**（分心）：上下文淹没训练信号
- **Confusion**（混淆）：多余上下文影响回答
- **Clash**（冲突）：上下文内部相互矛盾

本项目对应：图谱摘要里的 `content[:200]` 截断可能产生**半句话的语义碎片**，既是 Distraction 也是潜在的 Confusion 来源。

### 3.2 Anthropic：长时任务的三类技术

原文前提：任务跨越数十分钟到数小时，token 数会超过上下文窗口；**且即使窗口继续增大，上下文污染与相关性问题仍存在**。

| 技术 | 做法 | 关键细节 | 适用条件 |
|---|---|---|---|
| **Compaction（压缩）** | 接近窗口上限时把内容**高保真总结**，用摘要**开启新窗口**继续 | Claude Code 实现：总结时**保留架构决策、未解决的 bug、实现细节**，丢弃冗余工具输出；以压缩后上下文 + **最近访问的 5 个文件**继续。调优方法：**先最大化 recall**（确保捕获每一条相关信息），**再迭代提升 precision**。**最低成本、最安全的压缩形式 = 清理工具调用与结果**（tool result clearing）——"工具调用发生在很靠前的历史中时，智能体为何还需要看到原始结果？" | 需要大量来回交互、**要求维持对话流连续性**的任务 |
| **Structured Note-taking** | 定期把笔记**持久化到窗口之外**（`NOTES.md`、待办清单），之后取回 | 案例：Claude 玩 Pokémon 维持**数千步**的精确统计、自绘地图、记录成就、维护战斗策略；**上下文重置后读自己的笔记继续**多小时训练。产品化：Claude Developer Platform 的 **memory tool**（基于文件的窗口外存储） | 有**清晰里程碑**的迭代式开发 |
| **Sub-agent Architectures** | 子智能体各用**干净窗口**处理特定任务，主智能体以高层计划协调 | 子智能体可能消耗数万 token 探索，**只返回 1,000–2,000 token 浓缩摘要**；实现关注点分离 | **并行探索**能带来收益的复杂研究分析 |

其他可迁移要点：
- **System prompt 的 Goldilocks zone**：两个失败极端 = 硬编码脆弱 if-else（过左）/ 过于笼统无具体信号（过右）。推荐**分层组织**（`<background_information>` / `<instructions>` / `## Tool guidance` / `## Output description`）。
- **Just-in-Time 检索 vs 预推理检索**：只保留轻量标识符（文件路径、查询、链接），运行时用工具动态加载。代价是**运行时探索更慢**，需要精心设计工具与启发式。Claude Code 是**混合策略**：`CLAUDE.md` 前置加载 + `glob`/`grep` 即时导航。
- **Progressive Disclosure（渐进式披露）**：逐层组装理解（文件大小暗示复杂度、命名暗示用途、时间戳作相关性代理），只把必要的留在工作记忆。
- **元数据本身是信号**：文件层级与命名帮助判断信息如何被使用。
- 收尾建议：「**do the simplest thing that works**」。

### 3.3 Manus：生产级 Agent 的六条原则（含量化）

来源：Yichao 'Peak' Ji，《Context Engineering for AI Agents: Lessons from Building Manus》。本报告引用的是二手整理页（Agentic AI Knowledge Base），一手博文未直接获取成功，**细节建议回溯原文**。

**背景量化**（这几条是决策依据）：

| 指标 | 数值 |
|---|---|
| 框架**重建次数** | **4 次**（每次都是发现更好的上下文管理方法后重建） |
| 典型任务工具调用数 | 约 **50 次** |
| 平均 **输入:输出 token 比** | 约 **100:1** |
| 缓存输入价格 | **$0.30 / MTok** |
| 未缓存输入价格 | **$3.00 / MTok** |
| 价差 | **10 倍**（同时显著降低延迟） |

> 正因为 ~100:1 的输入输出比，上下文工程在 Manus 是**第一优先级问题**，不是优化项。

| # | 原则 | 做法 |
|---|---|---|
| 1 | **围绕 KV-Cache 设计** | KV-cache 命中率是**生产级 Agent 最重要的单一指标**。① 保持 prompt 前缀稳定——**哪怕只差一个 token**，从该点起缓存全失效（反例：system prompt 开头写精确到秒的时间戳）；② 上下文**只追加（append-only）**，不改先前的 action / observation；序列化必须**确定性**（很多语言不保证 JSON key 顺序）；③ 显式标记缓存断点（至少覆盖 system prompt 结尾） |
| 2 | **Mask, Don't Remove** | 动态增删工具会 ① 使工具定义之后的 KV-cache 全失效 ② 让历史 action 引用不存在的工具 → schema 违规/幻觉动作。解法：**上下文感知状态机 + 解码期遮蔽 token logits**，工具定义在前缀中保持稳定。附加技巧：一致前缀命名（`browser_*` / `shell_*`）支持组级约束 |
| 3 | **把文件系统当作上下文** | 文件系统 = 「终极上下文」（容量无限、天然持久、可直接操作）。**关键设计原则：所有压缩策略必须可还原（restorable）**——网页内容可丢，**只要 URL 保留**；文档内容可省略，**只要文件路径还在 sandbox 中**。从而避免激进摘要的**不可逆**信息损失 |
| 4 | **通过复述操纵注意力（Recitation）** | 创建 `todo.md` 并随任务推进更新，把目标**复述到上下文末尾**，对抗 lost-in-the-middle。典型任务跨 ~50 次工具调用，无主动注意力管理会跑偏 |
| 5 | **把错误留在上下文里** | 直觉是清理失败轨迹；Manus 经验**恰恰相反**——保留失败动作及其错误/stack trace，模型会**隐式更新信念**远离类似动作。**错误恢复是真正 agentic 行为最清晰的指标之一** |
| 6 | **不要被 Few-shot 带偏** | 上下文充满相似 action-observation 对时，模型倾向**继续遵循该模式**（如批量审 20 份简历会陷入重复节奏）。解法：引入**少量结构化变异**（不同序列化模板、替代措辞、轻微顺序/格式噪声）打破模式 |

**Manus 策略汇总表**（原文）：

| 策略类别 | 实现方式 |
|---|---|
| Cache context | KV-cache 优化为首要指标；稳定前缀、append-only、确定性序列化 |
| Offload context | 文件系统作主要外部记忆；**仅做可还原的压缩** |
| Reduce context | 引用（URL/路径）被保留时才丢弃内容；**绝不做不可逆压缩** |
| Isolate context | 上下文感知状态机做工具遮蔽；**不是**多 Agent 并行 |
| Attention management | `todo.md` 复述，防止长任务目标漂移 |

### 3.4 LangChain：Write / Select / Compress / Isolate

来源：LangChain 官方博客《Context Engineering for Agents》（2025-07-02）。核心比喻：**LLM 好比操作系统，上下文窗口就是 RAM**（Karpathy）。需管理三类上下文：Instructions / Knowledge / Tools。

| 策略 | 技术清单 | 案例与量化 |
|---|---|---|
| **WRITE**（存到窗口外） | ① **Scratchpads**：工具调用写文件，或运行时 state 字段；② **Memories**：跨会话记忆（每轮反思生成 / 定期合成） | Anthropic 多智能体研究者把计划存入 Memory，**防止超 20 万 token 被截断**；Reflexion（反思复用）、Generative Agents（定期合成）；ChatGPT / Cursor / Windsurf 自动生成长记忆 |
| **SELECT**（拉进窗口） | Scratchpad 选择 / Memories 选择（episodic 示例、procedural 指令、semantic 事实）/ **记忆索引**（embeddings + 知识图谱）/ **Tools 选择**（对工具描述做 RAG）/ Knowledge 选择（RAG） | **工具描述做 RAG 检索后，工具选择准确率提升约 3 倍**；Windsurf 的 Varun：「索引 ≠ 上下文检索」，需 AST 解析、按语义边界分块、grep/文件搜索、知识图谱检索、re-ranking。反面案例：Simon Willison 的地点记忆被意外注入到生成的图片中 |
| **COMPRESS**（只留必要 token） | ① **Summarization**：递归/分层摘要，可放特定位置；② **Trimming**：硬编码启发式过滤 | **Claude Code 超过 95% 上下文窗口触发 auto-compact**；Cognition 在 agent-agent 边界做摘要（用**微调模型**）；Provence（训练好的上下文剪枝器） |
| **ISOLATE**（拆分上下文） | ① Multi-agent（子 Agent 独立工具/指令/窗口）；② 环境隔离（Sandbox，只回传选定返回值）；③ State 对象（设计 schema，只暴露部分字段） | OpenAI Swarm（分离关注点）；Anthropic 多智能体研究者：隔离上下文的 Agent 并行优于单 Agent，**但 token 消耗最多达聊天场景的 15×**；HuggingFace deep researcher 用沙箱隔离 token 重的对象（图像/音频） |

### 3.5 记忆系统：从「更大的窗口」到「独立记忆层」

这一支的核心主张是：**百万 token 窗口不能替代记忆层**——Agent 质量瓶颈常是「记不住」或「记错了」。

| 系统 | 核心机制 | 对本项目的参考价值 |
|---|---|---|
| **MemGPT / Letta**（arXiv 2310.08560） | 把 LLM 当操作系统：**分页式虚拟上下文**——主上下文（有限）+ 外部存储 + 通过函数调用换页（page in/out）；自编辑记忆 | ✅ **概念直接可迁移**：主上下文 = 当前轮 prompt；外部存储 = 项目**已有的** `nodes/{id}.md` 文件与 `agent_runs` 表；换页 = 工具 `rag_search(source=graph)` |
| **Mem0**（arXiv 2504.19413） | 从对话中抽取事实、去重、更新，维护用户级记忆 | ⚠️ 与项目**已有**的用户画像（`core/profile/`）+ 图谱**同构** → 不引入，避免重造轮子 |
| **Zep / Graphiti**（arXiv 2501.13956，待核） | **时序知识图谱**作 Agent 记忆：实体/关系带时间有效性，新事实使旧事实失效（invalidation） | ⚠️ 同上；但「**时序失效**」思想对图谱有用（节点掌握度/内容随时间更新） |
| **RAPTOR**（arXiv 2401.18059） | **递归聚类 + 摘要成树**；检索时**树遍历**或**折叠树**，支持不同抽象层级的问答 | ✅✅ **对场景 B 最有用**：可为「学科 → 板块 → 节点」三级各生成摘要，提供低成本全局视图 |
| CoALA（认知架构分类） | working / episodic / semantic / procedural 四类记忆 | 📚 用于给现有组件定位：`agent_context`=working、`agent_runs`=episodic、图谱+画像=semantic |

### 3.6 压缩与剪枝（推理层，本项目不可控但要知情）

| 技术 | 机制 | 本项目可用性 |
|---|---|---|
| **LLMLingua / LLMLingua-2**（arXiv 2310.05736，待核） | 用小模型做**prompt 压缩**（token 级剪枝），保留语义 | ⚠️ 需额外模型；本项目更适合规则化裁剪 |
| **StreamingLLM / Attention Sinks**（arXiv 2309.17453，ICLR 2024） | 发现保留**少量初始 token**（attention sinks）可稳定注意力；由此支持滑动窗口流式推理 | ⛔ 模型内部，API 不可控。但**解释了「为什么丢最旧的历史反而相对安全」**——早期 token 有注意力锚点作用 |
| **H2O（Heavy-Hitter Oracle）**（arXiv 2306.14048，待核） | 识别并保留高注意力权重的 KV | ⛔ 推理层 |
| **SnapKV**（arXiv 2404.14469，待核） | KV cache 压缩，按重要 token 选择 | ⛔ 推理层 |

### 3.7 场景 A 的取舍：哪些用、哪些明确不用

| 技术 | 采用？ | 理由 |
|---|---|---|
| System prompt 分层组织 | ✅ | 低风险，改善指令跟随 |
| 图谱注入**按需切片**（progressive disclosure） | ✅✅ | 修 §2.4 硬失效点；`slice_graph` 已存在 |
| Just-in-time 拉取节点内容（`rag_search`） | ✅✅ | 项目**已有**该工具；正是 Anthropic 的混合策略 |
| 历史上限 + **摘要**分层（升级 `context_guard`） | ✅ | 沿用其自注的升级路径 |
| **Tool result clearing**（较早轮次工具结果替换为占位符） | ✅✅ | Anthropic 称"最低成本、最安全的压缩形式"；且**不破坏协议**（保留 `tool_call_id`，只清 `content`）|
| 前缀稳定化以命中 KV 缓存 | ✅（需先核实供应商支持） | Manus 实测 10 倍价差 |
| 可观测指标（裁剪率/截断率/token 占比） | ✅ | 无度量则无法验收 |
| **多 Agent 隔离** | ⛔ | Anthropic 明确：适合**并行探索**；本项目是单线教学对话。且成本最多 15× |
| **引入 Mem0 / Zep / Letta 作为新依赖** | ⛔ | 项目已有图谱 + 画像 + agent_runs，属**同构能力**；引入 = 重造轮子 + 双份事实源风险 |
| 每轮重跑全局 map-reduce | ⛔ | 成本与延迟不可接受（那是**离线**索引期的技术） |

## 四、调研 B：超窗产物生成（图谱文件）的学术界做法

### 4.1 先把约束拆开（这是解法的前提）

「不能在一个上下文窗口内生成」实际是**两个独立约束**：

| 约束 | 本质 | 表现 | 学界主线 |
|---|---|---|---|
| **(i) 输出上限** | `max_tokens` 是独立硬墙，与输入窗口无关 | 生成一半被截断，JSON 不完整解析失败 | **Plan-then-Expand**（分段生成） |
| **(ii) 全局视野** | 跨块一致性需要"看到全局"，全局塞不进窗口 | 同义概念重复、粒度漂移、**跨块边永远抽不到** | **层次化 map-reduce / 预生成摘要** |

**分开对症是本节的核心结论。** 只做 (i) 分段解决不了跨块一致性；只做 (ii) 层次化解决不了单次截断。

### 4.2 主线一：Plan-then-Expand（解输出上限）

| 工作 | 论文 | 方法 | 可迁移点 |
|---|---|---|---|
| **Plan-and-Write** | Yao et al., NAACL 2019 | 先由模型生成故事计划（plan），再据计划逐段生成 | 「先规划后写作」范式的起点 |
| **Re3** | Yang et al., EMNLP 2022 | **递归 re-prompting + 修订**：Plan / Draft / Rewrite / Edit 四阶段，模拟人类创作流程 | **递归**（把上一步产物作为下一步上下文）+ **修订回路** |
| **DOC**（Detailed Outline Control） | Yang et al., ACL 2023 | **分层大纲 + 细节展开 + 修订**；引入 Detailed Outline Control 缓解长文中的「细节丢失」 | ✅✅ **三级结构直接对应本项目的「学科 → 板块 → 节点」** |
| **LongWriter / AgentWrite** | Bai et al., arXiv **2408.07055**（2024-08，清华 + 智谱） | AgentWrite 是**基于智能体的流水线，把超长生成任务拆解为子任务**，使 off-the-shelf LLM 能生成**超过 20,000 词**的连贯输出 | ✅✅ **本项目图谱生成的最贴切范式** |
| **Skeleton-of-Thought** | Ning et al., 2023 | 先生成答案骨架，再**并行**填充各段 | 骨架与填充解耦后**可并发**（延迟收益） |

**LongWriter 的关键实验发现（摘要原文可核）**：
- 现象：当前长上下文 LLM **能处理 10 万 token 输入，输出却难以超过 2,000 词**；
- 根因：**有效生成长度本质上受限于 SFT 阶段见过的样本长度**——不是能力不足，而是 SFT 数据集缺长输出样本；
- 数据构造：用 AgentWrite 造 **LongWriter-6k**（**6,000 条 SFT / 输出 2k–32k 词**）；
- 效果：加入训练后把输出长度扩展到**超过 10,000 词**且保持质量；
- 评测基准：**LongBench-Write**（⚠️ 中文二手报道常写作 "LongWrite-Ruler"，与之不符，以论文为准）；
- 9B 模型 + DPO 在该基准上取得 SOTA，超过更大的专有模型。

> **对本项目的三重映射**：
> ① 「输出上限」= 我们遇到的 `call_llm max_tokens=2000` + 内容字段过大 → 直接对应 LongWriter 描述的「2000 词墙」；
> ② 「拆解为子任务」= 把「一次生成 N 个节点的结构 + 全文内容」拆成「骨架」+「逐节点内容」；
> ③ 项目**不能**微调模型（用第三方 API），所以不能走「喂长输出数据解锁」的路——**只能走工程拆解**，这反而让 AgentWrite 的流水线部分成为唯一可用路径。

### 4.3 主线二：层次化 Map-Reduce + 预生成摘要（解全局视野）

| 工作 | 论文 | 方法 | 可迁移点 |
|---|---|---|---|
| **GraphRAG** | Edge et al., arXiv **2404.16130**（微软，2024-04） | **两阶段索引**：① LLM 从源文档导出**实体知识图谱**；② 对**紧密相关实体构成的社区**（groups of closely related entities）**预生成社区摘要**。查询时 **map**：每个社区摘要各自生成部分响应 → **reduce**：汇总为最终响应 | ✅✅✅ **「跨块全局视野」的工业级解法，本方案的核心参考** |
| **RAPTOR** | Sarthi et al., arXiv **2401.18059**（2024-01） | **递归聚类 + 摘要成树**；检索时**树遍历**或**折叠树**，跨长文档整合信息 | ✅✅ 三级摘要树 ≈ 「学科 → 板块 → 节点」 |
| **LightRAG** | Guo et al., 2024 | 图结构 + 双层检索（局部实体 / 全局主题），强调**增量更新**成本低 | ✅ 增量更新是图谱长期维护的关键 |

**GraphRAG 的关键设计（摘要可核 + 正文常规做法）**：
- 社区摘要**在索引期预生成**（不是查询时现算）→ 这是它能规模化服务全局问题的根本原因；
- 查询用 **map-reduce**：局部（社区级）→ 全局（语料级），这解释了标题「From Local to Global」；
- 在**百万 token 量级数据集**的**全局意义建构类问题**（global sensemaking）上，**全面性（comprehensiveness）与多样性（diversity）显著优于常规 RAG baseline**；
- 社区检测通常用 **Leiden** 层次化算法（摘要未点名，属正文算法细节）。

> **对本项目的映射**：项目的图谱**已经有天然的层次** —— `subject`（学科）→ `board`（板块）→ `node`（节点），且 `graph_middleware.slice_graph` 已能按 subject/board 切片。缺的只是**为每一层生成摘要**（板块摘要 / 学科摘要），用作该层级的低成本全局视图代理。这比引入 Leiden 社区检测便宜得多（层次已经人工/规则定义好了）。

### 4.4 主线三：增量构建与跨批一致性

**iText2KG**（Lairgi et al., arXiv **2409.03284**，WISE 2024）是最直接对应「跨批次一致性」的学术工作：

- 定位：**增量式、主题无关、无需后处理**的知识图谱构建；即插即用、**零样本**。
- 四个模块：
  1. **Document Distiller**（文档蒸馏）——把原始文档提炼为后续抽取所需的输入；
  2. **Incremental Entity Extractor**（增量实体抽取）——处理**未解析实体**与**语义重复实体**；
  3. **Incremental Relation Extractor**（增量关系抽取）——处理**语义重复关系**，避免图不一致；
  4. **Graph Integrator and Visualization**——整合进图谱 + 可视化。
- 动机：传统方法受限于预定义实体类型与监督学习，且**未解析实体、语义重复实体、语义重复关系会导致图不一致，需要大量后处理**。
- 评测：在**三个场景**（科学论文转图谱、网站转图谱、简历转图谱）中**优于基线**（摘要未给具体数值，需查全文）。

> **对本项目的价值**：iText2KG 的四模块**恰好就是本项目 `graph_generator` 的四个缺口的对照表**。
> - Document Distiller → 项目缺失：现在直接把 5000 字原文喂进去，**没有"蒸馏"**（无章节定位、无主题标注）；
> - Incremental Entity Extractor → **已有等价物**（`_find_dedup_candidates` + `_confirm_synonyms`）；
> - Incremental Relation Extractor → 部分有（边由每批 LLM 抽），但**跨批边缺失**；
> - Graph Integrator → 部分有（`_write_to_graph`），但**无全局归一化阶段**。
>
> iText2KG 明确主张「在构建过程中处理重复与不一致，从而**无需后处理**」；本项目现在是「先乱建 + 事后补去重」，**顺序反了**——去重发生在写库时而不是抽取时，导致 LLM 每批都要看到全量 `existing_nodes`（缺口 #4）。

**其他相关方向**（未逐一核验，供延伸阅读）：
- **OpenIE with LLMs**（Trajanoska et al., 2023）：用 LLM 做开放信息抽取的可复现性研究；
- **KGGen**（2025）：面向文本语料的 KG 生成工具包，含实体/关系抽取与去重；
- **Docs2KG**：多模态文档转 KG；
- **Graphiti / Zep** 的**时序失效（temporal invalidation）**：新事实使旧事实失效——对「节点内容随教学进展更新」有参考价值。

### 4.5 工程侧：让"不可靠的长输出"变成"可验收的产物"

| 手段 | 说明 | 与缺口对应 |
|---|---|---|
| **Structured Outputs / Constrained Decoding** | 用 JSON Schema 约束解码（供应商级能力）。主流实现：JSON Mode / Constrained Decoding / Grammar-based。**关键限制：能约束"格式"，不能防"截断"**——输出被 `max_tokens` 砍断时，schema 也救不了 | 降低格式失败率，但**不能替代截断检测** |
| **截断检测** | 必须检查 `finish_reason == "length"`，把它当**失败**而非成功 | 缺口 #1、#2 |
| **分阶段产物落盘** | 骨架与内容分开存文件（骨架 JSON + 每节点 MD）→ 天然可断点续跑 | 缺口 #7、#9 |
| **幂等键** | `(file_hash, chunk_id, prompt_version, model)` 作缓存键；重跑不重复计费 | 缺口 #9 |
| **输出预算倒推分片** | 由 `max_tokens` 与"单个产出单元的体积"倒推每批处理几个单元 | 缺口 #1、#6 |
| **revision 回路** | 生成后做一次轻量校验/修订（Re3 / DOC 的做法） | 提升产物质量（可选） |

## 五、方案设计

### 5.1 场景 A：对话上下文分层管理

**A1（最高优先，修 §2.4 硬失效点）：图谱注入预算化 + 按需切片**

- **常驻层（小而稳定）**：学科清单 + 各学科节点计数 + 当前学科/板块 + 全局统计（十几个 token 级别）。
- **按需层（每轮动态）**：**只注入与当前话题相关的子图切片**——直接复用已有的 `graph_middleware.slice_graph(subject, board)`；配合项目的 `prerequisite` 扩跳（`rag_manager.search(hops=)`）取当前节点的**邻居子图 + 掌握度**。
- **工具层（just-in-time）**：节点详细内容不再预注入，改由 Agent 按需调用 `rag_search(source="graph")` 拉取（项目已有该工具）。
- **硬兜底**：给图谱区块设 token 上限（如 ≤8K），超限按优先级截断（当前节点 → 同板块 → 同学科），并记日志。

> 这一条同时命中三件事：修硬失效点、降低输入成本、符合 Chroma 的「聚焦提示显著优于长提示」与 Anthropic 的 progressive disclosure。

**A2：`context_guard` 从「丢最旧」升级为「分层 + 摘要」**

沿用其自注的升级路径（`context_guard.py:10-15`）：被裁段先压成一句话摘要置顶，再配省略说明。

- 分层保留：`system` + **首条 user**（任务锚点，呼应 StreamingLLM 的 attention sink 现象）+ 最近 N 轮完整 + 更早部分的**摘要**。
- 摘要调优按 Anthropic 的方法：**先最大化 recall，再迭代提 precision**。
- 明确不做无损保证——被裁内容已沉淀进图谱/画像/`agent_runs`，这是项目特有的低成本优势（**但对场景 B 不成立**，见 §5.2）。

**A3：Tool Result Clearing（最低成本、最安全的压缩）**

在 agent loop 中，把**较早轮次**的工具结果 `content` 替换为占位符（如 `[已清理的工具结果，需要时请重新调用]`），**保留 `role` / `tool_call_id` / 工具名**，因此**不破坏协议**。

- 优先清理 token 重的工具：`rag_search`（返回大段文档）、`fetch_webpage`（网页正文）——`download_resource` 的结果本来就是文件，天然可还原。
- 阈值：保留最近 K 轮（建议 2–3）的工具结果原样，更早的清理。
- 这是 Anthropic 点名的**最低成本、最安全**的压缩形式，因为工具调用可重放。

**A4：前缀稳定化（KV / Prefix 缓存）**

- 目标：让 system prompt 前缀在多轮之间**逐字节稳定**，从而命中供应商的 prefix cache。
- 做法：把**动态内容**（图谱摘要、用户画像、RAG 检索结果）**从 system prompt 移到消息序列的动态位置**（如最后一条 user 消息之前的独立 system 段、或直接并入 user 消息），保持头部 system prompt 只含静态指令 + 工具定义。
- 禁忌（Manus 原则 1）：system prompt 里**不能有时间戳/随机 id/正则序 JSON**；序列化必须确定性。
- ⚠️ **前置核实**：MiniMax-M3 与 DashScope 是否提供 prefix/KV 缓存及其计费（Manus 实测有缓存则差 10 倍；`token_estimator._MODEL_PRICING` 目前**没有缓存价维度**，需扩展）。

**A5：可观测（无度量则无法验收）**

新增采集：`system_prompt_tokens` 占比、裁剪率与裁剪条数、`finish_reason=length` 次数、每轮输入 token、缓存命中率（若可得）。落点：`agent_run_store` 已有 `token_usage` / `estimated_prompt_tokens` 字段，**扩展而非新建表**。

**明确不做**：多 Agent 隔离（单线教学场景，成本最多 15×）；引入 Mem0/Zep/Letta（与现有图谱+画像同构，重造轮子）；每轮重跑全局摘要。

### 5.2 场景 B：图谱生成三段式（骨架 → 归一化 → 内容）

**这是本报告对用户「不能一次生成」问题的正面回答。**

```
① 抽取骨架        ② 全局归一化        ③ 逐节点展开内容
  Skeleton  ────►  Normalize  ────►   Expand  ────► 落盘
  只有结构          全骨架在手           单节点独立
  输出极小          可补跨块边           输出小、可并发
  可整学科一次跑     同义合并/粒度对齐    可断点续跑
      │                  │                   │
      └──── graph_skeleton.json ─────────────┘
                      产物即进度（幂等）
```

**① 骨架段（Skeleton）**

- **只生成结构**：`id` / `name` / `summary`（一句话）/ `difficulty` / `estimated_minutes` / `edges`。**不生成 `content`**。
- 输出体积比现在小**一到两个数量级** → 不再截断；甚至可以把整学科的骨架分批次全部生成完再合并。
- 输入仍分块（保留现有 `_split_text`），但**块与块之间只需传递"已抽取节点清单"**，不需要传边、不需要传内容。

**② 归一化段（Normalize）—— 新增能力，解缺口 #5**

全骨架到手后，做一次**全局**处理（这一步才第一次"看到全局"）：
- **同义合并**：复用已有 `_find_dedup_candidates` + `_confirm_synonyms`（嵌入粗筛 + LLM 确认），但现在是在**纯骨架**上做，成本远低于带内容的版本。
- **id / 命名统一**：按统一命名规范（英文下划线）批量规范化，处理跨批命名漂移。
- **粒度对齐**：检查同一层级节点粒度是否一致（如有的批抽到"二叉树"，有的批抽到"二叉树的前序遍历"），必要时合并/拆分。
- **✅ 补跨块边（关键新增）**：此时**全学科节点都在手里**，可专门做一次/多次"边推断"调用——按板块分组，对每个板块内的节点 + 相邻板块的边界节点推断 `prerequisite` / `related` 关系。这解决「跨章节边永远抽不到」。
  - 成本控制：不要求两两判断，先按板块划分减少候选对；只对**同板块 + 相邻板块**生成候选。
  - 可选：复用项目已有的 `core/prerequisite.py` 多准则投票（micro F1 0.941）做**候选生成**，LLM 只做确认——**这是项目已有的、比纯 LLM 更可靠的资产**。
- 产物：`graph_skeleton.json`（归一化后）落盘 → 这就是**进度与幂等的载体**。

**③ 内容段（Expand）—— 解缺口 #1、#4、#6**

- **每个节点独立一次调用**：`call_llm(节点模板, [{"role":"user", "content": 节点信息 + 定向检索片段 + 大纲}])`。
- 上下文构造（**这是 just-in-time 检索的落点**）：不再传整本书或整章，而是用 **`rag_search(source="kb", q=节点名+summary)`** 定向取该节点的源文本片段（top-k，几 KB 级）。→ 上下文体量从"5000 字原文"降到"节点信息 + 若干相关片段"，**且更精准**。
- 输出预算：单节点内容设 `max_tokens` 4000–6000（按节点重要性分档），并按 **`finish_reason` 判失败**。
- 并发：节点之间相互独立 → 可并发（建议 4–8，配合限流退避）。
- **渐进填充（DOC 的层级展开思想）**：同一板块内的节点按依赖顺序生成，prompt 里带上**已生成的邻居节点摘要**，保证同一章节内讲解风格与粒度一致。
- 断点续跑：检查 `nodes/{id}.md` 是否存在且**内容非"待完善"占位**（现有代码在 `content` 为空时写 `待完善...`，可直接作为"未完成"标记）→ 只补缺失的。

**④ 异步化与进度（解缺口 #7）**

- `/kb/graph/generate` 从同步端点改为**后台任务**：立即返回 `task_id`，前端轮询进度（阶段 / 已完成节点数 / 总节点数 / 失败数）。
- 直接复用 `core/collector/manager.py` 的**任务模式**（创建 / 进度 / 取消 / 统计），不新建框架。
- 支持**取消**与**失败重试单节点**。

**⑤ 参数与检测（解缺口 #1、#2）**

- `call_llm` 增加 `max_tokens` 参数（默认保持 2000 向后兼容），图谱生成三阶段各自设置。
- 新增**截断检测**：`finish_reason == "length"` → 判失败，按阶段策略处理（骨架段：重试并缩小批；内容段：重试单节点，仍失败则降级写精简版并标记）。

## 八、风险与边界

| # | 风险 | 缓解 |
|---|---|---|
| 1 | **摘要不可逆丢信息**（对话侧） | 分层摘要只用于**对话历史**（内容已沉淀进图谱/画像/`agent_runs`）；**绝不用于图谱知识内容**（Manus 原则 3：只做可还原压缩） |
| 2 | 图谱切片可能漏掉相关节点 | 工具层兜底（`rag_search(source="graph")` 可随时拉）；切片失败降级为常驻层 |
| 3 | 三段式增加调用次数 | 单次输出小、失败率低、可并发，净收益需实测（§7.2）；骨架段可整学科一次跑，实际增加的主要是内容段 |
| 4 | 跨块边推断可能引入错误边 | 复用 `core/prerequisite.py` 的多准则投票（阈值可调、默认 dry-run）+ 高置信度才写库；项目已有 `graph_analyzer` 的 confidence ≥0.7 阈值为先例 |
| 5 | 前缀缓存依赖供应商 | **先核实 MiniMax / DashScope 的缓存能力与计费**；不支持则本项降级为"保持前缀确定性"，收益仍为正（确定性序列化本身有益） |
| 6 | 异步化引入并发问题 | 复用 collector 的成熟任务模式；`uvicorn --workers 1` 硬约束下**进程内任务队列**即可（无需引入 broker） |
| 7 | 为"上下文工程"引入重型框架 | **明确不做**。本项目需要的机制用现有组件就能实现（见 §5.3） |
| 8 | 改动触碰 agent loop 协议 | P0/P1 均**不改协议**（截断检测在 `call_llm` 层、图谱生成在独立模块）；P2 的 tool result clearing **保留 `tool_call_id` 只清 content**，协议不变 |

**YAGNI 边界（明确不做）**：
- 多 Agent 上下文隔离（场景不适配 + 成本 15×）
- 引入 Mem0 / Zep / Letta / LangMem 等记忆框架（与现有图谱+画像同构）
- 引入向量化「长期记忆」独立层（项目已有 `agent_runs` + 图谱 + 画像）
- 微调模型以解锁长输出（用第三方 API，不可行）
- 引入 Leiden 社区检测（项目的 `subject → board → node` 层次已定义，无需算法发现）
- 客户端 prompt 压缩模型（LLMLingua 类，收益不匹配额外依赖）

## 十、实施记录：P0 缺口 #1 / #2 修复（2026-09-13）

### 10.1 触发：Docker 生产日志

`docker compose logs` 中「生成学科图谱」出现两类报错，且**交替出现、几乎每块必现**：

```
学科图谱生成 LLM 返回无法解析的 JSON: {"nodes":[{"id":"behavior_policy",...,"content":"## 行为策略\n\n**定义**：策略 π(a|s) 表示在状态 s 下选择行为 a 的概率分布。在本章示例中使用了**均匀随
E-LLM-006 | AI返回了空回复，请重试 | detail=AI返回空内容
学科图谱生成 LLM 调用失败: [E-LLM-006] AI返回了空回复，请重试
```

**判读**：第一条在 `均匀随` 处**断在词中间**——JSON 括号从未闭合，这正是缺口 #1 描述的硬截断；第二条（空回复）同源：`max_tokens=2000` 的输出预算被 M3 的 reasoning 与正文共同消耗，预算耗尽时 `content` 可能整段为空 → `strip_think_tags` 后为空 → `E-LLM-006`。

### 10.2 实测复现（`call_llm`，真实 API）

| 输入要求 | `max_tokens` | 实际返回长度 | `extract_json` |
|---|---|---|---|
| 3 个知识点，content 约 300 字 | 2000 | 2334 字符 | ✅ True |
| 3 个知识点，content 约 300 字 | 8000 | 1137 字符 | ✅ True |
| **20 个知识点，content ≥ 250 字** | **2000** | **861 字符（截断，尾部断在** ``print(...)`` **中间）** | ❌ **False** |
| 20 个知识点，content ≥ 250 字 | 8000 | 13416 字符（仍被截断） | ❌ False |

结论：**输出需求一旦超过 2000 token 就必然整块丢弃**；8000 对单块 3000 字的教材（约 5–10 个节点、数千 token 输出）有充足余量，但不是无上限——分块大小与 `max_tokens` 必须成对调。

### 10.3 本次改动

| 项 | 内容 |
|---|---|
| 输出预算参数化 | `call_llm(system_prompt, messages, max_tokens=2000)`（默认不变，向后兼容）；新增 `finish_reason == "length"` warning，**截断不再与"模型没返回"混淆** |
| 图谱生成参数 | `GRAPH_MAX_TOKENS = 8000`（原硬编码 2000）、`GRAPH_CHUNK_CHARS = 3000`（原私有 `_split_text` 的 5000） |
