## 0. 一句话诊断

**功能覆盖面是完整的，"归属"是碎的 —— 同一个概念没有唯一落点。**

| 问题 | 现在的答案 | 应该是 |
|---|---|---|
| 谁是学习的主体 | 没人（唯一发起者 = 学生的一条消息） | 学生 + 一个显式的教学会话对象 |
| 对话历史的真相在哪 | 浏览器 `localStorage` | 服务端（或明确宣布客户端权威并撤掉服务端同步语义） |
| 数据落在哪 | 每个模块自己数 `parents[N]` → **4 个不同的 data 根** | 一个 `core/storage.py` |
| `users` 表谁定义 | 3 处各写一遍 | 1 处 |
| 删干净一个用户 | 运维后台一份手写清单，且**指向已过期的库路径** | 由 schema 派生 + 覆盖全部介质 |
| "未掌握 / 该学"是什么 | 常量 `50` 写 3 处 | 1 处 |
| 图谱掌握度分档 | 后端两套（四档 / 六档）+ 前端第三套 + 提示词第四份文案 | 1 处 |
| 会话状态存哪 | 每请求新建的 `kg` 实例上的临时属性 | 一等对象 |
| 知识库正文 | 原件 / 解析文本 / 向量 / whoosh **四份** | 仍然四份，但要有唯一写入与一致性校验 |

下面所有 P0/P1 都是这**一个病**的表现。因此重构主线是给关键概念找唯一落点（single owner），**不是重写**。

## 2. 问题清单

### P0-1 数据根四分五裂 —— 已造成两处**事实性错误**

**现象**：同一个"数据根"由每个模块自己用 `Path(__file__).parents[N] / "data"` 数出来，深度差一层就落到另一个目录。现有 4 个根：

| 根 | 谁在用（证据） |
|---|---|
| `<repo>/data/` | `knowledge.db`（`core/knowledge_graph.py:274`）、`conversations.db`（`core/conversation_store.py:27`）、`profiles/`、`keys/`、`prompts/`（`core/prompt_loader.py:14`） |
| `<repo>/backend/data/` | `kb/`（`core/kb/kb_manager.py:53`）、`rag/`（`core/rag/manager.py:44`）、`quiz/`（`core/quiz/quiz_store.py:19`）、`collector/`（`core/collector/store.py:35`）、`llm/`（`core/llm/user_models.py:35`） |
| `<repo>/backend/app/data/` | `agent_runs.db` + `debug_log.db`（`core/records.py:28`） |
| `<repo>/backend/eval_data/` | 评测夹具（内含**另一份** `knowledge.db`） |

**后果 1（脏数据 + 后台看错库）**：`backend-admin/app/core/db.py:121-123` 的 `_agent_runs_db()` 指向 `backend/data/agent_runs/agent_runs.db`，而主系统实际写 `backend/app/data/agent_runs/agent_runs.db`（`core/records.py:28`）。实测两个文件**同时存在**：

| 文件 | 大小 | 最后写入 |
|---|---|---|
| `backend/app/data/agent_runs/agent_runs.db`（真实） | 628 KB | 2026-09-28 |
| `backend/data/agent_runs/agent_runs.db`（后台在读） | 52 KB | 2026-09-13 |

→ ① **删号不会清 `agent_runs` / `llm_usage`**（运行记录与用量永久残留）；② 运维后台「用量与缓存命中」读的是 9 月 13 日就停更的库。`backend-admin/app/core/config.py:21-22` 的注释还把 `backend/data` 当成"主系统相对路径约定"照抄 —— 这正是"每个模块自己数深度"的必然漂移。

**后果 2**：`docker-compose.yml:44-55` 不得不挂 **6 个**数据卷（`./backend/app/data` 还得单独挂，`core/records.py:26-27` 注释自认这个坑）。

**后果 3（删号还漏 4 处）**：`debug_log.db`（`core/agent/debug_log.py:71` 有 `user_id`）、`data/profiles/{uid}.json`（只删了头像，`backend-admin/app/core/db.py:346`）、`collector/{uid}/collector.db`、题库孤儿题（`remove_node` / `remove_subject` 不清 `quiz.db` 里 `knowledge_point = node_id` 的行，`core/quiz/quiz_store.py` 连删除 API 都没有）。

**重构动作**：
1. 新建 `core/storage.py` 作为**唯一数据根声明处**：`DATA_ROOT` + 每域一个取径函数（`knowledge_db()`、`kb_dir(uid)`、`rag_dir(uid)`、`quiz_dir(uid)`、`records_dir(kind)`、`profiles_dir()`、`prompts_dir()`…），`backend-admin` 与脚本一律 import 它。
2. 一次性迁移脚本把 `backend/data/*`、`backend/app/data/*` 归位到单一根（保留旧路径回退一个版本，`ADMIN_*` / 新增 `DATA_ROOT` 环境变量同步）。
3. 删号清单改为**从 schema 派生**（见 P1-6），并覆盖：knowledge.db 行、节点 MD 目录、conversations、agent_runs + llm_usage、debug_log、profiles JSON + 头像、kb/rag/quiz/collector/llm 目录、whoosh 索引。

**验收**：`grep -rn 'parents\[' backend/app | grep -c data` = 0（只剩 `core/storage.py` 一处）；`docker-compose.yml` 数据卷 6 → 1；新增 `tests/test_purge_user.py` 断言"删号后 8 类介质都查不到该 uid"（含 agent_runs / llm_usage / debug_log / profiles / collector / quiz）。

### P0-3 对话历史的真相在客户端

- `/chat` 与 `/chat/stream` 直接用请求体里的 `messages`（`api/v1/chat.py:79-106`），**服务端不读 `conversations.db` 组装历史**；该库只是同步目的地（`core/conversation_store.py:30`）。
- 前端以 `localStorage` 为主（`chatStore.js:11-14,615-640`），`persist` → 500 ms 防抖 → `syncToBackend` 全量重传；后端 `adoptRemote` 只做时间戳 LWW 回刷，且 **`sync` 只 upsert、不传播删除**（`conversation_store.py:230-240`）→ 离线端旧快照可复活已删对话。
- 后果：跨 run 的"记忆"归浏览器；换设备 / 清缓存 = 教学上下文丢失；`agent_runs` 想当回放源却与会话**无关联键**（`TODO.md` §遗留技术债）。

**重构动作（必须先决策，二选一）**：
- **(a) 服务端权威（推荐）**：`/chat*` 从 `conversations.db` 取历史，前端只做缓存；删除改为墓碑（soft delete）后同步。
- **(b) 客户端权威**：撤掉服务端"防覆盖 / 合并"语义，只留一个备份端点，并在文档写明边界。

推荐 (a)：它同时解掉 P0-2 里"模型没有跨轮记忆主体"这一条。

**验收**：给定 `conv_id`，服务端能独立重放完整历史；两端并发问答不再丢消息；删除能跨端传播。

### P1-3 节点正文两种形态并存 + 漏判直读

- `create_node_with_content` **恒定**写骨架 `{id}.md`（`knowledge_graph.py:1668`，内容"待完善…"），小节化后**不删** → 同一节点可同时存在 `{id}.md` 与 `{id}/`。唯一正确出口 = `node_content_text:1126`（小节优先）。
- 漏判：`api/v1/knowledge.py:356` 直读 `nodes_dir/{id}.md` 当 `content`（docstring 称"小节化节点 content 为空串"，实际会返回骨架"待完善…"）；`scripts/inspect_graph_quality.py:184 body_of` 在 `:553` / `:586` / `:610` 及报告处**未做小节回落** → 小节节点被判 0 字，同名合并时把骨架文字 append 进保留者。

**动作**：(a) 小节化成功后删除骨架 MD（或写 manifest 标记并让读取层忽略）；(b) 把"读正文"收成唯一函数，并加**禁止直拼 `.md` 读正文**的静态测试。
**验收**：遍历 `backend/app`，除 `knowledge_graph.py` 外无第二处 `nodes_dir / f"{node_id}.md"`；体检脚本对小节节点不再报 0 字。

### P1-4 事件通道靠注释约定 + 通知易失

- 三套队列语义（全局 / per-user fan-out / 请求私有）只靠**注释**约束：`core/agent/events.py:60-63` 在 `queue=None` 时**静默回落**到 `publish(user_id=…)`，没有任何断言或类型约束；唯一"硬"保证是调用点记得传参（`chat_service.py:964,1042`）。
- `quiz_ready` 是出题后台任务约 40 s 后的异步通知，`publish(user_id=X)` 在无订阅者时**永久丢弃**，无重放、无落库补偿（`event_bus.py:202-209`）→ 学生关了页面，那道题就永远不来。
- `graph_updated` 多处不带 `user_id` = 全局广播（`api/v1/knowledge.py:128` 注释自认）。
- 非流式 `process_message` 建了队列却**无人消费**（`chat_service.py:964`）。
- 请求内事件与通知类事件的边界，本质上仍是 2026-09-26 那次"对话没反应"故障的同源问题（`TODO.md` §架构待决）。

**动作**：把三类通道做成三种**类型**（广播 / 用户通知 / run 事件），run 事件必须携带队列（`queue=None` 直接抛错）；通知类事件落一张 `pending_notices` 表，前端重连后按 `since` 补拉 —— 这同时是 P0-2 里"系统发起通道"的基础设施。
**验收**：`tests/test_event_bus.py` 增加"run 事件缺队列必须报错"；关页再开后能收到未送达的 `quiz_ready`。

### P1-5 前端上帝 store + 生命周期泄漏

- `chatStore.js` 1 131 行，管 8 件事；`graphStore.js` **不存在**。
- **未清理的副作用**：`disconnectSSE`（`:805`）**无任何调用方** → 组件卸载与登出都不断开长连接，`:707` 的 5 s 无限重连继续跑；`streamController`（`:933` / `:996`）只赋值从不 `abort`；`syncDebounceTimer`（`:127`）、`sseSuppressTimer`（`:582`）无取消；`ForceGraph.vue:194` 的 timeout 与内嵌 watch 卸载不停。
- 反向耦合：`chatStore.js:683` 用 `window.dispatchEvent` 驱动 `HomeView.vue:68-74` 重挂视图；**发射端无 `import.meta.env.DEV` 判断**（生产同样派发），只有接收端有（`HomeView.vue:174,180`）。
- 同一份边字段映射写 3 遍：`chatStore.js:271-278`、`utils/forceGraphEngine.js:107-119`、`components/ForceGraph.vue:199-200`。
- 三份真相：图谱在 store ⇄ 引擎内部归一化拷贝 ⇄ `HomeView` 的 `nodeDetailModal` 本地拷贝（靠 mastery 不一致 emit 回拉）；profile 被 4 处各自拉取。
- 多标签页无广播：全库无 `storage` 事件 / `BroadcastChannel` 监听，只靠后端 LWW 收敛。

**动作**：拆 store（`chat` / `graph` / `learning` / `sync` / `sse`）；SSE 归单一 owner 并绑定应用生命周期（登出即断、卸载即断）；流可取消；`normalizeEdge` 收成一处；`DEV` 判断挪到发射端。
**验收**：登出后网络面板无重连；新增"卸载 / 登出即断流"的 vitest 用例。

### P1-6 双 app 共享 schema，靠**手工三处同步**

`AGENTS.md §1` 明确要求：给 `knowledge.db` 加表要同步 `knowledge_graph._create_tables` + `backend-admin/app/core/db.py::delete_user_rows` 的删号清单 + `scripts/inspect_graph_quality.py` 口径。这是把 schema 迁移外包给**人的记忆**，而它已经漂移出了 P0-1 的脏数据；`users` 表 DDL 还额外在 `main.py:51` 与 `knowledge_graph.py:313` 各写一份。

**动作**：把 `knowledge.db` 的 schema（建表 + 补列 + 表清单 + 删号清单）收进一个共享模块（如 `backend/app/core/kg_schema.py`），`backend-admin` 与脚本 import 它；加测试断言"schema 中每张带 `user_id` 的表都出现在删号清单里"。
**验收**：新增一张表时删号清单**自动**覆盖（测试红→绿），`AGENTS.md` 的"手工同步三处"提醒可以删掉。

- ✅ **环境阻塞已定位并绕过（2026-10-07）**。根因是一个**沙箱行为缺陷，最小复现 3 行**：

  ```
  python -c "import pathlib; p=pathlib.Path('.x'); p.mkdir(mode=0o700); print(list(p.iterdir()))"

  ```

  即：在沙箱约束下用 POSIX `mode=0o700` 建目录，会让该目录**对本进程立即不可读、之后不可删**

  连读自身权限描述都被拒 → 跑 Windows 沙箱权限诊断脚本得 `NOT_THIS_CLASS`（工作区链路上
  当前用户已有完全控制，**未做任何权限改动**；报告 = `C:\Users\34239\Documents\GitHub\_acl-recovery_AI-tutor\acl-report-*.jsonl`）

#### A2-1b `publish` 拆 `broadcast` / `notify` ✅
