## 2. 不要动的东西（先划清，避免"重构"变"拆房子"）

这些是**已经解决问题**的设计，评审意见是"保持"：

1. **写入收口真的成立**。图谱节点 INSERT 全仓只有 `kg/nodes.py:279`，边 INSERT 只有 `kg/edges.py:82`；创建/改文/小节化都经 `mark_node_dirty` 登记索引（`_common.py:16-32`）；删除侧由 `remove_node` / `remove_subject` 内部清 RAG 索引。2026-10 新增的 `video_import` / `import_queue` **没有**绕开收口（走 `kb_manager.upload_and_index`，不直接造节点）。
2. **一次 run = 一个 `run_id` = 一份证据**。`stop_reason` 在事件、证据、调试日志三处同值；`llm_usage` 按 run 记账。排查"为什么输出没用"不需要猜，这是本项目相对同类项目最硬的能力。
3. **提示词/工具说明的单一来源**。`registry.build_tools_prompt()` 由 `guidance` 派生，授权分级由 `tier` 派生（`build_authorization_block`）—— 曾经手写两份漂移的教训已经吃过了。
4. **教学策略有纯函数出口**。`teaching/policy.py::decide()` 不读 kg、不落库、纯数据进出，配 golden 逐字符比对（`test_learn_block_golden.py`）。这是 Phase B 里做得最好的一步，应该成为其余模块的模板。
5. **事件通道三分**（广播 / 用户通知 / run 事件），且 run 事件**缺队列即抛**。2026-09-26 那次"对话没反应"的根因已被结构性消灭。
6. **1836 例回归网**。任何"大改造"的第一成本都是这张网，而不是代码量。

## 3. 问题清单

> 每条：现象 → 证据（file:line）→ 影响 → 建议 → 成本（人日，单人）。

### P0-1 会话真相仍在客户端 —— 服务端无法重放，也没有"记忆"

**现象**：`/chat` 与 `/chat/stream` 直接用请求体里的 `messages`；`conversations.db` 只是 upsert 镜像。前端以 `localStorage` 为主，同步只上行不删。

**证据**：
- `api/v1/chat.py:81`、`:106` —— `messages=request.messages`，全程不读库。
- `api/v1/conversations.py:21,51,76,119,138` —— 服务端**有**完整 CRUD + `sync`，但对话链路不消费。
- `core/conversation_store.py:189-195` —— sync 是 `ON CONFLICT DO UPDATE`；`:220-227` 自述"全量同步 = 逐条写入"，**缺失的 id 不会被删**。
- 前端 `chatStore.js:10-14`（头部注释"localStorage 为主"）、`:176-206`（`adoptRemote` 把后端有、本地没有的 push 回来）、`:1032-1034`（先 persist 触发 sync 再 delete，顺序不定且异常被吞）。
  > 以上为**审计当时**的行号与代码，修复后已不适用（现见 `chatStore.js` 头部注释与 `init()`）。

**影响**：
- 换设备 / 清缓存 = 教学上下文丢失（对一个"导师"产品，这是产品级缺陷，不只是架构债）。
- `agent_runs` 与会话**无关联键**，想回放"那一轮到底发生了什么"只能靠前端。
- 更隐蔽的一条：`guard.trim_history_to_budget` 压缩的是**前端传上来的历史**。历史不属于服务端，服务端就无法决定"什么值得留"。

**建议**：定服务端权威（旧方案 a）。分三步：① `/chat*` 接受 `conv_id`，服务端从 `conversations.db` 组装历史，`request.messages` 只取最后一条；② 前端 `localStorage` 降级为离线缓存，同步改 `PUT /conversations/{id}` + `DELETE`（带 tombstone），删 `sync` 的全量语义；③ `agent_runs` 加 `conv_id`（可空，不影响旧数据）。

**成本**：4–6 天（含迁移与两端兼容）。**这是本报告里唯一"不做就会一直拖住产品上限"的一条。**

#### 实施记录（2026-10-31 当日落地）

**结论**：三步全部完成，另加两处审查时未列的必要件。

| 步 | 落点 | 关键约束 |
|---|---|---|
| ① 服务端权威 | `chat_service._resolve_history` / `ConversationStore.append_turn` / `api/v1/chat.py` 传 `conv_id` | 有 `conv_id` → 只认库；无 → 原样透传（老前端逐字节不变）；库无该对话 → 客户端历史**一次性 bootstrap**（老用户迁移入口，且只补空缺、绝不覆盖） |
| ② 前端降级为缓存 | `chatStore.init()` 一次 `syncWithServer()`；`persist()` 不再上行 | 删掉 `syncToBackend` 的防抖全量写与 `loadFromBackend`（后者的 GET 原本只当布尔门闸） |
| ③ 删除跨端传播 | `conversations.deleted_at` + `soft_delete` / `tombstones`；`sync` 与 `GET` 都返回墓碑 | 墓碑行**拒绝任何写入**（`save_conversation` / `append_turn` 都跳过），否则 B 端下一次全量 sync 就把对话写回来 |
| ④ `agent_runs.conv_id` | `agent/store._COLUMN_MIGRATIONS` + `loop.run_agent_loop(conv_id=)` | 可空；老库由 `ensure_columns` 补列（**注意**：`CREATE INDEX` 若引用新列会先于补列执行而炸，故未建该索引） |
| ⑤ 改名通道（审查未列） | `PATCH /conversations/{id}` + `ConversationStore.rename` | 旧实现靠"全量 sync 顺带带 title"；`persist` 不再上行后此通道消失，不补 = 改名静默失效 |

**否决与取舍**（细节见《项目历程_决策与效果记录.md》D40 / D41）：不拆行级消息表（唯一需求是"能组装历史"）；压缩结果**不写回**会话（压缩是预算策略不是数据策略，写回 = 用户消息凭空消失）；assistant 的 `tools` 摘要由服务端从 `AgentRunResult.rounds` 派生（同形于 `tool_start`/`tool_result` 事件，前端组件零改动），`thinking` 不落库（体积大、刷新后本就不该重放）。

**遗留（明确不做 / 留给下一批）**：
- 客户端仍全量上行 `messages`（服务端只用最后一条）—— 传输优化留给"存量都迁完"之后。
- 墓碑无 GC：`conversations` 只增不减；需要时加 `deleted_at < now-30d` 的清理任务。
- 断连（生成器被 aclose）的那一轮**不落库**：agent 任务被取消，服务端拿不到结果。前端本地缓存仍有正文，用户重发即可。
- `chatStore` 未拆（P1-5 独立一条，不混在本次改动里）。

**验证**：`backend/tests/test_conversation_authority.py`（13 例，含"伪造中间历史不得进上下文""端点漏传 conv_id 会红""墓碑不被 sync 复活""老库补 `deleted_at` 列"）；`test_agent_run_store.py` 增老库补列 2 例；`chatStore.lifecycle.test.js` 增墓碑清除 1 例。后端 `1851 passed / 7 deselected`；后台 `43 passed`；前端 `22 passed`。

### P0-2 同步重活跑在事件循环里 —— 一次 PDF 冻住全站

**现象**：`upload_and_index` 是 `async def`，但内部同步解析（含 OCR、外部可执行）、同步写 sqlite/whoosh；建图与小节成文也直接在请求里 await 到底。

**证据**：
- `core/kb/kb_manager.py:275` —— `parse_document(...)` 同步直调，同函数 `:306-315` 的注释**自己**记录了"前端 120s 超时掐断 → `CancelledError` 绕过 `except`"的事故，却没把解析挪出 loop。
- `core/kb/parsers/book.py:283` —— `subprocess.run(["ebook-convert"...], timeout=300)`；`parsers/legacy.py:129-154` 同类。
- `core/kb/kb_manager.py:356-377` —— `_index_document` 逐条 `upsert_chunk` + whoosh `upsert_bulk`，均同步。
- `api/v1/knowledge.py:340`（`fill_pending_nodes`）、`:476`（`SectionGenerator.generate` 逐节 LLM）—— 请求内 `await` 全程。
- `core/kb/import_queue.py:76-86` —— 提交 N 条链接时串行 `await to_thread(expand)`，响应时长 = N 次 B 站接口。

**影响**：单 worker + 单事件循环下，一次扫描版 PDF / 一次整书建图 = **所有用户的对话与 SSE 一起停摆**。这不是"慢"，是"别人的请求超时"。

**建议**：`upload_and_index` 内整体 `await asyncio.to_thread(...)`（解析 + 分块 + 索引三段一起，避免"解析出线程、索引又回主线程"）；建图/小节生成改走已有的 `import_queue` 那套任务表（状态在 db，不在内存），请求只返回 task_id，进度走已有 `import_progress` 事件。

**成本**：2–3 天（`to_thread` 半天；建图入队 1.5–2 天）。

### P0-3 删除路径三处真缺口

**现象**：删资料不回收图谱侧账本；运维后台与主应用取径分叉；导入 worker 会把删掉的数据写回来。

**证据**：
- **账本悬空**：`kb_manager.delete_node`（`:460-487`）只清 `doc_chunks` / whoosh / 原件 / 截图，**不碰图谱库**。`doc_node_marks` 的 FK 只挂 `node_id`（`kg/schema.py:112-122`），`doc_id` 是裸 INTEGER；`kg/sources.py` 只有 `mark_doc_nodes / list_doc_marks / set_mark_status`，**没有按 doc_id 删除的实现**。于是 `GET /knowledge/source/{doc_id}/nodes`（`knowledge.py:485-507`）在资料删除后仍返回"关联节点"，`nodes.sources` 里的 doc_id 只增不减。
- **取径分叉**：`backend-admin/app/core/config.py:26-37,50-69` 只读 `ADMIN_DB_PATH / ADMIN_BACKEND_DATA_DIR / ADMIN_RECORDS_DIR`，默认硬编码 `<repo>/data/...`，**不读 `DATA_ROOT` / `AI_TUTOR_DATA_ROOT`**。而主应用是三级解析（`storage.py:42-46`）。标准仓库部署下两者恰好相同（有一致性用例锁着），但**便携/插件部署**（DSH 插件正是用 `AI_TUTOR_DATA_ROOT` 下发数据根）下，删号会删一个没人用的目录，真实数据 100% 残留（含 `llm/{uid}/models.json` 的明文 Key）。
- **删号后复活**：`import_queue._WORKERS` 是**进程内** dict（`import_queue.py:39`），worker 持有 `kb_manager` 的长连接；admin 删号只是 `shutil.rmtree`（`backend-admin/app/core/db.py:367-368`），不通知 API 进程 → 正在跑的导入下一集就把 `data/kb/{uid}` 重新建出来。

**影响**：① 用户的"来源"反查给陈旧答案，pending 增补队列指向不存在的资料；② 隐私/合规意义上**删号删不干净**；③ 这是"静默失败"型缺陷，不会报错。

**建议**：① `sources.py` 增 `purge_doc(doc_id)`（删 marks 行 + 从各节点 `sources` 剔除），在 `kb_manager.delete_node` 之后调用（图谱库不可用就记 warning，不阻断删资料）；② admin 侧把 `DATA_ROOT` 解析复制过来（两个 app 不能互相 import，用**同名环境变量契约** + 现有对照用例扩展一条）；③ 给 `import_items` 加 `lease/claimed_by`，删号前先按用户 cancel 并等待 worker 退出（或让 worker 每次落盘前校验用户是否仍存在）。

**成本**：2 天。

### P0-4 每轮额外一次 LLM + JSON 文件队列

**现象**：每次对话结束都无条件跑一次图谱分析（一次 `call_llm`），产物写一个共享 JSON 文件。

**证据**：
- `chat_service.py:983`（非流式）、`:1086`（流式）—— `runtime.spawn(_analyze_and_apply(...))`，无开关、无采样、无队列。
- `core/graph_analyzer.py:501` —— `call_llm(...)`。
- `core/knowledge_writer.py:33-49` —— 待审核建议落 `nodes_dir/ai_suggestions.json`：`open(..., "w")` 整体重写，**无临时文件 + rename、无锁、无 schema**；读改写发生在后台任务里，与 API 的读并发。
- `core/runtime.py:61-66` —— `spawn` 只保强引用，**无并发上限**。

**影响**：① 成本：每轮固定多一次 LLM（按轮计费，闲聊也算）；② 并发：N 个在线用户 = N 个后台 LLM 并发，无背压，配额打满时影响的是主对话；③ 数据：两个后台任务同时写 `ai_suggestions.json` → 后写覆盖先写（丢建议，且不报错）。

**建议**：① 加开关 + 采样（默认"有教学动作的轮才分析"：本轮调过写工具 / 学习模式 / 显式要求）；② 建议队列改落库（`records.connect`，与 `pending_notices` 同族），文件格式只保留为导出；③ `spawn` 加信号量（例如同用户 1 个、全局 8 个），排队而非并发。

**成本**：1.5–2 天。

### P1-2 正文形态分裂：同名并轨会静默丢正文

**现象**：节点小节化后主 MD 被删，但"同名并轨"仍以"主 MD 存在"为写入前提。

**证据**：
- `kg/nodes.py:364-380` —— `_merge_content_into` 第一行判 `md_path.exists()`，不存在直接 `return False`（无日志）。
- `remove_skeleton_md` 在小节化成功后删主 MD（`kg/content.py:159-189`，调用点 `section_generator.py:525`）。
- 同一个语义在 `graph_generator.py:1273` 有显式分流（`if mode == "append" and not self._has_sections(...)`）→ **同一规则两处实现，kg 这处漏了**。
- `kg/content.py:104-106` —— `update_node_content(append)` 对任何节点都往主 MD 追加；而 `node_content_text` 有小节时**只返回小节拼接**（`:18-24`）→ 追加进去的正文对 RAG / 详情页 / 填充判定都不可见。

**影响**：重复建图、工具补写在小节化节点上等于**没执行**，但操作回执是成功；主 MD 变成谁也读不到的影子数据（比"报错"更难查）。

**建议**：把"往节点写正文"收成一个按形态分派的函数（有小节 → 追加到末节或新建一节；无小节 → 写主 MD），`_merge_content_into` 与 `update_node_content` 都走它；补一条"小节化节点并轨"的回归（改回旧实现必红）。

**成本**：1 天。

### P1-3 loop 是"无状态 ReAct"—— 专项见 §4

一句话：loop 只管"问模型 → 跑工具 → 再问"，它不知道"这一轮是学习模式的开场 / 该讲 / 该考"。教学意图由 `chat_service` 以**字符串**注入，再由工具 handler 用 `learning.turn_of(kg)` **反向硬拦**，最后再由 `ensure_section_quiz_scheduled` 兜底补一道题。三层补丁，每层都在补偿上一层的不确定性。

### P1-4 事件契约靠三处同步

**证据**：发射 `core/agent/events.py` → 白名单 `chat_service._format_agent_sse:1174-1181`（**未知类型只记 debug 后丢弃**）→ 前端 `api/index.js` 分发。三处都是字符串比较，没有共享的 schema。

### P1-5 前端：God store + 生命周期可被撤销

**证据**：

### P1-6 导入队列状态机缺 lease

**证据**：`import_queue.py:151-172` 先置 `running` 再执行，`except Exception` 才写 failed → `CancelledError`/进程被杀是 `BaseException`，那一行**永久停在 running**；`kb_store.next_open_task:389-409` 只认 `status='pending'` 的分集，最后一条待办崩了就再也捡不回来（与 `import_queue.py:279-280` 的 docstring 自述"pending/running 都会继续跑"矛盾）。多进程（主服务 + `panel_server` 复用 `app.main:app`）下 `_WORKERS` 各一份，`next_pending_item` 读 + 置 running 是两次独立事务，无 CAS → 同一集可能被两个 worker 取走。

**建议**：`import_items` 加 `lease_until / claimed_by`，认领用单条原子 `UPDATE ... WHERE status='pending'` 判 `rowcount`；启动时把超时 `running` 重置为 `pending`（或 failed + 可重试）。

**成本**：1 天。

## 4. loop 专项（你点名的那部分）

### 4.1 它现在到底是什么

717 行（非空 647），职责清晰且**做对了**：流式逐 chunk、工具超时隔离、四道护栏（轮数/调用数/墙钟/重复）、连续失败熔断、证据级落库、`stop_reason` 三处同值、缓存前缀保护（`tool_choice="none"` 而非丢 tools）。

但它有一个**结构性定位**：**无状态编排器**。它不认识"教学"，只认识"消息 + 工具"。

### 4.2 五个具体缺口（都可量化）

| # | 缺口 | 证据 | 代价 |
|---|---|---|---|
| 1 | **工具全量注入**：17 个工具的 schema + 9,126 字指南，**每一轮**都发，不区分"开场轮 / 该讲 / 该考 / 闲聊" | `loop.py` 每轮 `tools=KG_TOOLS`；`registry.build_tools_prompt` | 单轮固定 ≈5.8k tokens（指南）+ ≈2k（schema）；占 48k 预算 16%，**且与图谱注入争同一块预算** |
| 2 | **没有回合级计划对象**：`policy.decide()` 已经产出了 `Directive(action, target, reason)`，但只被用来**渲染提示词**；loop 拿不到它 | `chat_service.py:343` → `_build_learn_block`；`loop.run_agent_loop` 签名无 plan | "该讲/该考"只能靠 176 行提示词表达，模型不遵守就只能事后兜底 |
| 3 | **收尾是硬编码**：达到上限 → 追加一句固定中文 + `tool_choice="none"`；失败 → 固定兜底文案 | `loop.py:113-116`、`:366-369` | 收尾不能"结构化交代已知/未知/下一步"，教学场景最需要这个 |
| 4 | **无自检**：判分被模型说成"答对了"、承诺出题却不调工具、越级记账 —— 三类都靠 `chat_service` 事后修补 | `ensure_section_quiz_scheduled:532`、`_build_learn_block` 里 6 条 ⛔ | 每加一个能力配一个兜底，兜底本身又长出新债 |
| 5 | **预算口径三套** | `chat_service:674`（固定段 45% 降级）、`guard.py:180`（48k−3k）、`loop.py:93`（48k 触发清理） | 三个阈值各自为政，改一个不知道影响的另外两个 |

### 4.3 目标形态：把 `Directive` 提升为 loop 的输入（TurnPlan）

不是重写 loop，是**给它加一个参数**：

```
TurnPlan（由 core/teaching/policy.decide() 产出，chat_service 传入）
  ├─ allowed_tools: list[str]   # 本轮该发给模型的工具子集（稳定排序，保缓存前缀）
  ├─ tool_choice: "auto"|"none" # 开场轮 / 收尾 / 纯讲解 → none（现 no_tools 语义并入）
  ├─ budget: {rounds, tool_calls, secs}
  └─ finish: "natural"|"structured"   # structured = 要求"已知/未解/下一步"三段收尾
run_agent_loop(..., plan: TurnPlan | None = None)   # None = 现行行为，逐字节不变
```

**为什么这是对的，而不是"加抽象"**：
- 它**不是在新增一层**——`Directive` 已经存在，只是被丢给了模板渲染。把它接到 loop 是**减少**一条信息绕路（当前路径：policy → 中文渲染 → 模型理解 → 工具调用 → 工具层硬拦比对）。这是"删重复"，符合项目既定原则。
- 工具裁剪直接降固定成本，且**缓存友好**：工具子集按"会话类型"固定，不逐轮抖动；`tool_choice` 语义并入后，`loop.py` 里 `no_tools` 的两段降级分支可以合并。
- 兼容性：`plan=None` 保持现状，1836 例不动。

**风险与守卫**：工具子集漏发 → 模型"没能力"。守卫 = 一张 `意图 → 最小工具集` 的表 + 断言每个工具的 `tier`/`guidance` 都至少被一个意图覆盖（类似 `test_tools_registry.py` 的做法）；任何未覆盖的意图回落到 `full`。

### 4.4 三步落地（每步可独立发布）

| 步 | 内容 | 行为变化 | 验收 |
|---|---|---|---|
| ① | 引入 `TurnPlan` 结构 + `run_agent_loop(plan=...)`，默认 `full` / `auto` | **零**（逐字节等价，golden 比对提示词与 tool 列表） | 全量绿 + 新增"plan=None 等价旧行为"用例 |
| ② | 学习模式接 plan：开场轮 `tool_choice=none` + 只读工具子集；讲解轮去掉 `quiz_generate`；出题轮反之 | 预期：学习轮固定成本 −40~60%，"开场就出题"从协议层彻底消失 | 单测断言三种 plan 的工具集；真机采样 20 轮看 `stop_reason` 与违反次数 |
| ③ | 结构化收尾 + 自检（判分结论由系统注入而非模型复述；"承诺未执行"在 loop 内检一次） | 收尾质量与一致性提升；可删掉 1–2 条后端兜底 | `agent_runs` 里 `finish` 段存在且可解析 |

**明确不做**：不引入第二个 agent / sub-agent（当前没有需要它的场景）；不改 `max_rounds` 语义；不把 loop 交给外部 harness（结论见《DSH 相关》讨论）；不为"分层好看"把 `loop.py` 拆成 5 个文件。
