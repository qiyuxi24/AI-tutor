## 〇、结论先行

### 0.1 一句话

**我们的缓存命中率低，不是模型/网关的问题，是"提示词把最易变的东西排在了最前面"** ——
现状可命中的前缀只有 **≈2.9K token（工具定义 + 模板开头 8 行）**，之后每一个 token 都在按
**标准输入价（4.20 元/M）** 计费；而其中 **5.4K 是完全静态的工具说明**，被排在了动态内容之后，**永久无法命中**。

### 0.2 实测结论（2026-09-28 探针，原始数据见 §1.5）

`backend/scripts/probe_prompt_cache.py` 用**真实模板 + 真实工具说明 + 真实 API** 跑了五组对照，
结论**推翻了 v1 的两个核心假设**：

| # | 事实 | 实测结果 |
|---|---|---|
| 1 | `cached_tokens` 可直接从响应读到（计费真值，非估算） | 相同请求第 2 次起 **5335/5336 = 100% 命中** |
| 2 | **消息内部改动 = 整条请求不再命中**，不存在"保住前半段" | 问题在 system 里变 → 命中塌到 **128 token（2.4%）** |
| 3 | **同一消息内重排（静态段前置）零收益** | P0-A 形状实测仍是 **128**，与现状完全相同 |
| 4 | **把动态内容移出 system（P0-B）也不够** | system 逐字节不变、只改 user → 仍 **128** |
| 5 | 真正生效的是**"本轮请求 = 上一轮请求 + 追加"** | 真实多轮追加：F2 命中 **5334 = 上一轮整条请求**（99.5%），F3 = 5361 ✓ |

**判定机理**（两条都能解释，结论一致）：

> **命中 = 存在一条"曾经完整发过的请求"，它是本轮请求的逐字节前缀**；
> 且匹配必须落在**完整消息边界**上 —— 只共享前面一段（哪怕 5330 token）而末尾不同，**一分不给**。

### 0.3 那么 15% 从哪来

按上述机理，我们的提示词形状**结构性不满足**命中条件：

- **跨轮**：system 提示词每轮都变（图谱注入 / 检索块 / `{{ student_message }}` / 画像）
  → 上一轮请求永远不是本轮请求的前缀 → **跨轮命中 ≈ 0**。
- **run 内**：同一 run 的 S 不变、消息只追加 → 本应命中；但
  `clear_old_tool_results`（改历史中段）与 `trim_history_to_budget`（重写历史）**把链打断**。
- **强制收尾**：丢了 `tools` —— 工具定义在缓存顺序最前，**等于第 0 个 token 就不同** → 必 0。
- 剩下的命中 ≈ "128 token 固定底 + 少量恰好同前缀的调用"。**真实归因用运维后台
  「用量与缓存」页按 `kind` 看**（已落地，见 §5.5）。

### 0.4 修正后的改造方向（**推翻 v1 的 P0-A**）

| 档 | 改动 | 预期 | 依据 |
|---|---|---|---|
| **P0-①** | 守住"整轮追加"链：**默认不做** Tool Result Clearing / 不重写历史 | run 内多轮命中 ≈ 上一轮全量 | §1.5 F 组 |
| **P0-②** | 强制收尾**保留 `tools`**（改 `tool_choice="none"`，需核验网关支持） | 该次调用 0 → 上一轮全量 | §1.5 机理（tools 在最前） |
| **P1-③** | 让 system 提示词**跨轮逐字节恒定**：图谱注入 / 检索块 / `student_message` 全部移出（问题本就在历史末条） | 是命中的**必要**条件，**单独不够** | §1.5 D 组 |
| **P1-④** | **逐轮注入与缓存天然冲突** —— 二选一：<br>ⓐ 把注入内容随会话持久化并**逐轮回放**（前缀账本）<br>ⓑ **取消逐轮预注入**，依据交给 `rag_search` 按需取 | 唯一能把命中率做到高的两条路 | §1.5 机理 |
| ~~**P0-A**~~ | ~~静态段前置 / 消息内重排~~ | **实测零收益，已否决**（省一整项改造） | §1.5 C 组 |
| **P1-⑤** | 观测口径与后台页面 | 已落地 | §5.5 |

**最重要的取舍**：P1-④ 的 ⓑ（取消逐轮预注入）会改变教学上下文的供给方式（"预注入"→"工具按需取"），
**必须 A/B**（§5.3）；它同时是**唯一**能把命中率做到 80%+ 的路径。
P0-①/② 与 P1-③ 则可以立即做 —— 它们不改变注入内容，只改"别破坏已建立的链"。

## 一、MiniMax 缓存机制（事实基线）

来源：MiniMax 开放平台《Prompt 缓存》与《Anthropic 主动缓存》（链接见 §8）。

### 1.1 两种缓存，我们只能用被动那种

| 维度 | **Prompt 缓存（被动）** | Anthropic 主动缓存 |
|---|---|---|
| 启用方式 | **自动**，无需改代码/加参数 | 需显式 `cache_control` 断点 |
| 接口 | OpenAI 兼容端点（**我们走这条**） | Anthropic 兼容端点（`/anthropic`） |
| TTL | **无固定值**，官方表述"根据系统负载自动调整" | 5 min，持续命中自动续期 |
| 写入计费 | **不额外收费** | 需额外付费（M2.7 例：2.625 元/M） |
| 支持模型 | M3 / M2.7 / M2.5 / M2.1 系列 | M2.7 / M2.5 / M2.1 / M2 |

> **结论**：我们在 OpenAI 兼容端点上，**没有任何 API 层面的旋钮可拧** ——
> 唯一能做的就是**把提示词组织成"前缀尽量长且尽量不变"的形状**。

### 1.2 硬规则（违反就失效）

1. **门槛**：输入 token **≥512** 才适用缓存。低于此的调用（如 `kb_graph_dedupe` 的几十 token 提示词）**本就不该指望命中**，不算损失。
2. **匹配顺序**：`工具定义 → 系统提示词 → 历史对话`，**前缀逐 token 精确匹配**。
   → 这三块中**任意一块内容变化，都会破坏其之后的全部缓存**。
   → 注意：`tools=` 参数排**最前**。**丢掉 `tools` = 从第 0 个 token 起就不同 = 整次调用 0% 命中**（见 §3.4）。
3. **粒度**：按前缀（不是按消息、不是按段落）。新增在**尾部**的内容不影响已缓存前缀 —— 这是"append-only 多轮对话天然友好"的原因。
4. **作用域/过期**：官方未给 SLA。**作用域（全局 / 账号级 / 节点级）与真实 TTL 均属待核验**（§8.3）。
5. **计费**：命中 token **0.84 元/M**、新增输入 **4.20 元/M**、输出 **16.80 元/M**（M3，≤512k）。
   官方示例：50,000 输入（45,000 命中 + 5,000 新增）+ 1,000 输出 = 0.0756 元，**对比无缓存 0.2268 元 → 省 66.7%**。
6. **长上下文分档**：M3 输入 >512k 走长上下文价，且**输入 token 数包含命中 token** ——
   即"命中缓存"**不会**帮你把请求降出长上下文档位，别指望这个。

### 1.3 官方最佳实践（原文两条）

> ① 把**静态的或重复的内容**放在对话**开头**（包括工具定义、系统提示词、历史对话内容）；
> ② 把**动态的用户信息**放在对话**最后**，以最大程度利用 cache。
> ③ 通过 API 返回的 usage tokens **监测缓存性能**，定期分析以优化策略。

**我们三条都没做到**（③ 的字段已采集但没算命中率，见 §3.7）。

### 1.4 观测字段（已就绪，别再造轮子）

`usage.prompt_tokens_details.cached_tokens`（OpenAI SDK 口径）。
**本项目已经取到了**：`core/token_counter.py::extract_usage` → `TokenUsage.cached_tokens`
→ `core/llm/usage.py::record` 落 `llm_usage.cached_tokens` 列。
**缺的只是"把它算成命中率并暴露出来"**（P1-F）。

### 1.5 实测：缓存到底怎么算命中（2026-09-28，`scripts/probe_prompt_cache.py`）

前缀一律用**真实模板 + 真实工具说明**拼出（不碰图谱/检索/库）；每组掺入**本组独有随机盐**以隔离
组间与跨次运行的污染，因此**结果可复现**。模型 MiniMax-M3，`max_tokens=16`，`thinking=False`。

| 组 | 形状 | 命中量（token） | 读法 |
|---|---|---|---|
| **A** | 完全相同的请求 ×3 | `128 → 5335 → 5335` | 相同请求第 2 次起 **≈100% 命中** → `cached_tokens` 可读 ✅ |
| **B** | 问题在 **system 里**变（**现状形状**）×3 | `128 → 128 → 128` | 消息内部一变，**整条请求作废**（2.4% 底） |
| **C** | 同 B，但把工具说明**前置**（v1 的 P0-A）×3 | `128 → 128 → 128` | **消息内重排零收益** → P0-A 否决 |
| **D** | system **逐字节不变**、问题移到 user ×3 | `128 → 128 → 128` | 只共享 system 这一段 → **一分不给**；P0-B 单独不够 |
| **F** | 真实多轮追加 `[S,u1]` → `+a1,u2` → `+a2,u3` | `128 → 5334 → 5361` | 命中量 = **上一轮整条请求**（99.5%）✅ |

F 组的两个数字值得盯：F2 的 `cached=5334` 恰好等于 **F1 的 `prompt=5334`**；
F3 的 `cached=5361` 恰好等于 **F2 的 `prompt=5361`** —— 这不是巧合，是"整条上一轮请求被复用"。

**复跑须知（踩过的坑）**：盐必须包含**每次运行都变的随机值**。
第一版探针的组盐是固定字符串（`"Aa"`/`"Bb"`…），于是**本次请求与上一次运行逐字节相同** →
系统直接复用上次的缓存条目，测出来全场 98–100%，结论完全失真。
修好后两次独立复跑一致（A 组 98–100%、B/C/D 组稳定 **2.4%**、F 组稳定 **99.5%** 且逐轮递增）。

**一个次要观察**：A/F 组偶尔出现"命中量比上一轮请求少约 100 token"（如 5351 → 5248），
疑似缓存按块取整/尾部未计。量级 2%，不影响结论，但**验收时别把"100%"当硬指标**（用 ≥95% 更稳）。

**由此得到的三条工程规则**（全部可机器验证）：

1. **缓存单元 = 一条完整请求**：想拿到命中，本轮请求必须**以某条曾发过的请求为逐字节前缀**。
   "把静态内容放前面"只能保证*前缀相同*，**保证不了*这条前缀曾经被完整发过*** —— 所以段序优化无效（C 组）。
2. **token 级部分命中不存在**：共享 5330 token 而末尾不同 → 2.4%（D 组）。别指望"保住大半"。
3. **唯一稳的命中来源是"追加"**：多轮对话里历史只增不改 → 每轮命中 ≈ 上一轮的全量（F 组）。
   ⇒ **任何"改写已发过的消息"或"每轮在中间插入新内容"的操作，都是把这条链剪断。**

## 二、业界成熟做法（可迁移的五条）

| # | 原则 | 依据 |
|---|---|---|
| 1 | **按"变化频率"排序，而不是按"逻辑结构"排序**：全局静态 → 用户级 → 会话级 → 轮级 | OpenAI 官方：变化的部分放**末尾**，否则无法命中；DeepSeek：**前缀必须字节级精确**，前面改一个字全废 |
| 2 | **append-only**：历史只追加，绝不改写已发送的消息 | Manus：KV 缓存与未缓存差 **10×** 价；改写中段 = 把中段之后的缓存全部作废 |
| 3 | **system prompt 里禁止出现时间戳 / 随机 ID / 会话 ID / 计数** | 这是缓存最经典的自毁方式；同类信息应下沉到 user 消息 |
| 4 | **一次会话/一个用户用一个稳定的路由键**（OpenAI `prompt_cache_key`） | OpenAI/Azure：同一 prefix+key 组合请求过密（≈>15 req/min）会抖动 miss；键值稳定才能把请求路由到持有该缓存的节点 |
| 5 | **命中率是一等指标**：落表 + 面板 + 告警 | 三家（OpenAI / Anthropic / MiniMax）都提供 usage 字段就是为此 |

**各家的机制差异（供选型参考）**：

| 供应商 | 触发 | 粒度 | 门槛 | TTL | 命中价 |
|---|---|---|---|---|---|
| **MiniMax**（我们在用） | 自动 | 前缀 | ≥512 | 不可控（按负载） | **0.2×**（写入免费） |
| OpenAI | 自动 | 128 token 递增 | ≥1024【二手】 | 5–10 min 闲置 | ~0.25–0.5× |
| Anthropic | **显式 `cache_control`** | 断点 | 1024/2048 | 5 min（1 h beta） | 0.1×（**写入 1.25×/2×**） |
| DeepSeek | 自动 | **64 token** | 无（64 起） | 按负载 | ~0.1× |

> 注：**不要被"DeepSeek 粒度 64、OpenAI 1024"误导去优化小段** ——
> 粒度小只影响"最小可缓存单元"，**和"前缀在哪里断掉"是两件事**。
> 我们真正的问题是**前缀在第 2.9K 处就断了**，粒度再小也救不了。

## 三、本项目现状审计（逐条定位破坏点）

> ⚠️ **v2 修正**：本节 §3.1–§3.3 的"段序"分析**只解释了"提示词里哪些东西每轮在变"，不解释"命中率为什么低"**。
> 实测（§1.5）证明**段序无关**（C 组）：关键是"本轮请求是否是上一轮请求的逐字节前缀"。
> 因此本节的正确定位是**"剪链点清单"** —— **任何一处每轮变化 / 中途改写，都会把链剪断**；
> 但**不要**据此去做段序重排（已否决，见 §4 的 P0-A）。§3.4–§3.8 的结论不受影响。

### 3.0 现状提示词形状（实测排版）

```
[API: tools = KG_TOOLS 的 JSON schema]                    ← 2,661 token，全局稳定 ✅
[API: messages[0].role = "system"]  ← chat_service._assemble 拼接的**单个** system 消息
  ┌ ① 静态头：persona + 全局底线（模板 1–11 行）            ← ~250 token，全局稳定 ✅
  │ ② {{ knowledge_graph_summary }}                        ← ~5.2K，**用户级·高频变** ⛔ 第 2 段！
  │ ③ 静态：「清单怎么读」+ 掌握度分档规则                    ← ~500 token，稳定
  │ ④ {{ current_position }}                               ← 用户级·常见变
  │ ⑤⑥ 静态：掌握度决定怎么讲 + 回复原则                     ← ~400 token，稳定
  │ ⑦ {{ user_profile }}                                   ← ~800 token，用户级·偶尔变
  │ ⑧ 静态：「教学方式」                                     ← ~400 token，稳定
  │ ⑨ {{ student_message }}  ← **当前学生问题**              ← **每轮必变** ⛔ 模板内！
  ├ retrieval 检索块（含 query 双端 echo）                   ← ~2.5K，**每轮必变** ⛔
  ├ TOOL_CAPABILITY_PROMPT（工具指南+策略）                   ← **5.4K，完全静态** ⛔ 排在最后！
  └ EMPTY_GRAPH_PROMPT（条件）                                ← 条件段
[API: messages[1..n-1]] 对话历史（append-only）              ← S8，最大的段
[API: messages[n] 当前学生问题]                              ← 与 ⑨ 重复
```

**代码真值**：`backend/app/services/chat_service.py::_assemble`（系统提示词拼装唯一出口）、
`data/prompts/system_prompt_common.j2`（唯一模板）。

### 3.1 ⛔ 根因一：最易变的大块坐在最前面（图谱注入在模板第 2 段）

`{{ knowledge_graph_summary }}` 是**全提示词里变动最频繁的大块**：
`chat_service._analyze_and_apply` 在**每次回复后**异步跑图谱分析，高置信度建议**直接改图**
（新增节点/边），随后前端 `graph_updated` 刷新 —— 也就是说**"图谱摘要变了"是常态而非例外**。

它却排在**第 2 段**（模板第 14 行），后面还跟着 ~8 段（合计 ≈8K）全部陪葬。
**这是本次命中率低的第一大来源。**

> 反直觉但关键：**排在前面的段更"贵"** —— 不只是它自己不能命中，而是**它之后的全部不能命中**。

### 3.2 ⛔ 根因二：`{{ student_message }}` 塞在 system prompt 里（每轮必变）

`student_message` 出现在模板**第 57 行**，而 system prompt 后面还追加了**检索块（每轮变）**和
**`TOOL_CAPABILITY_PROMPT`（5.4K，完全静态）**。

后果：**那 5.4K 静态工具说明，从上线那天起就一次都没命中过**，每次都按 4.20 元/M 全价付。
按 222 token/工具 × 12 工具算，这是每轮**固定**的 0.023 元白花（对比命中价）。

更荒诞的是**它是冗余的**：`build_api_messages` 会把当前学生问题作为**最后一条 user 消息**再发一次 ——
`{{ student_message }}` 在 system prompt 里是**第二份拷贝**，纯负债。

### 3.3 ⛔ 根因三：静态的 5.4K 工具说明排在动态检索块**之后**

`_assemble` 的拼接顺序是：模板（含动态） → 检索块（每轮变） → 工具说明（静态）。

**顺序装反了**：完全静态的 5.4K 被两个每轮必变的块压在了后面。
根据"变化频率排序"原则，它应该排在**所有动态内容之前**（甚至排在用户画像之前）—— 因为它**跨用户都一致**。

### 3.4 ⛔ 根因四：强制收尾调用丢弃 `tools`（该次调用 100% 不命中）

`agent/loop._finish_without_tools` 用 `_chat_once(ctx.messages, temperature=temperature)` **不带 tools** 收尾。
MiniMax 的缓存顺序是 **`工具定义` 在最前** —— **丢掉 tools 等于第 0 个 token 就不同**，
于是这次调用的缓存**必然全 miss**，而且 `ctx.messages` 里辛苦累积的历史前缀也一并作废。

触发面不小：`max_rounds` / 墙钟 / 调用次数 / 熔断**任一触发**都会走这条路（`loop.py` 三个终止点）。

> **改法（需核验）**：保留同一个 `tools=KG_TOOLS`，改用 `tool_choice="none"` 强制"只出文本不调工具"。
> 这样 tools 块逐字节不变 → 前缀保住；语义上仍保证"不再执行新工具"。
> **待核验**：MiniMax 是否支持 `tool_choice="none"`（OpenAI 与多数兼容网关支持 `auto`/`none`/`required`）。

### 3.5 ⚠️ 根因五：Tool Result Clearing 改写历史中段（run 内多轮前缀作废）

`agent/context.py::clear_old_tool_results` 把**较早批次**的 tool 结果正文换成占位符，
且 `loop` **每轮无条件调用一次**（幂等，batch > keep=2 时生效）。

这是"为省 token 而主动破坏缓存"的典型冲突：
- 省下的是**被清理的那部分**；
- 付出的是**被清理位置之后的所有前缀**（含整个 system prompt 之前的部分不受影响，但 tool 批次之后的内容全废）。

由于 `TOOL_RESULT_CLEARED` 是常量、位置固定，清理结果是**确定**的，但**与上一轮请求不同** → 上一轮建立的缓存链断裂。
**净收益需要实测**，不能凭"少发了 token"就认定划算 —— 被清掉的 token 若本来就在缓存里（0.84 元/M），
清理反而可能**亏钱**。

### 3.6 ⚠️ 根因六：`trim_history_to_budget` 重写历史中段

`agent/guard.py::trim_history_to_budget` 超预算时把中段压成"省略说明 + 规则要点"，
插入位置在**历史开头部分** → 该位置之后的缓存作废。

这条**保留不改**（它是硬预算兜底，且只在越线时触发）；但要意识到它**本质上是一次缓存重置**，
所以"预算线（48K）"与"缓存效率"是**一对反向拉力**：预算越松 → 越不改写 → 命中越好。
建议纳入 §5 的度量，用数据决定 `LLM_CTX_BUDGET` 是否要上调。

### 3.7 ⚠️ 根因七：一次性任务的 system prompt 里混入动态内容

| 调用点 | 问题 | 修正方向 |
|---|---|---|
| `graph_analyzer.py:320` | `full_system_prompt = ANALYZER_SYSTEM_PROMPT + graph_context` —— **当前图谱塞进 system prompt**，且它**每轮都跑**（`_analyze_and_apply`） | graph_context 移到 **user message** |
| `quiz/grader.py:121` | `_SHORT_ANSWER_SYSTEM_PROMPT.format(points=points)` —— 系统提示词随 `points` 变 | `points` 移到 user message |
| `quiz/generator.py:318` | `system_prompt = QUIZ_GENERATOR_SYSTEM_PROMPT`（**常量** ✅），材料在 user 侧 ✅ | 已符合，作为**正面样板** |

> 注意 `graph_analyzer` 是**每次对话回复后都跑**的后台调用 —— 它每轮构造一份**新的** system prompt，
> 命中率结构性为 0。属于"金额不大但频次极高"的一类。

### 3.8 ⚠️ 根因八：缺乏命中率观测

`llm/usage.py::summary` 的 `total` 只汇总 `calls / prompt_tokens / completion_tokens / total_tokens`，
**`cached_tokens` 只在 `groups[]` 里出现，`total` 里没有，更没有 `cache_hit_rate`**。
`GET /agent/usage` 因此报不出"命中率"这个核心指标 —— 15% 这个数是**手工算出来的**，不可持续。

### 3.9 备用模型 = 另一个缓存域（不是根因，但要知道）

`llm/fallback.py::LLM_CANDIDATES` 主→备静默降级。**两个服务商各自独立的缓存**，
降级那一次必然全 miss（这不是缺陷，只是测量时要注意把 model 维度切开看 —— `summary(group_by="model")` 已支持）。

## 四、改造方案

> ⚠️ **本节已按 §1.5 实测重排（v2）**：原 P0-A（静态段前置/消息内重排）**实测零收益，已删除**；
> 原 P1-E（Clearing 改按需）**升级为 P0** —— 它不是"省一点"，而是"别把链剪断"。
> 原则：**不动配额、不删内容、不改语义**；能不动注入内容就不动。
> 每一步都必须**可机器复核**（§5 的断言）。

### 4.0 落地记录（v3，2026-09-28，已用真实工具调用验收）

| 项 | 状态 | 落点 | 真实验收证据（`scripts/probe_loop_cache.py`） |
|---|---|---|---|
| **P0-①** Clearing 越线才触发 | ✅ 已落地 | `agent/loop.py`：新增模块常量 `AGENT_CLEAR_TOOL_RESULTS_TOKENS`（默认 `settings.llm_ctx_budget`），未越线时只记 `context.tool_results_kept` 日志、**不动历史** | A 节（默认阈值、真实 2 轮工具）：`#1 prompt=3214 cached=128` → `#2 prompt=3927 **cached=3214**`（= #1 整条请求，100%）→ `#3 prompt=4012 **cached=3927**`（= #2 整条请求，100%）。清理决策日志三次均为 `tool_results_kept` |
| **P0-②** 收尾保留 `tools` | ✅ 已落地 | `agent/loop.py::_finish_without_tools` → `tools=KG_TOOLS + tool_choice="none"`，网关拒绝时降级为旧行为并记 warning；`llm_calls` 按真实调用次数计 | 网关**接受** `tool_choice="none"`（实测返回 200，降级路径未触发）；离线回归锁死"收尾 tools 与轮内逐字节一致"与降级分支 |
| 测试 | ✅ | 新增 `tests/test_prompt_cache_stability.py`（5 条：默认不清理 / **前缀链逐字节** / 越线才清 / 收尾保留 tools / 网关拒绝降级） | 离线全量 `pytest -m "not llm_api"` 全绿（本次运行 1286 passed, 7 deselected；含其他会话并发新增的用例） |

> **A 节是本次最干净的证据**：第 1 次调用冷启动落在地板（128），第 2/3 次的 `cached` **恰好等于上一次的 `prompt`**
> —— 说明"上一轮整条请求被复用"，历史中段没被改写。若 P0-① 未生效（每轮清理），按 §1.5 机理
> 第 2 次起会回落到地板附近而不是 100%。

### ~~P0-A 静态段前置~~ → **已否决（v2，实测零收益）**

原方案想把 `TOOL_CAPABILITY_PROMPT` 提到图谱注入之前，让"全局静态前缀"从 2.9K 涨到 9.0K。
**§1.5 C 组实测：消息内重排 0 收益**（命中仍是 128）—— 因为缓存不认"这一段前缀相同"，
只认"**这条前缀曾经被完整发过**"。**此项取消，勿再做。**

> 唯一的例外情形：若某条消息**自身曾被作为完整请求发出过**（例如 `call_llm` 的固定任务提示词），
> 那么它内部的顺序确实不重要 —— 它整条就是缓存单元。这反过来说明：**要优化的是"请求的边界"，不是"段落的顺序"。**

### P0-B `{{ student_message }}` 移出 system prompt

**落点**：`data/prompts/system_prompt_common.j2`（第 57–58 行）
**做法**：删掉模板里的 `现在，学生的问题是：{{ student_message }}`；改用固定的收束语
（如"现在请看对话的最后一条学生消息，用最适合当下情境的方式开始引导"），
并保留原模板里那句"请用最适合当下情境的方式，开始引导"的语义。
**为什么安全**：当前问题**已经在** `messages` 末条（`build_api_messages` 保证），此处是第二份拷贝。
**验收**：`tests/test_prompt_loader.py` 新增"渲染结果不含学生问题原文"断言。
**风险**：模型对"问题写在 system 末尾"可能有行为偏好 → 需 A/B（§5.3）。

### P0-C 强制收尾保留 `tools` 块

**落点**：`agent/loop.py::_finish_without_tools` / `_chat_once`
**做法**：`tools=KG_TOOLS` + `tool_choice="none"`，替代"传空 tools"。
**前置核验**：MiniMax OpenAI 兼容端点是否接受 `tool_choice="none"`（否则退回现状）。
**验收**：`tests/test_agent_loop.py` 断言"收尾调用的 `kwargs["tools"]` 与轮内一致"。
**风险**：若网关不支持该参数会 400 → 需加 try/降级（失败则回退"不带 tools"）。

### P1-D 图谱注入降到最后

**落点**：同 P0-A（合并实施）
**做法**：图谱结构注入（5.2K、变动最频繁）排在用户画像之后、检索块之前。
**注意**：与预算框架 §4.4「不要为排版重排注入顺序」**不冲突** —— 那是禁止**为美观**重排；
本次是**为缓存**重排，且是预算框架 §4.1 位置规则 #1「静态在前、动态在后」的**完整落实**
（现状只做到了"消息序列末尾是当前问题"，没做到"按变化频率排序"）。
**验收**：见 §5.2 的"公共前缀长度"断言。

### P0-① Tool Result Clearing / 历史重写改为"越线才做"（**v2 升级为 P0**）

**落点**：`agent/context.py::clear_old_tool_results` 的调用点（`agent/loop.py`）、
`agent/guard.py::trim_history_to_budget` 的调用点（`chat_service`）
**做法**：两者**默认不触发**；仅当 `count_messages_tokens(ctx.messages)` 超过预算线时触发一次。
**理由（v2，实测）**：按 §1.5 的机理，改写历史中段 = **把"整轮追加"的链剪断**，
代价不是"那几条 tool 结果的 token"，而是**其后全部前缀的命中**（命中价 0.84 vs 输入价 4.20）。
清理省的是"未命中价"的 token —— **只有越线时才值得赌**。
**验收**：`cached_tokens` 口径的净收益（用真实 usage，不靠推理）。
**取舍**：净值 ≤0 时，保持现状并记 `ponytail:` 注释说明"为省 token 主动放弃缓存"。

### P1-F 命中率观测（**v2 已落地**，见 §5.5）

**落点**：`llm/usage.py::summary` + `api/v1/agent_runs.py` + 前端/后台面板
**做法**：
1. `total` 增加 `cached_tokens` 与 `cache_hit_rate = cached_tokens / prompt_tokens`；
2. `groups[]` 每行同样增加 `cache_hit_rate`（按 kind / model / day 维度看）；
3. 低于阈值（建议 **50%**）时打 warning，日志点名"提示词前缀被破坏"。

**验收**：`tests/test_llm_usage.py` 增断言（含 `cached_tokens=0` 时不除零）。
**说明**：这是**唯一必须先做**的一项 —— 没有它，P0/P1 的收益无法验证。

### P2-G 一次性任务的 system prompt 去动态化

**落点**：`graph_analyzer.py`（graph_context 下沉到 user）、`quiz/grader.py`（`points` 下沉到 user）
**验收**：断言同一 `kind` 的 system prompt 在多次调用间**逐字节一致**。

### 5.1 不变量（v2：按实测机理重写）

| 编号 | 断言 | 复核方式 |

| C-1 | `total.cache_hit_rate` 可查（`GET /agent/usage`、运维后台 `/usage`） | 接口返回（**已落地**） |

| C-3 | **相邻两轮之间，已发过的消息内容不得被改写**（除越预算线那次） | 同上：断言 `messages[:k]` 逐字节相等 |

### 5.2 前缀链测试（新文件，覆盖 C-2/C-3）

思路：不要测"两份 system prompt 的公共前缀"（v1 的错误思路，实测证明无意义），
而要测**"本轮请求是否以上一轮请求为前缀"**：

1. 构造一个 `AgentContext`，模拟一轮（`append_assistant_turn` + `append_tool_result`）；
2. 快照 `messages`；再追加下一轮内容，快照；
3. 断言 `第二轮快照[:len(第一轮快照)] == 第一轮快照`（逐字节）；
4. 对**越预算线**与**强制收尾**两条路径各写一条反例断言（说明"允许断链"的唯二情形）。

这样任何"中途改写历史 / 每轮往中间插内容"的改动都会立刻变红。

### 5.3 A/B 要求（不可跳过）

预算框架 §4.4 的铁律：**"改动注入顺序必须有 A/B 数据"**。本次改动**正是注入顺序改动**，
因此 C-2/C-3 落地后必须跑 A/B：

- 固定一组 20 轮教学对话，**同题同序**跑两版（现状 vs 重排）；
- 对比：① `cache_hit_rate` ② 答案质量（人工或 LLM-judge 盲评）③ 教学行为合规
  （是否仍遵守"学生说懂了要提议出题"等铁律）；
- 若质量下降 → **回滚顺序，只保留 P0-B/P0-C/P1-F**（这三项与教学质量无关）。

### 5.4 成本口径（估算公式，替换 §0.3 的假设数）

```
输入成本 = (prompt_tokens − cached_tokens) × 4.20 / 1e6
         +  cached_tokens                 × 0.84 / 1e6
         +  completion_tokens             × 16.80 / 1e6
命中率   = cached_tokens / prompt_tokens
```
真值从 `llm_usage` 取（`group_by="day"` 看趋势、`"kind"` 看归因）——
**本文所有金额均为【估算】，以 `llm_usage` 实测替换后才算数。**
