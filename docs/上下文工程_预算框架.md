## 〇、先说实话：没有论文给出"各段占百分之几"

这一点必须先摆明，否则整个框架会建立在假引用上：

- **没有任何论文直接给出"系统提示词 X%、历史 Y%、检索 Z%"的配额表。** 我按这个方向找过（RULER/有效长度、Lost in the Middle、Databricks 长上下文 RAG、OP-RAG、Chroma Context Rot、Anthropic/Manus/LangChain 工程博客）——**它们给的是每一段的"边际收益曲线"和"失效机制"，不是配额。**
- 配额只能由三样东西反推：① 文献给的收益曲线形状（哪里是峰值、哪里转负）② 本项目的**实测基线**（各段真实体量）③ 工程判断（哪些段可还原、哪些不可压）。
- 因此下文的每一行都标了依据：`【论文】` / `【实测】` / `【判断】`。**判断项欢迎被推翻，但推翻要带数据。**

## 一、结论先行

### 1.1 单一预算 B = 48K（不再打折）

| 记号 | 值 | 含义 |
|---|---|---|
| **B**（预算） | **48K token** | 所有段的目标合计上限，`LLM_CTX_BUDGET` 的新值 |
| 裁剪线 | **B − 输出预留 = 45K** | `context_guard` 把「静态段 + 历史」裁到这个数以内 |

**为什么 48K 不再套"有效长度 50%"的折扣**：48K 本身已落在多数模型的**有效区间（32–64K）**内（RULER：多数模型有效长度 ≥32K；Databricks：RAG 正确率峰值 8–32K，商业旗舰可到 64K）。把预算定成 48K，**等于把"标称窗口打折"这一步提前付掉了** —— 不需要在一个已经很保守的数字上再打一次折。

### 1.2 九段配额（单位 K token）

| # | 段 | 下限 | **目标** | 上限 | 实测基线 | 可压缩? |
|---|---|---|---|---|---|---|
| S1 | 输出预留（max_tokens） | 2 | **3** | 8 | 2（loop 默认 2000） | ⛔ 不可压 |
| S2 | 静态指令（common + 模式模板） | 0.8 | **1** | 1.5 | 0.9 | ⛔ 不可压 |
| S3 | 工具/技能说明（指南 + 策略 + schema） | 3 | **5.4** | 6 | 5.4 | ⚠️ 半可压（schema 必发） |
| S4 | 图谱**结构**注入（节点+边+掌握度） | 2 | **6** | 8 | 5.2（120 节点） | ✅ 可压 |
| S5 | 用户画像 | 0.3 | **0.8** | 2 | ~0.8 | ✅ 可压 |
| S6 | **图谱检索注入**（graph RAG 正文） | 0.8 | **2** | 3 | 与 S7 共享 top_k=5 | ✅ 可压（可重检索） |
| S7 | **知识库检索注入**（KB RAG 正文） | 0.8 | **2** | 3 | 同上，无独立配额 | ✅ 可压（可重检索） |
| S8 | **对话历史** | 6 | **21** | 30 | 随会话增长 | ✅ **最先压** |
| S9 | 当前轮（提问 + 工具/思维链回填） | 2 | **6** | 12 | 随工具轮数增长 | ⛔ 不可压（协议要求） |
| | **合计** | **≈17.7** | **47.2** | — | | 目标 47.2 + 0.8 抖动 = **48** ✓ |

> **弹性语义（重要）**：上限合计 73.5K **远超 B**，所以**上限不可同时取满**。规则是：任一段升到上限时，必须按 §3.1 的让位顺序从其他段扣回，**总和恒 ≤ B**。下限合计 ≈17.7K 是"地板"——低于此功能受损，不能再压。

### 1.3 本轮重点（用户 2026-09-15 指定）

1. **S8 对话历史 = 21K（44% of B）**，是最大的一段。
2. **S6 / S7 两段检索分开记账、分开配额** —— 不再像现在那样共用 `top_k=5` 且无体量约束。**具体分配策略待议**（见 §6）。
3. **S4 图谱结构 与 S6 图谱检索是两件事**：前者是"框架/定界"（节点名 + 掌握度 + 边），后者是"正文片段"。混在一起谈会让两边都调不准。

## 二、为什么是这个数（证据）

### 2.1 有效上下文长度远小于标称（决定了"不要按标称窗口配预算"）

**【论文，已核验】** *Why Does the Effective Context Length of LLMs Fall Short?*（arXiv **2410.18745**，An et al., 2024-10，RULER 128K 实测）：

| 模型 | 有效 / 声称 | 占比 |
|---|---|---|
| GPT-4-1106-preview | 64K / 128K | 50% |
| Llama3.1-70B / Qwen2-72B | 64K / 128K | 50% |
| Llama3.1-8B | 32K / 128K | 25% |
| GLM4 | 64K / 1M | ~6.4% |
| GradientAI/Llama3-70B | 16K / 1M | ~1.6% |

论文原话：**"大多数开源模型的有效上下文长度不足训练长度的 50%"**；机制是**位置频率左偏**（2K 训练长度下位置索引 i ≥ 1536 的占比不到 5%）。
另一条对本框架直接有用的发现：**多数失败案例集中在文档前 1/3（0–33.3% 深度）** —— 开头不是绝对安全区。

> **推论**：标称窗口越大，"水分"越多。**B=48K 是一个不需要再打折的保守值**（32–64K 是多数模型的实际舒适区）。

### 2.2 检索段：唯一"越多越差"的段

这条决定了"预算放大时谁涨"，所以单独列：

**【论文，已核验】** *Long Context RAG Performance of Large Language Models*（arXiv **2411.03538**，Databricks Mosaic，2024-11；20 模型 × 3 数据集 × 2000+ 实验）：

- **正确率随上下文先升后降**：多数开源模型峰值在 **8K–32K**；原文措辞"**多数 LLM 只在 16–32K tokens 内表现出 RAG 性能提升**"。
- **召回率单调上升，正确率不单调** —— 信息**确实在**上下文里，但模型**用不上**。
- **成本线性**：8K → 128K 输入成本 **16×**；64K → 96K 的边际收益对 GPT-4o 是 **0**、对 o1-preview 是**负**（0.831 → 0.824）。

**【论文，已核验】** *In Defense of RAG in the Era of Long-Context Language Models*（arXiv **2409.01666**，Yu et al., 2024-09）：检索块数与答案质量呈**倒 U 型**，存在 sweet point —— **用远少于全量的 token 得到更高的答案质量**。

**【论文，已核验】** Lost in the Middle 的开放域 QA 案例（arXiv **2307.03172** §4）：reader 性能**远早于**召回率饱和；检索文档 >20 篇后收益极小，**边际提升 ≈1.5%（GPT-3.5）/ 1%（Claude）**。

> **推论（本项目）**：S6+S7 目标合计 4K、上限合计 6K，**且不随预算放大而放大**。预算从 48K 涨到 64K 时，多出来的额度给 S8 历史，不给检索。

### 2.3 位置：头尾是贵地，中间是雷区

**【论文，已核验】** Lost in the Middle（同上）：

- 相关信息位于**开头或结尾**时最好；位于**正中间**时显著下降。
- GPT-3.5-Turbo 在 20 篇文档、答案在第 10 位（正中）时 **52.9%**，**低于闭卷基线 56.1%** —— "给了文档反而不如不给"；与 oracle（88.3%）差 **>20 个百分点**。
- 上下文 10 → 20 → 30 篇，平均性能持续下降；**"扩展上下文模型"曲线与普通版几乎重合**（窗口更大 ≠ 更会用）。
- **query-aware contextualization**（把查询同时放在数据前后）在键值检索任务上把 300 键值对准确率从 **45.6% 拉到 100%**。

**【论文，已核验】** Chroma *Context Rot*（2025-07；18 模型 / 194,480 次调用）：**1 个干扰项就使性能低于基准**；且**打乱的干草堆一致优于逻辑结构化的**（不要迷信排版）。

### 2.4 本项目实测基线（可复现）

`reports/probe_context_budget.py` 的输出（MiniMax 校准系数 1.15）：

| 段 | 字符 | token | %B(48K) |
|---|---|---|---|
| S2 静态指令（common 541 + adaptive 790） | 1,331 | 916 | 1.9% |
| S3 工具指南 3,148 + 策略 1,043 + **schema 6,169** | 10,360 | **5,350** | 11.1% |
| S4 图谱注入（120 节点，降级后） | 8,266 | 5,218 | 10.9% |
| S7 检索注入（现为两源共享 5×500 字符） | 2,500 | 2,500 | 5.2% |
| **固定成本合计**（不含 S8/S9/S1） | — | **13,984** | **29.1%** |

→ **固定段已占 29.1% × B**（框架给固定段的目标是 36%，即 17.2K）；`B − 固定 − 输出预留 = 48 − 14.0 − 3 = 31K` 可给 S8+S9，**S8 拿 21K + S9 拿 6K 正好放得下，且余 4K 抖动** ✓

另：S3 的 schema 是**每轮必发的硬成本**，**2,661 token / 12 个工具 ≈ 222 token/工具** —— 新增工具时先算这笔账。

## 三、弹性规则（谁让谁）

### 3.1 让位顺序（固定，不可协商）

```
不可压（无外部还原源）        可压（有外部还原源 → 只做可还原压缩）
├─ S1 输出预留 3K            ├─ S8 对话历史     → agent_runs / conversations / 图谱 / 画像（已落库）
├─ S2 静态指令 1K            ├─ S6 图谱检索     → 可随时 rag_search(source="graph") 重取
└─ S9 当前轮 6K              ├─ S7 知识库检索   → 可随时 rag_search(source="kb") 重取
  （协议要求，砍了就是功能缺失） ├─ S4 图谱结构     → SQLite + nodes/*.md（正文由 S6 补）
                             └─ S5 用户画像     → data/profiles/{id}.json
```

**【判断，依据 Manus 原则 3「只做可还原压缩」】**：压缩必须可还原。检索正文可以丢（query 还能重跑）、节点头摘要可以丢（`rag_search` 还能拉），**但 S1/S2/S9 丢了就是功能缺失**，不参与压缩。

### 3.2 触发阶梯

| 触发 | 动作 | 现状 |
|---|---|---|
| **固定段（S2–S7）> 40% × B（19.2K）** | 记 warning（固定成本开始挤压历史） | ✅ 已实现（2026-09-15，`chat_service._build_system_prompt`；当前 13,984 ≈ 占线 72.8%） |
| 固定段（S2–S7）> **45% × B（21.6K）** | **强制降级**：图谱注入按当前体量减半重建一次 | ✅ 已实现（2026-09-15，同函数；仍越线 → 记 error 照发） |
| 「静态段 + 历史」> **B − 输出预留 = 45K** | 历史压缩：`[说明+要点] + [首条 user 锚点] + [最近 N 轮]` | ✅ 已实现（`agent.guard.trim_history_to_budget`，2026-09-15 由「只丢最旧」升级为分层） |
| 较早轮次的 tool 结果 | 正文换占位符（保留 `tool_call_id`，协议不变） | ✅ 已实现（`agent/context.py::AgentContext.clear_old_tool_results`，保留最近 2 个工具批次）。**落点在 loop 内**：跨请求历史（`ChatMessage`）里没有 tool 消息，放 guard 是死代码 |
| 固定段（S2–S7）≥ 80% × B（38.4K） | 图谱降级：省节点摘要 → 限量节点 | ✅ 已实现（`GRAPH_INJECT_MAX_CHARS` 阶梯） |
| 单段越上限 | 按 §3.1 顺序从后续段扣回 | ✅ S4/S6/S7 已实现（S6/S7 按源独立截断 3K，2026-09-15）；S8 走分层 |
| `system_prompt` 自身 > 45K | 记 warning 点名（无可裁余地） | ✅ 已实现（2026-09-13 由 info 改 warning；2026-09-15 起先尝试图谱降级） |

### 3.3 单调性例外

**预算放大时，只有 S8（历史）可以跟着涨。** 依据 §2.2：检索段边际收益转负；S4 图谱段的合理体量取决于**图谱规模**而不是预算（由图谱自身的降级阶梯管，不由预算管）。

## 四、位置规则

1. **静态指令在最前**、**学生当前问题在最后** —— ✅ 现状满足（`prompt_loader` 按 `common + mode` 拼接，消息序列末尾是当前问题）。
2. **S6/S7 检索块前后各放一次当前问题**（query-aware contextualization）—— ❌ 未实现。这是 §2.3 里唯一"低成本高确定性"的收益点（KV 任务 45.6%→100%），代价约 50 token。
3. **检索片段按相关性降序**（最相关在最前）—— ✅ 现状满足（`rag_pipeline` 按融合分数排序）。
4. **不要为了"结构好看"重排注入顺序**：Chroma 实测打乱的干草堆一致优于结构化的。**改动注入顺序必须有 A/B 数据**，否则保持稳定（同时利于前缀缓存）。
5. **中间段只放"不被读到也不致命"的内容**：S8 中段历史、低分检索片段。

## 五、技能/工具段的预算规则（"skill"）

**现状**：本项目**没有 skills 机制**（`data/prompts/*.j2` 零处 "skill"），S3 就是这一段，共 **5.4K token**：

| 子项 | 实测 | 说明 |
|---|---|---|
| `TOOLS_PROMPT`（逐工具指南） | 2,017 | 注册表由 `spec.guidance` 生成（2026-09-15 双源收口） |
| `TOOL_POLICY_PROMPT`（跨工具策略） | 672 | 掌握度归属、说"懂了"要出题、权限限制 |
| `KG_TOOLS` schema（API `tools=` 参数） | 2,661 | **≈222 token/工具 × 12 个**，每轮必发 |

**规则**：

1. **常驻只放渐进披露的第一、二层**：【论文，方向已核验】Anthropic Agent Skills（2025-10）三层 = ① metadata（name + description）常驻 → ② 正文命中时才加载 → ③ 附带资源按需读。本项目的 `guidance`（何时用/何时别用）+ `description`（做什么）**就是 ①② 的等价物**，方向正确。
2. **禁止把 skill/工具长正文塞进 system prompt**：长示例、完整 API 说明、大段模板属第三层，应落文件 + 工具读取。
3. **schema 是硬成本，新增工具先算账**：`工具数 × 222 + 指南增量 ≤ 6K 上限`，超了先合并工具或压缩 description。
4. **若将来引入 skills**：单 skill 常驻 metadata **≤0.5K token**（name + 一句话 + 何时触发），正文按需。

## 六、S6 / S7 分离记账（2026-09-15 决定，细节待议）

**为什么要分开**（三条理由，都指向"不该共用一套参数"）：

| 维度 | S6 图谱检索 | S7 知识库检索 |
|---|---|---|
| 数据来源 | 自产 `nodes/{id}.md` | 上传文档（PDF/EPUB…） |
| 与已有上下文的关系 | **与 S4 结构注入天然重复**（同一批节点） | 无重复，全新内容 |
| 单块体量 | 节点正文，通常 500–2000 字符 | `chunk_text` 500 字符/块（固定） |
| 主要失效模式 | **冗余**（说了两遍） | **噪声**（Chroma：1 个干扰项即有害） |
| 可还原性 | 高（图谱小，随时重取） | 中（重取要重新 embedding） |
| 现有配额 | 与 S7 共用 `top_k=5`，**无体量约束** | 同上 |

**已定的**：两段各自 `[下限, 目标, 上限]` = `[0.8, 2, 3]` K token，**独立截断**，互不挤占。
**待议（下一轮）**：① 各自的 top_k 与去重规则（S6 是否跳过已出现在 S4 的节点）② 跨源融合的配额分配（现在 `rag_pipeline` 是分组拼接，谁多谁少没有依据）③ 是否需要"检索段总开关"（图谱小的时候 S6 可能是纯冗余）。

## 七、不变量与验收（可机器复核）

6. **S8 Tool Result Clearing**：较早轮次的 tool result 换成占位符（保留 `tool_call_id`，不破协议）。
7. **query-aware 双端放置**（§4.2）：当前问题同时放在 S6/S7 检索块前后。

**P2（度量与自动化）**
8. 分段配额进配置 + 每轮按段记账（扩展 `agent_runs`），出面板。
9. 按 B-1/B-2 跑 20 轮基线，把 §1.2 的目标值从"文献 + 实测体量"换成"本项目实测收益拐点"。
