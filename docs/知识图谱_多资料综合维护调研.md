## 0. 结论先行

1. **"多资料维护图谱"不是一件事，是五件事**：`溯源 → 对齐 → 补全 → 冲突 → 增量`。
   其中**溯源（provenance）是前四者的前提**，不是可选的锦上添花 —— 没有"这条知识来自哪本书/哪一章"，对齐无法复核、冲突无法裁决、覆盖度无法度量。
2. **我们当前最大的两个缺口是"溯源"与"跨源对齐"**：
   - 节点/边**完全没有来源字段**（`page`/`book`/`chunk_id` 都没有）；
   - 语义去重（`_find_dedup_candidates`）**只在单次生成内生效**，换一次上传/重新生成就是两套节点。
3. **业界没有可直接搬的成品，但有成熟的可拼装流水线**：schema 层 + instance 层两级融合；
   教育域有对口论文（arXiv:2305.04567，北邮，教材/课件/大纲三源融合），其"属性取并集 + 保留原始边 + 粗粒度优先"三条策略可以直接借鉴。
4. **落地顺序建议**：`L0 溯源 → L1 跨源对齐 → L2 冲突队列 → L3 按源增量 → L4 覆盖度度量`。
   与已完成的多准则投票推断（先修关系）天然衔接 —— 冲突检测可以复用同一套"多准则 + 证据链"骨架。

## 1. 需求拆解：多资料维护到底要解决什么

| # | 问题 | 典型场景 | 教学价值 |
|---|---|---|---|
| 1 | **对齐**（同一概念，多种表述） | 教材 A 叫"散列表"，教材 B 叫"哈希表"；教材 A 讲"进程"，B 讲"任务" | 避免图谱被同义节点稀释，学生看到的是一张完整地图 |
| 2 | **补全**（不同资料覆盖不同知识点） | 教材 A 有"红黑树"，教材 B 有"B+树" | 覆盖度并集 → 更完整的知识地图 |
| 3 | **冲突**（定义/归属/顺序矛盾） | A 说"先讲数组再讲指针"，B 反之；同一概念在两书里难度/板块归属不同 | 暴露矛盾本身就有价值（启发式教学），但**不能静默合并** |
| 4 | **增量**（新书来了怎么办） | 已有图谱 + 新上传一本教材 | 增量 O(新书) 而非 O(全库) 重跑，成本可接受 |
| 5 | **溯源**（每条知识的依据） | "这个节点是哪本书讲的？" | 支撑前三者的**复核与裁决**；也是"讲错了能追责"的前提 |

**多资料的核心价值主张**（可用于对外表达）：
- **覆盖度 ↑**：多本书的知识点是并集；
- **可信度 ↑**：一个概念被 N 本书共同支撑（support count），支撑越多越核心 —— 这一点 arXiv:2305.04567 用"三源交集 = 最有价值知识点"做了实证；
- **矛盾显式化**：不同教材的差异被摆到台面上，而不是被一次性生成的图谱悄悄抹平。

## 2. 我们的现状（代码事实，不含推测）

| 环节 | 现状 | 位置 |
|---|---|---|
| 抽取 | 单次生成：按「书序 × 分块序」扫知识点，LLM 抽节点 | `core/kb/graph_generator.py::generate_subject_graph` |
| 去重/合并 | **同一次生成内**：嵌入粗筛（0.78）+ LLM 二次确认 + 降级（0.90） | 同上 `_find_dedup_candidates` |
| 写入 | `_write_to_graph` 返回 `merged_nodes`；**写路径另有 3 套并行实现** | `knowledge_writer.py` / `knowledge.py` 的 `create_node`/`decompose` |
| 板块（board） | **只有 generator 会写** → 其他路径建的节点永远进不了板块栏 | 见结构调研文档 |
| 溯源 | **零**：节点 MD 有正文，但没有"来自哪个文件/哪一页/哪个 chunk" | — |
| 增量 | **无**：重新生成 = 重跑全库 LLM 抽取 | — |
| 掌握度/先修 | 先修关系已可**多准则无监督推断**（本次 P0 落地） | `core/prerequisite.py` |

> 结论：**现在是"单源一次性生成"，不具备多源维护的基础设施**。硬做会在两处翻车：
> 同义节点跨次生成不合并；冲突内容被后一次生成覆盖。

## 3. 业界方案调研

### 3.1 融合的两个层次（通用框架）

LLM 时代的图谱构建综述（arXiv:2510.20345）把融合明确分成两层，**顺序不能颠倒**：

| 层 | 融合对象 | 典型手段 | 我们的对应物 |
|---|---|---|---|
| **Schema 层**（本体融合） | 实体类型、关系类型、层级 | 本体对齐、canonicalization、schema 与实例**共演化**（AutoSchemaKG / AdaKGC / EDC） | 我们的"学科 → 板块 → 知识点" + 关系类型（prerequisite / related / confusion…） |
| **Instance 层**（实例融合） | 具体节点与边 | 实体对齐/消解（ER）、属性融合、边合并 | `_find_dedup_candidates` 的 LLM 确认合并 |

**关键洞察**：Schema 层不统一时，Instance 层必然打架（同一概念在不同资料里挂在不同的"学科/板块"上，
我们的 `board` 归属冲突就是这个问题的实例）。

### 3.2 代表系统与可借鉴点

| 系统 | 做法（一句话） | 我们能借鉴什么 |
|---|---|---|
| **KARMA**（arXiv:2502.06472，NeurIPS 2025） | 多智能体协作增补图谱：抽取 / 校验 / **冲突消解** 分工；先多轮抽取再统一裁决 | "抽取"与"裁决"分离；冲突消解是**独立角色**而不是抽取的副产物 |
| **多源教育 KG 融合**（arXiv:2305.04567，北邮） | 教材/课件/大纲三源各建子图，再四步融合（见 §3.3） | 最对口：属性**取并集**、**保留原始边**、融合后取**最粗粒度**；"三源交集 = 核心知识点" |
| **In-context Clustering ER**（arXiv:2506.02509，2025） | 用 LLM 做**上下文聚类**实现实体消解（一次判一批，不是两两判） | 把 O(n²) 两两判定降成 O(n/k) 批量聚类 —— 直接解决我们"跨源对齐"的成本问题 |
| **KGGen**（NeurIPS 2025） | 文本→图谱，强调**密度与语义一致性**（质量而非数量） | 评测要盯"密度/一致性"，不只看节点数 |
| **iText2KG**（WISE 2024） | **增量式**文本→图谱，schema 驱动，免后处理 | 增量不是"再跑一遍"，而是"按 schema 对齐后再融合" |
| **LightRAG**（arXiv:2410.05779） | 增量更新算法复用同一套图索引进程，**避免全量重建索引**（成本论证明其价值） | 我们要的正是这个性质：新增一本教材的成本 ∝ 新书，不 ∝ 全库 |

### 3.3 教育域对口论文的四步融合（arXiv:2305.04567）

**数据**：教材 / 课件 / 课程大纲三个异构源 → 三个子图（5 级粒度：课程→知识单元→章→知识块→知识点），
覆盖数百门课程、60k+ 实体、80k+ 三元组（Neo4j）。

**融合四步**（这是本方案最主要的借鉴来源）：

| 步骤 | 做法 | 对我们的启发 |
|---|---|---|
| a. 实体名称匹配 | 字符串匹配 + 字面相似度 + 语义相似度**三路并用** | 与我们的"向量粗筛 + LLM 确认"同构；它额外用了字符串/字面，成本低、可作前置快筛 |
| b. 定位粗粒度实体 | 融合后节点取**最粗粒度**层级 | 我们目前是"哪个先建就用哪个"，粒度不统一 → 应显式取"最全的那个" |
| c. 属性并集 | 除 `url` 外全部属性**取并集**（丢信息 = 丢价值） | 节点正文应**合并**而非覆盖（当前 `update_node_content` 是覆盖语义，冲突） |
| d. 保留原始边 | 融合前所有连接关系**全部保留**并指向新节点 | 避免"合并节点导致边丢失"，这正是我们最该学的防御性设计 |

**它的量化指标**（可借用）：课程相关度 = 跨课程**等价边数 / 课程节点数**；
**三源交集 = 同时出现在教材、课件、大纲中的概念**（"最有价值知识点"，通信原理课 16 个）。

**它的局限（对我们更重要，是反面教材）**：
- **没有精度/召回/F1、没有金标准、没有消融** —— 只有相关度、频次、交集等统计分析；
- 实体对齐的模型、阈值、权重、决策规则**全部未给出**，对齐错误率未评估；
- 未做教学效果实证。
→ 如果我们做多源融合，**评测口径必须比它严**（照抄本次先修推断的做法：标注集 + P/R/F1 + 阈值扫描）。

### 3.4 冲突消解：三条技术路线

| 路线 | 做法 | 适用 | 风险 |
|---|---|---|---|
| 规则/文本匹配 | 对比同一概念在各源的定义文本 | 快、可解释、零 LLM 成本 | 只能抓字面矛盾 |
| 结构一致性 | 同一概念在不同源的前置/层级关系是否自洽（**环检测**、层序矛盾） | 抓"顺序类"冲突（先修关系、板块归属） | 需要已有结构 |
| LLM 仲裁 | 把多源证据交给 LLM 判定（detect-then-resolve） | 语义矛盾（定义不同、术语所指不同） | 成本 + 幻觉；**必须记录证据与置信度** |

**共性结论**：主流做法是 **detect-then-resolve 两段式** —— 先检测（可自动）再消解（**人在环**）。
没有任何可信工作主张"冲突全自动静默解决"。

我们的现成武器：`core/prerequisite.py` 的**多准则 + 证据链**骨架可直接复用为冲突检测器
（把"是否先修"换成"两源说法是否一致"，投票 → 置信度 → 进裁决队列）。

### 3.5 增量更新：怎么避免全量重建

| 做法 | 说明 |
|---|---|
| 以**资料为单位**做 run | 每本书一次抽取 + 一次融合，成本 ∝ 新书体积 |
| 对齐**先于**写入 | 新节点先与已有节点对齐，命中则走"丰富/合并"，未命中才新建（iText2KG 思路） |
| 复用图索引 | 增量只更新受影响子图（LightRAG 的增量更新算法证明了"不重建索引"的可行性） |
| 幂等键 | 用 `(source_doc_id, chunk_id, span)` 做幂等，防止重复上传同一本书产生重复节点 |

**必须接受的代价**：增量必然引入"版本漂移" —— 同一个概念前后两次融合结果可能不同。
对策是把合并决策落表（见 L1），可追溯、可回滚。

## 4. 对本项目的落地设计（分层）

### L0 溯源层（**前置，必须先做**）

**目标**：每条节点/边都能回答"来自哪份资料的哪一段"。

| 项 | 设计 |
|---|---|
| 数据 | `nodes` / `edges` 增 `sources` 字段（JSON 数组）：`[{doc_id, doc_name, chunk_id, span, extracted_at}]` |
| 兼容 | 老节点 `sources = []`（"来源未知"），不阻塞 |
| 复用 | `kb` 侧已有 `chunk_id` / `path` 溯源（混合检索的 chunk 已带 path + 父级扩展）→ 抽取时把 `chunk_id` 一路带到写入 |
| 用户隔离 | `doc_id` 归属某 `user_id`，删除资料时需联动（见 §5 风险 5） |
| 验收 | 任一节点可列出"支撑它的资料段落数"；支持按资料反查"这本书贡献了哪些节点" |

> 这一层不做，后面全白做 —— **对齐结果无法复核、冲突无法裁决、覆盖度无法度量**。

### L1 对齐层（跨源实体对齐）

**目标**：新资料抽出的节点，先与已有节点对齐，命中则融合，未命中才新建。

| 阶段 | 手段 | 复用/新增 |
|---|---|---|
| ① 阻塞/粗筛 | 向量相似度 + 字符串/字面相似度（三路并集，取候选集） | 复用 `_find_dedup_candidates` 的向量粗筛；**补字符串/字面路** |
| ② 候选压缩 | **批量上下文聚类**（一次判一批，而非两两判） | 借鉴 arXiv:2506.02509，把 O(n₁×n₂) LLM 调用降到 O(n/k) |
| ③ 仲裁 | LLM 二阶段（生成候选 → 校验理由） | 复用现有 LLM 确认逻辑 |
| ④ 融合写入 | 属性/正文**取并集**（不覆盖）+ **保留原始边** + 取最粗粒度 | 借鉴 arXiv:2305.04567 步骤 b/c/d |
| ⑤ 决策落表 | `merge_decisions` 表：`(kept_id, merged_id, score, evidence, decided_by, ts)`，支持回滚与人工复核 | 新增 |

**工程前提**：写路径必须先收敛（现在是 4 套并行实现）——否则融合逻辑要写 4 遍。

### L2 冲突层（检测 → 人工裁决）

| 冲突类型 | 检测手段 | 处置 |
|---|---|---|
| 术语/定义冲突 | LLM 对比各源定义 + 证据链 | 进**待裁决队列**，不静默改 |
| 先修方向冲突 | 多准则投票（**复用 `core/prerequisite.py`**）+ 环检测 | 低置信度入队；高置信度**标注**而非改写 |
| 板块/学科归属冲突 | 多源标签集合不一致 | 保留多值 + 标记"归属不一致" |
| 难度/时长冲突 | 数值区间不一致 | 取区间或标注分歧 |

**红线**：AI 不改人类内容（现有护栏 `_guard_human_content` / `_guard_human_edge` 继续生效），
冲突只能"**提出建议 + 留证据**"，由人裁决。

### L3 增量层（按资料入库）

- 单位：**一份资料一次 run**（不是"全库重跑"）；
- 幂等：`(doc_id, chunk_id, span)` 去重，重复上传不产生新节点；
- 失败隔离：单份资料融合失败不影响已有图谱（沿用 RAG 侧 `return_exceptions=True` 的思路）；
- 成本目标：**增量成本 ∝ 新资料规模**，与 LightRAG 的增量主张一致。

### L4 覆盖度度量（多源价值必须可量化）

| 指标 | 定义 | 用途 |
|---|---|---|
| **支撑度** support | 每个概念被多少份资料支撑 | "核心知识点"识别（对齐 arXiv:2305.04567 的三源交集） |
| **覆盖率** coverage | 已有图谱节点 / 资料中抽出的概念并集 | 图谱是否跟上了资料 |
| **对齐率** | 对齐命中数 / 新抽节点数 | 融合是否真的在合并而不是膨胀 |
| **冲突率** | 入队冲突数 / 对齐对数 | 资料间矛盾程度（也可作为教学质量信号） |
| **冗余率** | 疑似同义但未对齐的节点对数 | 对齐召回是否够（用向量低阈值反扫） |

报告形式沿用本次 P0：**JSON 报告 + 控制台表格**，可回归。

## 5. 关键工程约束与风险

| # | 风险/约束 | 说明与对策 |
|---|---|---|
| 1 | **写路径未收敛** | 4 套写实现（`knowledge_writer` / `graph_generator._write_to_graph` / `knowledge.py` 的 `create_node` 与 `decompose`）→ 多源融合会被迫写多遍。**必须先收敛写路径**（结构调研已列为 P0 之外的 P0） |
| 2 | **覆盖语义冲突** | `update_node_content` 是覆盖；多源融合需要 `merge` 语义。不改语义就会丢掉前一本教材的讲解 |
| 3 | **LLM 成本** | 对齐天然 O(n₁×n₂)；只靠向量粗筛不够，必须加批量聚类，并设"每份资料的 LLM 预算上限" |
| 4 | **用户隔离** | 图谱/知识库全按 `user_id` 分区；跨用户的"教材"绝不能互相融合（融合逻辑必须带 user_id 维度） |
| 5 | **资料删除的溯源联动** | 删掉一本教材后，仅由它支撑的节点怎么办？策略需预先定义（保留但标"来源已删除"／降级／删除），并落审计日志 |
| 6 | **版本漂移** | 增量融合可能改变已有结论 → 必须有 `merge_decisions` 可回滚 |
| 7 | **评测缺失** | 教育域对口论文自己都没做定量评测；我们必须自建标注集（先修推断已跑通这条路），否则又是一篇"只有统计、没有精度"的工作 |

## 6. 分阶段计划（建议）

| 阶段 | 内容 | 交付信号 |
|---|---|---|
| **P0** | L0 溯源字段贯通（`doc_id/chunk_id/span` 从 KB 到节点/边）+ 节点"来源"可查 | 任取一个节点能列出它来自哪本书的哪段 |
| **P1** | 写路径收敛（4→1）+ 正文/属性 `merge` 语义；离线评测集（两份教材的同义/互补标注） | 写路径唯一，评测脚本能给出"对齐 P/R/F1" |
| **P2** | L1 跨源对齐（三路粗筛 + 批量聚类 + 二阶段仲裁 + `merge_decisions`） | 上传第二本教材后，同义节点被合并、边不丢、决策可回滚 |
| **P3** | L3 增量按资料入库（幂等键 + 失败隔离 + 成本对比报告） | 新增一本书的成本与全量重建的成本对比数字 |
| **P4** | L2 冲突检测队列（复用多准则投票骨架）+ L4 覆盖度指标 | 冲突率/支撑度/覆盖率进 JSON 报告 |

**与已完成工作的衔接**：P4 的冲突检测直接复用 `core/prerequisite.py` 的"多准则投票 + 逐准则证据"骨架；
先修关系本身就是多源冲突最容易发生的地方（A 书说 A→B，B 书说 B→A）。
