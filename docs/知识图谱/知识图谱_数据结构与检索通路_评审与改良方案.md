## 0. 结论速览

**一句话**：当前 schema 是"**能跑通教学闭环的最小集合**"，不缺表、不缺字段数量，
缺的是**字段的语义边界** —— 学科靠 `tags` 位置猜、层级不存在、身份只靠字符串脸、
学习状态钉死在知识本体上、检索只有一条腿（向量）。

### 1.1 表结构（唯一权威 = `core/knowledge_graph.py::_create_tables`）

```sql
-- knowledge_graph.py:129-145
nodes(
  id TEXT PRIMARY KEY,          -- ⚠️ 全局主键（跨用户唯一，见 §2.4）
  name TEXT NOT NULL,
  file_path TEXT NOT NULL,      -- ⚠️ 装饰性：真实路径 = nodes/{user_id}/{id}.md（:669）
  tags TEXT DEFAULT '[]',       -- ⚠️ 混装：学科名 + 难度档（"一级/二级/三级"）+ 自由标签

  added_by TEXT DEFAULT 'human',
  created_at TEXT,

-- knowledge_graph.py（KG-D4/D6 后：+ created_at/updated_at + 唯一索引 + mastery_events）

  id INTEGER PRIMARY KEY AUTOINCREMENT,

  -- UNIQUE INDEX idx_edges_unique(user_id, from_node, to_node, relation)  ← KG-D6
```

### 1.2 三条隐含约定（没有一处写在 schema 上）

### 1.3 检索通路地图（三条，互不共享索引）

## 2. 逐项评审（问题 → 后果 → 判据）

### 2.1 学科建模：靠标签位置猜（P0）

**现状**：`node_subject()` 遍历 `tags` 取第一个非难度标签。
**问题**：把"分类维度"编码成"数组位置"，属于数据模型里的隐式契约 —— schema 无法约束、索引无法加速、迁移无法表达（`WHERE subject='x'` 写不出来，只能全量 Python 过滤，见 `get_nodes_by_subject:571-573`）。
**已发生的后果**：`TODO_Graph_Quality §0.1` 实测 tags 分布出现 6 个 ≤2 的杂标签；`compute_stats` 必须额外合成一个「未分类」分组（`graph_middleware.py:27`、`:207-210`）来兜住漏网节点 —— 这个合成分组本身就是模型缺陷的补丁。
**判据**：一个维度若要参与**过滤、统计、隔离**（这里三者都参与），就必须是列，而不是数组里的约定位置。

### 2.2 难度与层级共用一个标签空间（P0）

**现状**：`graph_generator` 写入 `tags = [subject] + ["一级"|"二级"|"三级"]`（难度映射）。
**问题**：`一级/二级/三级` 字面像"层级"，实际是"难度档"，且与学科标签抢 `tags[0]`。
**判据**：同一个字段承担两种语义（分类 + 标度），读方必须知道写入顺序才能正确解释 —— 这是隐式耦合。

### 2.3 层级（part_of）不存在（P0）

**现状**：教材的章—节结构在生成时被丢弃，只留下一个扁平 `board` 名。
**后果**：
1. 无法按"第 5 章"选片 → `参照系契约 G1` 的 `slice_graph` 选片只能按 `subject/board`，对话链路至今未接（`参照系契约 §5 G1` 第 1、2 步仍未做）；
2. 注入降级只能"按 focus 邻域 + 字符数"砍节点（`graph_analyzer.py:245-268`），丢的是**随机语义块**而不是"整章"；
3. 出题/讲解无法表达"本章内"的范围（`quiz` 只能按 `subject` 或 KB 文件范围检索）。
**判据**：`part_of`（结构与包含）与 `prerequisite`（学习依赖）是**两种不同关系**，混用会同时破坏两者 —— 项目目前只有后者，前者缺失。

### 2.4 `nodes.id` 全局主键（**有意取舍，建议不改**）

**现状**：`nodes.id TEXT PRIMARY KEY` 全局唯一 → `_node_id_exists_globally:714-724`、`generate_node_id` 回退 `new_001:743-749`。
**问题**：系统其余部分**全部按 `user_id` 分区**，唯独主键全局共享命名空间 → 两个用户都给"二叉树"建节点时，第二个用户要么换 id、要么（写了同名并轨后）仍各自独立（因为并轨查的是 `user_id` 内，`find_node_by_name:263` 只遍历 `self.nodes`）。
**判定**：**不改**。改成 `(user_id, id)` 复合主键 = 21 个端点 + 前端 + `rag.chunks.node_id` + `quiz` + `agent_runs` 证据链全动，收益只是"少一次全局查重"。正确做法是**把取舍写进文档**：`id` 是全局命名空间里的稳定标识，用户内唯一性由 `find_node_by_name` 保证。

### 2.5 身份层只有"字符串归一化"，没有别名（P0）

**现状**：并轨（去重 L1）唯一实现 = `normalize_node_name`（NFKC + 去空白 + 小写 + 剥 `_extended`/「复习」类后缀）+ 同学科过滤（`:49-62`、`:251-269`）。
**问题**：这一档只能处理"字面相同 + 碎片后缀"，**处理不了同义不同名**（`TODO_Graph_Quality §5.1` 已点名："栈/堆栈"这类同义不同名仍会各建一个）。
原设计依赖 L3 语义档（嵌入粗筛 + LLM 复核）兜底，但**嵌入长期欠费**（`Arrearage`）→ 变成"零兜底"。
**业界对照**：SKOS 把"首选标签 `prefLabel`"与"替代标签 `altLabel`"作为**概念的一等属性**；Neo4j GraphRAG 的 Entity Resolution 是三档串联（精确属性 → 语义 → 模糊），我们只实现了中间档。
**判据**：字符串归一化是"减法"（剥后缀），别名是"加法"（显式声明同义）—— 后者不依赖嵌入、可人工维护、可审计。

### 2.6 掌握度：学习状态钉在知识本体上（P0）

**现状**：`nodes.mastery INTEGER`（单个数字）+ `nodes.difficulty/estimated_minutes`（也是学习侧参数，但这两个属于知识本体，合理）。
**问题**：
1. **语义错位**：`nodes` 描述"知识是什么"，`mastery` 描述"某人学到哪" —— 两者生命周期与所有权都不同（知识节点可被多个用户/多本教材共享，掌握度不能）；
2. **不可回溯**：`grade_answer` 答对 +20（`tools/grade_answer.py:6-7`），但**没有一条记录说"这 20 分是哪道题、什么时候加的"**；`quiz.attempts` 表存了作答（`quiz_store.py:54-60`）却**没有回指图谱节点**（题目的 `node_id` 是 KB 节点，§2.13）；
3. **不可演化**：无法做遗忘衰减、时间序列、置信区间 —— 而知识追踪的标准做法（BKT/DKT）恰恰把掌握度建模为**学生 × 知识点**的隐状态，由**作答事件序列**驱动；
4. **合并即污染**：同名并轨（`create_node_with_content:818-822`）时掌握度如何合并无定义（保留谁的？相加？取大？）。
**判据**：状态类字段必须能回答"谁改的、什么时候、凭什么" —— 现在三个都答不出来。

### 2.7 边：约束与属性都缺（P1）

| 缺什么 | 后果 | 证据 |
|---|---|---|
| `UNIQUE(user_id,from,to,relation)` | 并发/脚本直写可产生重复边；查重只在 `add_edge` 代码里（SELECT 一次） | `:1023-1031` |
| `created_at` / `updated_at` | 无法做增量索引、无法审计"这条边谁哪天连的" | 表定义 `:149-161` |
| `sources`（来源段落） | 多资料调研 L0 的溯源层无法落地；L3 引用只能到 node 不能到页 | `多资料综合维护调研 §4 L0` |
| `weight` | 多源融合/多准则推断给出的置信强弱无处存（`confidence` 有列但建图不写） | `:156` |
| 校验触发器 | 直接 SQL/脚本写非法 relation 不会报错（代码枚举只在 `add_edge:1012`） | 同上 |

### 2.8 无向关系的方向语义（P1）

`related` 与 `confusion` 在语义上**无向**（"A 与 B 相关"、"A 与 B 易混"），但存储与查重都是**有向**的（`:1025` 查 `(from,to,relation)`）→ `A→B(related)` 与 `B→A(related)` 可以并存，渲染时图谱上出现两条重叠边。
**判据**：关系类型必须显式声明有向性；无向关系要么归一化存储，要么在查重时做对称检查。项目现在是"隐式有向"，全靠调用方自觉（`graph_analyzer` 未做对称检查）。

### 2.9 检索：单腿 + 只走一种边 + 分数不可比（P0/P1）

| 子问题 | 现象 | 锚点 |
|---|---|---|
| **单腿** | 嵌入 API 欠费 → `search()` 直接返回 `[]`（**无关键词兜底**）→ 图谱按需检索全失效，只剩注入侧的全量框架 | `rag/manager.py:204-210` |
| **只走 prerequisite** | 扩跳函数名就叫 `_expand_prerequisites`；`related/confusion/extension` 在检索里**完全没用**（而 `confusion` 在教学上最值钱：学生易混点） | `rag/manager.py:219-268` |
| **分数不可比** | graph 源给余弦（0~1），kb 源给 RRF 分（与排名相关，量级完全不同）→ pipeline 只能按源拼块，不能统一重排 | `rag_pipeline/sources.py:54-74`、`:133-180` |
| **chunk 与节点结构不对齐** | `chunk_markdown` 按 MD 标题切（`rag/chunker.py:43-84`），而节点正文已是"定义/要点/示例/易错"五段式 → 语义单元被切散 | 同上 |
| **`chunk_index` 段内重复** | `flush()` 内 `enumerate(_split_long_paragraph(text))` → 每个小节从 0 开始，同节点内索引重复 | `rag/chunker.py:60-74` |
| **向量解码开销** | `embedding` 存 JSON 文本 + 检索时全表 `SELECT` 再 `json.loads` | `rag/vector_store.py:40-51`、`:111-145` |
| **两条 whoosh 冲突** | kb 的 whoosh 把 `node_id` 定为 `NUMERIC`，图谱 `node_id` 是 `TEXT` → 复用需改 schema + 迁移（这是 `参照系契约 §8` 判"不做"的依据） | `hybrid_search/whoosh_index.py:61-70` |

## 3. 调研：业界怎么建模（可借鉴点 + 本项目取舍）

| 主题 | 业界做法 | 对本项目的取舍 |
|---|---|---|
| **概念的标签** | SKOS（W3C）：`prefLabel`（首选名）/`altLabel`（别名）/`hiddenLabel`（同义检索用）；`broader`/`narrower` 表达层级；`related` 表达非层级关联 | **借 `altLabel`**：`node_aliases` 表（§4.3）。`broader/narrower` 即 `part_of` 的反向视图 → 用 `parent_id` 表达，不必两张表 |
| **层级 vs 依赖分离** | 教育域学科图谱普遍区分"上下位关系（父子概念）"与"先修关系（学习顺序）"两类边 | **必须分离**：`part_of`（`parent_id`/`path`）+ `prerequisite`（现有边）。现状只有后者 |
| **学习状态建模** | 知识追踪（BKT/DKT）：掌握度 = **学生 × 知识点**的隐状态，由**作答序列**更新（`p(L)`、学习转移 `p(T)`、猜对 `p(G)`、失误 `p(S)`）；KLI 框架的 KC（knowledge component）同样把"知识"与"学习者状态"分开 | **借"分开"**：`mastery_events`（事件）+ `nodes.mastery`（物化缓存）。**不引入 BKT 参数**（YAGNI：没有足量作答数据，先让证据可回溯） |
| **关系属性** | 属性图 / RDF 具化（reification）：边的来源、权重、时间、置信度是**边自己的属性**，不是两端节点的 | 采纳：`edges` 增 `sources`/`weight`/`created_at`（§4.2） |
| **图谱检索** | GraphRAG 家族把检索分层：Local（邻域）/Global（社区摘要）/DRIFT（社区+局部）；多跳可交给 LLM 迭代或 Personalized PageRank | 本项目**不做社区摘要**（无需求、成本高）；**借"按关系类型分策略扩跳"**（§5.3）—— 这是 Local 的最小可用形态 |
| **混合检索融合** | 结构化+稠密+稀疏多路结果用 **RRF**（倒数排名融合）统一，避免分数尺度不可比 | 已有 `hybrid_search/fusion.py::fuse` → **跨源（graph+kb）直接复用**，而不是拼段落（§5.5） |
| **全文索引** | SQLite **FTS5** 内置（无需 whoosh 第三方依赖），`tokenize=trigram` 可支持中文子串匹配 | 见 §5.2：实测 SQLite 3.50.4 已内置 FTS5；trigram 只覆盖 ≥3 字查询 → `LIKE` 兜底 1–2 字 |
| **溯源** | 语料/抽取类图谱普遍保留 `(doc_id, span)` 级 provenance，支持"这句话凭什么"审计 | 复用本仓库 `多资料综合维护调研 §4 L0` 的设计（`sources` JSON），不另造 |

**核实状态**：SKOS/BKT/DKT/FTS5/GraphRAG 分层为公认事实（FTS5 已本机实测，见 §5.2）；
`多资料综合维护调研 §7` 的 arXiv 编号沿用该文档的核实结论，本文不重复引用。

## 4. 目标 schema（v2）

> 原则：**只 ADD COLUMN / CREATE TABLE，不重建表**（SQLite 无法给已有列加 `CHECK`，重建表代价远大于收益）；
> 迁移幂等（跑 N 次结果相同）；老数据 `NULL`/`''` 一律解释为"未知"，不阻塞任何读路径。

### 4.1 `nodes` 新增列

| 列 | 类型 | 语义 | 谁写 | 回填 | 状态 |
|---|---|---|---|---|---|
| `subject` | `TEXT DEFAULT ''` | **学科**（一等公民，替代 tags 位置约定） | 所有写路径（`create_node_with_content` 统一注入） | `UPDATE nodes SET subject = <node_subject 的当前结果>`，一次性脚本 | ✅ D1 |
| `updated_at` | `TEXT` | 变更时间（增量索引/审计"上周改过哪些节点"） | `update_node_info` / `update_node_content`（含并轨）/ `add_node` | `= created_at`（补列那一支执行一次） | ✅ 2026-09-23 |
| `parent_id` | `TEXT` | **part_of 父节点**（章→节→知识点）；`NULL` = 顶层 | 建图（`graph_generator` 按章节单元设）+ 手动编辑 | 留空（老数据无层级信息，不瞎猜） | ⏳ D7 |
| `path` | `TEXT DEFAULT ''` | 物化路径 `学科/章/节`，供**选片**用（免递归 CTE） | 同上（由 parent 链推导，一致维护） | 留空 | ⏳ D7 |
| `deprecated_file_path` | — | `file_path` 保留列但**标注 deprecated**（真实路径由 `nodes_dir/{id}.md` 推导） | 无 | 无 | 仅注释 |

**新增索引**：`CREATE INDEX idx_nodes_user_subject ON nodes(user_id, subject)`（选片/统计走它）。
**`mastery_events` 落地后**，`nodes.mastery` 语义降级为"**当前值缓存**"（唯一写入方仍是掌握度更新路径，§4.4）。

### 4.2 `edges` 新增列 + 约束

| 列/约束 | 内容 | 说明 | 状态 |
|---|---|---|---|
| `created_at` | `TEXT` | 建边时间 | ✅ 2026-09-23 |
| `updated_at` | `TEXT` | 最近修改（改 label/relation） | ✅ 2026-09-23 |
| `UNIQUE INDEX` | `(user_id, from_node, to_node, relation)` | 把"代码查重"升级为"数据库约束"（防御脚本直写） | ✅ 2026-09-23 |
| `weight` | `REAL DEFAULT 1.0` | 强度（多源支撑数 / 多准则得分）—— 与 `confidence` 分工：**confidence = 这条边对不对，weight = 有多强** | ⏳ **暂缓**：目前没有任何写入方，加了就是第二个 `confidence`（1.6% 填充的反面教材）。等多准则/多源融合真正开始写它时再加（KG-D10 前置） |
| `sources` | `TEXT DEFAULT '[]'` | `[{doc_id, doc_name, chunk_id, span, extracted_at}]`（对齐多资料调研 L0） | ⏳ 归 KG-D8 |
| **无向归一化约定** | `related` / `confusion`：写入时按 `from_node < to_node`（字典序）**归一化**后存一行 | 消除重叠边；读取时双向展开。⚠️ 需先扫存量看有没有反向重复（§6 P0 验收） | ⏳ 待拍板（会改存量边）；⚠️ 唯一索引是**有向**的，不做归一化时 `A→B` 与 `B→A` 仍会并存 |

**实现要点（KG-D6，2026-09-23）**：

- 列/索引都在 `_auto_migrate` 里幂等补（`ALTER TABLE ADD COLUMN` + `CREATE UNIQUE INDEX IF NOT EXISTS`），**不重建表**；
- **有重复边时索引建不上 → 只告警、不阻断启动**（否则整个后端起不来），由 `inspect_graph_quality.py` 报出后人工合并；真实库（679 边）实测重复组 **0** → 索引已建成；
- 唯一约束会兜住"并发/脚本直写"的漏网（`add_edge` 的 SELECT 查重不是原子的）；`add_edge` / `update_edge_by_id` 把 `IntegrityError` 映射回 `ValueError("边已存在…")`，API 侧 update 路由据此返回 **409**（与 create 口径一致）。

**不做的**：给 `relation` 加 SQL 级 `CHECK`（SQLite 加不上已有列）→ 用 `BEFORE INSERT/UPDATE` 触发器，或**只在写入层守**。
**本次判定：不加触发器** —— 两条写路径其实都已守（Pydantic `EdgeRelation` 字面量 + `add_edge` 枚举校验），触发器只能挡手写 SQL；唯一索引已覆盖真正的现实风险（脚本直写重复）。**等出现直写边的脚本（如 §4.2 的无向归一化迁移）时再加**。

### 4.3 新增表一：`node_aliases`（别名层，判重 L1.5 档）

```sql
CREATE TABLE IF NOT EXISTS node_aliases (
    alias_key  TEXT NOT NULL,          -- normalize_node_name(别名)，判定键
    node_id    TEXT NOT NULL,
    user_id    INTEGER NOT NULL,
    source     TEXT DEFAULT 'ai',      -- ai（图谱写回时自动登记）/ human（人工标）/ merge（并轨时继承）
    created_at TEXT,
    PRIMARY KEY (alias_key, user_id),
    FOREIGN KEY (node_id) REFERENCES nodes(id) ON DELETE CASCADE
);
```

**写入时机**（三处，都不依赖嵌入）：
1. `create_node_with_content` 未命中同名时：把 `name` 本身登记为别名（幂等，等价于"自名"）；
2. **并轨命中时**：把被并入的 `name` 登记为**保留者**的别名 —— 即"同一个概念曾用名"；
3. 人工/LLM 显式标别名（可选）。

**读取**：`find_node_by_name` 先查别名表，未命中再走现有归一化比较 → 这样"栈 / 堆栈"只要有人（或某次 LLM 判定）登记过别名，之后**零嵌入**也能并轨。
**判据**：让"同义"成为可累积的数据，而不是每次都要重新算（算还算不出来，因为嵌入欠费）。

### 4.4 新增表二：`mastery_events`（掌握度证据链）

```sql
CREATE TABLE IF NOT EXISTS mastery_events (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id     INTEGER NOT NULL,
    node_id     TEXT NOT NULL,
    delta       INTEGER NOT NULL,        -- +20（判分答对）/-N（误判纠正）
    before_val  INTEGER NOT NULL,
    after_val   INTEGER NOT NULL,
    reason      TEXT NOT NULL,           -- quiz_correct / quiz_wrong / self_report / manual / ...
    evidence    TEXT DEFAULT '',         -- 证据引用：question_id / attempt_id / 对话 run_id
    created_at  TEXT DEFAULT (datetime('now')),
    FOREIGN KEY (node_id) REFERENCES nodes(id) ON DELETE CASCADE
);
```

**唯一写入点（已落地）**：掌握度变更的**唯一出口 = `KnowledgeGraph.update_node_info`** —— 5 条改 `mastery` 的路径（`update_mastery` 工具 / 判分回写 `apply_mastery_after_answer` / `PUT /node/{id}/mastery` / `PUT /node/{id}` 通用更新 / 问题拆解）**全部经它**，所以在它内部记账即可，**新增写路径不需要自己记账**。事件与节点更新在**同一事务**提交（不会出现"事件写了但 mastery 没改"）。

**理由参数（谁写）**：`update_node_info(..., mastery_reason=, mastery_evidence=)` 两个关键字参数，默认 `manual`（→ 老调用方零改动）。
- `quiz_correct` + `question:<id>`：判分答对（唯一主信号）
- `self_report`：`update_mastery` 工具的 3 种硬证据
- `manual`：前端/人工/其他

**读取**：`KnowledgeGraph.get_mastery_events(node_id, limit)`（倒序）—— 回答"为什么是 60 分"。

**顺带解决三件事**：① 可回溯（"为什么是 60 分"）；② 合并节点时可按事件重放决定 `mastery`（而不是猜，**尚未接**：当前并轨不动掌握度）；③ 未来接遗忘衰减/BKT 时，**数据已经在**。
**明确不做**：不引入 BKT/DKT 模型参数、不做知识状态推断（无足量作答数据，YAGNI）；不做定期清理（单用户量级 ≈ 作答次数，行数无风险）。

### 4.5 新增表三（可选，看 §5.2 结论）：图谱全文索引

```sql
-- 方案 B（推荐，零依赖）：trigram
CREATE VIRTUAL TABLE IF NOT EXISTS nodes_fts USING fts5(
    node_id UNINDEXED, name, summary, content, tokenize=trigram
);
```
⚠️ **实测边界（本机 SQLite 3.50.4）**：`tokenize=trigram` 对 **≥3 字**查询命中
（`先进后出` ✅、`数据结构` ✅），**1–2 字不命中**（`堆栈` ✗、`栈` ✗）—— 中文高频词多是 2 字。
故落地形态见 §5.2（trigram + LIKE 兜底），或改用"写入时 bigram 展开 + `unicode61`"（对标 whoosh 现有做法）。

### 4.6 迁移与回滚

| 步骤 | 内容 | 幂等 | 回滚 |
|---|---|---|---|
| M1 | `ADD COLUMN`（nodes/edges）+ 建索引（`PRAGMA table_info` 判存在，**沿用 `_auto_migrate:166-184` 既有模式**） | ✅ | 删列需重建表 → **不提供自动回滚**；备份 `knowledge.db` 即可（§7） |
| M2 | `subject` 回填（一次性脚本，纯读 old + 写 new） | ✅ | 置空即可 |
| M3 | `created_at/updated_at` 回填（老行 `= created_at` 或 `NULL`） | ✅ | 无害 |
| M4 | 无向边归一化 + 去重（`--apply` 前先 dry-run 报告） | ✅ | 需备份（删边不可逆） |
| M5 | `nodes_fts` 建表 + 全量填充（可从 nodes + MD 正文重建） | ✅ | `DROP TABLE`（可重建） |

## 5. 检索通路改造设计

### 5.1 三条通路的定位（不要互相替代）

| 通路 | 定位 | 本次改动 |
|---|---|---|
| ① 参照系注入 | **每次必在**的框架约束（`参照系契约 L1`） | **不动**（G1 的"结构化选片"在 ②③ 就绪后再接，见 §5.4） |
| ② 按需检索 | 命中才用（"这个知识点正文在哪几段"） | 补关键词兜底 + 按 relation 分策略扩跳 + 跨源统一融合 |
| ③ 结构化切片 | 图谱页选片 | 从 `subject/board` 升级为 `subject/path`（有了 `parent_id` 之后） |

### 5.2 图谱检索补"第二条腿"（解决嵌入欠费即全失效）

**目标**：嵌入不可用时，仍能按关键词召回节点（至少 `name` 与 `summary` 命中）。

| 方案 | 做法 | 成本 | 判断 |
|---|---|---|---|
| **A（推荐先做）** | `name/summary` 用 `LIKE '%kw%'`（节点规模 10²–10³，全表扫描可忽略）；正文命中交由已有 MD 读取 | 1 个查询分支 | ✅ 最少代码，立刻消除"单点依赖" |
| B | FTS5 `tokenize=trigram` + 1–2 字回落 A | 建表 + 同步写入 + 迁移 | 加**相关性排序**（BM25）时才值得 |
| C | 写入时 bigram 展开 + `unicode61`（对标 whoosh 现有中文分析器） | 索引体积 ~2x + 展开逻辑 | 只有在 B 的排序不够、且 2 字命中率是瓶颈时 |

**评分与融合**：关键词命中的分数**不能**直接与余弦混排（尺度不同）→ 统一走 RRF（§5.5）。
**顺带**：`rag/chunker.py` 的 `chunk_index` 改全局递增（修 §2.9 的索引键重复），使 `(node_id, chunk_index)` 成为**唯一溯源键**。

### 5.3 图结构扩跳：从"只走 prerequisite"到"按关系分策略"

| 关系 | 方向 | 建议跳数 | 教学用途 |
|---|---|---|---|
| `prerequisite` | **反向**（补前置） | 1–2（现有默认 1） | 学生卡住 → 补基础 |
| `confusion` | 双向 | 1（同桌） | "你容易和 X 混" —— 主动预防，现有检索完全没用上 |
| `extension` | 正向 | 1 | 学有余力 → 进阶 |
| `related` | 双向 | 0（默认关） | 噪声大，按需开 |

**接口形态（最小改动）**：`rag_manager.search(user_id, query, top_k, hops, relations=...)` 的 `hops` 从 `int` 扩为**按关系配置**（默认值保持现状 → 老调用方零改动）。
⚠️ **预算纪律**：扩跳是注入体量的放大器（现注释已自认"最多翻倍"，`rag/manager.py:227`）→ 新增关系必须**共享同一个条数上限**，不能各扩各的。

### 5.4 结构化选片（依赖 §4.1 的 `parent_id`/`path`）

- 现状：注入超预算时按"focus 邻域优先 + 字符数"二分截断（`graph_analyzer.py:245-268`）—— 丢的是任意语义块；
- 目标：`subject` → `path` 前缀 → focus 邻域 三级优先（与 `graph_middleware.slice_graph` 的三级粒度**同构**）；
- 收益：模型看到的是"**第 5 章整章**"而不是"第 3、7、12 章各两个节点"—— 参照系契约 I1-3（正面约束）因此更实。
- 前提：`parent_id` 先落地并有数据（老数据补不出来 → 只对新生成图谱生效，老图谱仍走字符降级）。

### 5.5 跨源统一融合（消除"拼段落"）

现状：graph 命中给余弦、kb 命中给 RRF 分，pipeline 按源组织成区块（`rag_pipeline/sources.py` 两个源各自 `RagHit`）。
**改法（复用已有件，不新增抽象）**：
```
各源内部排序 → 取排名 → hybrid_search.fusion.fuse(多源排名, weights) → 统一 top_k → 渲染区块
```
即把 `fusion.py` 的 RRF 从"kb 内部双路"推广到"**跨源多路**"。收益：① 分数可比；② 排序可调（图谱权重 vs 资料权重）；③ 免去"哪个源排在前面"的隐式规则。

## 6. 分阶段落地路线

> 排序依据 = **风险 × 收益 / 改动面**。每阶段独立可交付、可回滚。

### P0（先做，都是"小改动 / 高收益"）

| 编号 | 内容 | 落点 | 验收（可执行） |
|---|---|---|---|

## 7. 风险与回滚

| 风险 | 说明 | 对策 |
|---|---|---|
| **迁移不可逆** | `ADD COLUMN` 无法优雅回滚（SQLite 改列 = 重建表） | 动手前备份 `data/knowledge/{knowledge.db,nodes/}`；`ADD COLUMN` 本身**不重写数据**，风险低于"重建表" |
| **老数据补不出层级** | `parent_id/path` 对存量图谱为空 | 明确：层级**只对新生成图谱生效**；老节点走原降级路径，不猜 |
| **无向归一化会删边** | M4 会修改/删除存量边 | 先 dry-run 出报告（类似 `inspect_graph_quality.py --fix-dupes` 的默认只读），人工确认后 `--apply` |
| **掌握度双写不一致** | 事件写成功但 `nodes.mastery` 没更新（或反之） | 两者**同一事务**提交；`mastery_events` 唯一写入点 = 现有掌握度更新路径（收敛后再加事件） |
| **`subject` 回填错** | 老数据的 tags 已经是污染的 | 回填 = 现状 `node_subject()` 的结果（**不引入新判断**）；错的仍是错的，但从此**可被 SQL 查出并修**（这正是改良收益） |
| **改动面外溢** | 21 个图谱端点 + 前端依赖 `id/name/tags/mastery`（`ForceGraph.vue`、`EditDialog.vue`） | 本次新增列**全部可选**（有默认值）→ 老读路径不感知；只有写路径与统计路径需要逐步接入 |
| **网页存档节点的 subject 语义** | `create_node_from_webpage` 的 tags = `["网页", host]` → KG-D1 后 `node_subject` 会得出"网页"并**写进 `subject` 列**，前端学科栏可能多出"网页"分组（用户 5 当前无此类节点，故未暴露） | 属产品决策（网页节点算不算一门学科）→ 本次不改；若要修，需显式表达"学科为空"并在 `add_node` 区分"显式空"与"未提供" |
| **存量 `chunk_index` 未迁移** | KG-D5 只让**新索引**的 `(node_id, chunk_index)` 唯一，已有 `rag.db` 里旧的重复 index 仍在 | 影响面小（仅溯源键）；需要时 `index_user_graph` 重建索引即可 |
