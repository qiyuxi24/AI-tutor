## 0. 结论速览

**一句话**：图谱本体仍是**一张关系网**（今日不变）；在其上新增**一层按知识相关度算出的主题归属**，作为 UI 下钻与（将来）AI 理解组织结构的依据。

| 项 | 结论 |
|---|---|
| 分级依据 | **知识相关度**（节点名 + 摘要的语义聚类），**不是教材章节** |
| 为什么 | 教材目录组织的是"教学进度"（几何被拆在 6 个年级），不是"知识结构" |
| 层数 | **学科下 2 层**：省（课内一级模块）→ 市（课内二级模块）→ 知识点 |
| 落地形态 | 2 张表：`themes`（主题树）+ `node_themes`（多对多归属） |
| 本轮范围 | **只做数据结构**（表 + 读写接口 + 聚类落库）；UI 下钻下一轮 |
| 聚类算法 | **LLM 归纳**（一次调用产出两层主题树 + 命名） |

## 1. 问题：教材目录 ≠ 知识结构

用户原话（2026-09-26）：

> "不要严格根据章节，更应该根据知识相关度来划分……比如小学初中的数学实际上是分散讲课的，几何学被拆得很碎，分在了不同的年级进行教学。"

**两个正交维度被混淆了**：

| 维度 | 谁给的 | 服务什么 | 若拿它做骨架 |
|---|---|---|---|
| **教学进度**（年级 / 章 / 节） | 教材作者 | 按顺序教 | ❌ 几何被拆在 3–9 年级，散成 6 处 |
| **知识结构**（主题 / 概念） | 知识自身的相关度 | 理解、查找、组织 | ✅ 几何聚成一块 |

且**不是所有知识都是树**：

| 学科 | 真实结构 | 强制单归属的后果 |
|---|---|---|
| 数学、物理 | 树 | 贴合 |
| 编程、CS | **DAG**（"递归"既是"函数"的下属，也是"算法思想"的下属） | 丢信息 |
| 历史 | **网 + 时间线**（一战与二战是因果，非父子） | 找不到自然父子 |
| 医学、法律 | 分类体系 | 贴合 |

**结论**：主题树必须是**视图**，不能是**骨架**；关系网永远为主体。这决定了本方案的三层结构（§2）。

## 2. 核心模型

```
① 关系网（已有，不动）   节点 + 边（prerequisite / related / confusion / extension）
                          ← 图谱主体，力导向图渲染的就是它

② 主题归属（新增，多对多） 节点 → [主题A, 主题B, ...]（带权重 + 主归属标记）
                          ← 数据层。通用于 DAG/网状知识，将来给 AI 用

③ 主题树（新增，2 层）    省(课内一级模块) → 市(课内二级模块)
                          ← UI 层。展开/收起用；UI 只认"主归属"渲染
```

**② 与 ③ 分离是通用性的来源**：

- 遇到树状知识 → ② 退化为单归属，③ 与之一致；
- 遇到网状知识 → ② 保留多归属（信息不丢），③ 仍给出"最像主线的一棵树"，不崩。

**两条兜底**：

| 兜底 | 作用 |
|---|---|
| **允许"无归属"** | 聚不进去的节点留在「其他」，**不强行安放** |
| **每学科一棵树** | 与现有"一次渲染一个学科"一致；数学与物理都有的"向量"各归各的 |

## 3. 硬约束（用户拍板）

### 3.1 一门课 = 一张图

```
      计算机 ✗    ← 太粗，不得成为一门课
      数学   ✗    ← 太粗，不得成为一门课
  ┌────┴────┐
 几何      代数   ✓  ← 这个粒度（或更细）才是一门课 = 一张图
 数据结构  ✓      ← "数据结构"可以，"计算机"不行
```

| # | 约束 | 落点 |
|---|---|---|
| C1 | `subject` 是**锚点**（用户上传时指定），**不参与聚类、不往上合并** | `themes.subject` 仅作分区键 |
| C2 | 主题树**硬限制 2 层**（省 → 市），不加深、不往上合并 | `themes.level ∈ {1,2}`，应用层校验 |
| C3 | 主题必须**比课更细**（粒度约容纳 10 个知识点），禁止"比课更泛"或"与课同名" | 聚类 prompt 写死 + 人工可改 |

**C2 用应用层校验、不加 SQL `CHECK`**：SQLite 给已有表改 CHECK 需重建表（`评审文档 §4` 已记该坑），而"将来要 3 层"的可能性不该付重建代价。文档写明硬限制，代码守。

### 3.2 关于 `subject` 本身过粗

`subject` 是**用户手填**的，系统拦不住"数学"这种填法。是否在建图入口加**软提示**（"建议填到一门课的粒度，如『几何』『代数』"）——**待定**，不影响本文设计（属产品层）。

## 4. 数据结构（本轮交付物）

```sql
-- ① 主题树：学科内的一棵树（省 → 市）
CREATE TABLE IF NOT EXISTS themes (
    id          TEXT PRIMARY KEY,          -- 全局稳定 ID（与 nodes.id 同一命名空间约定）
    user_id     INTEGER NOT NULL,
    subject     TEXT NOT NULL DEFAULT '',  -- 分区键 = 课名（C1）
    name        TEXT NOT NULL,             -- "几何" / "三角形"
    parent_id   TEXT,                      -- NULL = 省(L1)；否则指向上级主题
    level       INTEGER NOT NULL,          -- 1=省, 2=市（C2：硬限 1~2，应用层校验）
    order_index INTEGER DEFAULT 0,         -- 同层展示顺序
    source      TEXT DEFAULT 'ai',         -- ai / human
    created_at  TEXT,
    updated_at  TEXT,
    FOREIGN KEY (parent_id) REFERENCES themes(id) ON DELETE CASCADE
);

-- ② 归属：节点 ↔ 主题，多对多（通用性的落点）
CREATE TABLE IF NOT EXISTS node_themes (
    node_id    TEXT NOT NULL,              -- FK → nodes(id) ON DELETE CASCADE
    theme_id   TEXT NOT NULL,              -- FK → themes(id) ON DELETE CASCADE
    user_id    INTEGER NOT NULL,
    weight     REAL DEFAULT 1.0,           -- 归属强度
    is_primary INTEGER DEFAULT 0,          -- 主归属：UI 树按它渲染
    source     TEXT DEFAULT 'ai',          -- ai / human
    created_at TEXT,
    PRIMARY KEY (node_id, theme_id)
);

CREATE INDEX idx_themes_user_subject ON themes(user_id, subject);
CREATE INDEX idx_node_themes_theme   ON node_themes(theme_id);
CREATE INDEX idx_node_themes_node    ON node_themes(node_id);
```

### 4.1 四个关键设计点

| 设计 | 解决什么 |
|---|---|
| `node_themes` **多对多** | "递归"可同时属「函数」与「算法思想」——通用性的根本 |
| `is_primary` 单独一列 | 数据层保留全部归属，UI 只认主归属渲染 → 界面整齐、信息不丢 |
| `source`（ai / human） | **重算聚类不覆盖人工修改**——没有这条，手动调整下次刷新即失效 |
| `parent_id` + `level` | 本轮只落 L1，将来加 L2 **不用改表**；历史类非树知识可只 1 层 |

### 4.2 "顺序"从哪来

| 顺序类型 | 载体 | 是否新增 |
|---|---|---|
| 主题之间的展示顺序 | `themes.order_index` | 新增 |
| 主题之间的**语义先后**（"几何是代数的前置"） | 由现有 `prerequisite` 边**聚合**得到（前端按 §5 规则算） | ❌ 不存 |
| 节点之间的学习顺序 | 现有 `topological_sort` / `get_learning_path` | ❌ 一行不改 |

**核心**：聚类**不产生边**。边永远来自原关系网，聚类只决定"这些边的两端显示成什么"。所以聚类算错，关系也不会错——最坏只是分组难看。

## 5. UI 模型：地图式渐进下钻（下一轮实现）

### 5.1 交互

```
【初始：只看到"省"】
        几何 ────── 代数
          │  ╲
        统计 ──── 概率

【展开"几何"：它变成"市"，其他仍是"省"】
        几何 ────── 代数          ← 代数仍是省级的聚合点
         ├ 三角形
         ├ 圆                      ← 几何内部展开
         └ 四边形
         三角形 ┈┈┈┈ 代数          ← 跨层边
```

每个节点**各自记录展开状态**，互不影响。展开到"市"后再下钻 → 进入**详情面板**（知识点 + 掌握程度 + 相关题目），不再往图里加节点。

### 5.2 边折叠规则（"向上卷"）

> **对每一条原始边，把两端各自"上卷"到当前可见的最高祖先，然后连线；若两端卷到同一个点，则它是内部边，不画。**

三种情况全部自动覆盖：

| 原始边 | 当前可见状态 | 结果 |
|---|---|---|
| 全等三角形 → 相似三角形 | 几何未展开 | 两端都卷到「几何」→ 自环 → **不画** |
| 全等三角形 → 二次函数 | 几何已展开、代数未展开 | 画 **全等三角形 ┈ 代数** |
| 全等三角形 → 二次函数 | 两边都展开 | 画 **全等三角形 ─ 二次函数** |

**省与省的聚合边**（"几何与代数的前后关系"）是同一条规则的产物：**边权 = 底下有多少条边**（可据此调节粗细或过滤）。

这套做法即**分层折叠 / 边捆绑（hierarchical collapsing）**，是标准解法，**纯前端计算**，不需要新数据结构。

### 5.3 为什么这样设计是通用的

- 聚类只影响"分组是否好看"，不影响"关系是否正确"；
- 网状/历史类知识即使聚类质量一般，下钻仍能工作（退化为浅层分组）；
- 允许无归属 → 不强行分类。

## 6. 聚类算法：LLM 归纳

| 项 | 设计 |
|---|---|
| 做法 | 把该 `subject` 下的**节点名清单**（必要时附 `summary`）交给 LLM，要求输出 2 层主题树 + 每个节点的主归属，并允许一个节点出现在多个主题下 |
| 触发 | **建图完成后自动一次** + **手动"重新整理主题"**；**不是每轮对话调用** |
| 成本 | 311 节点名 ≈ 3–5K token，一次调用可容纳（【估】，实现时实测） |
| 为何选它 | 唯一能**同时给出分组与组名**的做法（"几何"这种高阶概念，嵌入聚类给不出名字） |
| 为何不用嵌入/图社区 | 嵌入聚类无命名能力；图社区依赖边质量且与"按名称相关度"的诉求不符 |

### 6.1 prompt 硬约束（示意）

```
这是《数据结构》这门课的知识点清单。
请分成 5-8 个【课内模块】，每个模块下再分 3-5 个子模块。

硬性要求：
- 模块必须是这门课内部的概念（如"树结构""图算法"）
- 禁止输出比本课程更宽泛的概念（如"计算机基础""编程语言"）
- 禁止输出与本课程同名的模块（如"数据结构"）
- 每个子模块应能容纳约 10 个知识点
- 若某知识点确实横跨多个主题，可以放进多个主题（在输出中重复出现）
```

### 6.2 稳定性纪律

| 纪律 | 说明 |
|---|---|
| 结果落库 | 算一次存起来，**不是每次打开图谱都重算** |
| `source='human'` 保护 | 重算时**跳过**人工调整过的主题与归属 |
| 人工可改 | 改名 / 移动节点 / 调整顺序；改过的标记为 `human` |

## 8. 边界与风险

| 风险 | 说明 | 对策 |
|---|---|---|
| 聚类结果不稳定 | LLM 每次可能不同 | 落库 + `source='human'` 保护 + 手动触发 |
| 聚类质量差 | 分组难看 | 只影响 ③，不影响 ①②；人工可改 |
| 主题泛化（"计算机"） | LLM 不听话 | prompt 硬约束（C3）+ 人工可改 |
| 节点过多装不下 | 上千节点时 prompt 超限 | 本轮 311 可一次；将来分批 + 层次化（记 TODO） |
| 无归属节点 | 语义孤岛 | 归「其他」，不强行安放 |
| 多归属导致视觉重复 | 同一节点出现在多个主题 | `is_primary` 保证 UI 单归属 |
| `themes.id` 全局命名空间 | 与 `nodes.id` 同理 | 沿用同一约定（`评审文档 §2.4` 的取舍） |

## 9. 验收标准（AC）

| 编号 | 断言 | 复核方式 |
|---|---|---|
| AC-T1 | 两张表建成；重复启动幂等；老库自动补表 | 重启后端两次，`PRAGMA table_info` / 行数不变 |
| AC-T2 | 对 user 5 聚类后，L1 主题数在 **5–8**、每个 L2 子模块覆盖约 **10** 个知识点 | `sqlite3` 统计 |
| AC-T3 | 每个知识点都有 **且仅有 1 个** `is_primary=1` 的归属（无归属者除外） | SQL 断言 |
| AC-T4 | 多归属确实发生（存在节点归属 ≥2 个主题） | `SELECT node_id, count(*) ... HAVING count(*)>1` |
| AC-T5 | 重算**不覆盖** `source='human'` 的主题与归属 | 手工改一条 → 重算 → 值不变 |
| AC-T6 | 主题中**无**比课程更泛或同名的项 | 人工比对（C3） |
| AC-T7 | 出题 / 统计 / 检索 / 注入行为不变 | 全量回归测试 + 统计数字与改动前一致 |

### 9.1 真机验证记录（2026-09-26）

> 环境：`--user 5` / 学科「强化学习」，该课共 **302** 个本科节点（uid5 全库 367 节点）。
> 三次迭代均在同一学科上实测（LLM 输出有波动，下表为各次实际落库值）。

| 迭代 | prompt 状态 | themes | assigned | unassigned | 覆盖率 | 关键现象 |
|---|---|---|---|---|---|---|
| 第 1 次 | 旧 prompt | 20 | 128 | 174 | **42%** | 主动停止分配：把「每个二级主题应能容纳约 10 个知识点」读成「每个只放 10 个」（15 个 L2 × ~8–10 ≈ 128，数字吻合） |
| 第 2 次 | 修覆盖率口径 | 23 | 300 | 2 | **99.3%** | 覆盖率达标，但暴露树形缺陷：① `最优行为价值的计算(48)` 错挂在「多臂老虎机与探索利用」下；② 同课内近义 L2 并存（`策略评估与求解(30)` / `策略评估与迭代求解(57)`）；③ L2 大小 3~57 极不均；④ 出现「课程综合与未识别片段」兜底命名 |
| 第 3 次 | 清空 AI 主题走"首次聚类"路径，含 4 条新结构纪律 | 28（L1 7 + L2 21） | 293 | 9 | **97%** | 错挂消失、近义重复消失、bandit 下只剩相关主题；多出「教学示例与编程工具」收纳代码工具类节点（`泡吧问题(19)` / `学生MDP建模(27)` / `Utils工具模块(14)`）；残余 2 个 L2 超 30 阈值、9 个未归类中 6 个为噪声/碎片节点 |

**第 3 次 L1 全名单**（7 个）：强化学习基本概念与历史 / 马尔可夫决策过程与数学基础 / 价值函数与贝尔曼方程 / 动态规划求解MDP / 蒙特卡洛方法与无模型学习 / 多臂老虎机与探索利用 / 教学示例与编程工具。

**残余超阈值 L2**（新纪律要求 >30 需拆同级兄弟，本次仍有两个）：`函数式MDP与异步动态规划(37)`、`奖励设计与状态价值分析(35)`（L2 节点数区间 **2~37**）。

**残余噪声未归类**：9 个未归类节点中 6 个为噪声/碎片节点（`unknown_content_segment`、`*_review`、`*_review_course1`），与 `TODO_Graph_Quality.md` 的 **GQ-7**（禁碎片节点）/ **GQ-12**（清历史噪声）同源。

**关于 AC-T2 的口径**：AC-T2 里"每个 L2 覆盖约 **10** 个知识点"是**容量口径**（一个二级主题大致能装多少），**不是硬上限**。原表述已被第 1 次迭代证明会引起误读（模型据此主动只放 10 个），这正是第 1 次覆盖率仅 42% 的根因；修 prompt 后改为"全量分配、容量为参考值"。

**数据结构侧 AC 实测（只读 SQL）**：
- **AC-T4 ✓**：多归属真实发生（存在节点归属 ≥2 个主题）。
- **AC-T3 ✓**：有归属的节点**恰好 1 个** `is_primary=1`；`nodes_not_exactly_1_primary=67` 全部是**无任何归属**的节点（65 个非本科 + 2 个未归类），符合 AC「无归属者除外」。

> 附注：第 2 轮**沿用既有命名（D3）确实生效**（沿用了第 1 轮的 15 个 L2 名）→ 结构缺陷会被继承，这正是必须修 prompt（而非只靠人工 `update_theme`）的直接证据。

## 13. 与既有文档的对齐（合并清单）

> 本节回答"本方案与图谱族已有文档的关系"：哪些结论**被修订**、哪些**保持不变**、哪些待办**被解锁**。
> 目的：消除两套说法。与本节冲突的旧表述以本节为准（并已在对应文档处加注）。

### 13.1 被修订的既有结论

| 文档 | 原表述 | 本方案的修订 |
|---|---|---|
| `论文与开源实现调研 §1.1` | "它的社区摘要、Leiden 聚类这些核心组件，对我们**没有意义**" | **拆分**：社区**摘要**仍不做；**聚类（分组）**现在要做 —— 但产物只是"主题 + 名字"，不是"摘要报告"。成本差约一个量级（见 §13.2 对照表） |
| `论文与开源实现调研 §3.1` | LightRAG 的"双层（低层实体 / 高层主题）"思想可借，且"我们的学科/板块两级恰好同构" | **修正**：`subject/board` 是**教学组织**（来源=文件夹/课名），**不是知识主题**；`themes` 才真正对应 LightRAG 的"高层主题" |
| `评审文档 KG-D7` | `nodes.parent_id` + `path`（part_of），章节点真实存在 | **取代**：层级**不进 `nodes`**（避免给章节点出题、污染统计与检索），改为独立 `themes` + `node_themes`；分级依据由"教材目录"改为"知识相关度" |

| `TODO_Graph_Quality GQ-9` | 启用 `board` 区分书籍来源、做主题隔离 | **关联**：层级分组由 `themes` 承担；`board` 去留见 §13.4 |

### 13.2 "聚类" 与 "社区摘要" 的精确区分（最容易混淆的一处）

| | GraphRAG 社区 | 本方案的 `themes` |
|---|---|---|
| 目的 | 给 Global Search 提供答案源 | **UI 分组/导航** + 将来给 AI 用 |
| 产物 | 社区 + **每个社区一段 LLM 摘要报告** | 主题 + **名字**（不写摘要） |
| 调用量 | 社区数 × 摘要调用（海量） | **一次调用产出整棵树** |
| 增量 | 不友好（新文档要重算社区） | 可重算；`source='human'` 保护人工修改 |
| 对图的影响 | 产生新的"社区节点/报告" | **不新增节点**，只新增归属关系 |

**结论**：`论文调研 §4.1`「不做 LLM 社区摘要」的结论**不变**，且我们仍然规避了那个成本坑；但「**聚类分组**没意义」这个引申结论**不成立**——因为我们的聚类不产生摘要、不产生节点。

### 13.3 保持不变的既有结论

| 结论 | 出处 | 为何不受影响 |
|---|---|---|
| 不做 LLM 社区摘要 | `论文调研 §4.1` / `§5 附` | 只要分组与命名，不写摘要（§13.2） |
| 不引入 Neo4j / GraphRAG 框架 | `论文调研 §4.3` | 仍是 SQLite 邻接表 + 派生表 |
| `edges` / `topological_sort` / `get_learning_path` 不动 | `评审文档 KG-D6/D9` | 主题层**不产生边**（§4.2） |
| L1/L2/L3 契约与不变量 | `参照系契约 §3` | 主题层属**容器**，不改角色定义 |
| 出题 / 掌握度 / RAG / 注入链路不变 | `AGENTS.md §2` | 不新增节点、不改 `nodes` 语义（§7） |
