## 0. 六个问题的答案（速览）

| 问题 | 一句话回答 |
|---|---|
| **长什么样** | 不是一张"图"，而是**四张关系表（`nodes` / `edges` / `node_aliases` / `mastery_events`）+ 三类派生索引（chunk 向量、稀疏关键词、MD 正文文件）**：元数据在 SQLite，正文在每节点一个 `.md` 文件，向量/全文在按用户分区的派生库里（§1） |
| **为什么这么选** | 因为图的**用途**是"每次调用的教学参照系 + 可审计的路径依据"，不是"从海量文本里找答案"。用途决定了它必须**小、稳、可解释、可增量、零额外服务**（§2） |
| **与行业比** | 与 GraphRAG 家族（图=检索索引）**路线不同**：我们不抽取式建图、不做社区摘要、不做 KGE 补边；与同类 AI Tutor 项目比，我们的**工程化程度更高**（用户级隔离 + 两级切片 + 闭环写回 + 别名层），但**缺多跳遍历/全局查询/评测**（§3） |
| **方便检索吗** | **单跳与结构化查询很方便**（有索引、有递归 CTE、SQL 示例见 §4），**多跳与全文排序不方便**（缺 `parent_id` 层级、缺按关系类型的图遍历、缺 FTS）——但瓶颈是**索引与检索策略**，不是"选错存储"（§4.4） |
| **准确率** | **结构正确性 100%（约束兜底）／检索可用（有实测口径）／去重分档明确／最短板 = 抽取质量无量化指标**（§5.3）；外部可比数字目前**为零**，这是要补的第一块 |
| **参考谁** | 见 §6：微软 GraphRAG（五张表 + text_unit 溯源）、Neo4j GraphRAG（Schema 系统 + 实体消解三档）、LightRAG（双层关键词 + 增量）、HippoRAG（PPR 多跳）、Zep/Graphiti（时间轴）、MOOCCubeX（先修评测集）、AI_Tutor（`kg_hop_depth` + 开/关对照） |

## 1. 数据结构全貌

### 1.1 DDL（唯一真值 + 状态标注）

```sql
-- ① nodes：知识点本体（元数据）              [已落地] 创建于 knowledge_graph.py:145-162
nodes(
  id               TEXT PRIMARY KEY,   -- 全局命名空间（跨用户唯一，见 §2.4 的取舍）
  name             TEXT NOT NULL,      -- 中文首选名（判重键 = normalize_node_name(name)）
  file_path        TEXT NOT NULL,      -- ⚠️ 装饰性残留：真实路径 = nodes/{user_id}/{id}.md
  tags             TEXT DEFAULT '[]',  -- JSON 数组：自由标签（KG-D2 起不再放难度档）
  subject          TEXT DEFAULT '',    -- 学科（KG-D1 新增：一等公民，取代"tags 首位"的位置约定）
  board            TEXT DEFAULT '',    -- 板块（学科下的一级分组名，扁平）
  summary          TEXT DEFAULT '',    -- 一句话摘要（注入/兜底检索用）
  mastery          INTEGER DEFAULT 0,  -- 掌握度 0-100（KG-D4 已加事件表 → 此处 = 当前值缓存）
  difficulty       INTEGER DEFAULT 3,  -- 难度 1-5（知识本体属性）
  estimated_minutes INTEGER DEFAULT 15,-- 预估学习时长（知识本体属性）
  added_by         TEXT DEFAULT 'human', -- human / ai（AI 权限护栏依据）
  created_at       TEXT,
  confidence       REAL,               -- 抽取置信度（当前 1.6% 填充，待赋能或删）
  user_id          INTEGER REFERENCES users(id)
)

-- ② edges：知识点之间的关系                  [已落地] 创建于 :165-178；KG-D6 已加时间戳 + 唯一索引
edges(
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  from_node  TEXT NOT NULL,   -- FK → nodes(id) ON DELETE CASCADE
  to_node    TEXT NOT NULL,   -- FK → nodes(id) ON DELETE CASCADE
  relation   TEXT NOT NULL,   -- prerequisite / related / confusion / extension（代码枚举 :1012）
  label      TEXT DEFAULT '', -- 人读标签（"前置知识"/"易混淆"）
  added_by   TEXT DEFAULT 'human',
  confidence REAL,
  user_id    INTEGER REFERENCES users(id),
  created_at TEXT,            -- [KG-D6] 建边时间（老行 NULL = 未知）
  updated_at TEXT             -- [KG-D6] 改 relation/label 时刷新
  -- [KG-D6] UNIQUE INDEX (user_id, from_node, to_node, relation) —— 把代码查重升为数据库约束
  -- 仍缺（刻意）：weight（无写入方）、sources（KG-D8）
  -- 无向语义约定（待拍板）：related / confusion 按 from_node < to_node 归一化存一行
)

-- ③ node_aliases：别名层（判重 L1.5 档）      [已落地 2026-09-23] 创建于 :183-192
node_aliases(
  alias_key  TEXT NOT NULL,   -- normalize_node_name(别名)：判定键
  node_id    TEXT NOT NULL,   -- FK → nodes(id) ON DELETE CASCADE
  user_id    INTEGER NOT NULL,
  source     TEXT DEFAULT 'ai',  -- ai（自名）/ merge（并轨继承）/ human（人工标）
  created_at TEXT,
  PRIMARY KEY (alias_key, user_id)   -- 先到先得；先建者胜
)

-- ④ mastery_events：掌握度证据链              [已落地 2026-09-23]（KG-D4）
mastery_events(
  id, user_id, node_id,         -- FK → nodes(id) ON DELETE CASCADE
  delta, before_val, after_val, -- 变更量 + 前后值（"为什么是 60 分"可回放）
  reason   TEXT NOT NULL,       -- quiz_correct / self_report / manual
  evidence TEXT DEFAULT '',     -- question:<id> 等外部凭证
  created_at TEXT
)
-- 唯一写入点 = KnowledgeGraph.update_node_info（5 条改 mastery 的路径全经它，与节点更新同事务）

-- ⑤ 索引                                     [已落地]
CREATE INDEX idx_nodes_user_subject ON nodes(user_id, subject);
CREATE UNIQUE INDEX idx_edges_unique ON edges(user_id, from_node, to_node, relation);
CREATE INDEX idx_mastery_events_node ON mastery_events(user_id, node_id);
```

### 1.2 派生索引（三类，按 user 分区，**不在 knowledge.db 里**）

| 派生库 | 结构 | 粒度 | 作用 | 锚点 |
|---|---|---|---|---|
| 节点正文 | `data/knowledge/nodes/{uid}/{id}.md` | 节点 | 讲解正文（五段式）；检索命中后取它 | `:105-106`、`get_node_content_preview:…` |
| 向量索引 | `data/rag/{uid}/rag.db` → `chunks(node_id TEXT, node_name, heading, content, chunk_index, embedding TEXT, user_id)` | **chunk** | 语义检索（余弦 top-k） | `rag/vector_store.py:40-51` |
| 稀疏/全文 | kb 用 whoosh（`data/kb/{uid}/whoosh_index/`，自定义 CJK bigram） | chunk | BM25 关键词检索（**目前只服务上传知识库，图谱侧未接**） | `hybrid_search/whoosh_index.py:61-70` |

> ⚠️ 一个容易误读的点：**"图谱"在检索上其实有两个粒度的承载物** —— 结构（nodes/edges，供注入与导航）与文本（MD chunk，供语义检索）。
> 二者用 `node_id` 关联，这就是为什么"改节点正文"必须同步 `invalidate_content_cache` + 重建该节点的 chunk 索引。

### 1.3 实体关系图（含分区与派生）

```
                    ┌──────────────────────── knowledge.db (全局单库) ────────────────────────┐
                    │                                                                        │
  users(id) ──1:N──>│  nodes(id, name, subject, board, tags, mastery, difficulty, …, user_id) │
                    │      │  ▲                                                              │
                    │      │  └──────── node_aliases(alias_key, node_id, user_id, source)      │
                    │      │                     (别名 → 本体，多对一)                        │
                    │      ▼                                                                 │
                    │  edges(from_node → to_node, relation, label, confidence, user_id)       │
                    │      relation ∈ {prerequisite, related, confusion, extension}           │
                    └────────────────────────────────────────────────────────────────────────┘
                             │ node_id                    │ node_id
                             ▼                            ▼
        data/knowledge/nodes/{uid}/<id>.md        data/rag/{uid}/rag.db :: chunks
                （正文 = 教学内容本体）               （向量 = 语义检索索引，可重建）
```

**语义约定（全库统一，写进 docstring 的三条）**
1. **边方向**：`A → B (prerequisite)` 表示 **A 是 B 的前置**（先学 A）→ 查前置要沿边**反向**走（`get_prerequisites` 的递归 CTE）。
2. **学科归属**：`subject` 列（KG-D1 后），空则回退"tags 第一个非难度标签"（兼容存量）。
3. **同名并轨**：`normalize_node_name` 归一后相同（同用户、同学科或未归档）→ 不新建，只并入正文，**并返回实际落点 ID**（调用方必须用返回值建边）。

### 1.4 一条数据的一生（把结构串起来看）

```
教材 PDF ──kb 解析──> 章节/单元文本 ──graph_generator(LLM)──> {节点 + 边 + tags/subject/board}
   │                                                                    │
   │                                                     create_node_with_content()  ← 唯一写入口
   │                                                      ├─ L1 精确同名 → 并轨（返回已有 id）
   │                                                      ├─ L1.5 别名   → 并轨（node_aliases）
   │                                                      └─ 新建 → nodes 行 + nodes/{uid}/{id}.md
   ▼
对话检索：build_graph_context（每次注入全量框架，超 12000 字符降级）
        + rag_manager.search（向量；嵌入失败 → _keyword_search 兜底）
        + _expand_prerequisites（沿 prerequisite 反向扩跳，默认 0 跳）
   │
   ▼
LLM 回答 → 写回（graph_analyzer / agent 工具）→ 更新 nodes/edges/MD → graph_updated 事件 → 前端刷新
```

## 2. 为什么选这种结构（逐决策：选了什么、放弃了什么、什么时候该改）

| # | 决策 | 放弃了什么 | 选它的理由 | 什么时候该改 |
|---|---|---|---|---|
| 2.1 | **关系库邻接表（SQLite）而非图数据库** | Cypher 声明式多跳、GDS 图算法、原生 PPR | 规模 = **单用户 10²–10³ 节点 / 10³ 边**；Docker 单容器不增服务；递归 CTE 已能表达先修链与拓扑序；迁移/备份 = 一个文件 | 需要**频繁多跳遍历 + 图算法**（PPR、社区检测）且单图 >10⁵ 节点时 |
| 2.2 | **`nodes` + `edges` 两张表，而非 RDF 三元组表** | 谓词可任意扩展、W3C 标准互操作 | 我们的"属性"是**字段**（mastery/difficulty/subject），不是**可无限增长的谓词**；两表能加索引、能写约束 | 要接入外部本体（如按 CELTSC 标准交换）时，可加一层导出，不必改存储 |
| 2.3 | **正文存 MD 文件，元数据存库** | 全文 SQL 检索、事务一致性 | 正文是"教学内容"，需人工可读可编辑、可 diff、可版本化；库只放**可索引的结构化字段** | 正文需要**全文检索排序**时，加 FTS 索引（不必搬进库） |
| 2.4 | **`id` 为 TEXT，全局唯一（非 per-user）** | 用户内命名自由 | 改 `(user_id,id)` 复合主键要动 21 个端点 + 前端 + 全部跨表引用，收益仅"少一次全局查重" | 只有当**跨用户共享知识库**成为需求时才值得改 |
| 2.5 | **学科升为 `subject` 列（KG-D1，2026-09-23）** | 少一列、少一次迁移 | 学科要参与**过滤/统计/隔离**三件事 → 必须是列；原"tags 首位"是位置约定，schema 无法约束、无法索引 | 已改，无需回退 |
| 2.6 | **`part_of`（层级）与 `prerequisite`（依赖）分离** | 只用一种边更简单 | 两者语义正交：章包含节 ≠ 节是章的前提；混用会同时破坏组织与学习顺序（现在只有后者，`parent_id` 待做 KG-D7） | 层级上线后会带来"章节点"还是"虚拟路径"的取舍（见评审文档 §8 待拍板） |
| 2.7 | **别名单独建表，而不是给 nodes 加 `aliases` JSON 列** | 少一张表 | 别名要**反查**（这个写法归哪个节点？）→ 需要索引与唯一约束；JSON 列无法高效反查，且无法约束"一个写法只归一主" | 若要支持跨用户共享别名，主键需加维度 |
| 2.8 | **掌握度保留在 `nodes.mastery`，另加事件表（KG-D4 计划）** | 彻底外移到 `user_node_mastery`（更"正确"） | 外移要动 21 个端点 + 前端；而事件表已能回答"谁改的、凭什么、何时" —— **收益的 80% 用 20% 的改动拿到** | 出现"一个知识点被多个学习者共用"的真实需求时（当前每用户一张图，暂不需要） |
| 2.9 | **不做 KGE 补边 / 不做社区摘要** | GraphRAG 系的"全局问题"能力 | KGE 补边会产生**不可解释的边**，与"可审计的路径依据"目标冲突；社区摘要要海量 LLM 调用且**增量不友好**，而我们的图不是从文本抽的（`论文与开源实现调研 §2.5 §1.1`） | 若要做"整本书在讲什么"的全局问答，需另建**只读**的社区/主题层，不污染教学图 |
| 2.10 | **注入 = 全量框架 + 字符预算降级，而非检索式注入** | 省 token | 契约要求图谱**每次都在**（参照系语义）；检索式注入会让"约束"变成"命中才约束" | 选片能力（KG-D11）上线后可改为**按学科/层级选片**（仍是"选片"，不是"检索"） |
| 2.11 | **三档去重（精确 → 别名 → 语义）而非单一 LLM 判定** | 更少代码 | 精确档零成本零误判、能挡住绝大多数重复；语义档贵且依赖嵌入（当前欠费）→ 分档可在任一层降级仍可用 | L3 语义档恢复后按 `dedup_status` 暴露质量 |
| 2.12 | **每条边只有一个 `relation`（枚举 4 值），不引入权重语义**（`weight` 待加） | 更细的关系类型（如 5 类 12 种） | 类型越多，LLM 抽取时的混淆与人工维护成本越高；4 类覆盖教学主需求，且**放宽是兼容的**（加枚举值不影响存量） | 多源融合需要表达"有多强"时加 `weight`（与 `confidence` 分工：对错 vs 强弱） |

## 3. 与行业方案对比

### 3.1 先说结论：我们和主流不是同一条路线

`论文与开源实现调研 §0` 已给出三分法，本文补**数据模型视角**：

| 路线 | 图是什么 | 数据模型的典型形态 | 我们 |
|---|---|---|---|
| A 检索索引 | 图 = 索引 | 实体表 + 关系表 + **文本单元表 + 社区表**（溯源与聚合是刚需） | ✗ 不是这条 |
| B 教学参照系 | 图 = 可行域与坐标系 | **知识点本体 + 先修关系 + 学习状态**（状态必须能与本体分离） | ✓ 我们在这条 |
| C Agent 记忆 | 图 = 记忆 | **带时间轴的事实**（valid_from/valid_to）+ 增量写入 | ⚠️ 部分（KG-D4 事件表是它的轻量版） |

### 3.2 逐项对比（数据模型维度）

| 维度 | 本项目 | 微软 GraphRAG | LightRAG | Neo4j GraphRAG | Zep / Graphiti | MOOCCubeX / EduKG | 同类 AI_Tutor |
|---|---|---|---|---|---|---|---|
| 图来源 | **AI 从教材抽取 + 对话写回 + 人工建** | LLM 从文本抽 | LLM 抽 | LLM 抽（可带 Schema 约束） | 从对话增量抽 | 人工/规则 + 教材（EduKG 407 本教材、23.7 万知识点）【二手】 | LLM 抽三元组 |
| 图角色 | **教学参照系**（每次注入） | 检索索引 | 检索索引 | 检索索引 | Agent 记忆 | 教学资源组织 | 检索索引 |
| 节点模型 | 知识点（id/name/subject/board/tags/难度/时长） | `entities(id,title,type,description,text_unit_ids)` | entity + 描述 + 向量 | `(:Entity)` + 动态属性 | 实体 + **时间属性** | 知识点 / 教学资源 / 教学设计（三层）【二手】 | `[实体,关系,实体]` 三元组 |
| 边模型 | `edges(from,to,relation,label,confidence)` + **`created_at`/`updated_at` + 唯一约束**（KG-D6） | `relationships(id,source,target,description,weight,text_unit_ids)` | relation + 描述 + 权重 | `[:RELATED]` + 属性 + **向量索引** | 事实 + valid_from/valid_to | 先修关系（数学/心理/CS 含人工标注） | 三元组 |
| 层级（part_of） | ⚠️ 仅扁平 `board`（`parent_id` 待做 KG-D7） | 有 community 层级（聚类，非目录） | 低层实体/高层主题 | 由 Schema 定义 | ✗ | **有**（章节树/知识点树） | ✗ |
| 别名/实体消解 | **L1 精确 + L1.5 别名**（零嵌入）；L2 未做；L3 嵌入恢复后可用 | LLM 抽取时合并 | LLM 抽取时合并 | **三档：精确属性 → 语义 0.85–0.95 → 模糊**（`neo4j-graphrag-python`，本仓库 `TODO_Graph_Quality §6` 亦引） | LLM 裁决 | 人工/规则 | ✗ |
| 学习状态 | `nodes.mastery`（当前值）+ **`mastery_events` 事件表**（谁改的/从多少到多少/凭什么，2026-09-23 落地） | ✗（无学习者维度） | ✗ | ✗ | ✗（但有时序能力） | 有学习者画像/行为（2.96 亿行为） | ✗ |
| 溯源粒度 | ⚠️ 节点级（`file_path` 装饰性；`sources` 待做 KG-D8） | **text_unit 级**（每实体/关系挂 `text_unit_ids`） | chunk 级 | 可挂 chunk | 对话轮级 | 资源级 | ✗ |
| 存储 | SQLite（+ MD 文件 + 派生向量库） | Parquet + 向量库 | KV + 图 + 向量三存储 | Neo4j（原生图库） | Neo4j/图库 | 图库/关系库 | **Excel**（`knowledge_graph.xlsx`） |
| 检索 | 全量注入 + 向量 + prerequisite 反向扩跳 | Local / Global / DRIFT | **双层关键词** + 增量 | 向量 + 全文 + 图遍历 + 混合重排 | 时序召回 | 服务于推荐/诊断 | 向量 + **`kg_hop_depth` 图遍历** |

> 表中外部实现的具体字段名与阈值：GraphRAG 五张表的**存在**为【二手】多篇交叉印证，字段名为【常识】级的普遍描述；Neo4j 三档消解引自本仓库既有调研的核实结论；
> Zep / LightRAG / HippoRAG 的定性描述见 `论文与开源实现调研 §1.3 §3.1`。**具体性能数字一律未核实，勿引用。**

### 3.3 我们明显更弱的地方（诚实清单）

| 缺口 | 业界怎么做的 | 我们的现状 | 对应改造项 |
|---|---|---|---|
| **多跳检索** | HippoRAG 用 PPR 一步多跳；AI_Tutor 用 `kg_hop_depth` 沿边扩跳 | 只有沿 `prerequisite` **反向**扩跳（`_expand_prerequisites`），且默认 0 跳 | KG-D9（按关系分策略） |
| **全局/主题查询** | GraphRAG 的社区摘要（Global Search） | 无（**且短期不需要**：我们的图是教学结构，不是文档集合） | 明确不做 |
| **溯源粒度** | 实体/关系挂 `text_unit_ids`，可指到段落 | 节点级，`file_path` 还是装饰性的 | KG-D8 |
| **实体消解覆盖** | 三档串联 + 批量上下文聚类（arXiv:2506.02509） | 只做了 L1/L1.5（零嵌入）；L2 缺失；L3 语义档随**嵌入恢复**（2026-09-23）重新可用 | KG-D3 已补一档；L2/L3 见 `TODO_Graph_Quality §2.2` |
| **层级/目录结构** | 教育图谱普遍有章节树；EduKG 有教材-知识点映射 | 只有 `board` 一级扁平分组 | KG-D7 |
| **端到端评测** | 同业用"KG-RAG vs 纯 RAG"模式切换做 A/B（AI_Tutor） | **已有** `scripts/eval_graph_injection.py`（图谱开/关 A/B，单变量、指标零额外 LLM 调用）：首跑命中率 25.0% → 62.5%；2026-09-23 扩到 **14 例**并修正口径后重跑，**公平口径下两组持平（39.0% vs 36.6%）**，但关闭组仍有 42 次徒劳检索、2 例状态误述、token 多 65%（`知识图谱_P1扩跳与AB对照实验.md §8`） | 指标仍是**代理口径**；⚠️ 两次结论相反 → 需多次重复取均值，见 §5.5 |

### 3.4 我们更强或与众不同的地方（可以自信讲的部分）

1. **用户级图谱隔离**：`KnowledgeGraph(user_id)` 每人一张图 —— 同类开源多数是全局单图（`论文与开源实现调研 §4.1`）。
2. **图既读又写**：对话中发现新知识点写回同图（GraphRAG 系普遍只读）。
3. **教学语义分级**：`subject → board` 两级分组对应教学组织（LightRAG 的"双层"是检索语义层，我们的更可解释）。
4. **不做社区摘要 = 省掉最大的成本坑**，且图不是文本抽的 → 无需为"抽取准确率"付出二次 LLM 校验成本（代价见 §5.3）。
5. **可审计**：结构约束（无悬空边/自环/重复边/先修环）+ 每次运行可凭 `run_id` 回源完整输入输出（参照系契约 AC-L3-1）。
6. **零额外服务**：SQLite + 文件 + 派生库，单容器可跑（对比 Neo4j 系要加一个服务）。

## 4. 方便检索吗？—— 能力矩阵

### 4.1 现在就能高效做的（附真实 SQL）

```sql
-- ① 先修链（递归 CTE，实现在 get_prerequisites）
WITH RECURSIVE chain AS (
  SELECT from_node, 1 AS depth FROM edges
   WHERE to_node = ? AND relation='prerequisite' AND user_id = ?
  UNION ALL
  SELECT e.from_node, c.depth+1 FROM edges e JOIN chain c ON e.to_node = c.from_node
   WHERE e.relation='prerequisite' AND e.user_id = ?
) SELECT DISTINCT from_node FROM chain;

-- ② 学习顺序（Kahn 拓扑，实现在 topological_sort，Python 侧）

-- ③ 学科/板块切片（KG-D1 后走索引，不再是全表 Python 过滤）
SELECT * FROM nodes WHERE user_id = ? AND subject = ? AND board = ?;

-- ④ 别名/同名定位（KG-D3）
SELECT node_id FROM node_aliases WHERE alias_key = ? AND user_id = ?;

-- ⑤ 节点邻域（注入降级时的 focus 邻域）
SELECT * FROM edges WHERE user_id=? AND (from_node=? OR to_node=?);

-- ⑥ 关键词兜底（KG-D5，嵌入不可用时的通路）
SELECT * FROM nodes WHERE user_id=? AND (name LIKE ? OR summary LIKE ?);
```

### 4.2 检索通路一览（谁在什么时候用哪条）

| 通路 | 触发 | 检索方式 | 粒度 | 现状 |
|---|---|---|---|---|
| 参照系注入 | **每次调用** | 全量框架渲染 + 字符预算降级（12000 字符） | 节点 + 边 | ✅ 已上限控制 |
| 图谱语义检索 | `rag_search` / 对话按需 | 向量余弦 top-5（`MIN_SCORE 0.25`）+ prerequisite 反向扩跳 | chunk | ⚠️ 嵌入欠费 → 走兜底 |
| 图谱关键词兜底 | 嵌入失败时自动 | name/summary 子串（0.35/0.30） | 节点 | ✅ 2026-09-23 新加 |
| 图谱切片 | 图谱页 | `subject` / `board` 两维 | 子图 | ✅（对话链路未接，缺"当前位置"信号） |
| 上传知识库 | 对话按需 | 向量 + whoosh BM25 → RRF → top-5 | chunk | ✅（嵌入恢复后双路齐全；欠费期间入库的 NULL 向量块需重传才恢复向量召回） |

### 4.3 不够方便、需要改造的查询

| 查询 | 现在的代价 | 缺什么 | 改造项 |
|---|---|---|---|
| "第 5 章下的所有节点" | **做不到**（无层级字段） | `parent_id` / `path` | KG-D7 |
| "沿 related/confusion 走 2 跳" | 只能手写邻接（只实现了 prerequisite 一种） | 按关系类型的遍历检索 | KG-D9 |
| "全库按关键词排序找" | 无 BM25（whoosh 只覆盖 kb） | FTS5 | KG-D12 |
| "上周改过哪些节点" | ~~做不到~~ → ✅ 可查（`nodes.updated_at`，2026-09-23 落地） | — | 已完成 |
| "两个源命中的结果统一排序" | 余弦 vs RRF 分**量纲不同**，只能拼段落 | 跨源 RRF | KG-D10 |
| "这个知识点被哪本书哪一页支撑" | 只能到节点 | `sources` | KG-D8 |

### 4.4 判断：结构不是检索的瓶颈

- **规模**：单用户 10²–10³ 节点、10³ 边；SQLite 带索引的等值/范围查询与递归 CTE 在这个量级**毫秒级**，全表扫描（如兜底子串匹配）也在可接受范围。【已核实：`_keyword_search` 每次遍历 `kg.nodes`，规模约束已在 docstring 写明】
- **"缺索引"清单已清到只剩一项**：`subject` 列（KG-D1 已补）→ `updated_at`（2026-09-23 已补节点与边）→ **仍缺 FTS（排序维度，KG-D12）**。
- **一句话**：在"每个用户一张小图 + 每次都要注入框架"这个场景下，**关系库邻接表是合适的**；真正需要图数据库的是"单图很大 + 频繁多跳 + 要图算法"的场景（我们不是）。

## 5. 准确率

### 5.1 先分清四层"准确率"（混在一起谈没有意义）

| 层 | 指标 | 我们现在的数字 | 证据强度 |
|---|---|---|---|
| ① **结构正确性** | 悬空边 / 自环 / 重复边 / 先修环 | **全 0** | 【已核实】体检 `inspect_graph_quality.py --user 5`；⚠️ 靠代码约束兜底（`add_edge` 校验），**不是模型判得准** |
| ② **抽取质量**（节点/边的知识正确性） | 无直接指标；代理指标：正文中位长度、空壳率、同名组数、主题污染数 | uid5：正文中位 **213 字**、<200 字 **43.4%**、同名组 **23**、tags 杂标签 6 类 | 【已核实】`TODO_Graph_Quality §0.1`。**这是最短板：没有"正确率"这个数** |
| ③ **去重/对齐** | 精确率（误合并率）、召回率（漏合并率） | L1 精确档 = **结构上零误判**（归一化相同才合并）；L1.5 别名档精确但覆盖率取决于登记；L2 缺失；L3 语义档随嵌入恢复重新可用（2026-09-23） | 【已核实】代码 + 体检 |
| ④ **检索质量** | Recall@k / MRR | 见 §5.2（口径齐、数字有，但**是 mock 嵌入 + 特定数据集**） | 【已核实】但适用范围有限 |
| ⑤ **学习效果**（端到端） | 图谱开/关对照下的答案质量 | **已做**：首跑 25.0% → 62.5%，2026-09-23 扩到 14 例 + 修正口径后重跑 → **公平口径持平（39.0% vs 36.6%）**，关闭组代价更高（token +65%、42 次徒劳检索、2 例状态误述）。口径/数字/坑见 `知识图谱_P1扩跳与AB对照实验.md` §4+§8 | 【已核实】⚠️ **两次结论相反** → 只能当"机制有效、覆盖未见提升"的方向性证据 |

### 5.2 已有的实测数字（**用之前必须看它的适用边界**）

**(a) 检索质量**（`backend/eval_data/report_mock.json`，CMRC2018 trial，1000 queries）【已核实】

| 策略 | Recall@1 | Recall@3 | Recall@5 | MRR |
|---|---|---|---|---|
| 纯向量（mock hash） | 0.470 | 0.603 | 0.669 | 0.545 |
| 纯 BM25 | **0.964** | 0.986 | 0.989 | 0.975 |
| hybrid（RRF，生产默认） | 0.766 | 0.880 | 0.936 | 0.828 |
| fuse（线性 0.6/0.4） | 0.818 | 0.902 | 0.959 | 0.869 |

> ⚠️ **三条边界，缺一条就会误用**：
> 1. **mock 嵌入**（字符 bigram hash），**不是** text-embedding-v4 的真实表现 → 不能当作"我们的向量检索准确率"；
> 2. CMRC2018 是抽取式阅读理解，**query 与原文有大量字面重叠** → BM25 天然占优（0.964），**不能外推到**"学生口语提问"场景；
> 3. 它测的是 **kb（上传文档）**通路，不是图谱通路。
>
> **它能支持的结论只有两条**：① 混合检索优于单路向量；② **关键词通路是刚需**（正是 KG-D5 加兜底的旁证）。

**(b) 先修关系**（`backend/eval_data/report_prereq.json`，内置 8 条人工 gold）【已核实】

| 口径 | P | R | F1 |
|---|---|---|---|
| 基线（LLM 直接给的边） | 0.833 | 0.625 | 0.714 |
| **多准则新增** | **1.000** | **1.000** | **1.000** |
| 合并（基线 ∪ 新增） | 0.889 | 1.000 | 0.941 |

阈值扫描显示 **0.20–0.40 是稳定平台期**（P=R=1.0），默认 0.30 落在平台中部（非拟合点）。
> ⚠️ 8 条 gold，是**回归自检与口径固化**，不是统计结论；外部可比评测需 MOOCCubeX 实数据（尚未下载）。

### 5.3 与业界口径对照（我们缺哪个数）

| 业界指标 | 业界做法 | 我们的位置 |
|---|---|---|
| 实体消解阈值 | 语义档 0.85–0.95（Neo4j GraphRAG，本仓库 `TODO_Graph_Quality §6` 引） | 语义档**未启用**（嵌入欠费）→ 当前只能用零嵌入的 L1/L1.5 |

### 5.4 为什么"准确率"目前说不高：三个结构性原因

1. **图的产出方是 LLM，且没有 gold**：`graph_generator` 抽质量只能靠"正文够不够深/有没有碎"这类代理指标（GQ-5/6 已在改），正确性无从度量。
2. **本该兜底的语义档长期欠费失效（2026-09-23 恢复）**：设计上是"精确 → 语义"两道闸，欠费期只剩第一道（L1.5 别名是补的，覆盖靠事件驱动）；恢复后 L3 可重新启用，但**历史欠费期的漏合并已形成存量**（体检仍报 23 组同名）。
3. **评测对象错位**：现有评测脚本测的是 **kb 检索**与**先修推断**，**图谱自身的检索质量还没测过**。

### 5.5 补齐顺序（按"性价比"排，可直接接着做）

| 优先级 | 做什么 | 产出 |
|---|---|---|
| 1 ✅ | ~~**图谱开/关 A-B 对照**（同一组问题，注入图谱 vs 不注入；统计知识点覆盖度 + 幻觉率）~~ → **已有实现**：`scripts/eval_graph_injection.py`（+ 14 例数据集 + 报告）。**剩余**：把"幻觉率"从代理口径升级为人工标注样本 | 参赛材料最需要的量化证据 ✅；顺带验证参照系契约 L1 |

## 7. 不确定与待核实（诚实清单）

1. 上表外部实现的**字段名/阈值**多为【二手】或【常识】，写入参赛材料前需回原文核对（`论文与开源实现调研` 的引用纪律同样适用）。
2. §5.2 的两个数字各有硬边界（mock 嵌入 / 8 条 gold 样本），**不可外推**。
3. `subject` 回填会把存量**已污染**的 tags 原样带进 `subject`（回填=现状口径）→ 收益是"从此可用 SQL 查出并修"，不是"数据变干净了"。
4. CELTSC 基础教育知识图谱标准与我们的 `subject/board/tags` 是否冲突 **未核查**（涉及材料合规表述）。
5. "图谱小 → 不需要图数据库"的判断依赖规模不增长；若未来做**跨用户共享知识图谱**，结论需要重估（评审文档 §8 待拍板）。
