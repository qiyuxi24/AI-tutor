## 1. P0-A：按学科导出恒为空

### 根因
`backend/app/api/v1/knowledge.py` 的 `export_knowledge` 用 `n.get("subject") == subject` 过滤，但：
- `nodes` 表**没有 subject 列**，节点 dict 里也不存在 `"subject"` 键；
- 学科是从 `tags` 推导的（`KnowledgeGraph.node_subject()` 是唯一权威实现）。

→ 任何带 `subject` 参数的导出都恒返回空文件。

### 修复
```python
# 学科归属只能由 node_subject 从 tags 推导：nodes 表没有 subject 列
nodes = [n for n in nodes if kg.node_subject(n) == subject]
```

### 顺带发现的第二个缺陷（同一路径，本会 500）
修好过滤后，回归测试立刻暴露：`Content-Disposition: attachment; filename=数据结构-export.md`
—— HTTP 头只能是 latin-1，**学科名是中文就抛 `UnicodeEncodeError`**，整条导出链路直接 500。

修复：改用 RFC 5987 的 `filename*=UTF-8''<percent-encoded>`。

```python
headers={"Content-Disposition": f"attachment; filename*=UTF-8''{quote(filename)}"}
```

> 结论：P0-1 表面是"过滤写错"，实际是"**该功能对中文用户从不可用**"——过滤让它返回空文件，就算过滤对了也会 500。

## 2. P0-B：掌握度分档收敛为四档

### 根因
同一份 `mastery`（0~100）在三处用了三套口径：

| 位置 | 旧口径 | 后果 |
|---|---|---|
| 前端 `ForceGraph.masteryLevel` | 0 / 1-29 薄弱 / 30-69 学习中 / ≥70 已掌握（四色） | — |
| 后端 `graph_middleware._bucket` | 0 / 1-69 学习中 / ≥70 已掌握（**三档**） | 1~29 分的节点在图谱上是红色"薄弱"，在仪表盘里被算进"学习中" |
| 后端 `weak_points` | `mastery < MASTERY_LEARNING(=1)` → 只剩 0 分 | 注释写"0 或 <30"，实现只统计 0 分 |

而且 `graph_middleware` 的注释当时**谎称**"与前端四色语义保持一致"。

### 修复思路：确立唯一真值源，而不是两边各改一处
后端补出缺失的"薄弱"档（而不是把前端的四档压成三档）—— 因为**四档才是真实产品意图**：
节点红/黄/绿三色是有意义的教学信号，且 `weak_points` 的注释本身指向 `<30`。

```python
MASTERY_WEAK = 30         # 1 ~ 29 薄弱（已开始学但未入门）
MASTERY_MASTERED = 70     # ≥70 已掌握

def mastery_bucket(mastery) -> str:   # 全库唯一分档实现
    m = int(mastery or 0)
    if m >= MASTERY_MASTERED: return "mastered"
    if m >= MASTERY_WEAK:     return "learning"
    if m >= 1:                return "weak"
    return "unstarted"
```

连带修正：
- `_subject_stats` 新增 `weak_count`（四档计数之和 = 节点总数，可自校验）；
- `weak_points` 改用 `< MASTERY_WEAK`（即 0~29，"待补强"语义）；
- 前端 `DashboardView` 补齐"薄弱"档（卡片 + 分布条 segment + 图例 + 学科行），并把"未开始"配色从红改为中性灰（与图谱配色对齐）；
- 前端 `ForceGraph.masteryLevel` 与后端常量互相注释指向对方，形成**显式跨端契约**。

> 契约的固化方式：后端 `test_mastery_bucket_boundaries` 把 0/1/29/30/69/70/100 七个边界值钉死；
> 今后任一端改阈值，测试或代码注释会立刻暴露不一致。

## 3. P0-C：多准则无监督先修推断（核心）

### 3.1 问题：为什么不能只靠 LLM 直接给先修边

现状是 LLM 生成图谱时一次性输出 `prerequisite` 边，问题是：

| 问题 | 后果 |
|---|---|
| 不可复现 | 换个模型/温度，边就变了，无法回归 |
| 不可解释 | "为什么 A 是 B 的前置？"答不出，无法人工复核 |
| 不可量化 | 无法说"我们的先修关系准确率是 X%" |
| 易遗漏 | 单次生成只看当前上下文，跨章节的隐含前置关系抓不到 |

学术界把这件事叫**概念先修关系识别（Concept Prerequisite Relation, PR）**，已有成熟的无监督路线。

### 3.2 方法族 → 本项目的落地映射

参照 Alatrash et al., IJCKG 2025（**arXiv:2509.05393**）的**多准则投票**：对每个有序对 (A, B)，
让多条**互相独立**的准则各自投票，加权汇总后过阈值才认定。

论文四族特征 → 我们没有 Wikipedia 超链接、也没有标注数据，因此做了诚实映射：

| 族 | 论文信号 | 本项目准则 | 我们用什么代替 |
|---|---|---|---|
| 链接族 | Wikipedia 超链接结构 | **C1 正文引用** | 节点 MD 正文中的术语引用（不对称计数） |
| 文本族 | 术语构成 / 难度 | **C2 名称包含** / **C6 难度差** | 同上，直接可用 |
| 文本族 | 语义距离 | **C5 嵌入相似度** | text-embedding-v4（相似度过高 → **反对**，那是同义词） |
| 图族 | 邻域结构 | **C4 共同前置邻居** | 已有 prerequisite 结构（同层概念 → **反对**） |
| 文档族 | 文档内位置 | **C3 次序** | 教材次序（显式传入）；缺省用 `created_at` 近似 |

**缺失信号一律弃权，不猜**——这是与论文的关键差异，也是本方案能保持精度前提。

### 3.3 准则明细（方向 = 支持 A→B）

| 准则 | 权重 | 投 +1（支持 A→B） | 投 -1（反对） | 弃权条件 |
|---|---|---|---|---|
| C1 正文引用 | 3.5 | 讲 B 的正文引用 A 名 N 次 > 反向 | 反向引用更多 | 双方正文互不引用 |
| C2 名称包含 | 2.5 | `A.name ⊂ B.name`（"树" ⊂ "二叉树"） | 反向包含 | 名称相同/为空 |
| C5 语义相似 | 2.0 | —（不做正向证据） | 相似度 ≥ 0.90（疑似同一概念） | 嵌入不可用或相似度低 |
| C4 共同前置 | 1.5 | — | 共同前置 ≥2 且无包含关系且 Jaccard ≥ 0.5 | 见 §3.5 踩坑 |
| C3 次序 | 1.0 | A 在教材/入库次序更早 | B 更早 | 次序缺失或相同 |
| C6 难度差 | 1.0 | `difficulty(A) < difficulty(B)` | 反向 | 难度相同 |

### 3.4 打分与决策

```
score = Σ(权重ᵢ × 投票ᵢ) / Σ(全部权重)        # 分母固定 = 11.5，值域 [-1, 1]
候选条件：score ≥ threshold（默认 0.30）
```

**为什么分母固定而不是"只除参与投票的准则"**：固定分母让分数变成一种**绝对证据强度**
（全准则同向 = 1.0），从而**只需要一个旋钮**（threshold）就能控制召回/精度；
若按参与准则归一，一条弱准则单独出现也能得 1.0，就必须再加"最小支持权重"第二个旋钮。

按此设计，阈值 0.30 的语义很清楚：
- 一条强准则（C1=3.5）单挑 → 0.304，**刚好成立**；
- 一条中等准则 + 一条弱准则（C2+C6=3.5）→ 0.304，**成立**；
- 只有弱准则（C6+C3=2.0）→ 0.174，**不成立**（避免"难度低就是前置"这种噪声）。

### 3.5 关键设计决策与踩坑记录

| # | 决策 | 为什么 |
|---|---|---|
| 1 | 提取 `infer_prerequisites` 为**纯函数**（不碰 DB、无副作用） | 评测脚本、API、未来的 graph_generator 三处复用；单测无需建库 |
| 2 | 权重"人为设定"而非学习得到 | 没有标注数据可训练；且权重可解释（可写进材料）比拟合更重要 |
| 3 | C4 从"共享 1 个前置就反对"改为**"≥2 个且无包含关系"才反对** | 实测踩坑：`A→B`、`A→C` 并存时，B、C 的前置集合都是 `{A}`，旧的 Jaccard 规则直接**杀掉正确的传递边 B→C**（"共享 1 个前置"无法区分兄弟与链式，弃权才是诚实的） |
| 4 | 单字概念（栈/树/图）在"正文引用"中要求**≥2 次命中** | 中文无词边界："树"会命中"二叉树"、「树是递归结构」两次。若直接屏蔽单字名会丢掉大量核心概念（栈/树/图）→ 折中为计数门限 |
| 5 | 结果按分数降序**贪心加边 + 保 DAG** | 先修关系有环则学习路径无法拓扑排序。`add_edge` 内部虽也有环检查，但那是"抛异常"，这里提前过滤避免噪声边互相污染 |
| 6 | 已存在**间接路径**的边直接丢弃（跨跳冗余） | `A→B→C` 已成立时再补 `A→C` 只增加视觉噪声，不增加信息 |
| 7 | 单节点入度上限 5（`max_parents_per_node`） | 枢纽概念（如"变量"）会被大量弱证据指向，上限直接约束假阳性破坏面 |
| 8 | 文档族次序默认用 `created_at` 近似 | `generate_subject_graph` 按「书序 × 分块序」写库，入库顺序≈扫读顺序；但它是**近似**（手动建的节点会打乱），故只给 1.0 权重，并允许 `order=` 覆盖 |

### 3.6 代码地图

| 位置 | 作用 |
|---|---|
| `backend/app/core/prerequisite.py:56-70` | 权重、阈值、相似度门限等全部常量（改这里=调行为） |
| `:81-115` | `Vote` / `PrereqCandidate`（边 + 逐准则证据 + `to_dict`） |
| `:118-160` | `_Context`：一次推断的预计算（名称/正文/次序/已有 prerequisite 结构） |
| `:164-256` | 六条准则（每条一个函数，签名统一 `(a, b, ctx) -> Vote`） |
| `:283-350` | `infer_prerequisites`：打分 → 排序 → 贪心接受（跨跳过滤 + 保 DAG + 入度上限） |
| `:352-365` | `_reachable`：BFS 判可达（跨跳与环检测共用） |
| `:367-395` | `apply_candidates`：唯一写库入口，逐条容错（重复/成环/权限失败只跳过该条） |

### 3.7 接口契约

```
POST /api/v1/knowledge/prerequisite/infer
body: { subject: "数据结构", threshold?: 0.30, max_parents?: 5, apply?: false }
resp: { subject, node_count, candidate_count,
        candidates: [{from, to, from_name, to_name, score, votes: [
            {criterion, value, weight, reason}]}],
        applied?: {created: [...], skipped: [{from, to, reason}]} }
```

- 默认 `apply=false`（dry-run）：只出候选与证据，**不改图谱**。
- `apply=true` 时写入 `prerequisite` 边（带 `confidence=score`）。
- **AI 护栏仍然生效**：`KnowledgeGraph.add_edge` 规定 AI 不能在「两端都是人类创建」的节点之间加
  `prerequisite` 边 —— 这类边会以 `PermissionError` 进入 `skipped`，是**预期行为**而非失败。

## 4. P0-D：先修关系离线评测

### 4.1 为什么评测口径要分三档

第一版评测把"已有边"当作已知输入，导致召回虚低（自己把自己当漏检）。正确口径是分三档：

| 档位 | 比什么 | 回答什么问题 |
|---|---|---|
| `baseline` | 现有 LLM 给的 prerequisite 边 vs 全部 gold | 现状基线有多好 |
| `added` | **本模块新补的边** vs 「基线漏掉的那部分 gold」 | **补得对不对 + 漏检补全率** ← P0 的核心指标 |
| `merged` | 基线 ∪ 新增 vs 全部 gold | 管线跑完后的图谱整体质量 |

### 4.2 实测结果（内置样本，`--embed mock`，阈值 0.30）

| 学科 | gold | 基线 P/R/F1 | 新增 P/R/F1 | 合并 P/R/F1 |
|---|---|---|---|---|
| 数据结构 | 6 | 1.000/0.667/0.800 | **1.000/1.000/1.000** | 1.000/1.000/1.000 |
| C语言 | 2 | 0.500/0.500/0.500 | **1.000/1.000/1.000** | 0.667/1.000/0.800 |
| **micro-avg** | 8 | 0.833/0.625/0.714 | **1.000/1.000/1.000** | 0.889/1.000/0.941 |

**阈值扫描（micro-avg `added`）**：

| 阈值 | 0.15 | 0.20 | 0.25 | **0.30** | 0.40 | 0.50 | 0.60 |
|---|---|---|---|---|---|---|---|
| P | 0.200 | 1.000 | 1.000 | **1.000** | 1.000 | — | — |
| R | 1.000 | 1.000 | 1.000 | **1.000** | 1.000 | 0.000 | 0.000 |
| F1 | 0.333 | 1.000 | 1.000 | **1.000** | 1.000 | 0.000 | 0.000 |
| FP | 12 | 0 | 0 | **0** | 0 | 0 | 0 |

结论：**0.20~0.40 是稳定平台期**（P=R=1.0），0.15 以下弱证据涌入（12 条假阳性），0.50 以上全部漏空。
默认 0.30 落在平台期中部，不是"拟合出来的某个点"。

> ⚠️ **样本量诚实声明**：这是 8 条 gold 的人工常识样本，用于**回归自检与口径固化**，
> 不是统计意义上的评测结论。真正的外部评测需要 MOOCCubeX 规模的数据（见下）。

### 4.3 外部数据集（MOOCCubeX）接入方式

脚本已按"**每学科一次独立推断**"建模，只要把外部数据转成同一结构即可：

```json
{ "subjects": [{ "subject": "...", "order": ["c1","c2"],
                "concepts": [{"id","name","difficulty","summary"}],
                "contents": {"c1": "正文…"},
                "existing_edges": [["c1","c2"]],
                "gold": [["c1","c2"]] }] }
```

- MOOCCubeX 提供**人工标注的先修关系**（可作 `gold`）与概念集；
- 其概念**没有现成讲解正文** → `contents` 留空即可，C1 自动弃权，仍可用 C2/C3/C4/C6 打分
  （此时建议补 `order`，否则 C3 只能靠 `created_at`，而外部数据没有入库顺序）。
- **未做**：本次未下载 MOOCCubeX 数据（体量大、需要网络与存储预算），因此**没有跨数据集的泛化结论**。
