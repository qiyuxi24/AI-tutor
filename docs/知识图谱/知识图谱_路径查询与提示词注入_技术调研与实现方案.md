## 一、结论速览

先给判断，再给证据。

**1）"路径查询"和"节点注入"是同一条流水线的两端，必须一起设计。**
图上的路径/子图检索决定"取到哪些节点"，注入形式决定"这些节点以什么面貌进入提示词"，预算决定"能放多少"。三者任一失配，收益都会被吃掉大半。本报告的组织顺序即按此流水线。

**2）路径查询没有"唯一正确解"，只有"按查询类型匹配"的范式。**

| 查询类型 | 首选检索范式 | 代表实现 | 取数代价 |
|---|---|---|---|
| 实体级（"关于 X 的一切"） | 实体锚点 + 邻域/社区扩展 | GraphRAG Local | 中 |
| 全局/主题级（"整体在讲什么"） | 社区摘要 Map-Reduce | GraphRAG Global | 高（预生成） |
| 多跳关系（"A 和 B 怎么连上"） | 有界多跳 / 路径检索 / PPR | ToG、RoG、GNN-RAG、HippoRAG | 中–高 |
| 语义不相似但结构相关（先修/前置） | 沿特定边**反向**遍历 + 深度衰减 | 本项目扩跳（P1） | 低 |
| 需要精确可复核的关系 | 图查询语言 | text→Cypher（Neo4j） | 低 |

**3）注入形式里最反直觉的一条：三元组 vs 自然语言没有定论，且证据相互矛盾。**
支持"线性化三元组更好"（arXiv 2402.11541、GIVE）与支持"自然语言更好"（CoTKR §5.8）的论文都存在。**唯一可靠的结论是：必须对自己的任务做 A/B 实测。**

**4）"保持性能"的关键不是少放，而是放对位置、放对量。**
Lost in the Middle 证明相关信息在**正中间**时性能可能**低于不给**（GPT-3.5 在 20 篇文档、答案位于正中时 52.9%，低于闭卷基线 56.1%）；RULER 证明多数模型有效上下文**不足标称的 50%**。所以注入策略的核心是**预算上限 + 剪枝 + rerank + 头尾摆放**。

**5）最佳注入策略：分层 + 分场景 + 硬预算。**
小 always-on 层（框架/定界）稳定注入，深知识按需检索；依赖用户个体状态的查询用"稳定注入"（本项目 P1 实测命中率 25.0%→62.5%、token 仅 +6%），开放语料问句用"按需检索"。检索段给**固定小配额**，不随总预算放大。

**6）对本项目：S4（图谱结构注入）与 S6（图谱检索正文注入）必须分开治理。**
预算框架已明确二者是两件事，本报告的实现方案（第七章）据此给出改动点。

## 二、问题界定与坐标系

### 2.1 把问题拆成一条流水线

用户问的是两个问题，但它们是一条链：

```
用户查询 / 上下文
   │
   ├─(1) 检索 retrieval ── 图上"路径查询"：从哪进、走几跳、取哪些子图或路径
   │
   ├─(2) 选形 serialization ── 三元组？自然语言？JSON？取多少条？
   │
   ├─(3) 注入 injection ── 放系统提示词（always-on）还是工具返回（on-demand）？放头/中/尾？
   │
   └─(4) 预算 budget ── 给这段多少 token？超了剪谁？
```

四个环节各有成熟研究：检索对应 GraphRAG / ToG 一脉；选形对应 verbalization 一脉；注入对应 context engineering 一脉；预算对应长上下文与 RAG 效率研究一脉。**本文的价值在于把四者串成一条可落地的链**——单看任何一环，都会漏掉其他三环的约束。

### 2.2 三条路线的分野（回扣既有调研）

既有文档《知识图谱_论文与开源实现调研.md》把业界用法分三条路线：

| 路线 | 图是什么 | 代表 | 每轮对话 |
|---|---|---|---|
| A 检索索引 | 图是**索引** | GraphRAG / LightRAG / HippoRAG | 命中才用 |
| B 教学参照系 | 图是**教学可行域与坐标系** | **本项目**；MDPI 智能导学(2025) | **每次注入** |
| C Agent 记忆 | 图是**长期记忆** | Zep/Graphiti / Mem0 | 按需召回 |

本报告聚焦**路线 A 与 B 共用的"注入段"技术**：无论图是索引还是参照系，"取哪些节点、以什么形式、放多少进提示词"这套问题是同一套。C 路线（记忆）的图规模与生命周期不同（时序、增量、个性化），本文不展开，仅在其"何时注入"的判断上引用（见 §6.1）。

### 2.3 报告内部术语约定

- **路径查询**：在图上从锚点出发、按边关系取一条或多条**节点序列**（路径）或**节点集合**（子图）的过程，包含图遍历、最短路、PPR、beam search、Cypher 等具体手段。
- **注入**：把检索结果写进 LLM 输入的措辞过程。
- **always-on 注入**：每轮固定写入系统提示词；**on-demand 注入**：由模型在需要时通过工具取回。
- **S4 / S6**：本项目预算框架里"图谱结构注入"与"图谱检索正文注入"两段的编号。

## 三、图上如何做"路径查询"：范式地图

### 3.1 检索索引三模式：GraphRAG 的 Local / Global / DRIFT

Microsoft GraphRAG 是最常被引用的参照系，它把"怎么在图上取数"分成三种模式。【已核实，arXiv 2404.16130；微软 DRIFT 博客 2024-10-30；GraphRAG 官方 local-search 文档】

| 模式 | 起手 | 取数路径 | 适合 |
|---|---|---|---|
| **Local Search** | 查询→语义匹配出相关**实体** | 以实体为访问点，取：关联实体、关系、实体协变量、所属**社区报告**；再取关联的**原始文本块**；候选数据**按优先级排序并裁剪到预定义大小以适配单个上下文窗口** | 特定实体的问题（关联实体少） |
| **Global Search** | 忽略实体级检索 | 对**选定层级**的社区摘要做 **Map-Reduce**：Map 阶段逐批让 LLM 生成中间答案 + 数值有用性评分，Reduce 阶段过滤、排序、综合成最终答案 | 语料全局 / 主题性理解 |
| **DRIFT Search**（0.4.0 新增） | 先用社区级上下文拿"全局视图" | 再生成**后续查询**交给 local search 深挖具体 | 既需全局又需细节的复杂问题 |

**一条容易被忽略的工程事实**：local search 的候选数据统一"排序 + 裁剪到预定义上下文窗口大小"——**注入体量是被显式截断控制的**，不是全量塞入。这条决定了后面所有注入策略的基调（见 §5.4）。

### 3.2 结构化检索：双层关键词与个性化 PageRank

- **LightRAG（arXiv 2410.05779, HKUDS）**【已核实摘要】：**双层检索**——低层=**实体**、高层=**主题（topic）**，图结构与向量表示并存，检索同时用两层关键词；支持**增量插入**，新文档进来不必像 GraphRAG 那样重算社区。
- **HippoRAG（NeurIPS 2024）/ HippoRAG 2（2025）**【已核实摘要】：在 KG 上跑 **Personalized PageRank（PPR）**，以查询实体为种子，得到节点的收敛权威分，用于多跳记忆检索。
- **TERAG（arXiv 2509.18667, 2025-09）**【已核实摘要】：轻量 NER 建图 + **PPR** 检索，把成本压到极致——**构建 token 以 TERAG 为 100% 基线时，AutoSchemaKG 为 861%、LightRAG 为 1434%**；它保留 **≥80%** 的重基线检索精度，并做到用 AutoSchemaKG+HippoRAG1（Full-KG）**3–11% 的输出 token** 达到其 **80% 准确率**。

这条路的共同点：**先用便宜的手段把候选压小，再让 LLM 处理**——与"全量塞图"正相反。

### 3.3 Agentic 多跳：把路径查询交给 LLM 迭代

当问题需要"边走边判断"（下一步走哪条边），一类方法是把 LLM 当 agent，在图上做多轮检索+推理：

| 方法 | 出处 | 机制 | 关键数字 / 代价 |
|---|---|---|---|
| **ToG / Think-on-Graph** | ICLR 2024（Sun et al.） | LLM 作 agent，在 KG 上做 **beam search**，LLM 给候选路径打分，迭代探索关系三元组，产出**可验证推理轨迹**；无需训练 | 让较小开源模型也能超过 GPT-4 【已核实摘要】 |
| **ToG 2.0** | 2024 | 更强**剪枝**；联合 KG + 文本检索，"逻辑链扩展"与"上下文扩展"交替 | 补 KG 不完整 / 粒度不足 【已核实摘要】 |
| **RoG / Reasoning on Graphs** | ICLR 2024 | LLM 作规划器，先生成**关系路径**作"计划"，再从 KG 抽事实作推理链（planning-retrieval-reasoning） | 增强可解释性 【已核实摘要】 |
| **GNN-RAG** | arXiv 2405.20139 | GNN 先在**稠密 KG 子图**上推理得候选答案；再抽"问题实体↔答案"的**最短路径**；路径 **verbalize** 后注入 LLM | WebQSP/CWQ SOTA，**8.9–15.5%** 提升；模型尺寸小 【已核实摘要】 |
| **Graph-CoT** | — | 三阶段循环：Reasoning（决定需要哪些图数据）→ Interaction（函数调用取节点/邻居/度）→ Execution（结果喂下一轮） | 缺点：大规模图上**迭代查询开销大**、函数调用可能不准 【二手】 |
| **Graph-R1** | ICML 2026, arXiv 2507.21892（LHRLAB） | **知识超图**作环境；agent 多轮 **think→query→retrieve→answer**；**双路检索**（实体超边检索 + 直接超边相似度检索）+ **RRF 融合**；GRPO 端到端 RL 训练 | 2Wiki 上每 1K token 构建 **5.69s / $2.81**（GraphRAG 8.04s/$3.35、HyperGraphRAG 6.76s/$4.14）；生成 **120K 节点 / 98K 超边**；平均查询 **7s**；答案 **1200–1500 token**；6 个基准 SOTA F1 【已核实摘要】 |

**取舍**：Agentic 方法在复杂多跳与 OOD 场景优势明显，但引入了**多轮 LLM 调用**的延迟与不确定性——Graph-CoT 的"迭代查询开销"就是典型代价。对延迟敏感的教育对话场景，这类方法更适合作为**兜底**而非默认路径。

### 3.4 剪枝：控制注入体量的关键一环

这是本文最想强调的一环。**图遍历检索的子图规模随跳数指数增长**：子图太大 → 计算成本高 + 噪声降低生成质量；跳数太小 → 子图缺关键知识。必须做折中——这就是"图剪枝"。【已核实摘要，*GRAPH Retrieval-Augmented Generation: A Survey* §2.5.1；GraphRAG survey】

| 方法 | 出处 | 剪枝思想 |
|---|---|---|
| **PathRAG** | arXiv 2502.14902 | 认为 GraphRAG/LightRAG 的症结是**子图冗余**而非不足；用**带距离感知的 flow-based 剪枝**：从锚点按 hop 衰减 α∈(0,1) 传播"资源"，路径得分取资源（瓶颈/平均），取 **top-K 路径**。**路径比 ego-network 更紧凑**、更贴合多跳结构、缩小幻觉面。缺点：稠密图上**路径枚举昂贵**。【已核实摘要】 |
| **G-Retriever** | — | kNN + **PCST（Prize-collecting Steiner Tree）** 剪枝取子图 【已核实摘要】 |
| **SubgraphRAG** | — | 轻量 **MLP 抽子图**，可调子图大小做效率–效果权衡 【已核实摘要】 |
| **PG-RAG** | — | 伪图上 **DFS + contribution matrix** 选"事实轨迹"（节点路径）【已核实摘要】 |
| **CrumbTrail / KGTrimmer** | NUS CS6101 项目 | bottom-up 分层去除环 / 弱支持节点，同时保证受保护实体从根可达 【二手】 |

**对注入的直接意义**：剪枝不只是"省 token"，更是"去噪"。PathRAG 的立论——**冗余子图本身就是噪声源**——与 §5.3 的"位置/注意力"证据互相印证。

### 3.5 混合检索融合：图 + 向量 + RRF

图检索补的是**语义不相似但结构相关**的召回（先修、前置、因果），而向量检索补的是语义相似。二者互补，工程上常**并行跑再融合**：

- 用 **RRF（Reciprocal Rank Fusion，score = Σ 1/(60+rank)）** 或加权线性融合；多检索器场景 RRF 稳定优于简单排序。【二手，Neo4j/LangChain 工程博客】
- 代表：WeKnow-RAG（Xie et al., 2024）等混合检索方法。【二手】
- 本项目 P1 已实现"向量初检 + 图扩跳补充"的近似结构：补充命中 `score = 初检最高分 × 0.6^depth`，**保证补充项排在语义初检之后**——这实际是一种简化的加权融合。

### 3.6 另一条实现路径：text → Cypher

除了"取子图再注入"，还有一条更"数据库"的路径：**让 LLM 直接生成图查询语言**。

- **Neo4j + LangChain `GraphCypherQAChain`**：LLM 生成 Cypher 查询图库。【二手】
- 两个提升准确率的工程要点（CSDN 实作记录）【二手】：
  1. **CoT 提示**——先"识别核心实体"→再"识别核心关系"→再"写 Cypher"；据称把 Cypher 生成准确率从 **60% 提升到 90%+**；
  2. 给 LLM 一份**图谱 schema 速查手册**（有哪些 label / relationship）。
- 缺点：强依赖 schema、生成可能出错；适合 schema 稳定的领域图。本项目图谱是**用户级个性化图**、schema 动态，此路暂不优先。

### 3.7 小结：本项目在范式地图上的位置

本项目当前走的是"**系统提示词注入框架 + 有界反向扩跳**"：检索扩跳只沿 `prerequisite` 边**反向回溯**（补前置，不补后继），补充条数 ≤ top_k（注入体量最多翻倍），默认 `hops=0`（关闭）。【项目实测，`知识图谱_P1扩跳与AB对照实验.md`】

对应到范式地图：它属于 **§3.1 的"实体/知识点锚点 + 邻域扩展"** 的轻量版，并用"**深度衰减 0.6^depth + 条数上限**"充当 §3.4 的剪枝。**它是少数派但合理的选择**——因为教育场景的图是"教学参照系"（路线 B），而非"从文本抽的检索索引"（路线 A），不需要社区摘要那一套。

## 四、相关节点如何注入提示词：形式与序列化

取到节点只是第一步，**"以什么面貌进入提示词"**直接决定模型能不能用上。

### 4.1 三种整合层次：从"喂进参数"到"喂进上下文"

Graph RAG 综述把图信息进入 LLM 的方式分两大层【已核实摘要，arXiv 2501.13958v2 §VI】：

**(a) 微调开源模型（把图喂进参数）**
- **node-level**：节点 + 邻居文本作为上下文（SKETCH、GraphGPT）；
- **path-level**：把 KG 路径作为**输入/输出训练目标**以增强推理（RoG、KGTransformer）；
- **subgraph-level**：图编码器读出 embedding，或**把子图展平成序列注入 prompt**（InstructGLM、LLAGA）。

**(b) 上下文学习（ICL，闭源模型——本项目所属）**
- **prompt 形态**：把图数据**转成自然语言描述**（节点/边），与检索内容、问题拼接；
- **graph-enhanced Chain-of-Thought**：ToG 在检索到的子图上先推理再 CoT；Graph-CoT 多轮图执行；
- **Collaborative KG Refinement**：用 KG 事实回修 LLM 草稿（KG-RAG、KELP、CogMG）；
- **关键设计**：在文本 prompt 中**保留子图的丰富性，但不冗余、不错置重点**。

> 对本项目的直接含义：我们不做微调（无标注数据、成本高），走 **(b) ICL 路线**；因此"序列化形式 + 位置 + 预算"这三件事就是全部可调空间。

### 4.2 verbalization：把图"说成"文本的五种做法

| 方法 | 出处 | 做法 | 结论 |
|---|---|---|---|
| **KAPING** | arXiv 2306.04136（Baek et al., 2023） | 三元组 (s,r,o) **线性 verbalization**（直接拼接，如 `(Lady Susan, written by, Jane Austen)`） | 作者观察到**在 LM prompting 中简单线性拼接效果很好**，优于特意设计的 graph-to-text 【已核实原文摘要】 |
| **K-BERT** | — | 发现"直接拼接三元组 token 会与句子 token 密集交互 → **Knowledge Noise**"；用软位置 + **可见矩阵**隔离 | 解决噪声问题 【已核实摘要】 |
| **ERNIE 3.0** | — | 三元组作为 token 序列与句子拼接，随机 mask 关系/句子 token | — 【已核实摘要】 |
| **Knowledge Graph-to-Prompt** | RISS 论文 | 三元组转**自然语句**，用 **DPO 直接偏好优化** verbalization 模型 | 显著优于**表面层 verbalization** 【已核实摘要】 |
| **DALK** | — | 对采样知识**让 LLM 自己 rerank**，只保留 **top-k 三元组**喂回自身 | 提精度、控体量 【已核实摘要】 |

**K-BERT 的"Knowledge Noise"尤其值得本项目警惕**：如果直接把图谱节点/三元组拼进 prompt 而**不加结构分隔**，模型可能把"图里的事实"与"用户话里的语境"混为一体，产生错误关联。这正是"注入形式"要单独设计的原因。

### 4.3 三元组 vs 自然语言：证据是**冲突的**（本报告最需要提醒的一条）

这是本次调研里最反直觉的发现——**不存在"哪种形式一定更好"**：

- **支持"线性化三元组更好"**：
  - Dai et al., *Large Language Models Can Better Understand Knowledge Graphs Than We Thought*（arXiv 2402.11541, 2024）：通过 attention 分布分析，LLM 用 **raw linearized triples** 比 polished prose 更有效地利用事实知识——因为**结构三元组减少语言噪声、让注意力更集中在事实 token**。【已核实摘要】
  - **GIVE**（arXiv 2410.08475）：多数情况下 **triplets 提示的准确率高于 text**——三元组结构天然让 LLM 连起相关实体、构建忠实逻辑链，而文本还需额外解析步骤。【已核实摘要】
- **支持"自然语言更好"**：
  - **CoTKR**（arXiv 2409.19753）§5.8 *Comparison with Triple Method*：明确写道"若干研究（Dai 2024、Baek 2023）称 LLM 更能理解三元组形式，**但我们的结果相反**"，于是作者转向比较"用三元组形式的**知识改写**方法"。【已核实摘要】

**推论（写进方案）**：序列化形式无普适最优解，取决于任务类型、模型、以及是否需要"可读性/可解释"。**应做 A/B 实测，而不是照搬任何单篇结论。** 本项目 P1 已有 A/B 框架（见 §7.3），可直接复用。

### 4.4 工程经验：三种序列化选项与预算

一份工程指南给出可直接落地的三选项对照【二手，BigData Boutique《Knowledge Graphs Meet RAG: A Practical Integration Guide》】：

| 选项 | 特点 |
|---|---|
| **triple list（三元组列表）** | 省 token，但 LLM **较难推理** |
| **自然语言叙述** | 易推理，但 **token 约翻倍** |
| **结构化 JSON** | 折中 |

同一来源的其他建议：
- **子图上下文上限 1–2K token**；更大的子图**用小模型调用做摘要**；
- **返回"子图"而非"整条遍历路径"**（避免噪声）；
- 每次查询 **cap fan-out（每节点扇出上限）**、用类型过滤 / 学习权重**剪掉低相关边**；
- **~200ms / query** 是合理预算。

### 4.5 位置与顺序：注入形式的一部分

位置不是"排版细节"，而是**注入形式的一等公民**。

【已核实摘要，GraphRAG survey §2.5.2 Reranker】
> LLM 性能受相关信息**在上下文中的位置**影响（开头/中间/结尾）；也受 **in-context 知识顺序**影响，**越靠后的文档贡献越小**。检索一般按相关度粗排，仍需**细粒度 rerank** 才能达到最优下游表现。

【二手，Lost in the Middle 系列缓解策略】
- 最强证据放在**头/尾（bracketing）**，问题放**最后**（recency boost）；
- **少而精**（retrieve less）；
- 先 **cross-encoder rerank** 再按"极端顺序"排（最强放头、次强放尾、最弱放中间）；
- 压缩 / 摘要长输入。

### 4.6 注入纪律：避免"确定性幻觉"

这一条来自本项目 P1 的实测教训，属于"注入形式"里最容易被忽视的**负向规则**：

【项目实测，`知识图谱_P1扩跳与AB对照实验.md` §5】
- 当图谱检索为空时，LLM **不会说"我不知道"**，而是**向学生断言"你的知识图谱可能还是空的"**（关闭组 d1/d2/d3 均出现），而测试图谱实际有 7 个节点——这是**对学生个人数据的错误断言**，比"答不出"更有害；
- 处理：在系统提示词或检索工具返回里**区分"图谱为空"与"本次检索未命中"**，并**明确禁止向学生断言图谱内容状态**。

另一条可借鉴的工程做法【二手】：给注入内容打**来源标签**（如 `[fabric] / [qdrant] / [sessions] / [facts]`）并声明"视为先验知识、可放心使用"——让模型知道这段是可信注入而非用户输入，避免与用户话术混淆（正是 §4.2 K-BERT 想解决的"Knowledge Noise"）。

## 五、如何"保持性能"：位置、注意力与预算

"注入后性能不退化"不是靠直觉，而是靠三条被反复验证的规律。

### 5.1 图 RAG 本身就有 token 优势

【已核实摘要，*GRAPH Retrieval-Augmented Generation: A Survey*】
- 在快速图库上，图 RAG 比传统方法**少用 26%–97% 的 token**；
- **易更新**：加/删节点与边即可，无需全量重建。

这为"图注入"提供了一个反直觉的立足点：**用图的目的不是塞更多，而是用更少的 token 表达更结构化的关系**。

### 5.2 各方案的效率实测数字（可直接引用）

| 方案 | 出处 | 效率数字 |
|---|---|---|
| **TERAG** | arXiv 2509.18667 | 构建 token：TERAG 100%（基线）/ AutoSchemaKG **861%** / LightRAG **1434%**；达 Full-KG **80% 准确率**，仅用 **3–11% 输出 token**【已核实摘要】 |
| **FactRAG / HybridRAG** | GenAIK Workshop | Finance Bench 上**幻觉 −6%**、**token 用量 −80%**（对比传统 RAG）【已核实摘要】 |
| **Graph-R1** | arXiv 2507.21892 | 2Wiki 每 1K token 构建 **5.69s/$2.81**（GraphRAG **8.04s/$3.35**、HyperGraphRAG **6.76s/$4.14**）；平均查询 7s；答案 1200–1500 token【已核实摘要】 |

**评测口径也值得借用**（RAGRouter-Bench）【已核实摘要】：效率指标用 **token 消耗**，拆成 **构建成本**（一次性，摊到查询数）与 **推理成本**（每次查询，含检索期 LLM 调用 + 生成期上下文处理）；生成输入**截断到 8k token**，但成本按**完整检索输出**计（截断只去掉低排序段）。

### 5.3 位置与注意力：为什么"塞得多"反而更差

这是"保持性能"的第一性原理，四条硬证据（均来自本项目预算框架已核验的论文，可直接引用）：

**【论文】RULER / 有效上下文**（arXiv 2410.18745, An et al., 2024-10）
- 多数开源模型**有效上下文不足训练长度的 50%**：GPT-4-1106 为 64K/128K=50%；Llama3.1-8B 为 32K/128K=25%；GLM4 为 64K/1M≈6.4%；
- 机制是**位置频率左偏**（2K 训练长度下位置 i≥1536 的占比不足 5%）；
- 附加发现：多数失败案例集中在**文档前 1/3**——**开头也不是绝对安全区**。

**【论文】Databricks 长上下文 RAG**（arXiv 2411.03538, 2024-11；20 模型 × 3 数据集 × 2000+ 实验）
- 正确率随上下文**先升后降**，多数开源模型峰值在 **8K–32K**（原话："多数 LLM 只在 16–32K tokens 内表现出 RAG 性能提升"）；
- **召回率单调上升、正确率不单调**——信息确实在上下文里，但模型**用不上**；
- 成本线性：8K→128K 输入成本 **16×**；64K→96K 的**边际收益**对 GPT-4o 是 **0**、对 o1-preview 为**负**（0.831→0.824）。

**【论文】Lost in the Middle**（arXiv 2307.03172, Liu et al., TACL 2024）
- 相关信息在**开头/结尾**最好，**正中间**显著下降（**U 型曲线**）；
- GPT-3.5-Turbo 在 20 篇文档、答案位于第 10 位（正中）时 **52.9%**，**低于闭卷基线 56.1%**——"给了文档反而不如不给"，与 oracle（88.3%）差 **>20pp**；
- 文档数 10→20→30，平均性能持续下降；检索文档 **>20 篇后收益极小**（边际 ≈1.5% GPT-3.5 / 1% Claude）；
- **query-aware contextualization**（把查询同时放在数据**前后**）在键值检索上把 300 键值对的准确率从 **45.6% → 100%**。

**【论文】Chroma《Context Rot》**（2025-07；18 模型 / 194,480 次调用）
- **1 个干扰项即让性能低于基准**；**打乱的干草堆一致优于逻辑结构化的**（不要迷信排版）；
- Anthropic 同类表述：随上下文 token 增长，模型**准确召回**能力下降。

> **综合推论（可写进方案）**：注入段存在一个**倒 U 型的 sweet point**（呼应 *In Defense of RAG*, arXiv 2409.01666：检索块数与答案质量呈倒 U 型）。**"多"不等于"好"，超过拐点后每多一个 token 都在净亏。**

### 5.4 项目预算框架：把上述规律固化成配额

本项目已把上述论文规律落成《上下文工程_预算框架.md》【项目实测，可复现】：
- 单一预算 **B = 48K token**；裁剪线 = B − 输出预留 = **45K**；
- 九段配额（K token）：S1 输出预留 3 ｜ S2 静态指令 1 ｜ S3 工具/技能说明 5.4 ｜ **S4 图谱结构注入 6** ｜ S5 用户画像 0.8 ｜ **S6 图谱检索注入 2** ｜ **S7 知识库检索注入 2** ｜ S8 对话历史 **21** ｜ S9 当前轮 6；
- 固定段实测已占 **29.1% × B**；`B − 固定 − 输出预留 = 31K` 留给 S8+S9；
- **关键规则**：S6+S7 两段检索注入**目标合计 4K、上限合计 6K，且不随预算放大而放大**——预算从 48K 放大时多出的额度给对话历史（S8），**不给检索**。理由是 §5.3 的证据：**检索段是唯一"越多越差"的段**。

**这直接给出了本报告"最佳注入策略"的量化边界**：图谱相关注入（S4+S6）在 48K 预算下**合计约 8K token 是安全线**。

## 六、最佳注入策略

把前面三章的范式、形式、性能证据收敛成可执行的策略。

### 6.1 第一决策：何时注入——always-on、on-demand，还是分层

这是本报告最核心的决策点，业界存在**针锋相对的两派**【二手】：

- **always-inject 派**：ChatGPT 的记忆策略就是"**始终注入**"——与 Claude 的"按需检索"正相反。
- **on-demand 派**：Claude 按需检索；更值得注意的是——**Claude Code / Codex / Gemini CLI 等 Agent 工具的记忆"比想象中简单"——没有 RAG、没有知识图谱，就是滑动窗口。**

Context Engineering 给出了更细的框架【二手】：
- **pre-retrieval（推理前检索注入）**：传统 RAG 做法。推理时快，但**易溢出**、基于**静态查询式**、**无法随推理演化自适应**；
- **just-in-time（JIT）**：agent 维护轻量引用（文件路径 / URL / 存储查询），运行时用工具**动态加载**；
- **progressive disclosure（渐进披露）**：system prompt 只放"技能一行描述"，模型需要时再 `load_skill()` 把完整指令**按需注入**——"装 100 个技能，system prompt 只长 100 行，不是 100 页"；
- **分层记忆范式**：**always-on 层保持极小**（只放轻量"定位信息"），丰富的事实 / 过程 / 历史知识存**深层**，**按需检索**进入活动上下文——避免记忆持续挤占当前任务的预算。

**本项目已用实测回答了这个问题**【项目实测，`知识图谱_P1扩跳与AB对照实验.md`】：

- 系统提示词**注入图谱摘要**（"始终注入"）是**主收益来源**：期望知识点命中率 **25.0% → 62.5%**（Δ+37.5pp）；依赖个人状态的题 **30.0% → 80.0%**（Δ+50pp，2.7 倍）；token 成本仅 **+6%**（86392 → 91495）；
- 剥夺图谱后模型**不会说"我不知道"**，而是**反复徒劳检索**（关闭组在 3 道依赖题上共检索 22 次，其中一题 9 次）并**反过来向学生断言"你的图谱是空的"**；
- 同一道题"学 DP 前置够不够"：关闭组 8 轮 / 21295 token / 命中 1/3；开启组 3 轮 / **13552 token** / 命中 **3/3**。

> **结论**：对"**依赖用户个体状态**"的查询，**稳定注入 > 按需检索**（轮次更少、token 更低、命中更高）；对**开放语料问句**，按需检索更省。**最佳答案是分层**——把"框架/定界/用户状态"放进极小的 always-on 层稳定注入，把"深知识正文"交给按需检索。

### 6.2 第二决策：注入内容怎么组织

| 策略 | 要点 | 来源 |
|---|---|---|
| **剪枝（pruning）** | 子图随跳数指数增长；太大=噪声+成本，太小=缺知识；需折中 | GraphRAG survey §2.5.1【已核实】 |
| **路径化代替 ego-network** | 用 top-K 关系路径替代冗余子图，更紧凑、更贴合多跳结构、缩小幻觉面 | PathRAG, arXiv 2502.14902【已核实】 |
| **重排（rerank）** | 先粗排再细粒度 rerank（cross-encoder）；最强证据放头尾 | GraphRAG survey §2.5.2；LITM 缓解【已核实/二手】 |
| **混合检索融合** | 图 + 向量并行，RRF（Σ1/(60+rank)）融合 | Neo4j/LangChain 博客【二手】 |
| **压缩 / 摘要** | 大子图先小模型摘要；子图上下文上限 1–2K token | BigData Boutique【二手】 |
| **预算硬上限** | local search 候选"排序+裁剪到预定义窗口"；生成输入截断 8k | GraphRAG 文档；RAGRouter-Bench【已核实】 |
| **深度衰减 + 条数上限** | 扩跳补充命中 `score = 初检最高分 × 0.6^depth`，补充条数 ≤ top_k | 项目 P1【项目实测】 |

### 6.3 八条最佳实践（本报告的落地清单）

1. **分层**：小 always-on 层（框架 / 定界 / 定位）+ 大 on-demand 层（正文 / 深知识）。
2. **分场景定时机**：依赖**用户个体状态**的查询 → **稳定注入**；开放语料问句 → **按需检索**；二者并存时**混合**（图 + 向量 + RRF）。
3. **有界取数**：从查询锚点出发**有界多跳遍历**，**只沿需要的边方向**（如先修只回溯前置），加**剪枝 / 深度衰减 / 条数上限**。
4. **序列化做 A/B**：三元组列表（省 token）/ 自然语言（易推理）/ JSON（折中）——**必须对自己的任务实测**（§4.3 证据冲突），别照搬。
5. **排位置**：rerank 后把**最强证据放头尾**，问题置**末尾**；核心事实**不要埋中间**。
6. **给硬预算**：检索段**固定小配额且不随总预算放大**；子图上限 1–2K token；超限先剪枝 / 摘要。
7. **守纪律**：区分"图空" vs "本次未命中"；注入内容打**来源标签**；**禁止**向用户断言图内容状态。
8. **可观测**：用**规则可算的指标**（命中率、图谱提及数、检索次数、token、轮数、误报"图空"数）做 A/B，**零额外 LLM 调用**（复用项目 P1 的做法）。

### 6.4 决策矩阵：按"查询类型 × 约束"选策略

| 查询类型 | 注入时机 | 取数范式 | 序列化建议 | 预算 |
|---|---|---|---|---|
| 依赖**用户个体状态**（"我下一步学什么"） | **always-on**（结构）+ on-demand（细节） | 锚点 + 反向先修遍历 | 结构化列表（节点名+掌握度+边） | S4 固定，S6 小配额 |
| 实体级知识问答 | on-demand | 实体锚点 + 邻域 | 三元组或 NL，实测定 | ≤2K |
| 多跳关系（"A 到 B 怎么连"） | on-demand，必要时 agentic | 有界多跳 / 路径检索 / PPR | 路径序列（PathRAG 式） | ≤2K，超限剪枝 |
| 全局 / 主题性 | on-demand | 社区摘要 Map-Reduce | 摘要文本 | 固定层 |
| 需精确可复核的关系 | on-demand | text→Cypher | 查询结果表 | 视结果 |

## 七、实现方案：AI-tutor 图谱注入链路改造

### 7.1 目标与约束

- **目标**：在既有 B=48K 预算下，把图谱注入的收益做实（P1 已验证 25%→62.5%），同时压住三类风险：注入噪声、位置失效、确定性幻觉（"图谱是空的"）。
- **约束**：①不引入微调（无标注数据）；②不重算社区（图不是从文本抽的）；③不破坏 P1 已验证的收益；④所有指标**规则可算、零额外 LLM 调用**。

### 7.2 先把 S4 与 S6 分开治理（最关键的结构性动作）

预算框架 §1.3 已明确：**S4 图谱结构注入（框架/定界：节点名 + 掌握度 + 边）** 与 **S6 图谱检索注入（正文片段）** 是**两件事**，混在一起谈会让两边都调不准。

| 维度 | S4 图谱结构注入 | S6 图谱检索注入 |
|---|---|---|
| 内容 | 节点名 + 掌握度 + 边（"可见框架"） | 检索命中的正文片段（"证据"） |
| 时机 | **always-on**（每轮，定界用） | **on-demand**（按需，可重检索） |
| 配额 | 6K（目标）/ 8K（上限） | 2K（目标）/ 3K（上限） |
| 降级 | 节点数超限则截断（按学科/掌握度） | 超限则剪枝 / 只留 top-k |
| 主要风险 | 体量超限挤占历史 | 命中无关→噪声；空结果→幻觉断言 |

### 7.3 具体改动点（按流水线四环节）

**（1）检索侧**
- **扩跳默认值策略**：P1 留的 `DEFAULT_HOPS` 保持 0（零回归），但把"学生卡住 / 需前置"场景的 `hops=1` 在**系统提示词或工具描述**里显式引导；
- 保持**只沿 `prerequisite` 反向**（补前置不补后继——注入进阶内容属超纲）；
- 保留**深度衰减 `0.6^depth` + 补充条数 ≤ top_k**（充当 §3.4 的剪枝）。

**（2）选形侧（新增 A/B）**
- 新增一个**三元组 vs 自然语言**的注入形式 A/B（§4.3 证据冲突，必须自测）；用规则指标（命中率/token/轮数）评判，零额外 LLM 调用；
- **子图/注入上限对齐 1–2K token**（§4.4）；超限**先剪枝、再摘要**，不直接截断（避免截出半句误导）。

**（3）注入侧**
- **S4 结构注入放前段**充当"定界"（模型先知道"哪些知识点可见、掌握到几档"），**S6 正文按相关度排序**，最强证据靠头/尾，问题置末（§4.5 / §5.3）；
- **来源标签**：给注入段打标签（如 `[图谱结构] / [图谱检索]`），并声明为可信先验（§4.6）；
- **负向规则（必做）**：系统提示词或检索工具返回里**区分"图谱为空"与"本次检索未命中"**，并**明令禁止向学生断言图谱内容状态**（P1 §5 已列为待办）。

**（4）预算侧**
- S4 = 6K / S6 = 2K 硬上限；**检索段不随 B 放大**（§5.4）；
- 新增工具时先算"固定成本账"（项目实测：**222 token/工具**，12 个工具 schema 即 2661 token）。

### 7.4 验收与评测口径（复用 P1 的规则化框架）

- **主指标**：期望知识点命中率（P1 基线 25.0% → 62.5%）；
- **辅助**：图谱提及数、检索调用次数、token、LLM 轮数、**误报"图空"数**（P1 已内建该指标）；
- **新增**：注入形式 A/B（三元组 vs NL）的命中率与 token 对比；
- **方法学自证**：说明哪些是 mock、真实路径是什么（避免"数据造假"误读）。

### 7.5 落地路线（P2 建议）

| 优先级 | 动作 | 依据 |
