## 〇、结论速览

1. **可行，且定位是"增量视图"而非"替换"**：现有图谱是**图**（4 类语义边、可能成环、可多父），思维导图/大括号是**树**，二者不能直接互换。正确做法是**在渲染层从同一份图数据派生出一棵树来画**；力导向图**保留**——它承载的跨层语义关系（相关/易混淆/扩展）在树上根本表达不出来。
2. **零新增依赖即可落地**：思维导图首选 **`d3-hierarchy`（`d3.tree` / `d3.cluster`）自绘 SVG**——`d3@7` 已在依赖内，打包增量 ≈ 0，且与现有力导向内核同栈；大括号大纲用**递归 Vue 组件 + CSS 连接线**自绘（大括号可选 SVG path），同样零依赖。
3. **两种视图对应两种派生，语义必须分清**：**思维导图 = 依赖树**（沿 `prerequisite` 生成，表达"先学什么"）；**大括号大纲 = 归属树**（`subject → board → 节点`，表达"包含/从属"）。把两者混为一谈是产品事故。
4. **数据层零改动，且不重蹈 9/26 覆辙**：9/26「主题层」失败，根因是层级建在**结构层**（`themes` 表污染出题/统计/检索/渲染四条读路径）【项目实测】。本方案层级只在**渲染层**派生，不进 `nodes`/`edges`，不触碰那条红线。
5. **项目已有大量可复用资产**：`PathBoard` 的 prerequisite 分层口径、`forceGraphEngine` 的缩放/平移/右键菜单、掌握度四色、`nextNodeId`/`sourceNodes` 高亮联动，均可平移到新视图。
6. **最大风险 = 环与多父**：`prerequisite` 可能成环、节点可能有多前置 → 派生树必须做"**回边忽略 + 主父规则**"，否则无限递归或节点重复。
7. **⚠️ 本地库实测的坏消息（见 §八）**：`nodes.board` 在真实库里**近乎全空**（主力账号 `user 5` 的 122 个节点 `board` **全空**）→ **归属树当前只能画出「学科 → 知识点」两层**，`board` 层恒为"未分组"；且 `subject` 存在噪声值（`what`/`测试`/`核心概念`）。**结论：两种视图里「大括号」当前的增量信息远小于「思维导图」** —— 除非补齐 `board`（属建图侧，超出"只改渲染"边界），否则大括号 ≈ 按学科分组的长列表。**→ 建议把方案 §5.4 的 M1/M2 顺序对调：先做思维导图。**
8. **（v3 增补）幕布对标带来两项后续**：① **进入主题（下钻）+ 面包屑**——三视图目前只有"把节点移进视野"（`focusNode`），没有"把整张图降到以某节点为根"；② **同源双画法**——已派生好的树目前只有一种画法。二者都是纯渲染层，详见 **§九**。

| 视图 | 数据来源（不改数据） | 表达的关系 | 渲染引擎 | 新增依赖 | 落地成本 |

## 一、问题界定与坐标系

### 1.1 "改渲染"落在哪一层：三层模型

把"知识图谱"拆成三层，才能说清"只改渲染"改的是什么：

| 层 | 内容 | 本方案 |
|---|---|---|
| **数据层** | SQLite `nodes` / `edges`、节点正文 MD、向量索引 | 只**读**，不改 |
| **结构层** | 实体/表结构本身（如 9/26 的 `themes`/`node_themes`） | **不动**（改动此层即 9/26 的失败模式） |
| **渲染层** | 前端如何把 `nodes`/`edges` 画成可视界面 | **本方案的全部工作** |

**本章判断**：用户说的"只改渲染"，精确含义是——**在渲染层从既有 `nodes`/`edges` 派生出新视图，数据层与结构层一行不改**。这把问题和 9/26 的失败模式彻底区分开：9/26 动的是结构层，本方案只动渲染层。

### 1.2 现有图谱数据形态：是"图"，不是"树"

（真值见「素材0」；来源 `backend/app/core/knowledge_graph.py::_create_tables`【项目实测】）

| 对象 | 关键字段 | 对渲染的意义 |
|---|---|---|
| 节点 | `id, name, subject, board, tags, mastery, summary, content` | `subject`/`board` 提供**归属层级**；`mastery` 提供**四色**；`tags` 里含 `一级/二级/三级`（前端已解析，`chatStore.js:224-227`） |
| 边 | `from_node → to_node, relation, label, confidence` | `relation ∈ {prerequisite, related, confusion, extension}`，**图可成环、可多父** |
| 前端切片 | `fetchGraph()` 带 `subject` 参数 | **一次只渲染一个学科**（防图谱无限生长）→ 新视图也应是当前学科子图 |

**结论**：现有数据是"**多类型边的有向图 + 两级归属分类**"。层级化的两个天然抓手是：① `prerequisite` 边（依赖关系）；② `subject`/`board`（归属分类）。**这两条正好对应两种视图**（见 §三、§五）。

### 1.3 两条硬约束

1. **只改渲染 / 最大化复用**：不新增 SQLite 表、不改 `nodes`/`edges` 语义、不改后端接口（最多复用现有 `/knowledge/graph` 返回；节点 `level` 已在 `chatStore` 解析现成）。
2. **层级不许进结构层**（9/26 教训）：`docs/知识图谱/知识图谱_节点小节化_设计与实现方案.md` §1 明确记载——"主题层……层级建在**图谱结构层**：章/主题节点污染了出题、统计、检索、图渲染**四条读路径**；聚合下钻真机效果差"【项目实测】。任何"层级"只能是渲染层的派生结果。

## 二、外部范式：图 ↔ 树双视图，业内怎么做

### 2.1 图 → 树的派生算法：三层手段

| 手段 | 做法 | 成本 | 适用 |
|---|---|---|---|
| **DFS/BFS 生成树 + 回边忽略** | 保留"通向未访问节点的边"为树边；"回到已在栈上节点的边"（回边）丢弃 | O(V+E)，无损数据 | **首选**（渲染层、够用） |
| **主父规则（real/step parent）** | 多前置时选一个"主父"（真父），其余为次父 | 规则实现 | 与上一条合用，解决"多父" |
| **断环（FAS 启发式 / Edmonds）** | 反馈弧集贪心（Eades–Lin–Smyth）删边使图无环；或 Chu–Liu/Edmonds 求最小 arborescence | NP-hard（精确）/ 线性（启发式） | 需要"最优/可控"时才用 |
| **顶点复制（unfold）** | 同一定点被多条路径到达时**复制成多个树节点**（`igraph::unfold_tree`：BFS + 复制 + 反查表） | O(V+E) | 多父密集、且"重现"比"去重"更可接受时 |

关键事实（见「素材2」）：
- **环检测 = 回边检测**（CLRS Lemma 22.11）：有向图无环 **iff** DFS 无回边；三色标记遇灰（GRAY）即回边【已核实】。
- **多父**在所有 DAG 层级里都有成型术语：SSAS 的「**real parent / step parent**」【已核实】、HMC 论文的「**AND / OR 约束**」（OR = 只挂一个父）【已核实】（arXiv 2205.07833）。
- **最小 FAS 是 NP-hard**；工程上常用 **Eades–Lin–Smyth 贪心**（线性，实践良好）【已核实】。原文：*A fast and effective heuristic for the feedback arc set problem*, Information Processing Letters 47(6), 1993【已核实/数据库条目】。
- **Chu–Liu/Edmonds** 求以根为最小权 arborescence，天然同时解决"多父 + 断环"（每非根点恰一条入边、无环），但只在需要"加权最优"时才值得【已核实】。
- **"多父"还有第二条正统路线：复制顶点，而不是丢弃父亲**。igraph 的 `unfold_tree()` 即"BFS 展开 + 对被多次到达的顶点建副本"，输出树/森林并附 `vertex_index` 把新顶点反查回原图【已核实/原文】。它与本方案"首次到达入树、其余记次父"是**两种产品语义**：前者让同一知识点在图上**重复出现**（利于跨路径复现，但破坏"一个知识点 = 一个色块"的掌握度直觉），后者保证**不重复**。**本项目选后者**（节点即知识点，重复出现会让四色着色产生歧义）；把"复制"记为备选，仅在将来"要在一张图上串起多条学习路径"时启用。

> **本章判断**：对本项目，**DFS/BFS 生成树 + 主父规则 + 回边忽略** 已足够，且完全在渲染层完成、无损数据；Edmonds/FAS 属于"过度工程"，仅在将来需要"最优学习路径"时再引入。这与教育域主流做法一致——用**拓扑排序**把 prerequisite 图转成序列/树（见 §2.3）。

### 2.2 业界知识工具的"图视图 + 层级视图"如何共存

（完整表见「素材2」）核心结论：**绝大多数工具把"关系图"与"层级/大纲"当两套独立数据，而非同一份图派生两种渲染。**

| 工具 | 图视图 | 层级/大纲视图 | 是否同源派生 |
|---|---|---|---|
| Obsidian | Graph view | File Explorer + Outline | **分开** |
| Roam / Logseq | Graph Overview | block 大纲 | **分开** |
| Notion | ❌ 无原生关系图 | 数据库 + 嵌套页面 | 只做层级 |
| Heptabase | Whiteboard（卡片挂多白板=天然多父） | Tag DB | 以空间图为主 |
| **XMind** | 导图 | **大纲** | **同源、一键切换** ✅ |
| **TheBrain** | Normal ↔ **Outline** ↔ Mind Map | 同左 | **同源切换** ✅ |
| Gephi / CiteSpace | 力引导 / 网络图 | Sugiyama 层次 / Timeline | 同一数据换 layout |

- **一键"图↔树"切换的同源产品案例只有 XMind（导图↔大纲）与 TheBrain（Normal↔Outline↔MindMap）**；Obsidian 的 "Folders to Graph" 插件则是"把文件夹树**叠加进**图"【已核实/二手】。
- ⚠️ **未找到**：任何主流产品明确宣称"由一张**多类型边的有向知识图自动派生**出大纲树、并让用户在图/树间切换"。
- **"大括号"在成熟产品里是「一种内建骨架」，不是图派生的产物**：XMind 的「**逻辑图 / 括号图**」就是教学里最常见的"大括弧"骨架，官方/教程口径为表达**总分关系（整体—部分）**，且"课堂总结知识点时老师特别爱用"【二手/中文，XMind 结构页 + 教程】。更上游的教育学出处是 **Thinking Maps®（David Hyerle）** 的 8 张思维图之一 **Brace Map**，专表 **whole-to-part（整体—部分）**；其画法为"**整体在左，大括号向右张开连接部分，部分可再分解为子部分**"【已核实/XMind 工具页 + Thinking Maps 支持页】。→ 本项目的「大括号」视图与这套语义**对齐**（归属树 = 整体—部分），命名/提示文案可正当地写「**括号图 · 整体-部分**」。
- ⚠️ **一个关键差异要讲清**：XMind 的"导图 ↔ 大纲 / 括号图"是**同一份树数据换骨架**（无损，骨架=画法）；而本项目的括号图是**换了一棵树（归属树，来自 `subject`/`board`）**——比 XMind 更"名副其实"，但也更要向用户交代：**这张树画的是"含/属"，不是"先学/后学"**。

> **本章判断**：本方案——"**同一份 `nodes`+`edges`，按不同语义派生两种树、与力导向图并列切换**"——在现有产品中是**空白**，属差异化机会点；但它也意味着**没有现成实现可抄**，于是"派生算法 + 视图切换"这部分必须自己设计（见 §五）。

### 2.3 学习路径树：教育域的先例

| 系统 | 做法 | 与本项目的映射 |
|---|---|---|
| **Khan Academy 知识地图** | 每个知识点是网络节点，用**前置关系连线**，**颜色表示掌握状态**（绿=精熟、灰=未开始），先掌握前置再进下一概念 | 几乎与 `nodes`+`prerequisite`+`mastery` 一一对应【已核实】 |
| **ALEKS / 知识空间理论 KST** | 用**优先关系（Precedence Relation）** 构建知识节点结构，形式化为 **DAG**（节点=知识单元、边=前置关系） | 与 `prerequisite` 边同构【已核实】 |
| 学习路径算法文献 | 用**拓扑排序**把概念图（DAG）转成序列；显式区分 **prerequisite** 与 **sub-concept** 两类依赖 | 对应 `prerequisite` 与 `subject/board` 归属【已核实】 |

> **本章判断**：教育域已经把"prerequisite 图 → 学习路径"做成标准范式，且**掌握度着色**是标配。本项目的 `PathBoard`（学习任务栏）其实已经是这套范式的**列表版**（见 §4.2）——思维导图视图可以视为它的**图形版**。

| mind-elixir | MIT | ✅ 内置 | ✅ CSS 变量 | ✅ | ✅ | ~28KB（0 依赖） | ✅ 备选 A |
| ECharts tree | Apache-2.0 | ✅ | ✅ | ❌ 仅 label | ✅ | ~368KB（全量，按需可减） | ✅ 备选 B |
| markmap | MIT | ✅ | ⚠️ 默认按层级，需自定义 | ✅ | ✅（需符合 schema） | view 24KB + lib 106KB | 次选（偏"Markdown→图"） |
| mermaid mindmap | MIT | ❌ **无** | ⚠️ 弱 | ⚠️ 有限 | ❌ 仅缩进文本 | ~173KB+ | ❌ 排除 |
| AntV G6 | MIT | ✅ | ✅ | ✅ | ✅ | ~400KB / 11 依赖 | ❌ 太重 |
| GoJS | **商业** | ✅ | ✅ | ✅ | ✅ | 闭源 | ❌ $6,990 起，成本不符 |

**首选 `d3-hierarchy` 的四条理由**：
1. **零新增依赖**：`d3-hierarchy` 是 `d3@7` 的子模块，项目已装 d3，切换视图不增实质体积【已核实】。
2. **技术栈统一**："可切换"本质只是换布局函数（`d3.forceSimulation` ↔ `d3.tree`），`d3-selection`/`d3-zoom`/transition 模式与样式体系可复用。
3. **需求全中**：折叠（官方 *Collapsible Tree* 范式）、**四色**（`attr('fill', d => masteryColor(d.data.mastery))`）、节点内 HTML（`foreignObject`，可放 `renderMarkdown` 结果）。
4. **JSON 驱动**：`d3.hierarchy(json)` 天生吃 `{id,name,children}` 树。

**自付成本**：折叠动画、命中区域、缩放平移、FitView 需自写（均有官方/社区即用范式，`d3-zoom` 已在依赖内）。

**"首选增强" `d3-flextree`（本轮新增，一句话：解决节点名长短不一导致的排版留白/撞车）**：`d3.tree` 假设**所有节点同尺寸**——`nodeSize` 是单一 `[dx,dy]` 对全体生效、与 `size` 互斥，无法表达"这个名字 4 字、那个 12 字"【已核实/d3-hierarchy 仓库 + D3 文档】。`d3-flextree` 支持**可变节点尺寸**且保持 **O(n) 线性**，算法谱系 = Reingold–Tilford(1981) → Walker(1989) → Buchheim–Jünger–Leipert(2002) → **van der Ploeg(2013)《Drawing Non-layered Tidy Trees in Linear Time》**，即该论文 Java 实现的 JS 移植；每个节点暴露 `size/left/right/extents`，便于画不同宽度的标签框【已核实/README】。**合规提醒**：许可为 **WTFPL**（公有领域等价），但**不含明示免责声明/专利授权**，部分企业合规策略会拒收 → 若本项目许可敏感，可退化为"给 `d3.tree` 的 `nodeSize` 取全树最大节点宽"，代价是留白。维护度偏低（约 366★ / 103 commits）但算法稳定。

**备选**：`mind-elixir`（要开箱即用 + 可编辑，DOM 渲染、风格与现有 SVG 不完全统一）；`simple-mind-map`（**MIT、12.8k★、框架无关**，支持思维导图/逻辑结构图/组织图/鱼骨图/时间轴多骨架；但① 官方 README 声明开源库**已进入低维护状态**、活跃开发转向闭源客户端，② 自带一套 JSON schema 与主题体系，接入需写"我们的 `nodes/edges` → 它的 schema"转换层，③ 会引入与现有 SVG 不统一的整套样式 —— **收益不抵成本，仅作兜底**）【已核实/README】；`ECharts tree`（要成熟库、接受 Canvas、不要求节点内 HTML）。

> **本章判断**：思维导图**首选 `d3-hierarchy` 自绘 SVG**——它在"零依赖 + 同栈 + 完全可控"上全面胜出；`markmap`/`mermaid` 本质上更偏"Markdown 文本→图"，与本项目"结构化数据→图"的方向不匹配；商业库（GoJS）与重框架（G6/ECharts 全量）不划算。

### 3.2 大括号大纲：实现方式

（详见「素材3」）三种渲染载体：

| 载体 | 做法 | 优 | 劣 |
|---|---|---|---|
| **纯 CSS**（首选） | 嵌套 `<ul><li>` + `::before/::after` 的 `border-top/left` 画连接线，`last-child` 特判 | 零 JS、语义化、可访问、易无限嵌套、可纯 CSS 折叠 | 大括号形状难精细；需 `last-child` 特判 |
| SVG path | `<path>` 画贝塞尔/大括号曲线 | 形状任意可控、可动画 | 需算坐标、需 JS 维护 |
| Canvas | 直接绘制 | 海量节点性能好 | 无 DOM/无障碍、事件需 hit-test |

- **连接线**：主流纯 CSS 做法（two-wrongs.com / SO），VS Code 文件树的"缩进引导线"即同款逻辑（`tree.indentGuidesStroke` 着色）【已核实】。
- **大括号本身**：横/竖大括号可用 **SVG path** 画（形状可控），或 Canvas（Gullwings，~1KB）；纯 CSS（`border`+`border-radius`+`rotate`）仅适合简单场景【已核实】。
- ⚠️ **未找到**成熟的"大括号作树连接符"现成开源组件库——需自绘，但难度低。

> **本章判断**：大括号大纲**用递归 Vue 组件 + CSS 连接线自绘**（成本最低、零依赖、与 `ForceGraph` 同为"自绘"哲学）；大括号作为**可选视觉装饰**用 SVG path 叠加。这条路线与 Roam/Logseq 的 outline 实现思路一致——**持有节点树 + 递归组件 + 每节点 `expanded` 状态**，而不是靠 Markdown 中转到 HTML。

**大括号形状本身（本轮补充）**：教育域的 Brace Map 是"**整体在左、大括号向右张开、部分在右、子部分继续向右**"【已核实/XMind Brace Map 工具页】。纯 CSS（`border` + `border-radius` + 旋转）只能画简单弧；要画**标准大括号**建议一处极小 SVG —— 一条 `path` 的 "{" 形，或给每个分组行左侧叠 `path`。⚠️ **但当前实现（`GraphBraceNode.vue`）用的是"缩进大纲 + 左侧竖引导线"（VS Code 文件树缩进引导线同款），并非象形大括号** —— 这是有意的取舍：纵向列表里，竖线比横括号更省空间、可无限嵌套、且天然适配 `overflow-y: auto`。若产品要"一眼看出是大括号"，M3 再叠 SVG 即可，属**纯装饰、不影响派生层**。

**另一条备选路线（本轮新增）**：若将来"依赖"的表达力需求超过"树"（多父密集、要保留全部边），可换 **`d3-dag`**（`erikbrinkman/d3-dag`）的 **Sugiyama 分层布局** —— 它专为**非树的有向无环图**设计，天然支持多父与分层，是"不降级成树"的第三条路【已核实/仓库 + Observable 示例】。代价：新增依赖，且需先把图**断环**成 DAG（回到 §2.1 的 FAS）。当前数据规模（prerequisite 128 条、见 §八）不构成引入理由，**记录备用**。

### 5.1 总体架构：`graph` 视图按偏好挂载一种画法，切换入口放**设置页**

### 5.2 派生算法契约（核心，纯前端）

新增 `frontend/src/utils/graphTree.js`——**纯函数、无 Vue、无副作用、可脱离浏览器单测**（与 `forceGraphEngine.js` 同哲学）：

**A. `buildTaxonomyTree(nodes)` → 归属树（供大括号大纲）**
- 分组：`subject`（空 → "未分类"）→ `board`（空 → "未分组"）→ 节点。
- 输出 `{ id, name, kind, children }`；`kind ∈ {subject, board, node}`。
- 复杂度 O(n)；**无环风险**（纯分组，不涉边）。
- 排序确定化：subject/board 按名称或后端 `subjectSummaries` 顺序，节点按 `name`/`mastery`——**必须确定**，否则每次渲染顺序抖动。

**B. `buildDependencyTree(nodes, edges, { rootId })` → 依赖树（供思维导图）**
1. **只保留 `relation === 'prerequisite'` 的边**（related/confusion/extension 不参与成树）。
2. 建邻接表 `from → [to]`（`A→B` 表示 A 是 B 的前置，B 是 A 的后继）。
3. **根选择**：给了 `rootId` 用它；否则取"入度为 0 的节点"（无前置）作**多根**，用一个虚拟根 `{kind:'root'}` 统合为单棵树。
4. **BFS/DFS + `visited` 集合忽略回边**（环检测即回边检测，CLRS Lemma 22.11）——**天然防环**。
5. **多父处理**：节点首次被到达即入树；后续再有父到达它的 prerequisite 边，记为"次父"（可作虚线/角标），**不重复入树**。主父可优先取"拓扑序更早 / `confidence` 更高"的父。
6. **防御**：设最大深度上限（如 50）防退化栈溢出；空图/无 prereq 边 → 退化为"平铺一层"（所有节点并排）。

**输出统一为 `{ id, name, mastery, children }`**，两种视图各取所需：
- 大括号：递归组件直接吃 `children`；
- 思维导图：`d3.hierarchy(tree)` → `d3.tree()` 布局 → 自绘。

> **判断**：把"派生"独立成**纯函数**，是本方案的关键工程决策——它让"图→树"这件事**可单测、可复用、与视图解耦**，也避免把算法逻辑散进两个组件里。

## 七、风险、边界与未决问题

### 7.1 风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| **成环 / 多父**导致派生失败或节点重复 | 高 | §5.2 的"回边忽略 + 首次到达入树 + 主父规则 + 深度上限" |
| 误把"树"当"图"——用户以为缩进=依赖关系 | 中 | UI 明确标注：大括号=**归属**（含/属），思维导图=**依赖**（先学/后学）；图上不放 related/confusion |
| **丢失边信息**（related/confusion/extension 在树上不可见） | 中 | 保留力导向图作为"完整关系"视图；树视图只作**投影**，并在入口说明 |
| 大图（数百节点）树渲染性能 | 中 | 默认折叠到第 2 层；必要时 M3 引入虚拟滚动（素材3：`react-arborist` 类思路） |
| 派生树与 `PathBoard` 口径不一致 | 中 | 两者共用同一"分层"定义（后端 `path_board` 已有）；单测对齐 |
| 与"节点小节化"混淆 | 低 | 小节化在**内容层**（节点内 MD），本方案在**渲染层**，互不干扰 |

### 7.2 边界（本方案明确不做）

- **不改 `nodes`/`edges`**，不新增 SQLite 表，不动建图/检索/出题/统计。
- **不引入重型图库**（ECharts 全量 / G6 / GoJS）——违背"复用现有 d3"的初衷。
- **不做自动聚类/主题发现**（那是 9/26 已否决的方向）。

### 7.3 未决问题（需产品/需求确认）

1. 大括号大纲是否**只需归属树**，还是也要一个"依赖树模式"（与思维导图切换同一份树的不同画法）？
2. 思维导图的**根**如何定：按"入度为 0 的多根"（多棵森林）还是强制单选一个目标节点？
3. 是否需要**导出**（Markdown 大纲 / PNG）？
4. 树内节点是否要**预览正文**（复用 `renderMarkdown`）还是只显示 `name` + 掌握度色环？
5. **（本轮实测新增）`board` 近乎全空**（见 §八）→ 大括号视图当前只有两层："接受两层 + 诚实标注未分组"，还是"先补 `board`"？后者属**建图侧改动**（`graph_builder`/`graph_generator` 是否产出 `board`），**超出"只改渲染"边界**，必须先拍板；这直接决定 M1（大括号）是否值得先做。

**本轮新增未决（2026-10-11，幕布对标，详见 §九）**：
6. **下钻态要不要持久化**：`viewRootId` 每次进图谱都从根开始（简单、可预期），还是写 `localStorage` 记住上次钻到的位置（连续使用更顺）？前者成本为零，建议先做前者。
7. **节点悬停工具条放哪些动作**：`进入主题` / `打开详情` / `展开-收起` / `在图谱中定位` 里选几个？（幕布的做法是悬停出工具条，把动作收到节点上。）
8. **同源双画法的入口位置**：放在 M4 的面包屑条上（离当前树最近，且只对树视图可见），还是也进设置页（与"布局"并列、但会引入"排列组合"式选项）？——见 §9.4-M5 的判断。

**本轮已定（2026-10-10）**：
- **Q2 已定**：依赖树的根取"**入度为 0 的多根 + 一个虚拟根统合**"（`graphTree.js::buildDependencyTree`，已实现）——不强制单选目标节点。
- **布局切换入口已定**：**图谱页内不再放切换器**，改由**设置页「知识图谱 · 默认布局」**唯一入口（`settings/GraphPane.vue`），偏好经 `graphLayout.js` 单例持久化到 `localStorage`，图谱页只按偏好渲染。理由：图谱页要保持"看图"的纯粹，三选一的控件常驻会与画布控件（缩放/图例/任务栏）抢位置。

## 八、本地库实测（2026-10-10 抽样，`data/knowledge/knowledge.db`）

> 口径：直接读 SQLite 快照，不改数据。目的 —— 验证"这套数据结构**现在**真的能画成两棵树吗"，而不是只论证"理论上能"。
> ⚠️ 数字为**本次抽样**，写材料前需重跑。口径：节点按 `nodes.user_id` 分组统计（`subject`/`board` 直接取自 `nodes`）；边按 `edges.relation` **全库**统计（本次未做 per-user 拆边）。

**实测结果**

| 观测 | 数值 | 对渲染的含义 |
|---|---|---|
| 节点规模 | 全库 ≈161 节点；主力 `user 5` 独占 **122** | 单学科切片后规模不大 → 首屏性能**不是**当前瓶颈 |
| `nodes.board` 非空率 | **近乎 0**：`user 5` 的 122 个节点 `board` **全空**；仅 `user 9902/9999/10004` 有少量（算法进阶/编程基础/递归/定积分） | **归属树退化**：所谓"学科 → 知识板块 → 知识点"实际只有"学科 → 知识点"两层，`board` 层恒为"未分组" |
| `nodes.subject` 质量 | `user 5`：数据结构 38 / 线性代数 56 / 高中物理 23 / 其余各 1–2；**`user 1` 出现 `what`/`测试`/`测试标签`/`核心概念` 等噪声** | 归属树顶层分组**质量参差**：主力账号干净，历史/测试账号脏；顶层若改按名称排序，噪声 subject 会顶到前面 |
| 边按 relation | `prerequisite` **128** / `related` 87 / `extension` 32 / `confusion` **3** | **依赖树（思维导图）有真实原料**，是本项目里信息量最大的树视图 |
| 边被丢弃量 | 依赖树只吃 `prerequisite`，**丢弃 87+32+3 = 122 条**（约占全部边的 **49%**） | 印证 §七.1："树是投影、不是全图" —— **力导向视图必须保留** |

**结论（对方案的直接影响）**

1. **优先级反转**：原方案 §5.4 定"先做 M1 大括号"。**实测后建议反过来——先做 M2 思维导图**：`prerequisite` 有 128 条真边，而 `board` 是空的，**大括号视图当前 ≈ 一个按学科分组的长列表**，收益低；思维导图才是"新信息"。
2. **大括号视图需要产品决策**：要么接受"两层大纲"（诚实标注"未分组"），要么补 `board` —— 但补 `board` 属**数据/建图侧**，不在"只改渲染"范围内（见 §7.3-Q5）。
3. **性能待实测项可降级**：单学科切片 ≤ 数十节点，§六里"300 节点首屏"的实测优先级下调。
4. **`confusion` 仅 3 条**：与 `related/extension` 一起只在力导向视图可见 → 进一步确认"**两种树 + 一张图**"的三视图结构合理：图保关系、树保层级。
