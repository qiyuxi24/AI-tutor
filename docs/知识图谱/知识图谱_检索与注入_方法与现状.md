## 1. 方法论：检索 → 选形 → 注入 → 预算流水线

> "路径查询"与"节点注入"是**同一条流水线的两端**，必须一起设计：图上检索决定"取到哪些节点"，注入形式决定"这些节点以什么面貌进入提示词"，预算决定"能放多少"。任一失配，收益都会被吃掉大半。

```
用户查询 / 上下文
   ├─(1) 检索 retrieval —— 图上"路径查询"：从哪进、走几跳、取哪些子图或路径
   ├─(2) 选形 serialization —— 三元组？自然语言？JSON？取多少条？
   ├─(3) 注入 injection —— 放系统提示词（always-on）还是工具返回（on-demand）？放头/中/尾？
   └─(4) 预算 budget —— 给这段多少 token？超了剪谁？
```

**术语**：**路径查询** = 在图上从锚点出发、按边关系取节点序列/子集（含图遍历、最短路、PPR、beam search、Cypher）；**always-on 注入** = 每轮固定写入系统提示词，**on-demand 注入** = 由模型按需通过工具取回；**S4 / S6** = 本项目预算框架里"图谱结构注入"与"图谱检索正文注入"两段的编号。

### 1.1 路径查询范式地图

| 查询类型 | 首选检索范式 | 代表实现 | 取数代价 |
|---|---|---|---|
| 实体级（"关于 X 的一切"） | 实体锚点 + 邻域/社区扩展 | GraphRAG Local | 中 |
| 全局/主题级（"整体在讲什么"） | 社区摘要 Map-Reduce | GraphRAG Global | 高（预生成） |
| 多跳关系（"A 和 B 怎么连上"） | 有界多跳 / 路径检索 / PPR | ToG、RoG、GNN-RAG、HippoRAG | 中–高 |
| 语义不相似但结构相关（先修/前置） | 沿特定边**反向**遍历 + 深度衰减 | 本项目扩跳 | 低 |
| 需要精确可复核的关系 | 图查询语言 | text→Cypher（Neo4j） | 低 |

- **GraphRAG 三模式**（arXiv:2404.16130）：**Local**（实体锚点 → 关联实体/关系/协变量/社区报告/原始文本块，**候选排序并裁剪到预定义上下文窗口** ← 注入体量是被显式截断控制的）；**Global**（忽略实体级检索，对选定层级社区摘要做 Map-Reduce）；**DRIFT**（先用社区级上下文拿全局视图，再生成后续查询交给 local 深挖）。
- **双层关键词 / PPR**：LightRAG（arXiv:2410.05779）低层=实体、高层=主题，图与向量并存，支持**增量插入**；HippoRAG（NeurIPS'24）在 KG 上跑 **Personalized PageRank** 做多跳记忆检索；TERAG（arXiv:2509.18667）轻量 NER 建图 + PPR，构建 token 以 TERAG=100% 为基线时 AutoSchemaKG 为 861%、LightRAG 为 1434%，保留 ≥80% 精度。共同点：**先用便宜手段压小候选，再让 LLM 处理**。
- **Agentic 多跳**：ToG（ICLR'24）beam search + LLM 打分，产出可验证推理轨迹；RoG 先生成关系路径；GNN-RAG（arXiv:2405.20139）GNN 推理 + 最短路径 verbalize（WebQSP/CWQ **8.9–15.5%** 提升）；Graph-R1（arXiv:2507.21892）知识超图 + 双路检索 + RRF + GRPO。**取舍**：复杂多跳/OOD 优势明显，但引入多轮 LLM 调用延迟 → 教育对话场景更适合做**兜底**而非默认。
- **剪枝**（控制注入体量的关键）：图遍历子图规模随跳数指数增长。PathRAG（arXiv:2502.14902）用**距离感知 flow-based 剪枝**（按 hop 衰减传播资源，取 top-K 路径，路径比 ego-network 更紧凑）；G-Retriever 用 PCST；SubgraphRAG 用 MLP 抽子图。**剪枝不只是省 token，更是去噪**（冗余子图本身就是噪声源）。
- **混合检索融合**：图补"语义不相似但结构相关"的召回、向量补语义相似，并行跑再融合（**RRF**：`score = Σ 1/(60+rank)` 或加权线性）。本项目 P1 的"向量初检 + 图扩跳补充"（补充命中 `score = 初检最高分 × 0.6^depth`）是一种简化的加权融合。
- **text → Cypher**：让 LLM 直接生成图查询（Neo4j + LangChain `GraphCypherQAChain`）；要点是 CoT 提示（先识别核心实体→关系→再写 Cypher）与图谱 schema 速查。**本项目不优先**（用户级个性化图、schema 动态）。

**本项目在范式地图上的位置**：走"**系统提示词注入框架 + 有界反向扩跳**"——扩跳只沿 `prerequisite` 边**反向回溯**（补前置），补充条数 ≤ top_k，默认 `hops=0`（关）。它属于"实体/知识点锚点 + 邻域扩展"的轻量版，以"深度衰减 + 条数上限"充当剪枝。**是少数派但合理**——教育场景的图是"教学参照系"，不需要社区摘要那一套。

### 1.2 注入形式与序列化

**三种整合层次**（Graph RAG 综述 arXiv:2501.13958v2）：(a) 微调开源模型（node/path/subgraph-level）；(b) **上下文学习 ICL（本项目所属）**——把图转成自然语言描述、graph-enhanced CoT、Collaborative KG Refinement。→ 我们**不做微调**（无标注、成本高），故"**序列化形式 + 位置 + 预算**"就是全部可调空间。

**verbalization 五种做法**：KAPING（arXiv:2306.04136）线性拼接三元组优于特意设计的 graph-to-text；**K-BERT 的"Knowledge Noise"**（直接拼三元组会与句 token 密集交互 → 需软位置 + 可见矩阵隔离）——**值得警惕：不加结构分隔会把"图里的事实"与"用户话里的语境"混为一体**；ERNIE 3.0、KG-to-Prompt（DPO 优化 verbalization）、DALK（LLM 自 rerank top-k 三元组）。

**三元组 vs 自然语言：证据冲突（最需提醒的一条）**：
- 支持"三元组更好"：Dai et al.（arXiv:2402.11541）raw linearized triples 比 polished prose 更有效（减少语言噪声）；GIVE（arXiv:2410.08475）多数情况 triplets 准确率高于 text。
- 支持"自然语言更好"：CoTKR（arXiv:2409.19753）§5.8 明确"我们的结果相反"。
- **推论**：序列化形式**无普适最优解**，必须对自己的任务做 A/B 实测，别照搬单篇。

**工程三选项**（【二手】BigData Boutique）：triple list（省 token，难推理）/ 自然语言叙述（易推理，token 约翻倍）/ 结构化 JSON（折中）；建议子图上下文上限 **1–2K token**、返回子图而非整条路径、cap fan-out、**~200ms/query** 预算。

**位置与顺序是一等公民**：相关信息在**头/尾最好、正中间显著下降**；越靠后的文档贡献越小 → rerank 后把**最强证据放头/尾（bracketing）**、问题置**末尾**（recency boost）、先 cross-encoder rerank。

**注入纪律（负向规则，来自 P1 实测）**：当图谱检索为空时，LLM **不会说"我不知道"**，而是**向学生断言"你的知识图谱可能还是空的"**（测试图谱实际有 7 个节点）——这是**对学生个人数据的错误断言**，比"答不出"更有害。处理：区分"图谱为空"与"本次检索未命中"，并**明确禁止向学生断言图谱内容状态**。另一工程做法：给注入内容打**来源标签**（`[图谱结构]/[图谱检索]`）并声明"视为先验知识"，避免与用户话术混淆。

### 1.3 如何"保持性能"：位置、注意力与预算

**图 RAG 本身就有 token 优势**：快速图库上比传统方法**少用 26%–97% token**，且易更新（加/删节点边即可）。**用图的目的不是塞更多，而是用更少的 token 表达更结构化的关系**。

**效率实测**（可直接引用）：TERAG 构建 token 仅 3–11% 输出 token 达 Full-KG 80% 准确率；FactRAG/HybridRAG 在 Finance Bench 上幻觉 −6%、token −80%；Graph-R1 每 1K token 构建 5.69s/$2.81（GraphRAG 8.04s/$3.35）。

**位置与注意力：为什么"塞得多"反而更差**（四条硬证据，均来自本项目预算框架已核验论文）：
- **RULER / 有效上下文**（arXiv:2410.18745）：多数开源模型**有效上下文不足训练长度 50%**；机制是位置频率左偏；多数失败集中在**文档前 1/3**（开头也不是绝对安全区）。
- **Databricks 长上下文 RAG**（arXiv:2411.03538，20 模型 × 2000+ 实验）：正确率随上下文**先升后降**，多数开源模型峰值在 **8K–32K**；**召回率单调上升、正确率不单调**（信息在，但用不上）；成本线性（8K→128K 输入成本 **16×**）。
- **Lost in the Middle**（arXiv:2307.03172）：相关信息在头/尾最好、正中间显著下降（**U 型**）；GPT-3.5 答案位于正中时 **52.9% < 闭卷基线 56.1%**；query-aware contextualization 在键值检索上把 300 键值对准确率 **45.6% → 100%**。
- **Chroma《Context Rot》**（2025-07）：**1 个干扰项即让性能低于基准**；打乱的干草堆一致优于逻辑结构化的（不要迷信排版）。

> **综合推论**：注入段存在一个**倒 U 型的 sweet point**——**"多"不等于"好"，超过拐点后每多一个 token 都在净亏。**

**项目预算框架把上述规律固化成配额**（`docs/上下文工程/上下文工程_预算框架.md`）：单一预算 **B = 48K token**、裁剪线 = B − 输出预留 = **45K**；九段（K token）：S1 输出预留 3 ｜ S2 静态指令 1 ｜ S3 工具/技能 5.4 ｜ **S4 图谱结构 6** ｜ S5 用户画像 0.8 ｜ **S6 图谱检索 2** ｜ **S7 知识库检索 2** ｜ S8 对话历史 **21** ｜ S9 当前轮 6。**关键规则**：S6+S7 **目标合计 4K、上限合计 6K，且不随预算放大而放大**（多出的额度给历史 S8）——因为**检索段是唯一"越多越差"的段**。→ 图谱相关注入（S4+S6）在 48K 预算下**合计约 8K token 是安全线**。

### 1.4 最佳注入策略

**第一决策：何时注入**（业界针锋相对）：**always-inject 派**（ChatGPT 记忆 = 始终注入）vs **on-demand 派**（Claude 按需检索；Claude Code/Codex/Gemini CLI 的记忆"比想象中简单"——没有 RAG、没有知识图谱，就是滑动窗口）；Context Engineering 的三档：pre-retrieval / just-in-time / progressive disclosure；**分层记忆范式 = always-on 层保持极小，丰富知识存深层按需检索**。

**本项目已用实测回答**（见 §3）：**系统提示词注入图谱摘要是主收益来源**（期望知识点命中率首跑 **25.0% → 62.5%**；依赖个人状态的题 **30.0% → 80.0%**；token 仅 **+6%**）；剥夺图谱后模型反复徒劳检索并**反过来断言"你的图谱是空的"**。→ 对"**依赖用户个体状态**"的查询，**稳定注入 > 按需检索**；对**开放语料问句**，按需检索更省。**最佳答案是分层**。（⚠️ 上述"命中率提升"于 §3.5 重跑**未被复现**，引用须看修正口径。）

**第二决策：注入内容怎么组织**：剪枝 / 路径化代替 ego-network / rerank（最强放头尾）/ 混合检索融合（RRF）/ 压缩摘要（大子图先小模型摘要）/ 预算硬上限 / 深度衰减 + 条数上限。

**八条最佳实践**：① 分层（小 always-on 层 + 大 on-demand 层）；② 分场景定时机；③ 有界取数（有界多跳 + 只沿需要的边方向 + 剪枝/衰减/条数上限）；④ **序列化做 A/B**（证据冲突，必须自测）；⑤ 排位置（最强放头尾、问题置末）；⑥ 给硬预算（检索段固定小配额不随总预算放大）；⑦ 守纪律（区分图空/未命中、打来源标签、禁止断言图内容状态）；⑧ 可观测（用**规则可算的指标**做 A/B，**零额外 LLM 调用**）。

**决策矩阵（查询类型 × 约束）**：依赖用户个体状态 → always-on（结构）+ on-demand（细节），锚点 + 反向先修遍历，S4 固定/S6 小配额；实体级问答 → on-demand，实体锚点 + 邻域，≤2K；多跳关系 → on-demand（必要时 agentic），有界多跳/路径/PPR，≤2K；全局/主题性 → on-demand，社区摘要 Map-Reduce，固定层；需精确可复核 → on-demand，text→Cypher。

## 2. 注入链路改造设计（方法论 → 本项目）

### 2.1 先把 S4 与 S6 分开治理（最关键的结构性动作）
预算框架已明确：**S4 图谱结构注入（框架/定界：节点名 + 掌握度 + 边）** 与 **S6 图谱检索注入（正文片段）** 是**两件事**，混在一起谈会让两边都调不准。

| 维度 | S4 图谱结构注入 | S6 图谱检索注入 |
|---|---|---|
| 内容 | 节点名 + 掌握度 + 边（"可见框架"） | 检索命中的正文片段（"证据"） |
| 时机 | **always-on**（每轮，定界用） | **on-demand**（按需，可重检索） |
| 配额 | 6K（目标）/ 8K（上限） | 2K（目标）/ 3K（上限） |
| 降级 | 节点数超限则截断（按学科/掌握度） | 超限则剪枝 / 只留 top-k |
| 主要风险 | 体量超限挤占历史 | 命中无关→噪声；空结果→幻觉断言 |

### 2.2 四环节改动点
- **检索侧**：扩跳 `DEFAULT_HOPS` 保持 0（零回归），"学生卡住/需前置"场景的 `hops=1` 在系统提示词/工具描述显式引导；保持**只沿 `prerequisite` 反向**；保留深度衰减 + 条数上限。
- **选形侧（新增 A/B）**：新增**三元组 vs 自然语言**的注入形式 A/B（§1.2 证据冲突，必须自测），用规则指标（命中率/token/轮数）评判、零额外 LLM 调用；子图上限对齐 **1–2K token**，超限**先剪枝再摘要**（不直接截断）。
- **注入侧**：S4 结构注入放前段充当"定界"，S6 正文按相关度排序、最强靠头/尾、问题置末；给注入段打**来源标签**；**负向规则（必做）**：区分"图谱为空"与"本次检索未命中"，明令禁止向学生断言图谱内容状态。
- **预算侧**：S4 = 6K / S6 = 2K 硬上限，检索段不随 B 放大；新增工具先算固定成本（**222 token/工具**，12 个工具 schema 即 2661 token）。

### 2.3 验收与评测口径（复用 P1 的规则化框架）
主指标 = 期望知识点命中率；辅助 = 图谱提及数、检索调用次数、token、LLM 轮数、**误报"图空"数**；新增 = 注入形式 A/B（三元组 vs NL）；方法学自证 = 说明哪些是 mock、真实路径是什么。

### 2.4 落地路线（P2 建议）
P2-1 注入侧负向规则（区分图空/未命中）｜P2-2 S4/S6 分开记账 + 硬上限｜P2-3 序列化形式 A/B｜P2-4 子图上限 1–2K + 超限剪枝/摘要｜P2-5 向量检索欠费修复（**已解除**，2026-09-26 充值）。

## 3. 扩跳与 A/B 对照实验

### 3.1 P1-1 图谱检索扩跳
**为什么**：向量检索只能召回**语义相近**的节点，而前置知识常与当前问题语义不相似（学生问"动态规划"，召回不到"递归""记忆化"，但这恰是卡住根因）→ 用**图结构**补齐这类召回（对应 AI_Tutor 的 `kg_hop_depth`、HippoRAG 多跳）。
**实现要点**：位置 `RagManager.search()`（返回结构不变 → 上层零改动）；**只沿 `prerequisite` 边反向回溯**（补前置不补后继，注入进阶属超纲）；打分 `score = 初检最高分 × 0.6^depth`（保证排语义初检之后）；**补充条数 ≤ top_k**；**默认 `hops=0`（关闭）**，LLM 可在 `rag_search` 按需传 1~2。
**交付物**：`core/rag/manager.py`（`search(hops=)`）、`core/agent_tools.py`、`core/rag_tool.py`、`services/chat_service.py::_build_retrieval_context(graph_hops=)`、方向 bug 修复（见 §3.2）、`backend/scripts/eval_graph_injection.py`、`backend/eval_data/graph_injection_cases.json`、回归 `tests/test_kg_prerequisites.py`。

### 3.2 顺手修复：先修边方向 bug（重要）
`get_prerequisites` 的 SQL 方向反了。**全库统一语义**（`add_edge`/`topological_sort`/`knowledge_writer`/`graph_generator` prompt 四处一致）：**`A → B (prerequisite)` 表示 A 是 B 的前置**。修复前沿 `from_node=?` 取 `to_node` → 拿到的是**后继**。**影响面（4 个调用点、3 个受影响）**：`get_next_to_learn()`（把更高级内容当"建议先巩固的先修"）、`get_learning_path(target)`（目标的前置链全丢）、`GET /knowledge/node/{id}`（"前置依赖"显示的是后继）。修复 = 递归 CTE 里 `from_node`/`to_node` 对调 + docstring 写准语义。**这是 P1 的意外高价值产出**——错在教学主逻辑（"下一步学什么"）上，且属静默错误（不报错、只是答案反了）。

### 3.3 图谱开/关 A/B 对照（首跑，2026-09-12，5 例）
**设计（单变量）**：组 `off` 不注入图谱摘要 + `pipeline.unregister("graph")`；组 `on` 注入 `build_graph_context(detailed=True)` + graph 源正常注册；其余（模型/温度/画像/工具集/检索注入）全同。问题分 `general`（2 例，验证图谱**没有**造成过度限制）与 `graph_dependent`（3 例，验证参照系 L1/L2 的价值）。**指标全部规则计算，零额外 LLM 调用**。

**首跑结果**：`off` ALL 命中 **25.0%**（4/16）、`on` ALL **62.5%**（10/16），Δ +37.5pp；`graph_dependent` **30.0% → 80.0%**（Δ +50pp，2.7×）；token **+6%**（86392 → 91495）但回答更长（261→305 字）。

**三个关键发现**：① 图谱价值集中在"依赖学生状态"的问题，且对通用问题**无副作用**（`general` 也 16.7%→33.3%，未出现"超纲拒答"）；② **"始终注入 vs 按需检索"教科书级对照**：同一道"学 DP 前置够不够"，关闭组 8 轮/21295 token/命中 1/3，开启组 3 轮/**13552 token**/命中 **3/3**；③ 关闭组产出**关于学生图谱的确定性幻觉**（"你目前的知识图谱**可能还是空的**"，而测试图谱实际有 7 个节点）。

### 3.4 实验暴露的问题（后续处理项）
| # | 问题 | 证据 | 建议 |
|---|---|---|---|
| 1 | **嵌入 API 欠费，向量检索静默降级** | `text-embedding-v4` 返 `Arrearage`；捕获异常后返回空 | 优先处理（**2026-09-26 已充值解决**） |
| 2 | **检索为空时 LLM 断言"图谱是空的"** | 关闭组 d1/d2/d3 均出现 | 区分"图谱为空"与"本次未命中"，禁止断言图谱内容状态（涉及 L1 定界边界） |
| 3 | **LLM 用节点名称当 `node_id` 调工具** | 开启组 d2：`E-LLM-007 节点不存在：递归` | 工具参数描述强调"传 node_id 而非节点名" |

### 3.5 重跑：扩样本 + 口径修正（结论与首跑相反，2026-09-23，14 例）
**为什么重跑**：① 图谱 schema 改造落地（KG-D1~D6）；② 嵌入 API 恢复；③ A/B 被列为补齐评测的第一优先级；④ 首跑仅 5 例。数据集扩到 **14 例**（7 general + 7 graph_dependent，同一张合成图谱 7 节点/6 边）。首跑报告归档为 `eval_data/graph_injection_report_20260912.json`。

**口径修正（原指标会把"答对"记成"没答对"）**：重跑第一版结果相反（39.0% → 29.3%），逐条读回答后定位到**指标缺陷**——注入图谱后模型倾向抄 `node_id` 指代节点（ID 只存在于注入块里），只按中文名匹配就把这类回答判 0；反过来关闭组看不到图谱只能猜名字，猜中反而计分 → **指标同时惩罚正确行为、奖励猜测**。修正为三条口径（`--rescore` 可离线重算，不必重跑 LLM）：**定位率**（`expect_located`：中文名 ∪ node_id，词边界匹配）、**引用真实 node_id**（`cited_ids`：机制证据，关闭组按构造为 0）、**状态误述**（`state_misclaim`：误报图谱空 ∪ 掌握度误述，用 `nodes.mastery` 真值对照）。

**重跑结果（14 例 × 1 次运行 × MiniMax-M3）**：`off` ALL 命中(按名) 39.0% / **定位率 39.0%** / 检索 42 / 状态误述 2 / 319,982 token / 引用真实 ID **0/14**；`on` ALL 命中(按名) 29.3% / **定位率 36.6%** / 检索 **0** / 状态误述 **0** / **112,047 token** / 引用真实 ID **5/14**。

**四条结论（按证据强度）**：① **机制证据（最硬）**：开启组 5/14 引用真实 `node_id`、关闭组 0/14 → 注入确实生效；② **知识点覆盖持平**：公平口径 **39.0% vs 36.6%**（差 1 个期望点）——图谱注入既没降低覆盖，**也没有首跑那样的提升**；③ **成本与失败模式方向一致且幅度大**：token **−65%**、检索次数 **42 → 0**；④ **对学生状态的错误断言 2 例 → 0 例**（关闭组把责任推回学生，开启组用真值作答——这正是 L2"现在在哪"的价值）。

> ⚠️ **引用这些数字前必须知道**：**两次运行结论相反**（首跑 +37.5pp / 重跑 −2.4pp）→ 该指标**不稳定**，单次小样本不能作结论；写进任何材料前需**多次重复取均值 + 锁定模型版本**。且"定位率"仍**不等于答案质量**（只回答"有没有提到应提的知识点"，不判对错/讲解恰当性）。**任何地方引用此实验，都必须写成"首跑 62.5%，重跑未复现（持平）"。**
> **局限**：样本小（5/14 例、各 1 次运行、单一模型）；mock 嵌入下图谱 RAG 质量偏低（主变量是纯文本摘要注入，不受影响）；`general` 受"苏格拉底式反问"风格影响，只能横向对比；指标为规则匹配（两方向都会错）。

## 4. 现状诊断（2026-10-11，基线 `035b759`）

> 针对用户反馈两点：①「AI 不能自己新建知识图谱」②「每次知识图谱注入都是固定的，应该按用户问什么注入什么」。**两条都成立**，但根因不同，其中第二条更严重。本节只做**诊断**（是什么/为什么/证据）；改法与排期见 §5。

### 4.1 结论速览
| # | 判断 | 严重度 | 一句话根因 |
|---|---|---|---|
| ① | **AI 能建"节点"，但建不了"图谱"** | P0 | 没有「一次建骨架图」的工具；`decompose_question` 只是 HTTP 端点、**不在 agent 工具表**；`add_knowledge_node` 是 `tier=ask`（须先问）且一次只建 1 个节点，还要求模型自己写完整 Markdown |
| ② | **S4 图谱结构注入确实是"固定"的** | P1 | 入口函数**没有 query 参数**，同一张图两次调用返回逐字符相同文本 |
| ③ | **本该"按需"的 S6 图谱片段检索在产品链路上基本是死的** | **P0（最严重）** | `rag_manager.index_node` 全仓库**只有 1 个调用点**（后台图谱分析路径）；工具/手动/问题拆解/书籍建图 4 条写路径都不索引 |
| ④ | 真实数据佐证：最活跃用户 **122 个节点只有 5 个可被图谱检索（4.1%）**，BM25 腿为 0 | P0 | 同 ③ |

**总括**：图谱的「结构」每轮全量固定注入，「内容」本该按问题检索却因**从未建索引**而长期为空 → 用户看到"无论问什么都注入同一坨东西"。**"按需注入"不是设计缺失，是索引链路断了。**
> ⚠️ 需说清：**S4（结构）每轮必在不是 bug**，而是契约 L1 不变量（图谱是教学可行域，每次调用必须定界）；缺的是契约自己承认**还没做**的那半步：**选片**。

### 4.2 现状链路（实测）
```
POST /chat/stream → process_message_stream
  ├─ _build_system_prompt(inject_tools=True)
  │   ├─ _build_graph_summary(kg, detailed=True, focus_node_id=current_node)   ← ★ 无 query
  │   │    └─ GraphStructureSource.retrieve()  required=True，不看 query
  │   │         └─ graph_analyzer.build_graph_context(全量节点+全量边)
  │   ├─ _build_retrieval_context(last_user_msg, ...)   ← ★ 真正的按 query 检索（S6/S7）
  │   │    └─ GraphRagSource(query) → rag_manager.search() / KbRagSource(query) → kb_manager.search()
  │   └─ 组装 system_prompt_common.j2 的 {{ knowledge_graph_summary }}
  ├─ run_agent_loop(...)
  └─ await _analyze_and_apply(...)   ← ★ 全仓库唯一调用 index_node 的地方
```
两条通路分工：**S4 图谱结构**（每轮无条件，`required=True` 绕过节流与源选择）→ **正常工作、固定**；**S6 图谱片段**（有 query 且过 router 节流且被 `ctx.sources` 选中）→ **基本为空**；**S7 知识库片段** → 正常。

### 4.3 问题一：AI 建不了"图谱"（只能建"节点"，且被约束绑住）
**工具层面**：`add_knowledge_node` 能成功建节点 + 落 MD（实测 `node_inference: true, md_exists: true`），但**建"一整张图"的能力没有**，三层收紧：① **没有"一次建一批"的工具**（拆解成依赖树、批量建骨架、断点续填正文均已实现，但 `decompose` 只在 `POST /knowledge/decompose`，**不在 `NATIVE_SPECS`**，前端也无人调用 → **孤儿端点**）；② **授权分级归为"须先问"**（`tier=TIER_ASK`），且一次 run 工具调用上限 **12**（`AGENT_MAX_TOOL_CALLS`）、轮数上限 5 → 一轮建不出 >12 节点的图；③ **空图谱指引把"建节点"与"先检索到依据"绑死**（新学生无资料 → `rag_search` 必返空，字面读作"没依据就别建"）。

**更硬的缺陷：建了也不进图谱 RAG 索引**：`rag_manager.index_node` 的调用点只有一处（后台 GraphAnalyzer 路径）。对比 6 条写路径只有它索引（工具建节点 / 改正文 / 手动建节点 / 问题拆解 / 书籍建图 **全部 ❌**）。实测（离线探针）：工具建节点后 `vector_chunks=0, bm25_docs=0`；显式调 `index_node` 后才有 `bm25_docs=1`。**这个不对称很致命**：删除路径（`DELETE`）都清索引，**建的时候不写**。

### 4.4 问题二：注入"固定"——固定是真的，"按需"那条路是断的
- **S4 入口没有 query 参数**（不是忘了传，是签名里没有）：`_build_graph_summary(kg, detailed, focus_node_id, max_chars)` 内部固定以 `query=""` 调 pipeline，连续两次返回**逐字符相同**文本；`focus_node_id` 只在**超上限降级时**决定保留谁。
- **固定成本随规模线性增长**（每轮重发）：10 节点 **1,463 字符/1,043 token**；50 节点 **7,343 字符/5,083 token**；与问"你好"还是"红黑树怎么旋转"无关。上限保护存在（`GRAPH_INJECT_MAX_CHARS=12000`）但那是**天花板不是相关性**；`TODO.md` 记录 S4 在 367 节点时已连续触发降级阶梯（**预算早已饱和、没有余量**）。
- **真正按 query 的 S6 检索，索引里几乎是空的**：真实数据（只读快照）——用户 5：122 节点 / 向量 chunk 17 / **可检索节点 5 / BM25 0 → 覆盖率 4.1%**；9902（演示）：7/14/7/14 → 100%；10004：2/0/0/0。**用户在演示里看到的"红红绿绿的图谱"与模型看到的"按需检索结果"不是同一份数据**。
- **兜底通道救不回来**：`_keyword_search`（name/summary 子串）**只在本次 query 两条腿都没召回时**才跑 → 同一未索引节点"时灵时不灵"，且每次都全量遍历节点，与"索引"本意相悖。
- **附带发现：节点名/小节标题根本不参与 BM25**：whoosh schema `heading=STORED`、`node_name=STORED`（**STORED 字段不建索引**），只有 `content` 走 `content_zh`；`MIN_CHUNK_CHARS=50` 会把不足 50 字符的段落整段丢弃 → **按知识点名称检索图谱**天然漏召；独立复核更狠：一个 5 小节正文只保留 2 节，整节知识点进不了索引（丢的不是碎片，是整节）。

### 4.5 与既有契约/文档的关系（避免把"有意设计"当 bug 改掉）
| 判断 | 契约怎么说 | 结论 |
|---|---|---|
| S4 每轮必在 | L1 不变量 I1-1「每次调用都必须注入可行域」 | **不是 bug**，不要改成"检索命中才注入" |
| 应按问题选片 | 契约 §5 G1 第 1、2 步（复用 `slice_graph` 做选片）**明确计划、标注"未做"** | 属**契约内已规划未落地** |
| 不要"检索式替换全量注入" | 契约 §8 明确不做：「参照系必须每次在……正确的是**选片**而非**检索**」 | 改法必须保留"定界常驻 + 按 query 选片" |
| 建节点不进索引 / `tier=ask` / decompose 非工具 / 空图谱指引 | 现行文档零覆盖或只有机制说明 | **真缺口**（须补） |

### 4.6 影响（不修的代价）
① **能力口径与宣传不符**（对外讲"图谱驱动的自适应导学"，但"自适应"的按需半边 S6 几乎不工作；材料写"自动沉淀/零人工录入"而代码真值是 `tier=ask` + 铁律「本轮只输出询问文本」→ 演示验证会当场对不上）；② **成本随规模线性上涨**（S4 每轮固定重发，50 节点 ≈ 5K token/轮，且上限已饱和）；③ **AI 写回闭环半瘫**（AI 建的节点下轮对模型自己都不可见 → 重复建或回答"你的图谱里没有"）；④ **演示脆弱**（唯一 100% 索引的是演示用户 9902，换真实账号静默降级为空且不报错）；⑤ **可观测性为零**。

### 4.7 附带发现（优先级另定）
① 后台图谱分析**阻塞流式收尾**（流式路径在 `[DONE]` 前 `await _analyze_and_apply`，非流式是 `create_task`，两条路径时序不一致）；② `rag_search` 工具的图谱检索也受同一索引缺口影响；③ `_analyze_and_apply` 与工具写路径**重复建节点**（只有分析这条路索引）；④ **S6 的 BM25 腿没有分数下限**（向量腿守 `MIN_SCORE=0.25`，BM25 腿只按"有词面匹配"放行 → 实测返回过 0.0933/0.1186/0.1513 的无关片段）；⑤ `_keyword_search` **硬编码默认 `data_dir`**（无视 `RagManager(data_dir=…)` → 隔离环境测不出来）；⑥ `data/rag`（图谱）与 `data/kb`（上传文档）是**两套完全独立的索引**（这解释了"知识库检索正常、图谱片段为空"能长期共存）。

### 4.8 边界（没验证什么）
**已实证**：代码路径/调用点/签名/常量（逐行读码）、索引写入/检索行为（离线探针，假嵌入）、真实库索引覆盖率快照、S4 体量与 query 无关（探针+签名+md5）、相关测试子集 95 passed。
**未验证（勿写进材料）**：真实 LLM 端到端行为（未跑真 key）、向量腿真实召回率、A/B 收益量级（不引用"25%→62.5%"这类**未被复现**的历史数字）、前端交互、全量套件。

> 诊断的可信度**不依赖**任何探针脚本的存在——主证据是代码锚点、静态调用点、真实库只读快照与测试基线。

## 5. 改进计划（P0-1…P2-4 施工项）

> 输入 = §4 诊断（问题/证据/根因）。判据：每条任务都有**可执行验收**（命令 + 断言）；不可机器复核的条目不写。

### 5.1 设计原则
① **定界与依据分开治理**（`定界`永远常驻，`依据`按 query 选；反面：把 S4 改成"检索命中才有" → 违反 I1-1）；② **选片 ≠ 检索**（全量骨架始终在；反面：选片过窄致可行域失真）；③ **创建即入索引**（任何写节点路径的终点都要可被检索）；④ **单一收口**（索引收口只加一处，4 条写路径共用）；⑤ **先便宜后昂贵**（选片用规则 + 已有 RAG 命中，不新增 LLM 分类）；⑥ **可观测**（覆盖率/命中率必须一条命令可见）。

### 5.2 任务总览
| ID | 任务 | 优先级 | 依赖 | 预估 |
|---|---|---|---|---|
| **P0-1** | 图谱节点**创建即入索引**（唯一收口） | P0 | — | 1 天 |
| **P0-2** | 空图谱指引解绑「必须先检索到依据」 | P0 | — | 0.2 天 |
| **P0-3** | 让 AI 能"一次建一张骨架图"：`decompose` 变 agent 工具 | P0 | P0-1 | 1 天 |
