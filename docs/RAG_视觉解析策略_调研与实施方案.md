# RAG 视觉解析策略：调研与实施方案

> 创建：2026-09-13
> 背景：用户提出「PDF 解析与识图能力是否不足？能否直接把文档交给视觉模型解析？」
> 上游文档：`RAG_文档解析模块_调研与去耦合设计.md`（2026-09-12，格式覆盖与去耦合）、`RAG_召回与重排优化调研.md`
> 本文件回答一个问题：**文档里的「图」和「版面」，到底用什么引擎、怎么路由、怎么控成本、怎么防污染。**
> 结论先行，数据在中，方案与分期在后，末尾是验证与待办边界。

---

## 一、核心结论（先看这段）

1. **「直传 PDF 给模型」这条路不存在**。MiniMax-M3 的 OpenAI 兼容 chat 支持 `image_url`（URL/base64、`detail` 分档、单图 ≤10MB、请求体 ≤64MB），但 content parts **只有 text / image_url / video_url，没有 PDF / document / file 类型**。任何「视觉解析」方案都必须**由我们自己把页面渲染成图**——省掉的只是「理解」，不是「投喂」。渲染层已经在手上（PyMuPDF），所以这不是障碍，但决定了工程量。
2. **现有的短板不是「识别精度不够」，而是「根本没识」**。逐条查证后：扫描判定是**整份文档级**（混合型 PDF 静默丢内容，属真 bug）；**内嵌图片/图表 100% 丢弃**（不抽取、不配对 caption、不描述）；表格被线性化打乱；公式出乱码且无检测。这些是**能力与逻辑缺陷**，不是模型选得不好。
3. **成本答案出乎意料：专用 OCR API 比通用视觉模型便宜约 31 倍**。`qwen-vl-ocr`（阿里百炼，华北2）输入 **¥0.3/M**、输出 **¥0.5/M**；MiniMax-M3 同档位为 **¥4.20/M / ¥16.80/M**。按 200 页教材估算：`qwen-vl-ocr` 全量逐页 ≈ **¥0.3/本**，M3 视觉全量 ≈ **¥10/本**。**在专用 OCR 面前，成本不再是需要「按页抠」的因素**——这直接改变了策略形态（见结论 5）。
4. **本项目机器没有 NVIDIA GPU**（`nvidia-smi` 不存在），部署目标是 Docker 容器因此**本地 DocVLM 路线否决**：MinerU 2.5-1.2B、olmOCR-7B、PaddleOCR-VL 在 CPU 上不可用或慢到不可接受；唯一的 CPU 可行选项 Granite-Docling-258M（x86 6–8s/页）要引入 torch + transformers 重依赖，且精度在扫描件/复杂表格上明显不足，与既有「不引入重框架」决策冲突。**相关数据留档备查**（§3.3），不当选型。
5. **推荐形态：主路径走「云端专用 OCR」，旁路走「本地提取」，两者互为校验。** 因为成本已不是约束，路由判据应该回到**正确性**：干净单栏数字页 → 本地提取（无损、确定、零延迟）；扫描/复杂版面/公式/表格页 → `qwen-vl-ocr`；**图与图表 → 通用 VLM（`qwen3-vl-plus`）描述 + caption 配对入独立 chunk**（这是当前完全缺失、且性价比最高的一项能力）。**MiniMax-M3 不作主力**，改作降级备用引擎（复用现有 `llm/fallback.py` 机制，零新增供应商）。
6. **顺序上先做不花钱的那一半**。P0（逐页探针 + 契约升级 + 结构化分块）零 API 成本、改动小，且能立刻量化「现在静默丢了多少内容」；P1 才接云引擎。**没有 P0 的 P1，无法验收**——没有可信基线，无法判断云引擎是变好还是变坏。
7. **最大的风险不是钱，是污染**。这是在**建知识库**而非做一次性问答：模型抄错一个公式、漏三行、或「顺手总结」一下，会永久写进向量库并污染之后所有检索，且**难以发现**。因此**交叉校验闸门（§5.4）是方案的必备件，不是可选项**。

## 二、现状诊断（逐条查证，附位置）

### 2.1 现有链路

```
POST /kb/upload ─► kb_manager.upload_and_index ─► parse_document(filename, bytes) -> (text, ext)
                                                        │
                                              ParserRegistry（ext → BaseParser）
                                                        │
                                              BaseParser.parse -> ParseResult(text, meta)
                                                        ▼
                                     len(text) < 200 ? 拒收 : chunk_text(text) ─► 向量 + whoosh
```

### 2.2 缺陷清单（按严重度排序）

| # | 现象 | 位置 | 严重度 | 说明 |
|---|---|---|---|---|
| 1 | **扫描判定是整份文档级**：`SCAN_TEXT_THRESHOLD = 20` 对**全文** `strip()` 后的长度判定，触发条件是「整份 PDF 有效文本 < 20 字符」 | `parsers/pdf.py:24, 44-47` | **严重（静默丢内容）** | 一个 100 页 PDF，95 页扫描 + 5 页文本层 → 全文文本量远超 20 字符 → **OCR 永不触发 → 95% 内容静默消失，且不报错**。这不是质量问题，是数据损坏 |
| 2 | **解析契约在门面处被截断**：`parse_document()` 返回 `(text, ext)`，`ParseResult.meta` 被丢弃 | `parsers/__init__.py:100-105` | **严重** | 下游无法得知「这份文本是用什么方式、几页、有没有 OCR、质量如何」，导致既无法路由也无法验收 |
| 3 | **图片/插图/图表 100% 丢弃**：无抽取、无 caption 配对、无描述 | 全链路无相关代码 | **严重（能力为零）** | 用户直觉中的「识图能力不足」，实际是「识图能力为零」。图表是教材里信息密度最高的部分 |
| 4 | 表格被线性化打乱：`get_text("text")` 顺序输出，行列关系丢失 | `parsers/pdf.py:41` | 高 | PyMuPDF 自带 `page.find_tables()` 可解，零新依赖，未用 |
| 5 | 公式/特殊字体出乱码且无检测 | 同上 | 高 | 数学/CS 教材的核心内容被破坏成不可检索字符，且无任何告警 |
| 6 | 页眉页脚污染 + 多栏阅读顺序错 | 同上 | 中 | 多栏 PDF 的块序按 y 坐标重排即可缓解 |
| 7 | 分块是纯字符窗（500/50），`heading` 取首行前 30 字 | `kb_manager.py:54-90` | 中 | **结构在解析之后又被抹平**——只升级解析，收益会被这一层吃掉一半 |
| 8 | OCR 能力横向耦合：`pdf.py` 私有导入 `image.RapidOcrEngine` / `_have_rapidocr` | `parsers/pdf.py:64` | 中 | 换引擎要改两个文件；与 AGENTS.md §3.6 同类问题同源。上游文档已列为 P2，**本方案的 P1 依赖它** |
| 9 | 解析同步内联在 HTTP 请求内 | `kb_manager.py:157-208` | 中 | 云引擎逐页解析 200 页 = 分钟级 → 必然请求超时。必须异步任务化 |
| 10 | 无多模态基建 | `core/llm/` | 中 | `build_api_messages`（`messages.py:4-12`）content 直通，理论上可放 parts；但 `call_llm` 固定 `max_tokens=2000`（`call.py:41`），转写一页都不够 |
| 11 | `parsers/ocr.py` 能力层不存在 | — | 中 | 上游文档 P2 待办，本方案把它提升为 P1 前置 |
| 12 | 无 `data/kb/` 目录、无实测评测集 | `data/` | 中 | 当前知识库无上传文件，**没有可用语料** → 评测集需先自建（§5.1） |

### 2.3 一句话总结现状

**「解析 → 纯文本 → 按字符切」**，契约在纯文本处截断，版面/结构/图表全部丢失。上游文档已指出「解析质量的下一个瓶颈不是格式覆盖率，而是结构信息丢失与版面识别」——本文就是去解后半句。

## 三、调研

### 3.1 先把问题拆对：PDF 不是一个问题，是六个

不同页面的失效原因完全不同，用一把锤子必然失手。**这是「按页路由」而非「全局选型」的根本原因。**

| 页面类型 | 典型特征 | 现有链路表现 | 需要的引擎能力 |
|---|---|---|---|
| A. 干净数字版（单栏正文） | 文本层完整、无大图 | **基本正确** | 本地提取（增强结构即可） |
| B. 数字版复杂版面（双栏/表格/公式） | 文本层有但顺序/结构错 | 表格打乱、公式乱码、栏序错 | 版面还原 + 结构输出 |
| C. 纯扫描件 | 无文本层 | **仅当整份 <20 字符才 OCR**（缺陷 #1） | OCR + 版面还原 |
| D. 混合型（部分扫描） | 部分页无文本层 | **完全不处理**（缺陷 #1） | 逐页判定 |
| E. 图文混排（图表/示意图为主） | 大图 + 少量说明文字 | **图全丢**（缺陷 #3） | 视觉理解（描述图，非抄文字） |
| F. 数学/STEM 密集 | 公式、特殊字体、符号表 | 乱码（缺陷 #5） | 公式 → LaTeX |

**关键认知**：C/D 是**逻辑缺陷**（要么全 OCR 要么全不 OCR），E 是**能力缺失**（根本没有这条路径），F 是**渲染/字体问题**。三者修复手段不同，不要混为一个「解析精度」问题。

### 3.2 四条技术路线地形图

| 路线 | 代表 | 精度 | 速度 | 成本 | 依赖/门槛 | 本项目适配 |
|---|---|---|---|---|---|---|
| **① 本地传统 OCR** | RapidOCR（现有）、PaddleOCR、Tesseract | 字符级尚可，**无版面/表格/公式** | 快（CPU 可行） | 0 | 已在 `requirements.txt` | ✅ **保留**为扫描件兜底与离线能力 |
| **② 本地 DocVLM** | MinerU 2.5-1.2B、olmOCR-7B、PaddleOCR-VL-0.9B、Granite-Docling-258M、Marker 2 | **最高**（olmOCR-bench 72.7–85.8） | 需 GPU | 0（硬件成本高） | torch/transformers + 显存 | ⛔ **否决**（无 GPU，见 §3.3） |
| **③ 云端专用 OCR API** | **`qwen-vl-ocr`**（阿里百炼） | 高（专为文档/表格/公式训练） | 快（RPM 600–6000） | **¥0.3/¥0.5 每 M token** | 已有 DashScope Key，纯 httpx | ✅ **主力** |
| **④ 云端通用 VLM** | `qwen3-vl-plus`、MiniMax-M3、Gemini Flash | 高（通用理解强） | 中（8–15s/页） | ¥1/¥10（qwen3-vl-plus）、¥4.2/¥16.8（M3） | 已有 Key | ✅ **仅用于「描述图」**（②③不擅长的语义理解）+ M3 作降级备用 |

**为什么②③的分工不等于「便宜的干脏活」**：`qwen-vl-ocr` 是**转写**专精模型——它抄字准、结构还原好，但它**不是通用 VLM**，让它「描述这张电路图在讲什么」是错配；而 `qwen3-vl-plus` 抄整页文字比专用 OCR 贵且未必更准。**按「转写 vs 理解」分工，而非按价格分工。**

> 旧快照（`-2025-08-28` / `-2025-04-13` / `-1028`）单价 **¥5/¥5**，比新版贵约 16 倍 —— **版本选择直接决定成本，务必显式锁版本**。

**（d）图片传入与「内置任务」的两条调用路径**

| 路径 | 能力 | 代价 |
|---|---|---|
| **OpenAI 兼容** `POST /compatible-mode/v1/chat/completions` | `image_url` 支持 URL 或 **Base64 Data URL**；自带 `min_pixels` / `max_pixels` 控制；可自定义 prompt | **拿不到内置任务**（`ocr_options` 是 DashScope 侧参数） |
| **DashScope 原生** `POST /api/v1/services/aigc/multimodal-generation/generation` | 内置任务 `ocr_options.task`：`text_recognition` / `document_parsing`（→**LaTeX**）/ `table_parsing`（→**HTML**）/ `formula_recognition`（→**LaTeX**）/ `key_information_extraction` / `multi_lan` / `advanced_recognition`（→含**坐标** `words_info`）；支持本地路径 | 需另写 HTTP 调用（httpx 已装，**零新依赖**，但脱离现有 `chat_create` 基座） |

**像素与 token 的换算（用于预算）**：32×32 代模型下，A4 @200dpi（1654×2339 ≈ 3.87M px）≈ **3,780 tokens**；@150dpi（1240×1754 ≈ 2.18M px）≈ **2,124 tokens**。`max_pixels` 默认 8,388,608（512 token 的 32×32 网格 → 8192 单位）。

**（e）MiniMax-M3 视觉参数（备用引擎）**

`image_url` 支持 URL 或 base64，`detail` = low(≤600 tok) / default(1k–3k，≤5k) / high(数千–15k+)，单图 ≤10MB，请求体 ≤64MB，格式 JPEG/PNG/GIF/WEBP；`n` 仅支持 1；不支持音频。**无 PDF/document content part。**

### 3.4 成本模型（决策的核心算式）

**单页成本**（A4 @200dpi ≈ 3,780 输入 token；密排中文一页 ≈ 800 输出 token）：

| 引擎 | 输入 | 输出 | 单页 | 200 页/本 | 1000 页 |
|---|---|---|---|---|---|
| `qwen-vl-ocr-2025-11-20` | 3780 × 0.3/M = ¥0.00113 | 800 × 0.5/M = ¥0.00040 | **¥0.0015** | **¥0.31** | ¥1.5 |
| 同上 + Batch File（动态版/latest） | — | — | ¥0.00075 | ¥0.15 | ¥0.75 |
| `qwen3-vl-plus`（≤32k 档，通用理解） | 1/M | 10/M | ¥0.012 | ¥2.4 | ¥12 |
| **MiniMax-M3**（`detail=high`） | 8000 × 4.2/M = ¥0.0336 | 800 × 16.8/M = ¥0.0134 | **¥0.047** | **¥9.4** | ¥47 |

**由此得出的三个决策**：

1. **专用 OCR 比通用视觉便宜约 31 倍**（¥0.0015 vs ¥0.047/页）。**「按页抠成本」不再是设计目标** —— 与其为了省 3 毛钱搞复杂路由，不如让路由服务于**正确性**。这也是结论 5 的依据。
2. **但「便宜」不等于「该用」**：干净数字页上，视觉转写是「花 3 毛钱换一个**有幻觉风险**的结果」，而本地提取是**无损**的。所以路由判据 = 页面复杂度，**不是价格**。
3. **真正的成本大头会从「转写」转到「理解」**：`qwen3-vl-plus` 描述一张图 ≈ ¥0.004（1000 输入 + 300 输出），一本 200 页教材约 30–60 张有效图 ≈ **¥0.2**。仍然是可控量级（一本教材合计 <¥0.6）。

> **成本不是本方案的瓶颈，正确性与工程复杂度才是。** 这个结论改变了方案的形态，值得在评审时明确。

## 四、方案设计

### 4.1 五层结构（L0–L4）

```
                     PDF bytes
                        │
         ┌──────────────▼──────────────┐
    L0   │ 逐页探针（零成本、纯本地）        │  每页独立出 fingerprint
         │ 文本密度/乱码率/图占比/栏数/表格数 │
         └──────────────┬──────────────┘
                        │  route
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
    L1 本地增强      L2 云端专用 OCR    L3 图/图表理解
  （局部提取）      （qwen-vl-ocr）    （qwen3-vl-plus）
        │               │                │
        └───────┬───────┘                │
                ▼                        ▼
    L4  交叉校验（文本层 vs 视觉结果）    figure chunk
                │                        │
                └──────► 结构化 Markdown ◄┘
                              │
                    结构化分块（按标题/页/元素类型）
                              │
                        向量 + whoosh
```

### 4.2 L0 逐页探针（不花一分钱，先修缺陷 #1）

**这是 P0 的全部内容，也是整套方案的地基**：它同时（a）修掉「混合型 PDF 静默丢内容」的真 bug，（b）为 L1/L2 提供路由依据，（c）产出可验收的量化基线。

每页计算（全部基于 PyMuPDF，零新依赖）：

| 指标 | 取法 | 用途 |
|---|---|---|
| `text_chars` | `len(page.get_text("text").strip())` | 文本层是否存在 |
| `garbage_ratio` | 私用区（U+E000–U+F8FF、U+FB00–U+FB4F 等）+ 稀有符号占比 | 检测公式/特殊字体乱码（缺陷 #5） |
| `image_area_ratio` | `Σ page.get_image_info()[i]["bbox"] 面积 / page.rect 面积` | 判定扫描页 / 图文页（缺陷 #3 的前提） |
| `column_count` | `get_text("blocks")` 的 x 起点一维聚类（间隙 > 页面宽 8% 视为分栏） | 阅读顺序（缺陷 #6） |
| `table_count` | `len(page.find_tables().tables)` | 结构还原（缺陷 #4，PyMuPDF 自带） |
| `is_scanned` | `text_chars < 50 且 image_area_ratio > 0.6` | 扫描页判定（**逐页**，修缺陷 #1） |

路由决策（示例阈值，实施时用真实语料校准）：

| 条件 | 去向 |
|---|---|
| `text_chars ≥ 300` 且 `garbage_ratio < 1%` 且 `column_count == 1` 且 `image_area_ratio < 20%` | **L1 本地**（干净页，样本量应占多数） |
| 其余（扫描 / 多栏 / 乱码 / 大图 / 有表格） | **L2 云端 OCR** |
| 页面含 `image_area_ratio > 3%` 的独立图元（排除整页扫描） | 额外走 **L3** |

### 4.3 L1 本地增强（不改依赖，只改用法）

针对探针判定为「干净页」的页面，把 `get_text("text")` 换成结构化提取：

- **`get_text("dict" / "rawdict")`** → 保留 block/span 的 bbox、字号、字体名 → **按字号聚类还原标题层级**（`#/##/###`），按 bbox 排序还原阅读顺序、去页眉页脚（检测「同一 y 带在多页重复出现」的文本）。
- **`page.find_tables()`** → 表格 → Markdown/HTML 结构（PyMuPDF 内建，**零新依赖**）。
- 输出统一为**结构化 Markdown**（见 §4.6 契约），与 L2 产物同构 → 下游分块器只认一种格式。

> 这一层不引入任何模型：干净页上它是**无损**的，且是 L4 校验的基线来源。

### 4.4 L2 云端专用 OCR（主力：`qwen-vl-ocr-2025-11-20`）

- **渲染**：`page.get_pixmap(dpi=200)`（文本页可降至 150dpi 以省 token）→ PNG → base64 Data URL。
- **调用路径（两选一，建议分阶段）**：
  - **阶段一（推荐先做）**：OpenAI 兼容 + 自定义 prompt（直接复用现有 client 基座与 `fallback` 机制）。要求输出 Markdown + 页标记。
  - **阶段二（可选增强）**：DashScope 原生 `ocr_options.task`——`document_parsing`（LaTeX）/ `table_parsing`（HTML）/ `formula_recognition`（LaTeX）按元素类型分派。代价是新增一条 HTTP 路径（httpx 已装，零新依赖），但**脱离 `chat_create`**，需自建重试与限流。
  - **不建议一开始就上阶段二**：先把一条路径跑通并拿到基线数据，再决定是否值得为结构化收益增加第二条路径。
- **批大小由输出上限倒推**：`max_tokens = 8,192` → 预留余量后单请求输出预算 ≈ 6,000 token ≈ 密排中文 4–6 页 → **文本页 3–4 页/批**；**含公式或表格的页 1 页/批**（LaTeX 与 HTML 的体积是纯文本的 3–5 倍，且截断会毁掉整页）。
  - 若 `qwen3.5-ocr`（32,768 输出）确认可用且价格可接受 → 批大小可提至 8–12 页，请求数与成本进一步下降。
- **并发**：显式锁 `-2025-11-20`（6,000 RPM / 30M TPM）→ 并发 8–16 安全；遇 429 指数退避。**不要用动态版**（600 RPM）。
- **`detail` 概念不存在**（这是 MiniMax 的参数），改用 `min_pixels` / `max_pixels` 控制分辨率与 token。

### 4.5 L3 图与图表理解（当前完全缺失的能力）

**这是「识图」真正的落点，也是本方案中性价比最高的一块。**

- **抽取**：`page.get_image_info()` 拿每个图元的 bbox 与像素数据；过滤掉装饰性小图（面积 < 页面 3%）、重复出现的水印/logo（跨页 hash 去重）。
- **caption 配对**：**用本地几何信息，不用 OCR 坐标** —— 在同页文本块中找与该图 bbox 中心距离最近、且位于图下方/上方的文本块（常见「图 3-2 xxx」正则优先匹配）。本地几何比云端坐标更精确且免费。
- **描述**：图元 → `qwen3-vl-plus`（通用 VLM，¥1/¥10）+ prompt「描述这张图在讲什么，含坐标轴/图例/关键数值；若是示意图，说明它表达的结构关系」。**注意与 L2 的分工：L2 抄字，L3 理解。**
- **入库**：作为**独立 chunk**（`chunk_type="figure"`），内容 = `caption + 描述`，元信息带 `page` / `image_path` / `bbox` / `caption`。
  - 理由：图与正文的 embedding 分布差异大，混在一起会互相污染检索（上游同类调研的独立结论）。独立类型还允许后续走独立召回通道。

### 4.6 统一输出契约（结构化 Markdown）

**L1 与 L2 必须产出同一种格式**，否则分块器要分叉。约定：

```markdown
<<<PAGE 12>>>
## 2.3 二叉树的遍历

前序遍历的顺序是……

| 遍历方式 | 顺序 | 用途 |
|---|---|---|
| 前序 | 根-左-右 | 复制树 |

$$\text{Height}(T) = 1 + \max(h_L, h_R)$$

![图 2-4 二叉树遍历示意](figure:page12_img0)
图 2-4 二叉树遍历示意：三种遍历访问节点的先后顺序。
<<<PAGE 13>>>
```

要点：**页标记**（校验对齐、失败定位、增量重跑的最小单位）、**标题层级**（分块依据）、**`$...$` / `$$...$$` 公式**（可被检索）、**表格保留结构**、**图占位 + caption**（关联 figure chunk）。

### 4.7 结构化分块（否则前面全部白做）

**缺陷 #7 必须一起修**，否则结构信息在分块层被抹平：

- 按 `<<<PAGE n>>>` 与标题层级切分（而非字符窗）；超长小节再按段落滑窗。
- `heading` 取**真实标题**（层级路径，如 `2.3 二叉树的遍历`），不再取「首行前 30 字」。
- chunk 携带 `page` / `chunk_type`（text/table/formula/figure）/ `section_path` → 检索结果可溯源、可做同节扩展（与现有 parent-child 扩展协同）。
- 表格与公式**不拆散**（一个表格 = 一个 chunk，即使超长）。

### 4.8 解析链路的上下文工程（本节回应「上下文工程」诉求，但只覆盖解析侧）

> **说明**：用户提出「还没做上下文工程」。经查证，**对话/Agent 侧的上下文工程已有部分实现**（`core/agent_context.py` 上下文唯一写入点、`core/context_guard.py` 发送前 32K 预算守卫、`core/token_estimator.py` 预估、`agent_run_store.prune(30,180)` 分层保留）。因此「上下文工程」不应从零做，而应从**差距审计**做起。**该议题单独立项，不并入本文档**（见 §8 待办 T1）。本节只覆盖**解析链路**自己的上下文约束：

| 约束 | 做法 |
|---|---|
| **单请求输入预算** | `max_pixels` 控制分辨率：文本页 150dpi、复杂页 200dpi、图表页按图元原尺寸。拒绝「无脑塞 8192×8192」 |
| **单请求输出预算** | 由 `max_tokens` 倒推批大小（§4.4）；**宁可多请求，不可被截断**（`finish_reason == "length"` 必须视为失败并重试） |
| **无状态化 + 页级缓存** | 每页独立请求（无跨页上下文依赖）→ 按 `(file_hash, page_no, engine, prompt_version)` 缓存；引擎/prompt 升级只重跑受影响页，**重跑不重复计费** |
| **提示词角色约束** | system 明确「你是文档转写器：只转写，不总结、不补全、不翻译、不解释；不可辨认处输出 `[?]`；保留页眉页脚但用标记包裹」。**这是防幻觉的第一道闸门** |
| **失败降级链** | 单页失败 → 重试 2 次（退避）→ 降级到本地提取结果 → 标记 `page_status="degraded"`；**不因单页失败丢掉整份文档** |
| **成本记账** | 每次调用记 `tokens / ¥ / engine / page`（`usage.prompt_tokens_details.image_tokens` 可直接取图 token）→ 落 `meta.cost`，供配额与验收 |
| **并发与背压** | 全局并发上限（默认 8）+ 令牌桶对齐 RPM/TPM；429 退避不重试风暴 |
| **增量与幂等** | 同一文件重复上传 → 命中缓存直接复用；`file_hash` 变化才重跑 |

**工程前置（必做）**：

1. **解析异步任务化**：`upload_and_index` 目前同步内联（缺陷 #9）→ 抽成后台任务，复用 `core/collector/manager.py` 的任务模式（创建/进度/取消/统计）。前端上传后显示进度而非转圈。
2. **抽 `parsers/ocr.py` 能力层**：`pdf.py` 与 `image.py` 共用引擎接口（`Engine.render_*` / `Engine.transcribe_*`），解掉缺陷 #8。云引擎与 RapidOCR 都是该层的实现 → 可插拔、可降级、可 A/B。
3. **`parse_document` 契约升级**：新增 `verbose=True` 返回完整 `ParseResult`（含 `meta`），旧签名保持不变（上游文档已列为 P2，本方案必须提前）→ 解缺陷 #2。

## 五、验证方案（没有这节，前面都是空谈）

### 5.1 评测集（当前 `data/` 无上传文件，必须自建）

自建 **30–50 页**标注集，覆盖 §3.1 的六类页面（A/B/C/D/E/F 各 5–8 页），人工产出 reference Markdown。要求：**至少包含 1 份真实扫描件、1 份双栏论文、1 份含跨页表格的教材章节、1 份公式密集页。**

### 5.2 指标

| 维度 | 指标 |
|---|---|
| 文本保真 | 归一化后字符错误率 CER（对比 reference） |
| 表格 | cell 级还原率（含合并单元格）、跨页表格是否拼回 |
| 公式 | LaTeX 归一化后的 BLEU / 精确匹配率 |
| 阅读顺序 | 块序列与 reference 的 Kendall τ |
| 图表 | caption 配对准确率、描述人工可行性打分（1–5） |
| 端到端 | **同一批资料入库后 `/kb/search` 的 Recall@5 对照**（现状 vs 新方案）—— 最终唯一有意义的指标 |

### 5.3 对照实验

- 基线：现状（PyMuPDF 文本层 + 整份触发 RapidOCR）
- 实验组 1：仅 P0（逐页探针 + 结构化分块，不接云引擎）
- 实验组 2：P0 + L2（云 OCR）
- 实验组 3：P0 + L2 + L3（图表）

**预期形态**：实验组 1 在 C/D/E 类页面上会显著暴露基线缺陷（这也证明 P0 的价值）；L2 主要救 C/D/B；L3 只在 E 类页面有增益，但对「教材插图题」场景可能是决定性的。

### 5.4 交叉校验闸门（防污染，**必备件**）

同页若存在可用文本层（探针 `text_chars ≥ 300` 且 `garbage_ratio < 1%`）→ 计算本地提取与视觉结果的**归一化字符相似度**：

| 相似度 | 处置 |
|---|---|
| ≥ 0.95 | 采用视觉结果 |
| 0.7–0.95 | 采用视觉结果，标 `needs_review`，记日志 |
| < 0.7 | **保留本地结果**，标 `needs_review`，**拒绝用视觉结果覆盖** |
| 无文本层（纯扫描） | 无校验基线 → 标 `unverified`，**抽样人工复核**（或二次模型交叉比对） |

**没有这一层，本方案会降低知识库的可信度。** 另有两条硬闸门：`finish_reason == "length"` → 判失败重试；输出长度 < 本地文本长度的 50% 且本地可用 → 拒绝覆盖。
