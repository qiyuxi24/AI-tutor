## 0. 结论速览

| 问题 | 结论 |
|---|---|
| 各部分是否清楚明了？ | **分层清楚，但有 3 处模糊**：写入路径未统一、掌握度口径前后端不一致、学科归类逻辑散落 |
| 操作方法是否全部封装好？ | **否**。前端 1 处绕过 store；后端 5 处直接读写节点 MD 绕过 `KnowledgeGraph`；"AI 写节点"有 3 套并行实现 |

**一句话总结**：图谱模块的**读取路径**封装良好（分层清晰、单一数据源基本落地）；
**写入路径**是薄弱面 —— 同一个"写节点"动作存在多套实现，各自的 MD 模板、字段支持、副作用处理都不一致。

问题计数：**P0 × 2**（已发生的错误行为）、**P1 × 5**（结构缺陷，演进中会出事）、**P2 × 6**（清洁度）。

## 3. 封装完备性

### 3.1 前端：单一状态源契约的执行情况

**合规的部分** ✓
- `GraphSubjectBar` / `GraphBoardSidebar` / `GraphSearch` / `ForceGraph` **零** `apiClient`/`fetch`/`axios` 调用（全前端 grep 0 命中）。
- 全前端**未发现**直接给 store 图谱 state 赋值（如 `store.knowledgeNodes = ...`）的写法，组件均通过 `storeToRefs` 消费。

**缺口：`KnowledgeView` 形成第二图谱写入入口** ❌
- `views/KnowledgeView.vue:15` 直接 `import { generateKbGraph } from '../api/kb.js'`，`:93` 直接 `await generateKbGraph(...)`。
- 该端点后端是**写图谱**的（`api/v1/kb.py:191` → `generate_subject_graph`）。
- 但它成功后只更新本地 `genResult :95-101`，**不调用** `store.refreshGraph()` / `fetchSubjects()`，图谱刷新全靠后续 SSE 兜着。
- 对照：store 里**已有**等价且更完整的 `generateSubjectGraph :378-392`（同一 endpoint，且结束后 `fetchSubjects → fetchBoards → fetchGraph`）。
- 后果：同一个后端操作两套前端实现，一套带刷新编排、一套不带；store 的那个反而**无人调用**（见 §6）。

### 3.2 后端：`KnowledgeGraph` 封装被绕过的位置

`KnowledgeGraph` 对节点 MD 文件的读写，本应只通过
`get_node_content_preview :565`（读）与 `update_node_content :801`（写，内部含 `_guard_human_content :816` + `invalidate_content_cache :833`）。

实际有 **5 处**直接操作 MD 文件绕过了它【已核实】：

| # | 位置 | 行为 |
|---|---|---|
| 1 | `api/v1/knowledge.py:214-219` | `create_node` 直接 `open(kg.nodes_dir/...)` 写，并内联第三套 MD 模板 |
| 2 | `api/v1/knowledge.py:510-513` | `decompose` 直接写，内联第四套 MD 模板 |
| 3 | `api/v1/knowledge.py:125-129` | `get_node_detail` 直接 `open` 读 MD（未用 `get_node_content_preview`） |
| 4 | `core/knowledge_writer.py:141` | `create_node_from_ai` 自身也直接写 MD |
| 5 | `core/kb/graph_generator.py:439` | `_write_to_graph` 直接写 MD |

> 另：`core/rag/manager.py:43-47` 也直接读 MD（可接受，属检索侧只读，但同属"绕过类方法"）。

**注意区分**：`main.py:67` 与 `auth.py:25` 直接连 `data/knowledge/knowledge.db` 操作的是 **users 表**（鉴权），
不是图谱 nodes/edges，**不算**绕过图谱封装。`agent_run_store.py` / `conversation_store.py` / `quiz_store.py` 均为独立库，同样不算。

### 3.3 写入路径统一性（本次调研最重要的发现）

**"写一个节点 MD"有 3 套并行实现，4 处调用点**：

| 路径 | 位置 | `board` 字段 | 语义去重 | 权限守卫 | MD 模板 |
|---|---|---|---|---|---|
| `knowledge_writer.create_node_from_ai` | `:40`（AI 工具 + 建议应用共用） | ✗ 不支持 | ✗ | ✓ | 模板 A `:118-161` |
| `graph_generator._write_to_graph` | `kb/graph_generator.py:418` | ✓ 支持 | ✓（嵌入+LLM 二次确认） | ✗ 未调 | 模板 B `:439` |
| `api/v1/knowledge.py` create_node | `:198-219` | ✗ | ✗ | ✗ | 模板 C（"手动创建"） |
| `api/v1/knowledge.py` decompose | `:495-513` | ✗ | ✗ | ✗ | 模板 D（"问题拆解"） |

**危害**：改一处忘一处 —— 模板漂移、能力不一致（`board` 只有 generator 会写，
但 `get_nodes_by_board :547` 依赖它，意味着**其他路径创建的节点永远不会进板块栏**）。
`knowledge_writer.py:1-11` 自述是"AI 写图谱统一层"，但**并未真正统一**。

### 3.4 user_id 隔离

**整体合规** ✓
- `api/v1/knowledge.py` **全部 20 个路由**都带 `user_id = Depends(get_current_user)`，且每个 `KnowledgeGraph(user_id=user_id)` 均显式传参【已核实抽样】。
- `knowledge_graph.py:28` 的 `user_id` 是**必填位置参数**（无 `user_id=0` 这类危险默认值）—— 这点是安全设计，值得保留。
- `graph_generator.py:602/614`、`chat_service.py:252/376/433`、`rag/manager.py:94/131` 均显式传 `user_id`。

**缺口：SSE 端点用全局队列**【已核实】
- `knowledge.py:50` 校验了 `user_id`，但 `:58` 是 `subscribe()` —— **没传 user_id**。
- 于是走 `event_bus.py:188-189` 的全局模式，而全局广播会**同时投递到所有用户队列**（`:161-163`）。
- 后果：A 用户触发的 `publish("graph_updated")` 会让 **所有** 连着 `/knowledge/events` 的客户端收到通知并触发刷新。
- **危害边界**：事件 payload 不含节点数据，且前端刷新时用的是自己的 token，**不泄露数据内容**，
  仅造成"跨用户事件串扰 + 他人无谓刷新"。故定级 **P1**（越权路径）而非 P0。

## 4. 清晰度评估

### 4.1 命名一致性

| 概念 | 前端 | API 参数 | 后端 Python/列 | 一致？ |
|---|---|---|---|---|
| 学科 | `subject` | `subject` | `node_subject()` / `get_subjects()` / 表列**不存在**（从 tags 推导） | ✅ |
| 知识板块 | `board` | `board` | `node_board()` / 表列 `board` | ✅ |
| 节点 | `id/name/mastery/tags` | 同 | 同 | ✅ |
| 掌握度 | `mastery` 0-100 | `mastery` | `mastery` int | ✅ |
| **边起点** | `source` | **写 `from`** | **读 `from_node`** | ❌ **三套名** |
| **边终点** | `target` | **写 `to`** | **读 `to_node`** | ❌ 同上 |
| 未分类 | `'未分类'`（`chatStore.js:47`） | `subject=未分类` | `SUBJECT_UNCLASSIFIED`（`graph_middleware.py:27`） | ⚠️ 硬编码字符串双向约定 |

**边的命名问题最严重**：写用 `from`/`to`（`chatStore.js:484`），读用 `from_node`/`to_node`（SQL 列名直出，`knowledge_graph.py:175`），
前端再映射成 `source`/`target`（`chatStore.js:218-219`）。导致**四处 `||` 兜底**：
`chatStore.js:218`、`ForceGraph.vue:576`、`:597`、`:724`。
`chatStore.js:214-215` 的注释自己承认"ForceGraph 会再次做兼容映射，确保即使 Store 未映射也不会出错" ——
这是**有意的容错**，但病根在后端读写字段名不对称，任何新增的图谱消费方都得重复这套兜底。

### 4.2 职责边界：`graph_middleware` vs `knowledge_graph`

**边界本身清晰** ✓ —— middleware 全部委托 KG 查询方法，自身不查库（`:10` 声明属实）。
`list_subjects :93` 就是 `kg.get_subjects()`，`list_boards :101` 就是 `kg.get_boards_by_subject()`，属**薄封装**，可接受。

**问题：学科归类判定散落 ≥3 处**
- 权威实现：`knowledge_graph.py:473 node_subject()`
- `graph_middleware.py:32` 用 `not kg.node_subject(n)` ✓ 正确复用
- `graph_middleware.py:70-74`（`SUBJECT_UNCLASSIFIED` 分支）另行判定
- `knowledge.py:648`（export）**完全没复用**，写成 `n.get("subject") == subject`

## 7. 收口方向（仅给方向与顺序，不含实现）

按「先止血、再收口、最后清洁」排序：

**第一步：止血（P0，改动小、收益直接）**
1. `export_knowledge` 的学科过滤改用 `kg.node_subject(n)` —— 1 行级改动，但需补一个回归测试（当前该路径恒空，说明**没有测试覆盖**）。
2. 掌握度阈值抽出**单一真值**：或让后端 `_bucket` 对齐前端四档，或前端删掉"薄弱"档。
   无论选哪个，`graph_middleware.py:108` 那句注释必须同步改 —— 它现在是错误信息。

**第二步：收口写入路径（P1-1 / P1-2）**
3. 在 `KnowledgeGraph` 上加一个**原子方法**（如 `create_node_with_content()`），把
   `add_node` + 写 MD + 缓存处理合成一次调用，让 4 条路径都走它。
   这是收口的核心 —— 否则每加一个"写节点"的路径就会多一套模板。
4. MD 模板抽成模块级常量（当前 4 套内联模板散在 4 个文件里）。

**第三步：统一契约与入口（P1-3 / P1-5）**
5. `KnowledgeView` 改走 `store.generateSubjectGraph`，删除 `api/kb.js` 的 `generateKbGraph`。
6. 边字段统一：建议后端读侧也输出 `source`/`target`（或在 `_row_to_edge_dict :175` 里改名），
   一次性消掉前端 4 处 `||` 兜底；`POST /knowledge/edge` 换用 `CreateEdgeRequest` 让 schema 生效。

**第四步：越权与死代码（P1-4 / P2-1）**
7. `knowledge_events` 改 `subscribe(user_id=user_id)`（一行改动）。
8. 死代码二选一：**接上前端入口**（如 export 加下载按钮）或**删除**。
   建议 `/knowledge/subjects`、`/node-ids` 直接删（已有替代）；`/export`、`/decompose` 考虑接前端。

**第五步：真值源收敛（P2）**
9. `nextToLearn` 与 `stats.next_to_learn` 保留一个；`graphLoaded` 改为 `computed`（由数据推导，消灭脱节可能）。

## 8. 对子调研结论的核实与修正

本节记录本次**逐行读码后的修正**，避免后来者被不准确的初判误导。

| 初判 | 核实后 | 依据 |
|---|---|---|
| 「`create_node`/`decompose` 绕过 `_guard_human_content` 与缓存失效，**影响：高**」 | **修正为：结构性缺口（P1），无实际危害**。这两条路径写的是**新建节点**：`decompose` 明确 `added_by="ai"`（`:504`），`create_node` 默认 `"human"`（`:207`）—— 两者都不会触发 `_guard_human_content` 的拒绝分支（该分支只在 `caller=="ai"` 且 `added_by=="human"` 时抛错，`:423-433`）；新建节点的 ID 也不在 `_content_cache` 里，故 `invalidate_content_cache` 无影响。真正的问题是**模板第四套**与**未来副作用漏接** | `knowledge_graph.py:412-433`、`knowledge.py:504`、`knowledge.py:207` |
| 「SSE 全局队列 = **越权风险，高**」 | **修正为 P1**。事件 payload 不含节点数据，前端刷新用自己的 token，**不泄露数据**，仅跨用户串扰 + 无谓刷新 | `event_bus.py:161-163`、`knowledge.py:221` |
| 「前端绕过 store 的还有 `api/kb.js` 自身」 | 保留：`api/kb.js:46` 确实是第二入口，但**根因在 `KnowledgeView.vue:93` 的调用**，`api/kb.js` 只是承载者 | `KnowledgeView.vue:15,93` |
| 未提及 | **新增 P0-2**：掌握度分档前后端不一致，且后端注释声称一致 | `ForceGraph.vue:107-112`、`graph_middleware.py:108-119` |
