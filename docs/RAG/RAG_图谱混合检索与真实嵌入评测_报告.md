# 图谱 RAG 混合检索落地与真实嵌入评测报告

> 日期：2026-09-23（跨夜至 09-24）
> 触发：用户要求「给图谱的检索加上混合检索；API 已充值，跑一下实际效果，把评测做了、实验数据和报告留下」。
> 原始数据（JSON）：`backend/eval_data/report_graph_api.json`、`report_graph_mock.json`、`report_api.json`、`report_mock.json`
> 复现命令见 §8。

---

## 一、结论（先给答案）

1. **图谱 RAG 从"单腿"变成"双腿"**：原先只有向量检索（嵌入一挂就只剩 name/summary 子串兜底），现在向量 + whoosh BM25 双路宽召回 + 融合，且**两条索引腿解耦**——嵌入欠费时节点仍进 BM25，图谱检索不再整条失效。

2. **收益（真实嵌入 text-embedding-v4，CMRC2018 150 篇 → 308 个节点 / 567 条 query）**：

   | 指标 | 纯向量（改造前） | 混合检索（改造后） | 变化 |
   |---|---|---|---|
   | Recall@1 | 0.8254 | **0.8624** | +3.70pp |
   | Recall@3 | 0.9700 | **0.9806** | +1.06pp |
   | Recall@5 | 0.9841 | **0.9894** | +0.53pp |
   | MRR@5 | 0.8945 | **0.9195** | +2.50pp |

   嵌入质量差时收益更大（mock hash 嵌入：R@1 0.4603 → 0.7302，+27pp）——**混合检索本质是"嵌入不够好时的保险"**。

3. **融合策略定夺（此前 `TODO.md` 挂着 P0「RRF vs 加权」）**：两条通路的真实嵌入实测**一致指向加权融合（alpha=0.6 向量 / 0.4 BM25）**，故生产默认由 RRF 切为加权：
   - kb 通路（1000 query）：fuse R@1 **0.9790** / MRR **0.9878** vs RRF 0.9710 / 0.9828
   - 图谱通路（567 query）：fuse R@1 **0.8624** / MRR **0.9195** vs RRF 0.8519 / 0.9133
   - `rrf_fuse` 保留在 `fusion.py`（多查询/多路融合时"只看排名、对分数尺度不敏感"仍有价值，见 KG-D10）。

4. **顺带修掉 3 个真问题**（都由评测/回归暴露，见 §5）：whoosh `AsyncWriter` 的 commit 是**异步**的（写完立刻检索会漏召回）、加权融合下**误杀单腿命中**、BM25 分数尺度被余弦阈值误伤。

## 二、改了什么

| 文件 | 改动 |
|---|---|
| `core/hybrid_search/whoosh_index.py` | schema 参数化（`text_ids=True` 时 `chunk_id`/`node_id` 用 `ID`，支持图谱 TEXT 主键；kb 老索引 **NUMERIC 不迁移**）；图谱 schema 增 `node_name` 透传；**`AsyncWriter` → 同步 writer** |
| `core/rag/manager.py` | `_get_sparse()`（每用户 BM25 索引）；`index_node` 写 BM25 并**与嵌入解耦**；`search` 双路宽召回 + 加权融合 + 按各路尺度过滤 + 逐级降级；`delete_node_index`/`index_user_graph` 同步清 BM25；`stats` 增 `sparse_chunks` |
| `core/rag/vector_store.py` | `search` 返回项补 `chunk_index`（融合主键需要） |
| `core/kb/kb_manager.py` | 融合由 RRF 切为加权（`DEFAULT_ALPHA`）；质量闸门由"卡融合分"改为"按各路尺度" |
| `tests/test_rag_hybrid.py` | 新增 6 例（解耦 / 融合排序 / 兜底阶梯 / 删除 / stats / 重索引替换） |
| `scripts/eval_graph_rag.py` | **新增**：图谱通路评测（CMRC2018 段落级节点构造 gold，4 策略对比） |
| `scripts/eval_rag.py` | `load_cmrc2018` 带出 `answer`；"生产默认"列改为 `gated_fuse`（与生产逐行同口径） |

图谱侧融合主键用 `"{node_id}#{chunk_index}"` 而非数据库自增 id —— 因为 BM25 必须在嵌入**之前**写入（否则嵌入欠费时节点不入索引），那一刻拿不到自增 id。

## 三、评测方法

### 3.1 数据集（开源，仓库内已有）

**CMRC2018**（哈工大讯飞中文机器阅读理解，SQuAD 风格）的 trial 集：`backend/eval_data/cmrc2018_trial.json`（1 MB）。
- 每篇文档带 `context_text`、`title`、若干 `qas`（问题 + 答案 span）。
- 每道题的正确答案**原文就在文档里**，这一点决定了 §6 的结论边界。

### 3.2 图谱通路的 gold 构造（`scripts/eval_graph_rag.py`）

图谱通路此前**从未被量化过**（`eval_rag.py` 测的是 kb 通路，文档级 gold）。本报告用"段落即知识点"的近似：

```
CMRC2018 文档 → 按空行切段、超长段按中文句末标点二次切到 ~300 字（丢弃 <100 字碎段）
              → 每段用 create_node_with_content() 建成一个图谱节点（名称带序号防同名并轨）
              → index_node() 写入向量 + BM25 索引
query = CMRC2018 的 question
gold  = 第一个包含标准答案 span 的段落节点（答案落在被丢弃碎段里 → 该 query 跳过）
```

规模：150 篇文档 → **308 个节点**、**567 条可评测 query**。

### 3.3 指标与口径

- 指标：Recall@1/3/5、MRR@5，按 `node_id` 去重后计算（同一节点多片段只算命中一次）。
- 四策略均在**同一份图谱索引**上跑，两路各宽召回 Top-30：
  - `vector` 纯向量（余弦）
  - `bm25` 纯 whoosh（中文 bigram，分数 `s/(s+1)` 归一化）
  - `hybrid` RRF 排名融合（`min_score=0.25`）
  - `fuse` **生产默认**：加权融合 + 各路质量闸门（与 `kb_manager.search` / `RagManager.search` 逐行同口径）
- 图谱通路与 kb 通路用**同一评测集**，因此两表可横向对照。

## 四、实验结果

### 4.1 图谱通路（主结果）

**真实嵌入 text-embedding-v4**（308 节点 / 567 query）：

| 策略 | Recall@1 | Recall@3 | Recall@5 | MRR@5 |
|---|---|---|---|---|
| vector（改造前行为） | 0.8254 | 0.9700 | 0.9841 | 0.8945 |
| bm25（本次新增的腿） | 0.8713 | 0.9612 | 0.9735 | 0.9155 |
| hybrid（RRF） | 0.8519 | 0.9718 | 0.9894 | 0.9133 |
| **fuse（生产默认）** | **0.8624** | **0.9806** | **0.9894** | **0.9195** |

**mock hash 嵌入**（同规模，用来看"嵌入质量差时"的鲁棒性）：

| 策略 | Recall@1 | Recall@3 | Recall@5 | MRR@5 |
|---|---|---|---|---|
| vector | 0.4603 | 0.6085 | 0.6561 | 0.5380 |
| bm25 | 0.8713 | 0.9612 | 0.9735 | 0.9155 |
| hybrid（RRF） | 0.6772 | 0.8607 | 0.9206 | 0.7750 |
| **fuse（生产默认）** | **0.7302** | **0.8995** | **0.9418** | **0.8174** |

读法：
- **BM25 腿单独就能超过纯向量**（真实嵌入下 R@1 0.8713 > 0.8254；mock 下 0.8713 ≫ 0.4603）——向量腿是"语义泛化"的补充，不是主力。
- 混合检索在**两个嵌入质量档位上都是最优**（R@3/R@5/MRR 全面领先纯向量），改造方向成立。

### 4.2 kb 通路（对照，同评测集 / 1000 query）

| 策略 | 真实嵌入 R@1 | R@5 | MRR | mock R@1 | R@5 | MRR |
|---|---|---|---|---|---|---|
| vector | 0.9500 | 0.9850 | 0.9650 | 0.4700 | 0.6690 | 0.5445 |
| bm25 | 0.9640 | 0.9890 | 0.9747 | 0.9640 | 0.9890 | 0.9747 |
| hybrid（RRF） | 0.9710 | 0.9980 | 0.9828 | 0.7660 | 0.9360 | 0.8284 |
| **fuse（生产默认）** | **0.9790** | 0.9980 | **0.9878** | 0.8180 | 0.9590 | 0.8690 |

（mock 列即历史 `report_mock.json`，口径为"融合无闸门"。）

### 4.3 融合策略定夺

两条通路、两种嵌入质量档位，**四个场景全部是加权融合略优于 RRF**（差距 0.8–1.1pp R@1）：

| 场景 | fuse R@1 | RRF R@1 | 差 |
|---|---|---|---|
| kb / 真实嵌入 | 0.9790 | 0.9710 | +0.80pp |
| kb / mock | 0.8180 | 0.7660 | +5.20pp |
| 图谱 / 真实嵌入 | 0.8624 | 0.8519 | +1.05pp |
| 图谱 / mock | 0.7302 | 0.6772 | +5.30pp |

**决定**：生产默认切换为加权融合（`DEFAULT_ALPHA=0.6`）。理由除上述数字外还有一条工程理由 —— 加权融合的分数**有绝对含义**（余弦分量 + BM25 归一化分量），能配合 `MIN_SCORE` 做真实阈值过滤；RRF 只看排名，其归一化分在"单路命中"时恒为 0.5 左右，`min_score=0.25` 实际形同虚设。

## 五、评测过程中暴露并修掉的问题

1. **whoosh `AsyncWriter` 的 commit 是异步的**（读源码确认：它起线程 replay 操作并提交）。
   后果：① 索引完**立刻检索**（图谱增量索引 → 下一轮对话就查）会静默漏召回；② 删除与更新可能乱序。
   → 改为**同步 writer**（`_ix.writer()`），语义与 SQLite 索引侧一致。**kb 通路同样受益**。
2. **加权融合下"卡融合分"会误杀单腿命中**：只有 BM25 命中的文档融合分最高才 0.4（alpha 份额），过不了 `MIN_SCORE=0.25`；RRF 时代靠排名分侥幸掩盖了这个问题（回归用例 `test_hybrid_search_hits_bm25_only_doc` 直接红了）。
   → 质量闸门改为**按各路自己的尺度**判定：BM25 有词面匹配即算有效，向量腿仍守余弦 `MIN_SCORE`。
3. **BM25 归一化分与余弦不可比**：索引里文档越少 idf 越低，单文档时 `"栈顶"` 的归一化分只有 0.22 < 0.25 → 整条腿被误杀。
   → 同上，BM25 侧不套余弦阈值。
4. （测试侧）**中文 bigram 会让相似词互相召回**："旧标记词"/"新标记词" 共享 `标记`/`记词` 两个 bigram，导致"替换是否生效"根本测不出来 → 测试改用无共享 bigram 的英文标记词。

## 六、结论边界（不可外推）

1. **CMRC2018 的字面重叠极高**（答案原文就在文档里）→ BM25 天然占优。真实场景是**学生口语化提问**，与教材措辞的字符重叠远低于此，混合检索的收益结构会变（向量腿占比上升）。**不要把 0.87 当成"BM25 足够好"的证据。**
2. **gold 是自动构造的段落级标注**，不是人工知识点标注：答案出现在多个段落时只取第一个 → 系统性低估（尤其对"答案常见"的题）。
3. **图谱节点 = 文档段落**，粒度（~300 字）与真实图谱节点（正文中位 213 字）接近但不相同；不代表"人工建图"的质量。
4. **单一数据集 / 单一语言 / 单领域**，mock 与真实嵌入是两档质量而非两个模型；换嵌入模型必须重建索引（向量空间不可比）。
5. **kb 通路 `fuse` 列**：全量数据（`report_api.json`）跑于"融合后无闸门"的旧口径。图谱侧实测过"加闸门前后 top-5 指标完全一致"（两次数字逐位相同），据此判断该列可直接引用；若后续要严格对齐，用 `--embed api` 重跑即可（约 5 分钟）。

## 七、后续建议（按性价比）

1. **跨源统一融合（KG-D10）**：现在 graph 源给余弦、kb 源给加权分，`rag_pipeline` 只能按源拼区块（`_fuse` 是按 content 去重+按分排序，两源分数不可比）。既然两源内部都收敛到加权融合了，可评估把融合提到 pipeline 层。**注意**：加权融合要求两源分数尺度可比，跨源时要先归一化。
2. **图谱检索专项评测的 gold 升级**：用"教材章节标题 + 该节习题"做半自动 gold，比"段落"更接近真实知识点。
3. **端到端 A/B**：图谱开/关对最终回答质量的影响（现只有检索层指标，没有教学效果指标）。
4. 精排（Cross-Encoder）/ HyDE 仍在 `TODO.md` P2，建议先有"检索层已达标"的基线再做。
