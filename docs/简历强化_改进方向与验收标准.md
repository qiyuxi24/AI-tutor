# AI Tutor 简历强化：改进方向与验收标准

> 目标：把项目从"能写进简历"提升到"能扛住 30 分钟深挖的硬作品"。
> 面试官检验作品的三条标准：**① 能点开就用 ② 有量化结果 ③ 有工程纵深**。本文档每项改进都对应补齐其中一条，并给出可勾选的验收标准。
>
> 现状基线（2026-08）：91 个源文件 ≈1.7 万行、101 个 pytest 用例、CMRC2018 离线评测框架（mock 基线）、无 CI / 无 Docker / 无在线 demo。

## P0-1 真实模型量化评测

### 方向说明

目前 `backend/scripts/eval_rag.py` 的评测数字全部来自 mock hash 嵌入，只能证明**代码正确**，不能证明**方法有效**。简历上唯一能写"量化提升"的地方就在这里——必须用真实模型（text-embedding-v4）跑出结果并形成报告。

### 参考案例

**评测报告的标准格式**（参考 RAGAS / 各大厂 RAG 评测博客的通用写法）：

| 检索策略 | R@1 | R@5 | R@10 | MRR | 说明 |
|----------|-----|-----|------|-----|------|
| bm25（纯关键词） | 0.964* | … | … | … | 基线：短查询关键词重合度高 |
| vector（mock） | 0.470* | … | … | … | mock 无语义，仅作代码自检 |
| **vector（text-embedding-v4）** | **待跑** | … | … | … | 关键数据点 |
| hybrid（RRF 融合） | 待跑 | … | … | … | 生产默认策略 |
| fuse（0.6/0.4 加权） | 待跑 | … | … | … | 对照实验 |

*标注 * 的为 mock 基线，正式报告中替换为真实模型数字。

**报告应包含的分析点**（面试官必问）：
1. 为什么 mock 下 bm25 碾压向量？→ mock 是字符 hash 无语义，真实模型下预期反转
2. RRF vs 加权融合的取舍 → 写出你的选择理由（无需调参、对分数分布鲁棒）
3. 失败案例分析：抽 10~20 条 R@1 未命中的查询，归因（跨文档答案、同义改写、查询过短）

### 交付物

- `docs/RAG_评测报告.md`：完整对比表 + 归因分析 + 失败案例
- `backend/eval_data/report_api.json`：真实模型原始结果（可复现证据）
- README「核心功能」或「质量优势」处引用关键数字

### 验收标准

- [ ] `python scripts/eval_rag.py --embed api` 成功跑完（256 文档 / 1000 查询，可用 `--limit` 抽样但报告中注明抽样量）
- [ ] 对比表覆盖 ≥4 种策略 × 4 个指标（R@1 / R@5 / R@10 / MRR）
- [ ] 报告中至少 1 组结论是"真实模型与 mock 基线相反"并给出解释（这是面试金句）
- [ ] 任何人按报告中的命令可复现数字（随机种子/抽样范围已固定）
- [ ] README 中能出现一句带数字的话，例如"混合检索（宽召回+RRF）较纯向量检索 R@1 提升 X%"

## P0-2 Docker 生产部署

### 方向说明

"1.7 万行代码只能 `uvicorn --reload` 本地跑"是后端面试的硬伤。补齐生产级容器化，同时顺带解决 CORS 硬编码、`.env` 管理、前端构建产物托管三个问题。

### 参考案例

**架构**：`nginx（前端静态 + 反代 /api）→ gunicorn -k uvicorn.workers.UvicornWorker（后端）`，数据卷挂载持久化。

`backend/Dockerfile` 参考：

```dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app ./app
EXPOSE 8000
CMD ["gunicorn", "app.main:app", "-k", "uvicorn.workers.UvicornWorker", "-w", "2", "-b", "0.0.0.0:8000"]
```

`docker-compose.yml` 参考：

```yaml
services:
  backend:
    build: ./backend
    env_file: ./.env            # 与本地开发共源（根 .env 唯一真值）
    volumes:
      - ./data:/app/data              # 知识图谱 / 对话历史持久化
      - ./backend/data:/app/backend_data
    expose: ["8000"]
  frontend:
    build: ./frontend                 # 多阶段构建：node 构建 → nginx 托管
    ports: ["80:80"]
    depends_on: [backend]
```

`frontend/nginx.conf` 要点：`location /api { proxy_pass http://backend:8000; }` + SSE 需关闭缓冲（`proxy_buffering off; proxy_cache off;`），否则流式对话会卡住一次性吐出。

**可参考的同类项目**：GitHub 搜索 `fastapi vue docker-compose`，如 `lobehub/lobe-chat`（Dockerfile + compose 组织方式）、`RasaHQ/rasa`（Python NLP 项目的生产部署结构）。

### 交付物

- `backend/Dockerfile`、`frontend/Dockerfile`、`docker-compose.yml`、`frontend/nginx.conf`
- `requirements.txt` 增加 `gunicorn`
- `app/main.py` CORS 白名单改为读环境变量 `CORS_ORIGINS`（顺带完成「规划中」一项）
- README「快速开始」新增 Docker 启动小节

### 验收标准

- [ ] 在一台**只装了 Docker** 的干净机器上，`docker compose up -d` 后 30 秒内全站可用
- [ ] `curl http://localhost/api/health` 返回 200；前端对话流式输出正常（SSE 不缓冲）
- [ ] 上传知识文件 → `docker compose down && up` 后数据仍在（卷持久化验证）
- [ ] `.env` 缺失或 API Key 为空时后端启动报明确错误，而非静默崩溃

## P0-3 GitHub Actions CI

### 方向说明

后端面试官看到"零 CI"会直接质疑工程习惯。101 个测试已全 mock 零网络，天然适合进 CI，成本极低。

### 参考案例

`.github/workflows/ci.yml` 参考：

```yaml
name: CI
on: [push, pull_request]
jobs:
  backend-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.11" }
      - run: pip install -r backend/requirements.txt
      - run: cd backend && python -m pytest tests/ -q
  frontend-build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: "18" }
      - run: cd frontend && npm ci && npm run build
```

**可参考**：几乎所有中大型开源仓库的标准做法，如 `docsifyjs/docsify`（纯前端）、`encode/fastapi` 自身仓库（Python 多版本矩阵测试）。

### 交付物

- `.github/workflows/ci.yml`
- README 顶部加 CI 徽章：`![CI](https://github.com/<owner>/AI-tutor/actions/workflows/ci.yml/badge.svg)`

### 验收标准

- [ ] 提交一个 PR/push 后 CI 自动运行，101 个测试全绿
- [ ] 故意提交一个失败用例，CI 变红（验证拦截有效）
- [ ] README 徽章显示绿色

## P1-1 在线部署 + 演示资产

### 方向说明

没有在线链接，简历上的项目等于"死链"——面试官不会为你搭环境。哪怕部署到一台最低配云服务器（2核2G 足够），加上 30 秒演示动图，项目可信度翻倍。

### 参考案例

- **部署目标**：阿里云/腾讯云学生机或轻量服务器 + 备案可选（无备案可用 IP 或海外节点直连）
- **演示动图**：录制"登录 → 上传知识 → 递归式教学对话 → 图谱实时生长"30 秒全流程，放 README 顶部。工具：OBS 录屏 + [gifski](https://gifski.com)/ezgif 压缩
- **可参考**：`langgenius/dify`、`lobehub/lobe-chat` 的 README 首屏布局（徽章 → 一句话定位 → 演示图 → 亮点列表）

### 交付物

- 公网可访问地址（写进 README 徽章区）
- `docs/demo.gif` 或演示视频链接
- README 顶部「项目亮点」3 条（STAR 式），示例：
  - ❌ 差写法："实现了 RAG 检索增强问答"
  - ✅ 好写法："设计宽召回（Top-30）+ RRF 融合的混合检索，在 CMRC2018 评测集上 R@1 达 X%，较纯向量检索提升 Y%"
  - ✅ 好写法："实现两阶段流式对话架构（SSE 文本流 + 后台 function calling），对话响应首字延迟 <1s，知识图谱经事件总线实时更新"

### 验收标准

- [ ] 手机 4G 网络下打开首页 < 5 秒，完整走通"注册→对话→看图谱"流程
- [ ] 演示动图 ≤5MB、覆盖核心链路
- [ ] 3 条亮点中至少 2 条带量化数字
- [ ] 公开测试账号写进 README（或开放注册），面试官零配置可体验

## P2-1 健壮性补齐

### 方向说明

对应「规划中」清单的三项，完成后可在面试中回答"你考虑过生产稳定性吗"。

| 改进 | 方案参考 | 验收标准 |
|------|----------|----------|
| LLM 请求重试 | `tenacity` 指数退避（3 次），仅对 429/5xx/超时重试 | 新增单测：模拟 2 次失败后成功，验证重试次数与最终结果；模拟连续失败，验证返回标准错误码而非 500 |
| CORS 配置化 | 环境变量 `CORS_ORIGINS` 逗号分隔，默认仅本地 | 未配置时仅放行 5173 本地；配置后生效，有单测覆盖 |
| Toast 替代 alert | 引入轻量组件或自实现（项目已有 Pinia） | 全站 `grep -r "alert("` 零命中；错误码提示有统一出口 |

## P2-2 技术输出

### 方向说明

一篇讲透检索设计决策的博客（或 10 分钟讲解视频），是面试深挖时的"弹药库"，也证明你对自己写的每一行代码都有思考。

### 参考案例

- **选题 1（推荐）**：《从 mock 到真实：一次 RAG 检索评测的完整复盘》——写 mock 与真实模型评测结果反转的现象及归因，天然有故事性
- **选题 2**：《知识图谱驱动的自适应教学：两阶段流式架构设计》——讲 SSE + function calling + 事件总线的解耦
- **写法参考**：阮一峰博客的"问题→方案→验证"结构；掘金/知乎上搜 "RAG 检索评测" 看同行的深度基线
- **发布位置**：掘金/知乎/个人博客，链接放 README 和简历项目描述末尾

### 验收标准

- [ ] 发布 1 篇 ≥2000 字技术文章，含真实评测数据与架构图
- [ ] 文中每个技术决策都回答了"为什么这么选、放弃了什么备选方案"
- [ ] 链接写进 README「相关文档」与简历

## 时间线建议（3 周冲刺）

```
第 1 周：P0 三项（真实评测 → Docker → CI）        ← 决定项目上限
第 2 周：P1 两项（上线 + 演示资产 + 仓库清理）     ← 决定面试官第一印象
第 3 周：P2 两项（健壮性 + 博客），缓冲 + 彩排     ← 决定深挖时的表现
```

彩排方式：对着 README 自问自答 20 个"为什么"（为什么选 RRF？为什么 SQLite？SSE 断线怎么办？并发下知识库写入冲突怎么处理？），答不上来的就是下一个改进点。
