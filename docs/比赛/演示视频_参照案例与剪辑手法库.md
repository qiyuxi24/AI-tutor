## 一、同类作品的成片结构（4 个可对照的范本）

### 1. Devpost 官方视频指南（作品提交类，最权威的"该怎么拍"）

来源：<https://help.devpost.com/article/84-video-making-best-practices>

官方要点原文（摘译）：
- "要**screencast（录屏 + 旁白）**——花哨的营销视频对评委理解与评估你的应用没有帮助，不要那些 gimmick。"
- "**开场几秒就要当电影预告片**：先讲清你的应用做什么、对应赛题什么要求，之后才进入细节。"
- "**要剪辑**：数字视频的好处就是只给观众看最好的部分，把杂乱的部分剪掉；不要怕多录几条。"
- "**先写脚本、排练、再录**（get organized）。"
- 提醒：不要拖到最后一刻才上传，处理/上传可能几分钟到几小时。

【可照搬】我们的 §4/§5 逐字旁白稿 + 分段多录，直接对应"先写脚本、多拍几条、剪掉杂乱"。

### 2. 真实项目的 `DEMO_SCRIPT.md`（分镜脚本长什么样）

来源：[Claudate/project-multilevel-index · DEMO_SCRIPT.md](https://github.com/Claudate/project-multilevel-index/blob/fe63daa48bec698f4f5179b9517fdcb1543844e5/DEMO_SCRIPT.md)

结构特征（值得照抄的格式）：
- 每个"演示"一节：**`## 演示 N: 名称（Xs）` → 场景 → 步骤 → 每步 `[00:00-00:05]` 时间码 + 具体操作 + 期望输出**。
- 末尾固定三块：**GIF 制作指南 / 完整演示视频结构（开场10s → 核心概念30s → 实际操作90s → 结尾10s）/ 发布清单（勾选式）**。
- 环境准备单列：清屏、终端字号 16pt+、清爽配色、**关掉通知**。

【可照搬】这正是我们要给剪辑同学的"分镜表"格式；特别是**"期望输出"一栏**——录制时出错能立刻对照发现。

### 3. 真实项目的 `recording-guide.md`（录屏操作规范）

来源：<https://github.com/pengguogo/english-app/blob/main/docs/recording-guide.md>

特征：
- 明确**推荐演示路径**（首页→选学科→…→完成），"全程约 20 秒，覆盖核心学习闭环"。
- 工具链：OBS 录屏 → ffmpeg/Gifski 转 GIF；给 `ffmpeg` 具体参数（`fps=12, scale=640`）。
- **录制时分辨率 1280×720、时长 20–30 秒、目标体积 <5MB** 这类硬数字先定死。
- 文末注明"当前 demo.gif 已生成（640×400, 12fps, ~1.5MB）"——**成品参数写回文档**，可复核。

【可照搬】"先定演示路径 + 定死参数 + 成品参数写回文档"这套纪律；我们的落点是 §7.1 OBS 参数表 + §8 交付自检。

### 6. 三条会改动我们参数的硬要求（本次核实）

| 要求 | 原文 | 对文档的影响 |
|---|---|---|
| **分辨率不低于 1080p** | AIC 第七届区域赛提交流程："【演示视频】……**分辨率不低于 1080p**，时长 3-5 分钟"（[PDF](https://www.aicomp.cn/wp-content/uploads/2025/10/3.%E7%AC%AC%E4%B8%83%E5%B1%8AAIC%E5%A4%A7%E8%B5%9B%E7%AE%97%E6%B3%95%E5%88%9B%E6%96%B0%E8%B5%9B%E5%8F%8A%E7%AE%97%E6%B3%95%E5%BA%94%E7%94%A8%E8%B5%9B%E5%8C%BA%E5%9F%9F%E8%B5%9B%E4%BD%9C%E5%93%81%E6%8F%90%E4%BA%A4%E6%B5%81%E7%A8%8B.pdf)） | 我们的 1920×1080 合规；**不要为了压体积降分辨率** |
| **帧率取 25 fps 更保险** | 国内教学资源/评审规范常见口径："16∶9、编码 H.264/**25 帧**、1920×1080、码率 4Mbps、**片头时长 5 秒**"（[杭州西湖区教学资源规范 PDF](https://www.hzxhjy.cn/xhjyw/xjtz/jxxxtz/202405/P020240511356886463746.pdf)） | 30 fps 录、**导出可选 25 fps**（录屏无快速运动，25 与 30 肉眼无差，且更贴国内规范） |
| **避免画中画出镜** | 同上 PDF："作品画面不出现主讲教师本人画面"、"避免……以画中画的形式出镜" | **取消原计划的"右下角人脸画中画"**——教育类评审可能反感，改用**纯旁白**（我们的脚本本来就是纯旁白，无需改） |
| 检录照片须与视频一致 | AIC 第七届流程："【参赛选手检录照片】，证件信息须与视频中参赛团队一致，**如不一样，视为作弊**" | 若 AIC 要检录，视频里出镜/署名人必须与报名名单一致 |

编码参数锚点：YouTube 官方建议 1080p/30fps 用 8 Mbps（[来源](https://support.google.com/youtube/answer/1722171?hl=en)）。→ **视频 A：500 MB ÷ 10 min ≈ 6.7 Mbps 上限，导出取 6 Mbps VBR 是安全解；视频 B 直接 8 Mbps。** 与本目录计划 §7.2 的结论一致。


### 4. 比赛项目的"路演视频录制流水线"（最接近我们场景的工程化做法）

来源：[guopanqi/mindbridge 提交 5563d93](https://github.com/guopanqi/mindbridge/commit/5563d93a1ae53b26d833b1002aaca79ee865bc6c)（该项目 README 可见于 <https://cdn.jsdelivr.net/gh/guopanqi/mindbridge@main/README.md>）

该仓库把路演视频做成**可复现的流水线**：`路演/视频/` 放 `record-*.mjs`、`assemble.mjs` 这类录制与合成脚本，导出的 MP4 放 `路演/视频成品/`；目录里还区分了"决赛信息 / 参赛要求 / 视频剧本 / PPT 大纲脚本 / 成品"。
【推断】它的三段做法对本项目很关键：**①"模型剧本桩"（先写死剧本再录）②真实系统截图/录屏 ③样机外框合成**——第 ③ 条对 AIC 版有用：把 1080p 录屏套进笔记本样机外框，画面更像正式产品片，同时外框可以**盖住不想露出的浏览器区域**，一举解决去校名。

**四条对照后的共同结论**：写出分镜时间码表 → 定死录制参数 → 分段多录 → 关键处放大高亮 → 字幕与旁白统一 → 发布前勾选清单 → 成品参数回写文档。

## 三、评委视角的常见扣分点（每条都能避免）

| 扣分点 | 为什么会扣 | 对策（落在我们文档哪一节） |
|---|---|---|
| **PPT 式假演示**（用动效假装系统在跑） | 求"完成度"，防的就是"PPT 工程" | 全程真机录屏（计划 §4/§5） |
| 加速剪辑**掩盖卡顿/失败** | 一旦被看出跳帧，可信度崩 | 变速只用于**必然的等待**（出题 40 s、索引），并加 `×6` 角标（§7.2） |
| 无旁白 / 无字幕 | 评委静音看片是常态 | 全程字幕 + 分段录旁白（§7.2） |
| 画面出现校名/校徽/指导教师 | **AIC 明文红线**："不得出现参赛团队所在学校名称及 Logo、指导教师等信息……避免因违规导致扣分或取消参赛资格" | §5.2 去校名清单（一票否决项） |
| 出现第三方付费账号/无关品牌水印 | AI+教育明文"内容不得出现无关品牌水印" | 干净浏览器 profile 录屏（§5.2） |
| **分辨率 <1080p / 非 16:9** | AIC 第七届流程明文"分辨率不低于 1080p" | 全程 1920×1080、16:9（§7.1） |
| 检录照片与视频署名不一致 | AIC 第七届流程原文"如不一样，**视为作弊**" | 若需检录，出镜/署名与报名名单严格一致 |
| 配乐侵权 | 材料合规审查 + 教学资源规范点名"引用他人的音乐/图片/视频" | 只用剪映自带曲库，音量 ≤-25 dB |
| 时长超限 / 体积爆掉 | "严格控制在 3-5 分钟"；材料缺失或格式不符"按**无效申报**处理" | 导出后**读文件属性**核对（§8） |
| 演示 mock 数据 / 只放 PPT | AIC 要求"清晰展示作品**功能、实现流程与应用效果**"，且作品须"已完成开发" | 全程真机 + 真数据（计划 §4/§5） |
| 旁白说"已上线/有真实用户/支持并发" | 与取证范围不符，一问就崩 | 遵守 `可演示事实清单` §5 禁止说法 |
| 界面看不清（小字、缩放非 100%） | 评委看不清 = 讲不清 | 1080p + 100% 缩放 + 关键处放大（§7.1/§7.2） |
| 上传压线 | 平台处理/上传耗时不可控；AI+教育"截止后不再受理任何修改、补充" | 10/14 完成导出，10/15 只上传 |

## 四、剪辑手法清单（操作级，12 条）

> 全部基于 **OBS 录制 + 剪映专业版**。时间单位=成片时间。`【推断】`=经验判断，非来源原文。

| # | 手法 | 在剪映里怎么点 | 用在哪一幕 |
|---|---|---|---|
| 1 | **清垃圾** | 时间线选中段落 → `Delete`；`Ctrl+B` 按播放头切分以便逐段删 | 每一次操作间隙、误点、加载等待（省时间最多的一步） |
| 2 | **变速跳等待** | 选中片段 → 右上「变速 → 常规变速」→ `4x~8x`；配 `×6` 角标字幕 | 出题 40 s、资料索引、图谱渲染（参照 [Recorded 变速做法](https://recorded.app/zh-TW/blog/speed-ramping-screen-recordings/)） |
| 3 | **关键帧放大（局部聚焦）** | 片段上点「关键帧」→ 播放头 3 s 后 → 拉大「缩放」到 150–200%，移动「位置」对准细节 → 再打一个关键帧回位 | 小字节点标签、判分结论、来源引用、测试汇总行 |
| 4 | **蒙版聚焦** | 「画面 → 蒙版 → 矩形」+ 羽化，只留要看的区域，配合 #3 一起用 | 仪表盘数字、图谱某一片区域（参照 [剪映蒙版局部放大](https://www.douyin.com/shipin/7313515431799867443)） |
| 5 | **光标高亮**（优先在 OBS 里做） | OBS `来源→显示器采集` 里开"**高亮鼠标**"，比后期画圈省 80% 时间；后期补：贴纸圆圈 60 px / 描边 4 px / `#FF3B30`，位置关键帧追 1.5 s | 点击的按钮、刚新增的图谱节点 |
| 6 | **智能字幕 + 关键词上色** | 「文本 → 智能字幕 → 识别字幕」→ 逐条校对专有名词（知识图谱/掌握度/SSE）→ 字号 ≥40 px、白字 + 描边 3 px（浅色录屏必须加）；关键词单独一条亮色 `#3AA0FF` 叠加 | 全片 |
| 7 | **打字机字幕** | 「文本 → 动画 → 入场 → 打字机」0.6–1.2 s；**只用于结论句，全片 ≤4 次** | 片头作品名、关键结论句 |
| 8 | **分章进度条 + 章节条** | 顶部 60 px 黑底文字条写「01 概述 / 02 核心演示 / 03 效果总结」，入场用"向右擦除 0.4 s"；进度用两片 4 px 矩形 + 线性蒙版关键帧推进 | 全片导航（A 版 5 幕、B 版 4 段） |
| 9 | **数据卡片** | 「文本 + 矩形底色 + 数字滚动动画（入场-数字）」，逐行按旁白节奏出现 | **B 版效果验证段**（前后测对比表） |
| 10 | **转场克制** | 只用「叠化 0.3–0.5 s」与「无转场硬切」；禁用旋转/翻页/故障转场（评委对"掩盖剪辑"极敏感） | 段落之间 |
| 11 | **音量归一化** | 人声峰值约 `-6 dB`、BGM `-22 dB`；剪映无 LUFS 表时导出后用 `ffmpeg -af loudnorm=I=-16:TP=-1.5:LRA=11` 校准 | 全片；导出前听一遍 |
| 12 | **画面稳定性** | 素材统一 1920×1080；不用「智能补帧」放大低清素材；必要时套笔记本样机外框（参照 §一.4 #3）——外框同时可遮挡敏感区域 | 全片 |
| ⛔ | **不要画中画人脸** | 国内教学资源规范明文"作品画面不出现主讲教师本人画面""避免以画中画的形式出镜" | 我们脚本本就纯旁白，**保持纯旁白** |

**导出参数**（A/B 两版都用）：MP4 / **H.264(AVC)** / 1920×1080（16:9）/ **25 fps**（录制可用 30，导出转 25；国内规范常见口径是 25 帧）/ AAC 192 kbps。
- A 版码率 **6 Mbps** → 10 min ≈ 450 MB（500 MB ÷ 10 min ≈ 6.7 Mbps 理论上限，6 Mbps 是安全解）
- B 版码率 **8 Mbps** → 4 min ≈ 240 MB（卡 300 MB）
- 超体积时优先降到 5 Mbps，**不要降分辨率**（1080p 是硬要求，录屏文字一降就糊）。
- 片头建议 **3–5 秒**（国内教学资源规范口径"片头时长 5 秒"），**AIC 版片头绝不能含校徽校名**。

## 五、可选进阶：用 Playwright 自动录屏（解决"去校名 + 重录"两个痛点）

本项目前端已有 Playwright CLI 痕迹（`.playwright-cli/`），且 [english-app 的录屏指南](https://github.com/pengguogo/english-app/blob/main/docs/recording-guide.md) 明确提出"用 Playwright 驱动系统 Chrome 自动录制，脚本见 `scripts/record-demo.js`"。

【推断】对我们值不值得做：
- **值得**的场景：需要**同一条路径录 3–5 遍选最好**（自动录制可保证每次操作一致、无鼠标犹豫），或需要**固定裁剪视口**（`1280×720` 视口录制天然不露书签栏/任务栏 → 顺手解决 AIC 去校名）。
- **不值得**的场景：Agent 对话是**非确定性**的（模型输出每次不同），自动录制的"稳定"在这里是假象；核心教学闭环仍建议**人工操作 + 多录几条**。
- 折中方案：**纯 UI 展示段**（图谱浏览、仪表盘、判分结果）用 Playwright 自动录；**对话/出题段**人工录。
