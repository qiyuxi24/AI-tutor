## 一、上线拓扑全景：一次请求经过了什么

### 1.1 本项目的实际拓扑

```
                    ┌──────────────────────────────────────────────┐
   同学浏览器  ──▶  │  （可选）CDN / 云负载均衡  ← 只做静态加速时才有  │
                    └───────────────────┬──────────────────────────┘
                                        │  HTTP(S) :80 / :443
                    ┌───────────────────▼──────────────────────────┐
                    │  宿主机（Linux 云服务器 / 你的 Windows 电脑）  │
                    │                                              │
                    │   ┌──────────── 容器 ai-tutor ────────────┐   │
                    │   │  Nginx  监听 80                       │   │
                    │   │   ├── /            → /usr/share/nginx/html（Vue 构建产物）│
                    │   │   └── /api/*      → 反代 127.0.0.1:8000 │   │
                    │   │  Uvicorn 监听 8000（--workers 1）       │   │
                    │   │   └── FastAPI 应用                     │   │
                    │   └───────────────────────────────────────┘   │
                    │              │                │              │
                    │   ./data/*   │                │  出网        │
                    │  ./backend/data（挂载卷）      ▼              │
                    │                     MiniMax-M3 / 阿里 embedding│
                    └──────────────────────────────────────────────┘
```

**一句话总结：单机 + 单容器 + 双进程（Nginx/Uvicorn）+ 挂载卷存状态。**

### 1.2 分层职责表（每层坏了会怎样）

| 层 | 组件 | 职责 | 这一层挂了的表现 |
|---|---|---|---|
| DNS | 域名解析 | 把域名指向服务器 IP | 域名打不开，IP 直连正常 |
| 证书/TLS | certbot / 云证书 | 加密传输 | 浏览器"不安全"警告；使用 IP 直连无此问题 |
| 接入网关 | Nginx | 静态托管、反代、SSE 透传、体积限制 | 502 / 504 / 静态页能开但接口全挂 / 流式不吐字 |
| 应用 | FastAPI（Uvicorn） | 业务逻辑、Agent Loop | 接口 500、错误码 `[E-XXX]` |
| 进程守护 | entrypoint.sh + Docker restart 策略 | 拉起两个进程、任一退出则容器退出 | 容器反复 restarting |
| 存储 | SQLite + 节点 MD/索引文件 | 全部业务状态 | 数据丢失/锁库 |
| 外部依赖 | MiniMax（对话）、阿里（嵌入） | LLM 推理 | 对话超时/报错；**嵌入欠费会静默降级** |
| 宿主机 | Linux/Windows | 一切的地基 | 磁盘满、OOM、端口被占 |

> **运维第一原则：先定位"是哪一层坏了"，再动手。** 上表就是定位的坐标系——例如"首页能开、聊天转圈不出字"，直接跳到网关层的 SSE 排查（见 §2.3）。

### 1.3 三个必须记住的架构硬约束

这三条决定了本项目**不能**用什么手段扩容，运维手段必须绕着它们设计：

| 约束 | 原因（代码事实） | 运维含义 |
|---|---|---|
| **必须单进程（`--workers 1`）** | EventBus 是**进程内** per-user 队列；定时 GC 也是进程内任务（`AGENTS.md` §0） | ❌ 不能靠"多 worker / 多容器 + 负载均衡"扩容；扩了会出现"图谱更新事件只推给了其中一个进程"的诡异 bug |
| **SQLite 单写者** | 图谱/会话/画像/运行记录/KB/向量/出题全部是 SQLite（WAL 模式） | ❌ 不能多副本同时写同一个库；横向扩展前必须先把存储换成 PG/MySQL |
| **状态全在挂载卷** | `./data/*`、`./backend/data` | ⚠️ 容器可随意重建，但**卷不能乱删**；备份=备份卷 |

> `【建议】` 如果未来确实需要多实例：先做"存储外置（PG）"+"事件总线外置（Redis Pub/Sub）"两件事，再谈 Nginx upstream 多实例。**顺序反了会浪费大量排查时间。**

## 二、网关：反向代理、TLS 与流式长连接

这是本文重点章节。本项目的"网关"目前是**容器内的 Nginx**，它的配置在仓库 `nginx.conf`，可直接对照阅读。

### 2.1 先分清"网关"这个词的四个层次

业界的"网关"常被混用，选型前先对齐概念：

| 层次 | 代表 | 做什么 | 什么时候你才需要 |
|---|---|---|---|
| **接入网关 / 反向代理** | Nginx、Caddy、Traefik、云 SLB/CLB | 终止 TLS、路由、静态资源、限流、访问日志 | **本项目现在就需要**（已有 Nginx） |
| **API 网关** | Kong、APISIX、Higress、阿里云 API 网关 | 认证鉴权、配额、灰度、协议转换、OpenAPI 管理 | 有多个后端服务、要统一鉴权与配额时 |
| **服务网格** | Istio、Linkerd | 服务间 mTLS、流量治理、可观测（Sidecar） | 微服务数量 ≥ 十几个、有多团队协作时 |
| **边缘 / CDN** | 阿里云 CDN、Cloudflare | 静态资源就近分发、抗 DDoS、WAF | 用户地理分散、静态资源体积大时 |

> `【建议】` 本项目当前规模（单容器、单机、SQLite）**只需要接入网关层**。引入 API 网关或服务网格属于典型的过度设计——维护成本远超收益。等到"多后端服务 + 多用户租户 + 需要统一配额"时再说。

### 2.2 逐段读懂本项目的 `nginx.conf`

```nginx
server {
    listen 80;
    server_name _;                    # 兜底：任何 Host 都接（无域名/多域名都适用）

    client_max_body_size 100m;        # ① 上传大文件（PDF/电子书）必须放开，默认 1m 会 413

    root /usr/share/nginx/html;       # 前端构建产物（Dockerfile 从 node 阶段 COPY 进来）
    index index.html;

    gzip on;                          # ② 压缩
    gzip_min_length 1k;
    gzip_types text/plain text/css application/javascript application/json image/svg+xml;

    location /api/ {                  # ③ 后端反代
        proxy_pass http://127.0.0.1:8000;      # 同容器内的 Uvicorn
        proxy_http_version 1.1;                # SSE 需要 1.1（1.0 不支持 chunked）
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;          # 让后端拿到真实客户端 IP
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Connection "";        # 清空 Connection，保持长连接复用

        proxy_buffering off;                   # ④ SSE 关键：不缓冲，来一块转发一块
        proxy_cache off;
        proxy_read_timeout 300s;               # ⑤ LLM 慢：读超时必须远大于默认 60s
        proxy_send_timeout 300s;
    }

    location / {
        try_files $uri $uri/ /index.html;      # SPA 兜底：刷新子路由不 404
    }
}
```

**这五处配置都是"少了就出问题"的，逐条解释为什么：**

| 标记 | 配置 | 不配会怎样 |
|---|---|---|
| ① | `client_max_body_size 100m` | 上传知识库（PDF/电子书）返回 **413 Request Entity Too Large** |
| ② | `gzip_types` **不含** `text/event-stream` | 若把 `text/event-stream` 加进 gzip 列表，SSE 会被压缩**并因此被缓冲**，表现为"回答不逐字出、最后一次性蹦出来" |
| ③ | `proxy_http_version 1.1` + `Connection ""` | 用 HTTP/1.0 则不支持 chunked 传输，SSE 无法流式 |
| ④ | `proxy_buffering off` | Nginx 会把上游响应攒够缓冲区才吐给浏览器 → **流式变批式**（最经典的 SSE 事故） |
| ⑤ | `proxy_read_timeout 300s` | 默认 60s，而本项目单轮 LLM 调用可能 60s+（实测首轮对话 **68s**）→ **504 Gateway Time-out** |

> **本项目已做的应用侧加固**：`backend/app/api/v1/chat.py` 的 SSE 响应已显式返回
> `X-Accel-Buffering: no`、`Cache-Control: no-cache`、`Connection: keep-alive`。
> `X-Accel-Buffering: no` 的作用是**让 Nginx 无条件不缓冲**——这是"应用层自我保护"，即使运维忘了配 `proxy_buffering off` 也能流式。**上 CDN 时它更是必需**（多数 CDN 只认这个头）。

### 2.3 SSE / 流式长连接专项（本项目核心交互）

本项目的对话是 `POST /api/v1/chat/stream` 的 SSE 流（事件协议见 `AGENTS.md` §3.4）。**流式是运维最容易出问题的地方**，因为它同时踩了三个雷：长连接、代理缓冲、超时。

#### 2.3.1 排查模型：五处可能缓冲

一次流式回答从 LLM 到你的浏览器，要穿过这些"可能攒东西"的环节，**任何一处缓冲都会表现为"不吐字"**：

```
LLM API ──▶ ① httpx 客户端 ──▶ ② Uvicorn/ASGI ──▶ ③ Nginx ──▶ ④ CDN/云 LB ──▶ ⑤ 浏览器
             （无缓冲）          （StreamingResponse）  （proxy_buffering off）  （常见元凶）   （DevTools 验证）
```

| 环节 | 检查点 | 本项目状态 |
|---|---|---|
| ① httpx | 是否用了 `.stream()` 语义（异步逐块读） | ✅ 代码已按流式实现 |
| ② ASGI | 是否 `StreamingResponse` 且未做中间件压缩 | ✅ 无 GZip 中间件 |
| ③ Nginx | `proxy_buffering off` + `X-Accel-Buffering: no` | ✅ 两者都有（双保险） |
| ④ CDN / 云 LB | 是否支持 SSE、是否开了响应压缩/缓存 | ⚠️ **未上 CDN，路径未验证** |
| ⑤ 浏览器 | 是否 `EventSource`/`fetch` 流式读取、是否有缓冲 polyfill | ✅ 前端 `streamChat` 已实现 |

#### 2.3.2 命令行验证流式（关键技能）

`curl -N`（禁用 curl 自己的输出缓冲）可以**看到每一行的到达时间**，这是判断"到底哪一层在缓冲"的唯一可靠办法：

```bash
# 逐行打印并带时间戳：如果所有行在同一秒出现 → 某层在缓冲
curl -N -X POST 'http://<服务器IP>:8080/api/v1/chat/stream' \
  -H 'Authorization: Bearer <你的token>' \
  -H 'Content-Type: application/json' \
  -d '{"messages":[{"role":"user","content":"你好"}],"mode":"free_talk"}' \
  | while IFS= read -r line; do printf '%s  %s\n' "$(date +%T)" "$line"; done
```

判读标准：

- **正常**：`thinking` / `tool_start` / `text_delta` 事件**陆续**出现，时间戳递增
- **全程同一秒 + 最后突然出现**：缓冲在链路某处 → 按 ①→⑤ 顺序排查（本项目先怀疑 ④）
- **等 60s 后 504**：超时太短（Nginx `proxy_read_timeout` 或云 LB 的默认 60s）

#### 2.3.3 CDN / 云负载均衡的注意事项（`【未验证】`）

`【现状】` 本项目尚未上 CDN。若将来要上，注意这些**通用约束**（具体以云厂商文档为准，务必自测）：

| 事项 | 说明 |
|---|---|
| 是否支持 SSE | 部分 CDN/加速类型不支持长连接流式，需选"全站加速 / 动态加速"类产品并确认 |
| 响应压缩 | 开启压缩可能缓冲 `text/event-stream` → 建议对该路径**关闭压缩**或依赖 `X-Accel-Buffering: no` |
| 缓存规则 | **绝不能**缓存 `/api/*`（会串用户数据，属安全事故） |
| 超时 | CDN 的"回源超时"默认可能 30-60s，需调大 |
| 真实 IP | 上 CDN 后 `X-Real-IP` 会变成 CDN 节点 IP，需按厂商方式取真实客户端 IP（影响登录限流按 IP 统计） |

> `【建议】` 上 CDN 前**先做一件事**：把静态资源与 API 分开配置（静态走缓存、`/api/*` 全透传不缓存），否则会因为一个 `/api` 缓存规则造成用户间数据串号。

### 2.4 TLS / HTTPS：证书签发与续期的 2026 现状

`【现状】` 本项目当前是 **HTTP + IP/端口访问**（局域网场景，`http://192.168.5.196:8080`），没有域名与证书。
公网部署时建议按下面两条路线之一上 HTTPS。

#### 2.4.1 路线 A（推荐给国内服务器）：云厂商免费证书 + 云 LB/CDN 卸载 TLS

| 步骤 | 操作 |
|---|---|
| 1 | 买/备案域名，解析到服务器 IP |
| 2 | 云控制台申请免费 DV 证书（阿里云/腾讯云均有 1 年期免费额度） |
| 3 | 在云 LB / CDN 上配证书（TLS 在云端终止），回源用 HTTP |
| 4 | 服务器安全组只放行 443（+ 80 做跳转），**不暴露 8080** |

优点：不占服务器资源、不操心续期（云厂商代管）、可用 WAF。
缺点：云产品绑定、调试时多一层。

#### 2.4.2 路线 B：服务器自签（Let's Encrypt + certbot）

```bash
# Ubuntu / Debian
sudo apt update && sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d your-domain.com        # 自动改 nginx 配置 + 申请证书
sudo systemctl list-timers | grep certbot      # 确认自动续期定时器已启用
sudo certbot renew --dry-run                   # 演练续期（务必做一次）
```

> **重要：2026 年证书有效期正在快速缩短，续期自动化从"最好有"变成"必须有"。**

| 时点 | 事实（已核实） |
|---|---|
| 2026-01-15 | Let's Encrypt 的 **6 天（160 小时）短证书**与 **IP 地址证书** 正式 GA |
| 2026-03-11 | Certbot 支持 6 天证书：`--preferred-profile`（Certbot 4.0+）与 `--ip-address` |
| **默认值** | **6 天证书不是默认**，默认仍是 **90 天**；要用短证书需显式选择 ACME `shortlived` profile |
| 趋势 | 行业路线图指向 **2029 年所有证书最长 47 天** |

对运维的实际含义：

- 用 **90 天默认证书**：`certbot renew` 一天跑两次（上游建议），有充足的失败重试窗口 → **够用，本项目推荐**
- 若改用 **6 天短证书**：容忍度极低，续期失败几个小时就过期 → 必须做到"续期失败立即告警"，且客户端/中间设备要支持频繁轮换（老安卓设备对短证书兼容性差）
- **不要手工续期**：证书过期是运维事故里最常见、也最冤枉的一类

```bash
# 证书到期巡检（可放 cron，见 §3.8）
echo | openssl s_client -connect your-domain.com:443 -servername your-domain.com 2>/dev/null \
  | openssl x509 -noout -enddate
```

### 2.5 负载均衡与会话粘性：本项目**不能**横向扩容

这是运维里最容易被"想当然"坑到的地方，单独强调：

**❌ 错误做法**：为了"抗并发"，起 3 个容器 + Nginx `upstream` 轮询。

**会发生什么**：

1. **SSE 丢事件**：EventBus 是进程内队列（每个进程一份），图谱更新事件只推给了"处理该请求的那个进程"→ 用户在 A 实例订阅、变更发生在 B 实例 → **前端收不到 `graph_updated`**
2. **SQLite 写冲突**：多个进程写同一个库文件（WAL 支持多读单写）→ 高并发下出现 `database is locked`
3. **限流失效**：`chat_rate_limiter` / 登录限流是进程内计数器 → 3 个实例 = 实际配额 ×3
4. **agent_runs 的 GC 定时任务**重复执行（每个进程都跑）

**✅ 如果真需要更高并发，正确顺序**：

| 顺序 | 动作 | 目的 |
|---|---|---|
| 1 | SQLite → PostgreSQL | 解决"单写者" |
| 2 | EventBus → Redis Pub/Sub | 解决"事件只在单进程" |
| 3 | 限流器 → Redis 计数 | 解决"配额按进程算" |
| 4 | GC 定时任务 → 独立一次性任务（cron / 单独 worker） | 解决"重复执行" |
| 5 | 然后才上多实例 + Nginx upstream | 此时横向扩展才成立 |

> 在此之前，**纵向扩容（加 CPU/内存）是唯一正确的扩容方式**。本项目的瓶颈其实在 LLM API 的响应时间（单轮 60s+），而非本机 CPU——加机器并不会让回答更快。

### 2.6 限流与防护放在哪一层

| 层次 | 手段 | 本项目现状 | 适用场景 |
|---|---|---|---|
| 应用层 | `chat_rate_limiter`（20 次/60 秒）、登录限流（5 次/分钟/IP） | ✅ 已实现 | 按用户/业务语义限流，**最精确** |
| 网关层 | Nginx `limit_req_zone` / `limit_conn` | ❌ 未配 | 抗粗粒度洪峰、防单 IP 打满连接 |
| 边缘层 | 云 WAF、CDN 的 CC 防护 | ❌ 未用 | 公网暴露、遭攻击时 |

> `【建议】` 单机小流量下，应用层限流已足够。公网部署且发现异常流量后，再加 Nginx 限流（注意：**Nginx 限流是按 IP，学校/公司 NAT 出口会让整栋楼共用一个 IP**，阈值别设太紧）。真被攻击时再上云 WAF。

### 2.7 网关的访问日志（最被忽视的排障资产）

`【现状】` Nginx 用的是默认 access log 格式，写在**容器内**（`/var/log/nginx/access.log`），**容器重建即丢**。

`【建议】` 生产环境改成"带上游耗时的 JSON 格式 + 输出到宿主机"，便于按 `run_id`/`耗时` 排查慢请求：

```nginx
# 放在 server 块外（http 层）或 conf.d 文件顶部
log_format json_ops escape=json '{'
  '"ts":"$time_iso8601",'
  '"ip":"$remote_addr",'
  '"method":"$request_method",'
  '"uri":"$request_uri",'
  '"status":$status,'
  '"bytes":$body_bytes_sent,'
  '"rt":$request_time,'          # 总耗时
  '"urt":"$upstream_response_time",'  # 上游耗时 —— 排"是后端慢还是网络慢"的关键
  '"ua":"$http_user_agent"'
'}';
access_log /var/log/nginx/access.log json_ops;
```

判读技巧：

- `rt` 大而 `urt` 小 → 慢在**网络/客户端**（或静态资源）
- `urt` 大 → 慢在**后端**（多数情况是等 LLM，属预期）
- `status=499` → **客户端主动断开**（用户等不及关页面了，常发生在 LLM 太慢时）
- `status=502/504` → 见 §7 排查表

## 三、Linux 服务器运维

`【现状】` 本项目现在跑在你的 **Windows 电脑 + Docker Desktop** 上（局域网共享），生产目标形态是 **Linux 云服务器 + Docker Engine**（不要用 Docker Desktop，见 §3.3）。

### 3.1 服务器初始化清单（新机器 30 分钟）

| # | 事项 | 命令 / 说明 |
|---|---|---|
| 1 | 创建普通用户 | `adduser deploy && usermod -aG sudo deploy`，**不要用 root 日常操作** |
| 2 | SSH 免密登录 | 本地 `ssh-keygen -t ed25519` → `ssh-copy-id deploy@ip` |
| 3 | 关掉密码登录 | `/etc/ssh/sshd_config`：`PasswordAuthentication no`、`PermitRootLogin no` → `systemctl restart sshd` |
| 4 | 时区与时钟 | `sudo timedatectl set-timezone Asia/Shanghai && sudo timedatectl set-ntp true`（**时钟漂移会导致 JWT 校验失败、日志时间错乱**） |
| 5 | 系统更新 | `sudo apt update && sudo apt upgrade -y`；建议开 `unattended-upgrades` 只做安全更新 |
| 6 | 防火墙 | 只放行 SSH + 80/443（见 §3.6） |
| 7 | Swap | 小内存机器（1-2G）**必须配 2G swap**，否则构建镜像时 OOM（见 §3.9） |
| 8 | 安装 Docker | `curl -fsSL https://get.docker.com \| sh`、`sudo usermod -aG docker deploy` |
| 9 | 配置镜像加速 + 日志上限 | `/etc/docker/daemon.json`（见 §4.5） |
| 10 | 部署目录 | `sudo mkdir -p /opt/tutoragent && sudo chown deploy:deploy /opt/tutoragent` |

> ⚠️ **第 4 条最容易被跳过，但本项目的 JWT（`python-jose`）对时间敏感**：服务器时间偏差超过 token 的容忍窗口，会出现"刚登录就 401"。

### 3.2 目录布局规范

| 路径 | 用途 | 说明 |
|---|---|---|
| `/opt/tutoragent` | 代码 + compose + `.env` | 部署根目录（`git clone` 到这里） |
| `/opt/tutoragent/data/*` | **业务状态（卷）** | 图谱/会话/画像 —— **最需要备份** |
| `/opt/tutoragent/backend/data/*` | **业务状态（卷）** | 运行记录/KB/向量/出题/采集 |
| `/opt/tutoragent/logs` | 应用日志（`【建议】`挂载出来） | 见 §6.3 |
| `/var/backups/tutoragent` | 备份归档 | 见 §5.3 |
| `/etc/docker/daemon.json` | Docker 守护进程配置 | 日志上限、镜像加速 |

**为什么用 `/opt`**：FHS 里 `/opt` 是"附加软件包"，`/srv` 是"服务数据"。两者都合规，社区习惯把"自建应用部署"放 `/opt`。**关键是全机统一，不要一处 `/opt` 一处 `/home` 一处 `/srv`** —— 三个月后你自己会找不到数据在哪。

### 3.3 用 systemd 托管 Docker Compose（而不是 `nohup`）

`【现状】` Windows 侧靠 `start.ps1` 手动启动。
`【建议】` Linux 生产环境用 **systemd unit** 托管，获得：开机自启、崩溃自愈、统一日志、`systemctl status` 可观测。

```ini
# /etc/systemd/system/tutoragent.service
[Unit]
Description=TutorAgent (docker compose)
Requires=docker.service
After=docker.service network-online.target
Wants=network-online.target

[Service]
Type=oneshot
RemainAfterExit=yes
WorkingDirectory=/opt/tutoragent
# 启动：拉起整个 compose 项目（--remove-orphans 清理改名后残留的容器）
ExecStart=/usr/bin/docker compose up -d --remove-orphans
# 停止：优雅停服（先 SIGTERM 给容器，超过 docker 的 stop grace 再杀）
ExecStop=/usr/bin/docker compose down
TimeoutStartSec=0
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now tutoragent      # 开机自启 + 立即启动
sudo systemctl status tutoragent             # 看状态
sudo journalctl -u tutoragent -n 100 --no-pager   # 看这个 unit 的日志
```

**为什么 `Type=oneshot` + `RemainAfterExit=yes`**：`docker compose up -d` 是**立即返回**的（容器在后台跑），用默认的 `simple` 类型 systemd 会以为"主进程退出了"从而反复重启。`oneshot + RemainAfterExit` 表示"命令跑完就算服务在运行"，是正确的托管方式。

**与 `restart: unless-stopped` 的分工**：compose 的 restart 策略管**容器进程崩溃**；systemd 管**开机/整体拉起**。两者互补，都要有。

### 3.4 Docker 权限：`usermod -aG docker` 的取舍

| 做法 | 优点 | 风险 |
|---|---|---|
| 加入 `docker` 组 | 不用 sudo，开发/运维方便 | **等价于给了 root 权限**（能挂载宿主机根目录、能起特权容器） |
| 每次 `sudo docker` | 更安全 | 麻烦 |

`【建议】` 单机自用服务器：加入 `docker` 组可以接受，但要**知道**这一点。多人共用服务器：给个别账号加，不要给所有人加。

### 3.5 容器内不要用 root（`【建议】`）

`【现状】` 本项目容器内 **Nginx 和 Uvicorn 都以 root 运行**（`entrypoint.sh` 没有切用户，`Dockerfile` 里 pip 装到系统 Python）。

风险：容器逃逸时可获得宿主机 root 等价权限。加固方向（按性价比排序）：

1. **最省事**：`docker-compose.yml` 里限制能力并开只读根（部分目录仍需可写）
2. **中等**：Dockerfile 里 `useradd` + `USER appuser`，同时把数据目录 `chown` 给该用户
3. **较重**：换 Nginx 非特权镜像（`nginxinc/nginx-unprivileged`）监听 8080 而非 80

> 注意：加固后**数据卷的文件属主会变**（宿主机上是 `1000:1000` 之类），迁移旧数据时要 `chown -R` 对齐，否则出现"容器起来了但写不进数据"。
> 本项目当前是单机自用 + 不对外开放，**属于可接受的风险**；一旦公网多用户使用，建议做第 1、2 步。

### 3.6 防火墙：只暴露必要端口

```bash
# Ubuntu（ufw）
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp          # SSH（改过端口就换成你的端口）
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status verbose

# CentOS/Rocky（firewalld）
sudo firewall-cmd --permanent --add-service=ssh
sudo firewall-cmd --permanent --add-service=http
sudo firewall-cmd --permanent --add-service=https
sudo firewall-cmd --reload
```

**三个必须做的动作**：

1. **不要暴露 8080**：容器端口只在宿主机内部映射（`127.0.0.1:8080:80`），对外统一走 443（Nginx 或云 LB）
2. **云安全组也要配**：系统防火墙和云安全组是**两道独立防线**，只配一道会漏
3. **SSH 加固**：改默认端口、装 `fail2ban` 防爆破

```bash
sudo apt install -y fail2ban      # 默认策略即可挡住大部分 SSH 爆破
sudo fail2ban-client status sshd   # 看拦截情况
```

> **本项目的实际情况提醒（Windows + Docker Desktop 共享给同学时）**：Docker Desktop 安装时写的 `com.docker.backend.exe` 入站规则（`Inbound / Allow / Profile=Public / LocalPort=Any`）**只在「公用网络」下生效**。网络类别一旦变成 **Private（专用）**（换网络后很常见），该规则不匹配 → 同学连不上，此时必须放行。**别只看本机 `curl` 通不通，那恒为 200**。判别与放行命令见 §8.4。

### 3.7 磁盘 / inode：最容易被"日志"吃满

磁盘满是自建服务**最高频**的故障。按这个顺序排查：

```bash
df -h                      # 各分区使用率
df -i                      # inode 使用率（小文件太多时会先耗尽 inode）
du -sh /var/lib/docker     # Docker 数据（镜像 + 容器层 + 卷）
du -sh /var/log/*          # 系统与应用日志
docker system df           # Docker 视角：镜像/容器/卷/构建缓存各占多少
```

| 常见元凶 | 表现 | 处置 |
|---|---|---|
| **Docker 容器日志**（json-file 无上限） | `/var/lib/docker/containers/*/*-json.log` 巨大 | 配 `daemon.json` 日志上限（§4.5） |
| 构建缓存 | `docker system df` 里 Build Cache 巨大 | `docker builder prune` |
| 悬空镜像/停止容器 | 反复构建累积 | `docker image prune` / `docker container prune` |
| 应用日志 | `logs/tutor.log` 及其 `.1~.5` | 已配轮转（10MB × 5）；`【建议】`挂载到宿主机便于查看 |
| 备份文件 | `/var/backups` 越积越多 | 保留策略：日备 7 天、周备 4 周（§5.3） |
| SQLite WAL 膨胀 | `*-wal` 文件异常大（长事务/未 checkpoint） | 重启服务触发 checkpoint；长期异常需排查是否有长连接不提交 |

> ⚠️ **绝对不要**用 `docker system prune -a` 图省事：它会删掉**所有未被运行中容器引用的镜像**（包括你留作回滚用的旧版本镜像）。见 §5.2 的回滚策略。

### 3.8 计划任务（cron / systemd timer）

`【建议】` 在生产服务器上配这四条：

```cron
# crontab -e（deploy 用户）
# 1) 每日 03:00 备份到本地（并保留 7 天）
0 3 * * * cd /opt/tutoragent && bash scripts/backup.sh >> /var/log/tutoragent-backup.log 2>&1

# 2) 每日 08:00 巡检：容器健康 + 磁盘 + 证书到期
0 8 * * * bash /opt/tutoragent/scripts/healthcheck.sh >> /var/log/tutoragent-health.log 2>&1

# 3) 每周日 04:00 清理无用镜像/构建缓存（保留运行中与回滚版本）
0 4 * * 0 docker image prune -f && docker builder prune -f --filter until=168h

# 4) 证书续期（certbot 自带 timer 的话可省）
30 2 * * * certbot renew --quiet
```

> 更现代的做法是把这些写成 **systemd timer**（自带日志、依赖管理、`systemctl list-timers` 可见）。cron 胜在简单直观，够用就好。

### 3.9 资源限制与内核参数（SSE 场景）

SSE 是**长连接**：一个用户开着一个页面 = 一条长期占用的连接。相关的资源上限：

| 项 | 查看/设置 | 说明 |
|---|---|---|
| 文件描述符 | `ulimit -n`；systemd unit 里 `LimitNOFILE=65535` | 每条连接占一个 fd；默认 1024 在几百并发时会耗尽 |
| 端口范围 | `sysctl net.ipv4.ip_local_port_range` | 影响可建立的对外连接数 |
| SYN 队列 | `net.core.somaxconn`、`net.ipv4.tcp_max_syn_backlog` | 高并发建连时避免丢连接 |
| TIME_WAIT | `net.ipv4.tcp_tw_reuse=1` | 客户端主动关闭导致的 TIME_WAIT 堆积 |
| TCP keepalive | `net.ipv4.tcp_keepalive_time` | 长连接中途被中间设备静默断开的场景 |
| Swap | `swapon --show`；建议 2G | 内存不足时避免 OOM Kill（构建镜像尤其需要） |
| 内存限制 | compose `deploy.resources.limits.memory` | 防止单容器吃满宿主机 |

```bash
# 内核参数持久化（Ubuntu/Debian）
sudo tee /etc/sysctl.d/99-tutoragent.conf <<'EOF'
net.core.somaxconn = 1024
net.ipv4.tcp_max_syn_backlog = 2048
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_keepalive_time = 600
EOF
sudo sysctl --system
```

> ⚠️ **不要照抄网上的"高并发优化"全套参数**（如 `tcp_tw_recycle`、巨大的 `tcp_mem`）：参数只在你有实测瓶颈时才有意义，乱改反而引入难查的问题。**先有观测，再谈调参。**

### 3.10 系统日志与 journald 上限

## 四、Docker 镜像与运行时治理

### 4.1 核心心智模型：镜像 = **不可变的发布单元**

| 概念 | 运维含义 |
|---|---|
| 镜像（Image） | **发布物**。一次构建、处处运行；**内容不可变**（相同 tag 指向不同内容是灾难） |
| 容器（Container） | **运行实例**。可随时销毁重建（本项目正是靠这一条做到"数据不丢"） |
| 卷（Volume/Bind Mount） | **状态**。容器无状态、状态在卷 —— 这是"随时可重建"的前提 |
| 镜像仓库（Registry） | **分发通道**。本地构建 → 推仓库 → 服务器拉取，别用 U 盘拷 |

> 一句话：**把容器当"进程"（可杀可重启），把卷当"数据库"（要备份要保护）**。

### 4.2 镜像 tag 策略（别只用 `latest`）

`【现状】` 本项目镜像 tag 是 `ai-tutor:latest`（`docker-compose.yml` 固定）。
`【建议】` 生产增加**不可变 tag** + 复用 `latest` 做"当前版本"指针：

```bash
# 构建时同时打两个 tag：不可变（含日期+commit）+ 可变（latest）
GIT_SHA=$(git rev-parse --short HEAD)
docker build -t ai-tutor:$GIT_SHA -t ai-tutor:latest .
docker push <registry>/ai-tutor:$GIT_SHA
docker push <registry>/ai-tutor:latest
```

| tag 形式 | 用途 |
|---|---|
| `ai-tutor:20260913-079b8c4` | **回滚用**，永远指向同一份内容 |
| `ai-tutor:latest` | 便捷指针，仅用于"快速拉最新" |
| `ai-tutor:v1.2.0` | 正式发版（语义化版本） |

**为什么必须这么干**：回滚的唯一可靠手段是"用旧镜像重新起容器"。如果只有 `latest`，旧镜像被覆盖后**你就回不去了**（只能重新 build，而重新 build 出来的未必是当时的代码）。

### 4.3 分层与构建缓存：本项目的一个真实教训

`【现状】` `Dockerfile` 是标准多阶段构建：

```
Stage 1  node:22-alpine   → npm install（npmmirror）→ npm run build → /build/dist
Stage 2  python:3.13-slim → apt 装 nginx/curl/tzdata → pip install（清华源）
         → COPY backend/  → COPY data/prompts  → COPY --from=frontend-build dist
         → COPY nginx.conf / entrypoint.sh → CMD
```

**缓存的正确性依赖于"指令顺序"**：

| 顺序设计 | 效果 |
|---|---|
| `COPY requirements.txt` **先**，`pip install` 再，`COPY backend/` **最后** | 只有依赖变更才重装依赖；改一行 Python 代码只重建最后一层（秒级） |
| 反过来（先 COPY 全部代码再 pip install） | 改任意一个 `.py` 都触发全量重装依赖（几分钟） |

**真实教训（2026-09-13 实测）**：改了根目录 `data/prompts/*.j2`（提示词模板）后，容器里**完全没变化**。原因：`data/prompts` 是 `COPY` 进镜像的（不是挂载卷），必须 `docker compose up -d --build` 才生效。

| 改动内容 | 是否要 rebuild |
|---|---|
| `backend/app/**` Python 代码 | ✅ 需要 |
| `frontend/src/**` 前端代码 | ✅ 需要 |
| `nginx.conf`、`entrypoint.sh`、`Dockerfile`、`requirements.txt` | ✅ 需要 |
| **`data/prompts/*.j2` 提示词模板** | ✅ **需要**（最容易忘，因为它"看起来像配置"） |
| `data/knowledge`、`data/profiles`、`data/conversations`、`backend/data/*` | ❌ 不需要（挂载卷，改动即生效） |
| 根 `.env` | ❌ 不需要（重启容器即可：`docker compose up -d` 会重读 `.env` 并重建容器） |

### 4.4 Compose v5 的变化（2026 年时点，重要）

`【已核实】` **Docker Compose v5** 做了两件影响运维习惯的事：

1. **跳号**：从 v2 直接到 v5，目的是**避免与"compose 文件格式 v2/v3"混淆**（很多人把文件格式版本当 CLI 版本）
2. **内置 builder 被移除，build 委托给 Docker Bake**：`docker compose build` 底层走 Bake（与 `docker build` 同一套实现）

实际影响（`【实测】` 本机 Docker Compose **v5.3.1** + Docker Engine **29.6.2**）：

| 命令 | 状态 |
|---|---|
| `docker compose up -d --build` | ✅ 正常工作（本项目的日常命令） |
| `docker compose build` | ✅ 正常（底层委托 Bake） |
| `docker compose config --quiet` | ✅ 可用于**校验 `.env` 必填项**（配合 `${VAR:?}` 语法，缺失直接报错） |
| 高阶构建（多平台、缓存导出、并行构建矩阵） | 改用 `docker buildx bake`，用声明式文件管理复杂构建 |

> `【建议】` 现阶段**继续用 `docker compose up -d --build` 就够了**，不必迁到 Bake 声明式文件——那是在有"多平台镜像 / 多服务构建矩阵 / CI 复用构建定义"需求时才值得的复杂度。

### 4.5 守护进程配置（`daemon.json`）：上生产必配

```json
// /etc/docker/daemon.json
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" },
  "registry-mirrors": ["https://docker.m.daocloud.io"],
  "default-address-pools": [
    { "base": "172.30.0.0/16", "size": 24 }
  ]
}
```

| 配置项 | 为什么必须配 |
|---|---|
| `log-opts.max-size/max-file` | **默认无上限**，容器日志会无限增长直到吃满磁盘（头号事故来源） |
| `registry-mirrors` | 国内拉取基础镜像慢/失败 |
| `default-address-pools` | 避免与内网网段冲突（VPN、校园网常见） |

```bash
sudo systemctl restart docker
docker info --format '{{.LoggingDriver}}'; docker info | grep -A2 "Log:"   # 验证
```

> ⚠️ 日志上限**只对新创建的容器生效**（已有容器需重建）。

### 4.8 运行时治理（compose 里能配的"安全网"）

`【现状】` 本项目已配：`restart: unless-stopped`、`healthcheck`（`curl /api/health`）、4 个卷。
`【建议】` 按需增加：

```yaml
services:
  ai-tutor:
    # 资源上限（防止单容器吃满宿主机；注意 cpu 单位是"核"）
    deploy:
      resources:
        limits:
          cpus: "2.0"
          memory: 2g
    # 日志上限（也可在 daemon.json 全局配，二者取其一或都用）
    logging:
      driver: json-file
      options: { max-size: "10m", max-file: "3" }
    # 安全加固（本项目为 root 运行，逐步收紧）
    security_opt: ["no-new-privileges:true"]
    # 只读根文件系统（需要可写的地方单列 tmpfs/卷）
    # read_only: true
    # tmpfs: ["/tmp", "/var/cache/nginx", "/var/run"]
```

> ⚠️ `read_only: true` 对本项目**不能直接开**：Nginx 需要写 `/var/cache/nginx`、`/var/run`，后端需要写 `logs/` 与多个数据目录。要开就得把可写路径逐个列全，**收益（防篡改）与成本（调试难度）要权衡**。当前单机自用阶段不必开。

**healthcheck 的坑**：`start_period` 是首次启动的宽限期，这期间失败不计入 `retries`。本项目给了 30s（`start_period: 30s`），而实测**冷启动到 healthy 需要 30-90s**（依赖多时更久）。若发现容器被误判为 unhealthy 重启，**先加大 `start_period`，而不是删掉 healthcheck**。

### 4.9 Compose 编排进阶（知道有这些即可，按需用）

| 特性 | 用途 | 何时用 |
|---|---|---|
| `docker-compose.override.yml` | 本地/环境差异覆盖（自动加载） | 开发与生产配置分离 |
| `-f a.yml -f b.yml` | 显式合并多个 compose 文件 | 分环境（base + prod） |
| `profiles:` | 按 profile 启停可选服务 | 如"监控栈"只在需要时起 |
| `depends_on: condition: service_healthy` | 依赖服务健康后再启动 | 多服务编排（本项目单容器用不上） |
| `env_file:` | 整份 `.env` 注入 | ✅ 本项目已加（见 §8.3） |
| `secrets:` | 密钥以文件形式挂载（比环境变量安全） | 合规要求较高时 |

### 4.10 镜像与容器常见坑清单

| 坑 | 现象 | 处置 |
|---|---|---|
| 只用 `latest`，无不可变 tag | 无法回滚 | §4.2 |
| 改代码后不 rebuild | "改了没生效" | §4.3 对照表 |
| 构建上下文巨大（含 `data/`、`node_modules`） | 构建极慢 | `.dockerignore` |
| Windows 编辑导致 CRLF | Linux 里脚本报 `\r: command not found` | `sed -i 's/\r$//'` 兜底（本项目已做） |
| 容器时区是 UTC | 日志时间差 8 小时 | `ENV TZ=Asia/Shanghai` + `tzdata`（本项目已做） |
| 镜像架构不符（Mac M 系构建，x86 服务器跑） | 启动报 `exec format error` | `docker build --platform linux/amd64` |
| 容器内日志未挂载 | 重建后日志消失 | 挂载日志目录或改走 `docker logs` |
| 卷权限不匹配 | 容器报 Permission denied | `chown -R <uid>:<gid>` |
| `docker system prune -a` 误删回滚镜像 | 无法回滚 | 见 §3.7 警告 |

## 五、日常运营 SOP：发布 / 回滚 / 备份 / 巡检

### 5.1 标准发布流程（照这个顺序做，出事概率最低）

```bash
# ① 本地：确认要发布的代码状态干净、测试通过
cd /path/to/AI-tutor
git status                        # 确认改动都是要发布的
backend/venv/Scripts/python.exe -m pytest backend/tests -q -m "not llm_api"   # Windows
# Linux: backend/venv/bin/python -m pytest backend/tests -q -m "not llm_api"

# ② 服务器：先备份（见 5.3）—— 先备份再变更，是纪律不是建议
cd /opt/tutoragent
docker compose ps                                  # 记录当前状态
bash scripts/backup.sh pre-deploy-$(date +%F-%H%M)

# ③ 拉代码 + 重建（重建前先确定"回滚用的旧镜像 tag"）
git pull
docker image tag ai-tutor:latest ai-tutor:rollback-$(date +%F-%H%M)   # ★ 保留回滚点
docker compose up -d --build

# ④ 验证（四步，缺一不可）
docker compose ps                                   # 1) 容器 healthy
curl -fsS http://127.0.0.1:8080/api/health           # 2) 健康检查 200
curl -N -X POST http://127.0.0.1:8080/api/v1/chat/stream \
  -H 'Authorization: Bearer <token>' -H 'Content-Type: application/json' \
  -d '{"messages":[{"role":"user","content":"你好"}],"mode":"free_talk"}' | head -5   # 3) 流式真的在流
# 4) 浏览器打开首页，登录，发一条消息

# ⑤ 收尾：确认无异常后清理
docker compose logs --tail=100                      # 看有无报错
```

> **为什么第 ③ 步要打 `rollback-*` tag**：`--build` 会覆盖 `latest`，旧镜像将失去 tag 引用（变成 `<none>` 悬空镜像），回滚时你只能靠"记住那串 ID"。**一条 `docker image tag` 就能避免这个窘境。**

### 5.2 回滚策略

```bash
# 场景 A：新版本有问题，回滚到上一个镜像
cd /opt/tutoragent
docker compose down
docker image tag ai-tutor:rollback-2026-09-13-1030 ai-tutor:latest
docker compose up -d
docker compose ps && curl -fsS http://127.0.0.1:8080/api/health

# 场景 B：代码有问题（要退回旧代码重新构建）
git log --oneline -10
git checkout <旧commit>
docker compose up -d --build
```

**回滚的三条注意**：

1. **数据兼容性是回滚的前置条件**：如果新版本做过"数据库结构变更"（本项目有 `_auto_migrate`，会**自动加列**），回滚后旧代码遇到"多出来的列"一般无碍（SQLite 宽松）；但如果是**改列类型/删列**，回滚可能失败。**发布前先问：这次改动动了数据格式吗？**
2. **回滚要快，别在现场 debug**：先用旧镜像恢复服务（用户可用优先），再从容排查根因。
3. **回滚后也要验证**：同 §5.1 的四步。

### 5.3 备份与恢复（状态全在这里，最重要）

#### 5.3.1 备份什么

`【现状】` 全部业务状态在 **4 个挂载点**：

| 挂载点 | 内容 | 重要性 |
|---|---|---|
| `./data/knowledge/` | `knowledge.db`（节点/边/用户）+ `nodes/{user_id}/*.md`（节点正文） | ★★★ 核心资产 |
| `./data/profiles/` | `{user_id}.json`（用户画像） | ★★★ |
| `./data/conversations/` | 会话记录（SQLite） | ★★ |
| `./backend/data/` | `agent_runs/`（运行记录）、`kb/`（知识库+向量+whoosh 索引）、`quiz/`、`rag/`、`collector/` | ★★★（KB 与运行记录） |

`【现状】` 不在卷里、**需要 rebuild 才更新**的：`data/prompts/*.j2`（提示词模板，随镜像走）—— 备份时应连同代码仓库一起备份（它在 git 里）。

#### 5.3.2 怎么备（**关键：SQLite 是 WAL 模式，不能直接 `cp`**）

`【已核实】` 本项目所有 SQLite 都执行 `PRAGMA journal_mode=WAL`（图谱/会话/画像/KB/向量/出题/采集/运行记录）。WAL 模式下数据分散在 3 个文件（`.db`、`.db-wal`、`.db-shm`），**运行中直接 `cp` 可能拿到不一致的快照**。

三种正确做法（按推荐度）：

```bash
# ✅ 方案 1（推荐）：停容器后整目录打包 —— 最简单、最不会错
cd /opt/tutoragent
docker compose stop
tar czf /var/backups/tutoragent/data-$(date +%F-%H%M).tar.gz data backend/data
docker compose start

# ✅ 方案 2：在线备份（不停服），用 sqlite3 的一致性备份命令
sqlite3 data/knowledge/knowledge.db ".backup '/var/backups/kn-$(date +%F).db'"
sqlite3 backend/data/agent_runs/agent_runs.db ".backup '/var/backups/runs-$(date +%F).db'"
# 其余库同理（kb/kb.db、kb/doc_vectors.db、quiz/*.db、rag/*.db、conversations.db …）

# ✅ 方案 3：VACUUM INTO（SQLite 3.27+），产出紧凑且一致的副本
sqlite3 data/knowledge/knowledge.db "VACUUM INTO '/var/backups/kn-$(date +%F).db'"
```

`【建议】` 本项目直接**用方案 1**（规模小、停服几秒无感），并把脚本化：

```bash
#!/usr/bin/env bash
# scripts/backup.sh  —— 用法：bash scripts/backup.sh [标签]
set -euo pipefail
cd "$(dirname "$0")/.."
TAG="${1:-auto}"
DEST="/var/backups/tutoragent"
mkdir -p "$DEST"
echo "[$(date '+%F %T')] 开始备份 tag=$TAG"
docker compose stop
tar czf "$DEST/data-$TAG-$(date +%F-%H%M).tar.gz" data backend/data
docker compose start
# 保留 7 天（日备）—— 更复杂的保留策略用 logrotate 或 find -mtime
find "$DEST" -name 'data-*.tar.gz' -mtime +7 -delete
echo "[$(date '+%F %T')] 备份完成：$(ls -lh "$DEST" | tail -1)"
```

#### 5.3.3 恢复（**没有演练过的备份等于没有备份**）

```bash
cd /opt/tutoragent
docker compose down
tar xzf /var/backups/tutoragent/data-2026-09-13-0300.tar.gz    # 覆盖 data/ 与 backend/data/
docker compose up -d
docker compose ps && curl -fsS http://127.0.0.1:8080/api/health
```

`【建议】` **每季度做一次恢复演练**：在一个临时目录/临时机器上恢复一遍，确认：① 能起来；② 数据确实回来了（登录后能看到图谱节点）。演练记录写一行日志即可。

#### 5.3.4 异地备份（单机最脆弱的一环）

本机备份挡得住"误删/误改"，挡不住"服务器整个没了"。最低成本的异地方案：

```bash
# 把最近的备份同步到另一台机器/对象存储（示例：scp 到备用机）
scp /var/backups/tutoragent/data-*.tar.gz backup@backup-host:/backups/tutoragent/
# 或使用云对象存储（ossutil / coscli），并开启版本控制防误删
```

| 方案 | 成本 | 适合 |
|---|---|---|
| 云对象存储（OSS/COS） | 几毛钱/月 | 推荐，且有生命周期管理 |
| 另一台服务器 scp/rsync | 有第二台机器才行 | 有备用机时 |
| 手动下载到本地电脑 | 免费 | 偶尔为之（不可持续） |

### 5.4 日常巡检（5 分钟版）

```bash
#!/usr/bin/env bash
# scripts/healthcheck.sh —— 输出全部"通过/异常"，异常时非零退出（便于接告警）
set -uo pipefail
cd "$(dirname "$0")/.."
FAIL=0
chk() { printf '%-28s %s\n' "$1" "$2"; [ "$2" = "OK" ] || FAIL=1; }

# 1) 容器状态
ST=$(docker compose ps --format '{{.Status}}' 2>/dev/null | head -1)
[[ "$ST" == *healthy* ]] && chk "容器健康" "OK" || chk "容器健康" "异常：$ST"

# 2) 应用健康检查（走本机，不依赖外网）
curl -fsS --max-time 5 http://127.0.0.1:8080/api/health >/dev/null \
  && chk "http /api/health" "OK" || chk "http /api/health" "异常"

# 3) 磁盘（根分区 >85% 告警）
USED=$(df -h / | awk 'NR==2{print $5}' | tr -d '%')
[ "$USED" -lt 85 ] && chk "磁盘使用率" "OK (${USED}%)" || chk "磁盘使用率" "异常 (${USED}%)"

# 4) 最近备份是否在 26 小时内
LATEST=$(find /var/backups/tutoragent -name 'data-*.tar.gz' -mtime -1 2>/dev/null | head -1)
[ -n "$LATEST" ] && chk "最近备份" "OK" || chk "最近备份" "异常：24h 内无备份"

# 5) 日志里的错误（最近 200 行）
ERRS=$(docker compose logs --tail=200 2>&1 | grep -c '\[E-' || true)
[ "${ERRS:-0}" -eq 0 ] && chk "近期错误码" "OK" || chk "近期错误码" "异常：${ERRS} 条"

echo "---"; [ "$FAIL" -eq 0 ] && echo "全部通过" || echo "存在异常，请处理"
exit "$FAIL"
```

`【建议】` 把 §3.8 的 cron 配好，异常时通过邮件/钉钉/企业微信机器人告警（curl webhook 一行即可）。

### 5.5 配置与密钥管理

| 事项 | 做法 |
|---|---|
| `.env` 是唯一真值 | 本地与 Docker 共用根 `.env`（`config.py` 读取 `parents[3]/.env`，容器内靠 `env_file` 注入） |
| **绝不进 git** | `.gitignore` 已排除 `.env`；`.dockerignore` 也排除了它（密钥不进镜像） |
| 备份 `.env` | 单独加密备份（丢了 JWT `SECRET_KEY` 会**让所有人登录态失效**，且无法恢复旧 token） |
| 密钥轮换 | 换 `SECRET_KEY` = 全员重新登录（可接受）；换 LLM Key 只需改 `.env` + `docker compose up -d` |
| 环境差异 | 用 `docker-compose.override.yml` 或 `-f` 覆盖，**不要**在服务器上手改 compose 主文件（下次 `git pull` 会冲突） |

> ⚠️ **真实教训见 §8.3**：`environment` 白名单式的配置传递会**静默漂移** —— 你在 `.env` 里加了变量，容器里却拿不到，而服务"看起来正常"。这是本仓库已经踩过并修掉的坑。

### 5.6 安全运维清单（公网部署时逐项过）

| 项 | 检查 |
|---|---|

### 5.7 成本与容量

| 成本项 | 本项目情况 | 优化方向 |
|---|---|---|
| **LLM token** | 主要成本。Agent Loop 多轮 + 长 system prompt + 历史回填 | 已做上下文预算裁剪（`LLM_CTX_BUDGET`）；可考虑"简单问题走小模型"分流 |
| 嵌入 API | 阿里 `text-embedding-v4`（**曾有欠费降级**） | 关注余额；大批量灌库前先确认额度 |

| 磁盘 | 镜像 + 日志 + 备份 + 数据 | 日志上限（§4.5）、备份保留策略（§5.3） |

`【建议】` 给 LLM 花费设一个心理上限（如每月 X 元），并**每周看一眼用量**。Agent 类应用的成本曲线很容易在"用户开始玩起来"之后失控。

|---|---|---|
| **Metrics（指标）** | "系统整体健康吗？趋势如何？" | Docker 自带 stats、`/api/health`、Prometheus + cAdvisor + node_exporter |
| **Logs（日志）** | "这一件事为什么失败了？" | `docker logs`、`logs/tutor.log`、Nginx access/error log |
| **Traces（链路）** | "这次慢请求慢在哪一段？" | 应用已落 `agent_runs`（含每轮耗时）；外部用 OpenTelemetry 才能串起前后端 |

> **注意本项目的特殊性**：Agent Loop 的"慢"是**设计如此**（单轮 LLM 60s+），不是故障。**监控指标要盯"错误率与队列"，而不是盯"延迟"**——否则你每天都会收到"响应很慢"的误报。

### 6.2 最小可用的监控方案（单机，30 分钟搭好）

`【现状】` 无监控系统，仅有健康检查。
`【建议】` 分级实施，**别一上来就上全套**：

| 级别 | 方案 | 成本 | 能发现什么 |
|---|---|---|---|
| **L0（最低）** | `scripts/healthcheck.sh` + cron + webhook 告警 | 0 | 服务挂了、磁盘满、备份失败 |
| **L1（推荐）** | 上面的 + `cAdvisor`（容器指标）+ `node_exporter` + Prometheus + Grafana | 一台机器上多跑 3 个容器 | 资源趋势、容器重启、内存泄漏 |
| **L2** | 再加 Loki + Promtail（日志聚合）、告警规则（Alertmanager） | 更多内存 | 日志全文检索、按错误码告警 |
| **L3** | OpenTelemetry 全链路追踪（Tempo/Jaeger） | 改代码埋点 | 跨服务链路分析 |

```yaml
# docker-compose.monitoring.yml（L1 示例，用 profiles 或 -f 单独起）
services:
  cadvisor:
    image: gcr.io/cadvisor/cadvisor:latest
    volumes:
      - /:/rootfs:ro
      - /var/run:/var/run:ro
      - /sys:/sys:ro
      - /var/lib/docker/:/var/lib/docker:ro
    ports: ["127.0.0.1:8081:8080"]     # 只监听本机，别暴露公网
    restart: unless-stopped

  node-exporter:
    image: prom/node-exporter:latest
    ports: ["127.0.0.1:9100:9100"]
    restart: unless-stopped

  prometheus:
    image: prom/prometheus:latest
    volumes: ["./monitoring/prometheus.yml:/etc/prometheus/prometheus.yml:ro",
              "promdata:/prometheus"]
    ports: ["127.0.0.1:9090:9090"]
    restart: unless-stopped

  grafana:
    image: grafana/grafana:latest
    volumes: ["grafanadata:/var/lib/grafana"]
    ports: ["127.0.0.1:3000:3000"]
    restart: unless-stopped

volumes: { promdata: {}, grafanadata: {} }
```

> ⚠️ 监控组件的端口**一定要只绑 `127.0.0.1`** 或加认证：Prometheus/Grafana 暴露公网 = 送人一份你的系统内情。
> ⚠️ 小内存机器（2G）跑全套监控可能反而把自己压垮 → **从 L0 开始，缺什么补什么**。

### 6.3 日志治理（三处日志，别搞混）

| 日志 | 位置 | 特点 | 怎么看 |
|---|---|---|---|
| 容器 stdout/stderr | Docker json-file | 有大小上限（若配了 `daemon.json`） | `docker compose logs -f --tail=100` |
| 应用文件日志 | 容器内 `/app/backend/logs/tutor.log`（10MB × 5 轮转） | ⚠️ **未挂载到宿主机，容器重建即丢** | `docker exec ai-tutor tail -f logs/tutor.log` |
| Nginx 访问日志 | 容器内 `/var/log/nginx/access.log` | ⚠️ 同样未挂载 | `docker exec ai-tutor tail -f /var/log/nginx/access.log` |

`【建议】` 把这两个容器内日志目录挂出来（便于用系统工具检索、且重建不丢）：

```yaml
    volumes:
      - ./logs/backend:/app/backend/logs
      - ./logs/nginx:/var/log/nginx
```

日志排查的实用套路：

```bash
# 按错误码找（本项目异常均以 [E-XXX] 开头）
docker compose logs --since 1h | grep -o '\[E-[A-Z-]*-[0-9]*\]' | sort | uniq -c | sort -rn

# 找最慢的请求（需先在 nginx 配 json 日志，见 §2.7）
docker exec ai-tutor sh -c "grep -o '\"urt\":\"[^\"]*\"' /var/log/nginx/access.log" | sort -t: -k3 -rn | head
```

### 6.4 告警阈值建议（照抄起步，按实际调整）

| 指标 | 告警阈值 | 说明 |
|---|---|---|
| 容器非 healthy | 持续 > 2 分钟 | 服务不可用 |
| `/api/health` 非 200 | 连续 3 次 | 应用层故障 |
| 磁盘使用率 | > 85% | 提前处置，别等 100% |
| 内存使用率 | > 90% 持续 10 分钟 | 可能 OOM |
| 容器重启次数 | > 3 次/小时 | 反复崩溃 |
| 备份缺失 | 24h 内无新备份 | 静默失败最危险 |
| 证书到期 | < 14 天 | 见 §2.4 |
| LLM 错误率 | 5 分钟内 > 20% | 可能是 Key 失效/欠费（嵌入欠费会静默降级！） |

## 七、故障排查手册

**排查通用顺序**：`docker compose ps`（容器活着吗）→ `docker compose logs`（报什么错）→ `curl` 本机直连（绕过网络层）→ `curl` 经网关（定位代理层）→ 看外部依赖。

### 7.1 症状 → 定位 → 处置

| 症状 | 可能原因 | 定位命令 | 处置 |
|---|---|---|---|
| 浏览器打不开首页 | 容器没起 / 端口没映射 / 防火墙 | `docker compose ps`、`ss -ltnp \| grep 8080`、`curl 127.0.0.1:8080` | 起容器 / 检查端口与防火墙 |
| 首页能开，接口全 502 | 后端进程死了（Nginx 活着） | `docker logs ai-tutor \| tail -50` | 看后端启动报错（常是 `SECRET_KEY` 缺失） |
| 接口 504 | 后端处理超时（LLM 慢） | `docker logs`、Nginx `urt` | 加大 `proxy_read_timeout` 与云 LB 超时 |
| **流式不吐字，最后一次性出现** | 某层缓冲 | `curl -N` 打时间戳（§2.3.2） | 检查 Nginx `proxy_buffering off`、CDN 压缩、`X-Accel-Buffering` |
| 流式连 60s 后断 | 超时太短 | 看 Nginx/云 LB 超时配置 | 调大到 300s+ |
| 登录后立刻 401 | 服务器时间不准 | `date` vs 真实时间 | `timedatectl set-ntp true` |
| 登录返回 429 | 登录限流（5 次/分钟/IP） | 同 IP 多人测试时常见 | 等待或调阈值；注意 NAT 共享出口 IP |
| 聊天返回 429 | 聊天限流（20 次/60 秒） | `docker logs` 里 `[E-*]` | 等待或调阈值 |
| 对话报错但日志无异常 | LLM Key 失效/欠费；**嵌入欠费静默降级** | 手动 curl LLM 接口测试 | 换 Key / 充值；确认是"降级"还是"失败" |
| 上传大文件 413 | `client_max_body_size` 太小 | — | 已是 100m；更大需调整 |
| 上传后检索不到 | 嵌入欠费 → 只用 BM25；或索引未重建 | `docker logs` 找 embedding 相关 warning | 充值后重建索引 |
| 数据"丢了" | 卷被删 / 挂载路径写错 / 用了容器内路径 | `docker inspect ai-tutor \| grep -A20 Mounts` | 从备份恢复；核对 compose 卷映射 |
| 改了代码不生效 | 没 rebuild（或改的是挂载卷内的东西） | §4.3 对照表 | `docker compose up -d --build` |
| 改了 `.env` 不生效 | 变量没被注入容器（白名单漂移） | `docker exec ai-tutor env \| grep <变量名>` | 确认 compose 有 `env_file: .env`（§8.3） |
| 容器反复 restarting | 启动即崩（配置错误/端口占用/依赖缺失） | `docker compose logs --tail=100` | 修配置；看 entrypoint 的"服务进程退出"提示 |
| 容器 unhealthy 但服务正常 | `start_period` 太短 | `docker inspect --format '{{json .State.Health}}' ai-tutor` | 加大 healthcheck 的 `start_period` |
| 磁盘满 / 服务莫名失败 | 日志/镜像/备份占满 | `df -h`、`docker system df` | §3.7 |
| 构建时 OOM / 被 Killed | 内存不足（无 swap） | `dmesg \| tail`、`journalctl -k` | 加 swap；分步构建 |
| 镜像拉取超时 | 国内网络 | — | 配 `registry-mirrors`（§4.5） |
| `database is locked` | 多进程写同一 SQLite | `docker ps`（是否起了多份） | 恢复单实例；检查是否有脚本在裸连写库 |

### 7.2 三条"先别动手"的判断经验

1. **先确认"是不是只有你遇到"**：同学也复现吗？换浏览器/换网络（手机热点）呢？——能区分"服务问题"与"网络/客户端问题"。
2. **先看时间线**：`docker compose logs --since 30m`。多数故障紧跟着一次变更（发布/改配置/磁盘满），**先问"最近改了什么"**。
3. **不要在故障现场做"顺手优化"**：恢复服务优先，根因分析放到之后（写进 §8 那样的事故记录里）。

## 八、真实事故复盘（本仓库实例）

> 下面是本仓库 2026-09-13 一天内真实发生并修复的三个问题 —— **它们比任何教科书案例都更贴合本项目**，建议反复看。

### 8.1 事故一：镜像停在 13 天前，"新功能都没有"

**症状**：把容器跑起来给同学用，发现最新的功能（图谱 P0、MCP 搜索、混合检索）全都不在。

**根因**：镜像是 `2026-08-31` 构建的，对应提交 `f8b7a74`；此后隔了 8 个提交 + 38 处未提交改动。**`docker compose up -d` 只运行已有镜像，永远不会同步代码。**

**排查手段（可复用）**：

```bash
# 1) 看镜像构建时间
docker image inspect ai-tutor:latest --format '{{.Created}}'
# 2) 用"只 401 不 404"的新端点探针判断代码新旧
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/api/v1/agent/runs   # 401=有该路由(新) 404=旧代码
# 3) 直接看容器内有没有新文件
docker exec ai-tutor ls /app/backend/app/core/llm /app/backend/app/mcp_servers
```

**修复**：`docker compose up -d --build`（重建后实测：镜像 285 MB → 271 MB，新端点全部就绪）。

**沉淀的纪律**：**改了代码就必须 `--build`**；`docker compose up -d` 只适合"改 `.env` 后重启"。

### 8.2 事故二：Docker 版聊天 100% 崩溃（health 却是绿的）

**症状**：全部接口正常、首页正常、`/api/health` 200，**一发消息就 500**。

**根因**：`Dockerfile` 只 `COPY backend/`，而提示词模板目录被 `prompt_loader.py` 解析为**项目根**的 `data/prompts`（不在 `backend/` 下）→ 容器内 `/app/data/prompts` 根本不存在：

```
jinja2.exceptions.TemplateNotFound: 'system_prompt_common.j2' not found in search path: '/app/data/prompts'
```

`chat_service.py` 调用处没有兜底 → 聊天必崩。**而健康检查不碰模板，所以一直是绿的。**

**为什么长期没发现**：本地开发（`start.ps1`）有完整项目目录，模板存在；只有 Docker 部署才会暴露。部署"验证"只看了 health 和首页 → 给了虚假的安全感。

**修复**：`Dockerfile` 增加 `COPY data/prompts /app/data/prompts`。

**沉淀的经验**：

1. **"容器起来了" ≠ "功能可用"**。上线验证必须包含**一条真实的业务链路**（本项目：注册 → 登录 → 发一条消息）——这也是 §5.1 发布流程第 ④ 步"验证四步"的由来。
2. **凡是"代码里按相对路径找资源"，都要检查容器内该路径是否存在**。本项目系统性排查过一次：把 `backend/` 里所有 `parents[n]` 路径解析逐个算出容器内落点，只有 `data/prompts` 一处漏。
3. 健康检查要**尽量碰真实依赖**（能查 DB 就查 DB），否则容易"绿着挂"。

### 8.3 事故三：`environment` 白名单导致配置静默漂移

**症状**（尚未爆发的隐患）：`docker-compose.yml` 的 `environment` 是**硬编码 8 项**，而 `config.py` 有 **20+ 个配置字段**，并且 `.env` 被 `.dockerignore` 排除（容器内读不到文件）。

**后果**：往 `.env` 里新增任何变量（`FALLBACK_LLM_*`、`WEB_SEARCH_ENABLED`、`LLM_CTX_BUDGET`、`DEFAULT_ADMIN_PASSWORD`…）都**不会进容器**，服务静默使用默认值——**没有报错，只有"配置看起来没生效"**。

**修复**：`docker-compose.yml` 增加 `env_file: - .env`（优先级低于 `environment`，原有显式契约与 `${VAR:?}` 启动校验语义不变，但不再漂移）。

**沉淀的经验**：**配置传递不要用"白名单列举"** —— 列举必然漂移。要么整份注入（`env_file`），要么用 schema 校验（`compose config --quiet` 配合 `${VAR:?}`）。

### 8.4 Windows 局域网共享：防火墙 profile 陷阱（先查，再决定要不要提权）

**场景**：校园网/局域网内让同学用 IP 访问自己电脑上的服务。

**结论取决于「当前网络类别」是否与规则匹配 —— 两种情况截然相反**：

| 当前网络类别 | Docker 规则（`Profile=Public`）是否生效 | 结果 |
|---|---|---|
| **Public（公用）** | ✅ 匹配 | `http://<本机IP>:8080` 直接可用，**不用 UAC、不用加规则** |
| **Private（专用）/ Domain** | ❌ 不匹配 | **入站被阻止，同学连不上** → 必须放行（或把该网络改回"公用"） |

```
规则名   com.docker.backend.exe
方向     Inbound    动作 Allow    配置文件 Public      ← 注意：只有 Public 才生效
端口     LocalPort=Any    RemoteAddr=Any
```

**真实案例（2026-09-13，同一天内两次结论相反）**：上午网络类别是 `Public`、WLAN IP 为 `192.168.5.196`，规则匹配，免提权即可访问；下午换网络后 IP 变成 `10.31.91.205`、网络类别变成 **`Private`** —— 同一条规则不再匹配，**必须放行，否则同学连不上**。

**判别命令（放行前先看清楚）**：

```powershell
# ① 当前网络类别
Get-NetConnectionProfile | Select-Object InterfaceAlias, NetworkCategory
# ② Docker 规则覆盖哪些 profile
Get-NetFirewallRule | Where-Object { $_.DisplayName -match 'com\.docker\.backend' -and $_.Direction -eq 'Inbound' } |
  Select-Object DisplayName, Enabled, Action, Profile
# ③ ① 的类别不在 ② 的 Profile 里 → 需要放行
```

**放行（管理员 PowerShell，一行）**：

```powershell
New-NetFirewallRule -DisplayName "TutorAgent LAN 8080" -Direction Inbound -Protocol TCP -LocalPort 8080 -Action Allow -Profile Any
```

**最容易误判的一点**：**本机 `curl` 自己 IP 恒为 200，证明不了同学能连上** —— 本机访问不走入站规则（Windows 上这一条尤其容易骗人）。唯一可靠的验证是**用另一台设备实测**（手机连同一 WiFi 访问）。

**反例**：**dev 模式（Vite 5173）没有对应规则**，同样需要放行 `node.exe`。

**沉淀的经验**：**先查已有规则的 profile，再决定要不要提权**（本项目 `start-docker.ps1` 已内置这项自检，会直接提示网络类别与放行命令）。

**另一个常见坑**：校园网常有 **AP 客户端隔离**（同 SSID 设备互访被禁）——本机无法自测；验证方法是用手机连同一 WiFi 访问，或改用手机热点对比。

## 结语：这套运维体系的"最小可持续"版本

不需要一步到位，**按这个顺序补齐，每一步都独立有价值**：

| 步骤 | 做的事 | 投入 | 换来 |
|---|---|---|---|
| 1 | 记住「改代码 → `--build`」+ 发布前打 `rollback-*` tag | 0 | 不跑旧代码、能回滚 |
| 2 | 配 `daemon.json` 日志上限 + 挂载日志目录 | 10 分钟 | 不会被日志吃满磁盘 |
| 3 | `scripts/backup.sh` + cron + **一次恢复演练** | 1 小时 | 不怕数据丢 |
| 4 | `scripts/healthcheck.sh` + cron + webhook 告警 | 1 小时 | 挂了能第一时间知道 |
| 5 | systemd 托管 + 防火墙 + 时钟校准 + HTTPS | 半天 | 能长期无人值守运行 |
| 6 | L1 监控（cAdvisor + Prometheus + Grafana） | 半天 | 看得见趋势，能提前发现内存/磁盘问题 |
| 7 | 镜像仓库（ACR）+ 不可变 tag + Trivy 扫描 | 半天 | 发布有章法、供应链可控 |

> 最后一条也是最重要的一条：**每次事故都写进 §8 这样的复盘**。本项目的三条真实事故（镜像旧、模板没进镜像、配置白名单漂移）都不是"运气不好"，而是"没有验证真实业务链路"这一件事的三种表现。**把验证做成流程，事故率就会断崖式下降。**
