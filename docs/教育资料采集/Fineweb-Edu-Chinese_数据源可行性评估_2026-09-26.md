# Fineweb-Edu-Chinese 作为「资源采集数据源」可行性评估

> 日期：2026-09-26 ｜ 对象：TutorAgent 采集域（`core/collector/`）
> 结论前提：**赛前 9 天窗口（材料期 10/5）+ 嵌入 API 欠费 + 三赛同投**这三条约束下的判断，不代表长期技术判断。

---

## 〇、一句话结论

**技术可行，但作为"资源收集的数据源"不推荐，赛前尤其不要做。**
它真正值钱的用法是**评测集**（1-2 天可交付，直接补比赛量化证据），不是采集源。

**三个致命错配**（详见第二节）：
1. 它是**离线预训练语料**（parquet 批量文件），而采集域的适配器协议是 `search(关键词) → 候选(source_url) → fetch(单条)` 的**在线站点抓取**形态；
2. 它的"Edu"是**对训练 LLM 有教育价值**（知识密度打分），不是**某门课的教学资源**（无课程体系、无章节、无先修关系）；
3. 底层是网页抓取语料（Wanjuan / SkyPile / CCI2 / map-cc / opencsg-cc），**逐条内容版权不明** → 按本项目的 L0-L3 分级应归 **L2（仅个人学习）**，商用模式会被自动排除。

---

## 一、这个数据集到底是什么（已核实部分）

来源：OpenCSG 中文语料系列（arXiv 2501.08197），HuggingFace `opencsg/chinese-fineweb-edu` 系列。

| 版本 | 构成 | 规模 |
|---|---|---|
| V2.1 | 按教育评分分档：`4-5` / `3-4` / `2-3` | 1779 万行 / 70GB（4-5 档）；全量 9.58 亿行 / 2.42TB |
| V2.2 | `pretrain`（score 分档）+ `sft_qa`（143 万条，DeepSeek V3.2 蒸馏）+ `sft_context`（14.6GB，标注原文出处） | sft_qa 3.4GB；pretrain 4-5 档 70GB |

- **底层数据源**：CCI2、SkyPile、Tele-AI、Industry2、wanjuan1.0、WuDao、map-cc、opencsg-cc —— 全部是 **CommonCrawl 系网页抓取语料**。
- **字段**（以社区转存版本为例，需以下载到的 parquet 实际 schema 为准）：`id / text / tokens / score / url / meta`；`meta` 内含 `ori_source`（如 `Wanjuan`）、`ori_score`、`domain`。**部分版本带原始 url**，可做来源追溯。
- **许可**：HF 标签 `apache-2.0`；README 同时要求遵循 **OpenCSG 社区许可证**，**商业用途需发邮件至 lorraineg@opencsg.com 报备并取得许可**。

> ⚠️ 概念澄清（写材料时最容易被评委问倒的一点）：**Apache-2.0 覆盖的是"这个数据集的编排与分发"，不覆盖被抓取网页的原文版权**。逐条内容的授权状态仍然是"不明"。

## 二、五条错配（为什么不推荐）

### 2.1 形态错配：适配器协议不匹配 🔴

`core/collector/adapters/base.py` 定义的协议是：

```
search(query) -> list[CollectCandidate(title, source_url, license_level, ...)]
fetch(candidate) -> 文本/二进制
```

三个现有适配器（wikipedia / wikibooks / oiwiki）都遵循"**在线站点：搜索 → 拿 URL → 抓单条**"。

Fineweb 是**离线批量 parquet**：没有搜索接口、没有单条拉取服务。要接只有两条路：

| 路线 | 做法 | 代价 |
|---|---|---|
| A 伪装成适配器 | 本地先建倒排索引，"假 search" 返回本地行 | 等于自己写一个检索引擎，偏离采集模块定位，且 `CollectCandidate.source_url` 只能填原始网页 URL（抓不回来，与 fetch 语义冲突） |
| B 离线导入管线 | 复用 `scripts/seed_collector.py` / `pipeline_ingest.py` 的形态，一次性批量灌库 | 推荐路线，但它是**"预置语料"而不是"采集源"**：`CollectorView` 的"搜索→勾选→任务→进度"交互全线不适用，UI 与任务模型都要改 |

### 2.2 规模错配：最小可用档也是 70GB

- 最小的高质量档 **score_4_5 = 70GB / 1779 万行**。即便只取 1-2 个 parquet 分片（数百 MB～1GB，约 10-20 万行），也要走完：下载 → schema 验证 → 学科过滤 → 去重 → 分块 → 灌库 → 建 BM25 索引 → 检索质量评测。
- 当前 KB 体量是 **40 条 seed 词条**；灌入万级网页碎片后，`自动采集` 子树的 BM25 命中会大量挤占教材内容的检索配额。
- **嵌入 API 仍欠费**（阿里 text-embedding-v4 `Arrearage`）→ 只能 BM25-only 入库。BM25 在 CMRC2018 上表现不差（mock 口径 0.964），但**网页碎片文本**的关键词召回会引入语义不相关的片段（导航、广告、评论、鸡汤文里也含学科关键词），这是 CMRC2018 那种干净问答集不会暴露的问题。

### 2.3 内容错配：这里的"Edu"不是你要的"教学资源"🔴（对比赛叙事最致命）

Fineweb-Edu 的评分标准是"**这段文本对训练 LLM 有没有教育价值**"（知识密度 / 教科书式表达），不是"**这门课的教学资源**"。后果是三条硬伤：

1. **没有章节结构** → `chapterizer.py` 靠「第X章 / 回 / 篇」正则切章，网页语料**全部命中不了**，只能整段入库，拿不到任何层级。
2. **喂不进图谱生成** → `kb/graph_generator.py` 从结构化教材提取知识点与先修关系；喂碎片网页只会产出大量孤立、浅层节点，**直接放大** 9/20 评估里已列的弱点"图谱节点过浅（content ≤300 字）"。
3. **稀释出题严谨性** → `quiz/generator.py` + `quality.py` 的卖点是"**只依据真实材料出题、禁止编造**"。冲刺计划里已有一个已知瑕疵（KB 片段混入导致题目轻微漂移），灌入网页语料会把这个"小瑕疵"放大成"系统性问题"。**这是拿自己的强项去换一个不评分的模块。**

### 2.4 合规错配：比赛硬约束

按 `collector/types.py` 的 L0-L3 分级：

| 判定 | 依据 |
|---|---|
| **L2（仅个人学习可采）** | 底层为网页抓取语料，逐条授权状态不明；`ALLOWED_LICENSE["commercial"] = {"L0"}` → **商用模式会被 `kb_manager.allowed_node_ids()` 自动排除** |

其余合规要点：
- 商用需向 OpenCSG 邮件报备（赛题6 / 国创的商业叙事必须如实披露）；
- V2.2 的 `sft_qa` 是 **DeepSeek 合成的 143 万条 QA** —— 用于教学/出题等于注入 AI 生成内容，与本项目"依据真实材料、禁止编造"的设计原则以及赛题"原创性与真实性"要求存在冲突风险；
- 赛题2/5 均要求"引用他人技术或数据需**明确标注**并获得合法授权" → 用了就必须在方案里单列数据来源与授权说明。

### 2.5 时间/收益错配：9 天窗口内零评分收益

保守路径 5-8 天（下载 1 / schema 验证 0.5 / 学科过滤词表 1 / 灌库+索引 1 / 检索评测 1 / 文档与回滚 0.5+）。

**但收益是 0 分**：赛题2 的评分项是创新性 / 技术实现 / 功能完整性 / 方案完整性 / 应用价值 / 总结展望 —— **没有"数据源丰富度"这一项**；赛题5 也没有。采集模块已经能用（维基 / wikibooks / oiwiki），多加一个源在评委眼里只是"又一个爬虫"。

## 三、什么时候值得用：三个更高性价比的用法

### ✅ 用法 1（强烈推荐，赛前就做）：做中文学科检索的**评测集**

现状痛点：RAG 检索的量化证据只有 **CMRC2018（英文翻译阅读理解集）的 mock 口径**，缺中文学科检索指标 —— 这正好是赛题2「技术实现 20 分」和赛题5「应用效果 20 分」要的硬证据。

做法（1-2 天）：
1. 取 `pretrain/score_4_5` 的 **1-2 个分片**，用学科种子词过滤出 2000-5000 条中文学科语料；
2. 构造 query-doc 对（可用 `sft_context` 的"原文 + 问答"结构，或让 LLM 从文档生成问句）；
3. 复用 `scripts/eval_rag.py` 跑 Recall@1 / Recall@5 / MRR，与 CMRC2018 结果并列成表；
4. 输出进 `reports/`，直接引用到技术方案与答辩 PPT。

**这是唯一一个"1-2 天投入 → 直接换评分表分数"的用法。**

### ✅ 用法 2（赛后）：出题/解题模型的 SFT 语料

V2.2 `sft_qa` 143 万条 + `sft_context` 14.6GB（带原文出处）→ 可用于微调专用出题小模型。属赛后路线图，赛前勿动。

### ✅ 用法 3（半天，顺手做）：反哺学科种子词

用 score_4_5 子集统计学科术语共现，扩充 `subjects.json` 的 `seeds`，让现有维基/wikibooks 采集的召回更准。低成本、零风险。

## 四、如果坚持要接入：不翻车的最小方案（7 步）

> 前提：**只做预置语料（路线 B），不改适配器协议，不碰出题与图谱生成。**

1. **只取一个分片**：`load_dataset("opencsg/Fineweb-Edu-Chinese-V2.2", data_files="pretrain/score_4_5/<单个 parquet>")`；国内走 `hf-mirror` 或 ModelScope 镜像，**不要全量下载**。
2. **先验 schema**：确认是否有 `url` / `meta.ori_source`；无 url 则 `source_url` 填 `fineweb://<id>`（仍满足去重与断点续传的键要求）。
3. **学科白名单过滤**：用现有 dsa 种子词 + 术语表做关键词过滤；质量门槛建议 **≥500 字、中文占比 ≥70%、剔除导航/广告/版权声明正则**；目标 **≤5000 条**。
4. **独立目录 + 标 L2**：入库到 `自动采集/L2/网页语料/{学科}/`，与 `L0/学科教材` **物理隔离**（`allowed_node_ids()` 已支持商用模式自动排除 L2 子树）。
5. **禁止进入两条链路**：① 不作为出题依据（收紧 `CHAT_QUIZ_TOP_K` 的检索范围，排除 L2 子树）② 不作为 `graph_generator` 的输入。只做对话兜底检索。
6. **灌库后必须评测**：跑一次检索质量对比（灌前 vs 灌后 Recall@5）。**下降就回滚**。
7. **保留一键清空**：该目录可整树删除，不影响教材图谱与题库。

成本估算：磁盘 2-5GB；灌库 0.5-1 天（BM25-only，不依赖 embedding 额度）；总计 **2-3 天（不含评测集构造）**。

## 五、若最终采用，材料里的答辩口径（三句话）

1. 数据来源写全：`opencsg/Fineweb-Edu-Chinese-V2.2`（Apache-2.0 + OpenCSG 社区许可），底层为 CCI2/SkyPile/Wanjuan 等公开网页语料；
2. 授权分级写清：本系统将其标记为 **L2（仅个人学习）**，商用模式下由 `allowed_node_ids()` 自动排除，不参与出题与图谱生成；
3. 用途写窄："用于**中文学科检索质量的评测集与冷启动背景语料**"，不要写成"教学资源采集源" —— 后一种写法会让评委追问课程体系与内容准确性。

## 六、未核实项（不臆断）

1. V2.1 / V2.2 各版本的**确切 parquet schema**（是否有 `url`、`meta.ori_source`；不同版本与社区转存版本字段不一致）→ **下载单个分片后 `print(ds.features)` 确认**。
2. V2.2 `sft_context` 的"原文出处"字段结构与可用性（官方称 14.6GB、面向 RAG 检索训练）。
3. 国内下载 70GB 档的实际带宽与耗时（未实测）。
4. 单一分片内学科相关文档的**实际占比**（决定过滤后能否凑够 2000-5000 条），需抽样后才知道。
5. OpenCSG 社区许可对"竞赛作品展示"是否视为商业用途（建议发邮件确认，或按商用口径从严处理）。
