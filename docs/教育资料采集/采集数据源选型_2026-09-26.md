# 采集数据源选型决策（2026-09-26）

> 问题：资源采集模块到底该采什么？学科锚点 = 《数据结构》（计算机科学与技术 · 工学）。
> 前置结论（见 `Fineweb-Edu-Chinese_数据源可行性评估_2026-09-26.md`）：**采集模块不是主数据源**，主数据源必须是"有章节、成体系的教材"；采集只做"知识点的补充释义"。

---

## 〇、前提修正：本系统是多学科通用（2026-09-26 追加）

> 初稿按"锚定《数据结构》"给源，范围过窄。**本系统定位是覆盖大学 14 门类 + K12 + 考核类的全学科助学系统**
> （依据：`教育资料采集模块_设计讨论.md` §4.1，2026-09-05 用户确认"全部包含、不设范围限制"）。
> 因此**不存在"一个源搞定所有学科"**——正确形态是**三层源 + 按学科路由**。

### 多学科下的三层源架构

| 层 | 作用 | 源 | 覆盖 |
|---|---|---|---|
| **L1 通用知识层** | 全学科概念兜底（唯一能全覆盖的 L0） | **维基百科 + 维基教科书**（CC BY-SA） | 全学科 |
| **L2 学科专属层** | 该学科的深度内容，按学科路由启用 | CS→**OI Wiki / Hello 算法**；大学理/工/社科/商科→**OpenStax**（英文，CC BY）；K12→国家中小学智慧教育平台电子课本（结构骨架）；考核类→**官方考试大纲** | 单学科/单场景 |
| **L3 分散层** | 真题/教辅/讲义（无集中源） | `web_page` 白名单 + **AI 生成变式题**（复用 quiz 模块，绕开版权） | 按场景 |

**关键认知**：多学科场景下，**"教材本体"的主力永远不是采集，而是用户上传**（任意学科通用，这才是产品的真实能力）；采集只负责 L1 概念兜底 + L2 学科深度补充。

### 按场景的源组合（沿用设计文档 §4.5 矩阵）

| 场景 | 知识骨架（L0） | 目录/大纲源（决定章节树） | 题库/练习 |
|---|---|---|---|
| K12 同步学 | 维基百科（概念兜底） | 国家中小学智慧教育平台电子课本（**需核实 ToS，建议半自动**） | AI 变式题 |
| 大学本科 | 维基 + 维基教科书 + OpenStax（英文教材级） | 教材目录 / 用户上传教材 | 教材习题 + AI 变式 |
| 竞赛编程（CS） | **OI Wiki（L0，最优场景）** | OI Wiki 目录 / 《Hello 算法》`chapter_*` | OJ 题 + AI 变式 |
| 职业资格考核 | 维基 | **官方大纲（如软考 ruankao.org.cn，官方免费、集中）** | 真题→AI 变式（商用只走变式） |
| 通识自学 | 维基分类树 | — | AI 变式 |

**如果只能做一件事：把维基百科这个"唯一全学科 L0 源"变得可用（离线镜像 / 缓存预热），并把学科目录树落盘。**

## 一、先定判据（不满足这四条的一律排除）

| # | 判据 | 为什么 |
|---|---|---|
| 1 | **开放授权且可追溯**（CC BY-SA / 公有领域，能定到 L0-L1） | 赛题明文要求"引用他人数据需明确标注并获合法授权"；本项目 `usage_mode=commercial` 只放行 L0 |
| 2 | **有 URL、可按关键词发现**（适配 `search → 候选(source_url) → fetch` 协议） | 不改造采集域的适配器协议与前端交互 |
| 3 | **条目化 / 有章节结构** | 条目标题即知识点名 → 直接当图谱节点；有"第X章/chapter_" → `chapterizer` 能切章 |
| 4 | **中文 + 国内可稳定访问** | 已实测痛点：维基走外网慢；`oiwiki.py` 当前 base 是 `raw.githubusercontent.com`（国内常不稳） |

## 二、推荐源详解

### ① 《Hello 算法》—— 拿来做知识图谱本体（不是采集，是上传教材）

| 项 | 内容 |
|---|---|
| 仓库 / 站点 | `github.com/krahets/hello-algo`；在线阅读 `hello-algo.com`；PDF/EPUB 在 Releases |
| 内容 | 数据结构与算法入门全书，**章节以 `chapter_*` 命名**（天然贴合学习曲线）：数组、链表、栈、队列、哈希表、树、堆、图、排序、搜索、动态规划、贪心… |
| 背书 | 清华计算机系邓俊辉教授、亚马逊资深首席科学家李沐推荐；13 万 Star |
| 许可 | **CC BY-NC-SA 4.0（文本/代码/图片/视频一致）→ 禁止商业性分发** → 定 **L2**，`usage_mode=commercial` 自动排除 |
| 怎么用 | **下载 PDF 或 `docs/` 的 Markdown → 走用户上传教材链路**（`kb/parsers` → 分块 → 双索引 → `graph_generator` 建图）；章节命名对 `chapterizer` 友好 |
| 工作量 | **0.5-1 天**，同时直接交付 TODO P0 第 4 项「演示学科图谱（15-20 节点 + 先修边）」——一箭双雕 |

> 这是当前**唯一能同时满足"中文 + 成体系 + 有章节 + 开放授权 + 与《数据结构》完全对齐"的教材级语料**。

### ② OI Wiki —— 采集模块的主源（唯一可商用的 L0）

| 项 | 内容 |
|---|---|
| 站点 | `oi-wiki.org`；Gitee 镜像 `gitee.com/OI-wiki/OI-wiki`；`gh-pages` 分支可离线部署 |
| 内容 | 算法/数据结构/竞赛知识条目化百科：栈、队列、二叉树、图论、复杂度… **条目标题 = 知识点名**，含代码与复杂度分析 |
| 许可 | **除代码部分外 CC BY-SA 4.0 + SATA**（署名 + 相同方式共享 + 给仓库点 Star）→ **定 L0，个人与商用均可采** |
| 现状 | `adapters/oiwiki.py` 已实现且 17 个测试通过，**只差真网联调**（`TODO.md` 挂"待议"） |
| 必改一项 | `_RAW_BASE` 现为 `raw.githubusercontent.com`（国内不稳）→ 改 **Gitee raw 镜像**或**本地 gh-pages 静态站** |
| 工作量 | **0.5 天**（换 base + 真网联调） |

**强烈建议改成"本地离线部署"**（`git clone -b gh-pages` + `python -m http.server`）：
1. 演示零延迟、不依赖外网 —— 直接解决你记录的"采集慢、体验差"痛点；
2. 答辩可讲"**支持私有/离线数据源接入**"，把弱点转成设计点；
3. 避免比赛现场断网翻车。

### ③ 维基百科 / 维基教科书 —— 保留但降权

CC BY-SA → L0，合规没问题，但：外网访问慢、内容是百科式不成体系、切章命中率低。保留作为"兜底源"，演示时不主推。

## 四、多学科落地：代码侧必须先改的三件事

> 这三件比"换数据源"更决定多学科能不能成立。

| # | 事项 | 现状 | 为什么必须改 |
|---|---|---|---|
| 1 | **适配器加学科路由** | `manager.search` **并行遍历全部已注册适配器**（wikipedia / wikibooks / oiwiki / web_page），无学科过滤 | 多学科下必然串味：学"高中生物"会召回 OI Wiki 的算法条目。做法：给 `BaseAdapter` 加 `scope`（`universal` / `subjects=[...]` / `stages=[...]`）+ `priority`，`registry` 按学科筛选后再并行 |
| 2 | **学科目录树落盘** | 仓库里**没有 `subjects.json`**（`git ls-files` 只有加载器 `subjects.py`），它是运行时数据 | 学科树是"不遗漏"的骨架（设计文档 §4.3）。没有它，多学科只剩一个空壳的加载器。做法：按 `stage → 门类 → 学科 → seeds + 资源配比画像(knowledge:quiz) + 权威锚点` 建文件并提交 |
| 3 | **修文档漂移** | `教育资料采集模块_设计讨论.md` §5 写"`web_page` 未实现（Batch 3）"，但 `adapters/__init__.py` **已注册 `WebPageAdapter`** | 文档与代码不一致会让后续所有决策基于错误前提 |

## 五、落地顺序（多学科视角重排）

| 顺序 | 事项 | 产出 | 工作量 |
|---|---|---|---|
| 1 | **学科目录树 `subjects.json` 落盘并提交**（先做 3-5 个学科：CS / 高中数学 / 大学物理 / 软考 / 通识） | 多学科骨架 + 前端学科选择有数据 | 0.5 天 |
| 2 | **维基百科可用性**：缓存预热 或 本地镜像（Kiwix / dumps），不再实时打外网 | 唯一全学科 L0 源可用、演示不卡 | 0.5 天 |
| 3 | **适配器加 `scope` 学科路由** | 选"计算机"才出 OI Wiki，其他学科不串味 | 0.5 天 |
| 4 | OI Wiki 换 base（Gitee raw 或本地 gh-pages）+ 真网联调 | CS 学科深度源可用 | 0.5 天 |
| 5 | 《Hello 算法》Markdown 上传 → 切章 → 生成《数据结构》图谱 | **演示学科图谱（TODO P0 #4 关闭）+ 示范学科验证样本** | 0.5-1 天 |
| 6 | 材料里写清数据来源与授权（口径见下） | 合规 | 0.2 天 |

> 说明：OI Wiki 与《Hello 算法》从"主源"降级为 **CS 示范学科的深度源** —— 它们依然要做（演示数据靠它们），但不再代表全学科答案。

## 五之二、多学科与比赛的关系（不冲突）

- 赛题5 只有「需求分析 15 分」要求**锚定一个具体学科** → 用**示范学科**（《数据结构》）满足即可；
- 赛题5 的「方案可行性 20 分」细则原文含"**推广价值高**"与"说明在同类学科或院校的**复用条件**" → **多学科通用是这 20 分的加分项，不是扣分项**；
- 赛题2 的「功能完整性 20 + 应用价值 15」→ 多学科覆盖同样加分。
- **推荐口径**：面向全学科的通用自适应导学平台，本作品以《数据结构》为**示范学科**完成端到端验证与教学试点。

## 六、维基百科「网速慢」的解决方案（2026-09-26 追加）

### 6.1 慢在哪（代码级诊断，非猜测）

| 层 | 现状（`http.py` / `adapters/wikipedia.py` 实测） | 影响 |
|---|---|---|
| 网络 | `api_host = https://zh.wikipedia.org` 直连，跨境 RTT + 丢包 | 单请求 2-10s，30s 超时都可能触发 |
| 数据量 | `fetch` 走 `prop=revisions&rvprop=content`，**每次拉全量 wikitext**，中文条目动辄几十~几百 KB | 主要体积开销 |
| 并发 | `CollectorHttp(retries=2)` **未传 `max_concurrency` → 默认 4**；timeout 默认 30s | 20 条 = 5 批；一条慢请求占住信号量 |
| 缓存 | **无任何缓存**，同一条目重复采 = 重复跨境请求 | 演示反复点同一学科最痛 |
| 失败表现 | 超时/网络错 → 重试后**静默返回 None**，前端看到"0 条候选"而非"网络慢" | 体验上像"功能坏了" |

### 6.2 四套方案（按性价比排序）

| 方案 | 做法 | 工作量 | 效果 | 适用 |
|---|---|---|---|---|
| **A 预热/预置（推荐默认）** | 写 `scripts/warmup_collector.py`：按学科种子词批量 search+fetch，结果落 `data/collector/seed/{subject}/*.md`，再用 `seed_collector.py` 灌库 | **0.5 天 + 跑一夜** | **演示 100% 本地，零延迟** | 赛前必做 |
| **B 轻量 API + 提并发 + 缓存** | ① fetch 默认走 `prop=extracts&explaintext=1&exintro=1`（导言段，体积降 ~10×），全量 wikitext 仅按需 ② `max_concurrency` 4→8、timeout 30→15s ③ 加 title→内容落盘缓存 ④ 可选 `http2=True`（维基支持 h2 多路复用） | **0.5 天** | 日常采集体感提升数倍 | 日常必做 |
| **C 本地镜像（彻底离线）** | **Wikipedia dumps**：`dumps.wikimedia.org/zhwiki/` 的 `pages-articles` 分片 → **dump 里就是 wikitext，可直接复用现成的 `wikitext_to_md()`**，与代码最契合；或 **Kiwix zim + kiwix-serve**（REST API，与 MediaWiki Action API 不兼容，适配器要加后端分支） | 1-2 天 + GB 级下载 | 永久离线，全学科覆盖 | 有余力/赛后 |
| **D 换入口（小优化）** | `zh.m.wikipedia.org` 移动版；第三方镜像 | 0.1 天 | 收益有限且**第三方镜像有合规风险，不建议依赖** | 不选 |

### 6.3 推荐组合

> **A 兜演示 + B 管日常 + C 留作赛后。**
> 比赛现场**绝不允许**依赖实时跨境网络——演示数据全部走 A 的预置库。

### 6.4 B 方案的四处具体改动

1. `adapters/wikipedia.py::fetch` 加 `mode` 参数：`intro`（默认，`prop=extracts&explaintext=1&exintro=1`）/`full`（保持现 wikitext 路径）；
2. `http.py`：`max_concurrency=8`、`timeout=15.0`、可选 `http2=True`（需装 `httpx[http2]`）；
3. 新增 `core/collector/cache.py`：`title → (markdown, ts)` 落盘缓存 + TTL，命中直接返回；
4. 采集失败不再静默：返回明确的降级状态（"网络超时，已跳过"），避免前端表现成"搜不到"。

### 6.5 合规提醒

预置/离线的维基内容**仍然需要署名与 CC BY-SA 标注**（L0 定级不变），离线不等于免署名。

## 七、比赛材料里的数据来源口径（照抄即可）

> 本系统知识库的数据来源分两类：
> 1. **用户自主上传的教材/讲义/课件**（用户自行确保授权）；
> 2. **开放授权资源自动采集**：OI Wiki（CC BY-SA 4.0，L0，个人与商用均可采）、维基教科书与维基百科（CC BY-SA，L0）；《Hello 算法》（CC BY-NC-SA 4.0）仅用于**个人学习模式**，系统在商用模式下由 `allowed_node_ids()` 自动排除非 L0 内容。
>
> 系统在采集与检索全链路执行 L0-L3 授权分级（见 `core/collector/types.py`），L3 一律不采。

## 八、未核实项

1. OI Wiki Gitee 镜像的 raw 路径与同步时效（是否滞后上游）。
2. 本地 gh-pages 静态站的相对图片/MathJax 在入库后的表现（适配器已做相对图片处理，需实测）。
3. 《Hello 算法》PDF（Releases）与网页版的一致性（官方称 PDF 滞后 1-2 周）；若建图谱，建议用 `docs/` 的 Markdown 源文件而非 PDF。
4. CC BY-SA 4.0 的"相同方式共享"对本项目"把内容写进知识库并二次组织"是否触发衍生作品义务 —— 建议在方案中写明"署名来源 + 同样以开放方式提供"，从严处理。
