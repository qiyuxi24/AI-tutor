## 1. 目标与非目标

### 目标
让 TutorAgent 具备 **自主获取外部教育资源并入库** 的能力：
- 按学科/主题**搜索 → 下载 → 解析 → 入库**学习资料（教材、讲义、词条、开放课程文本）
- 按学科/主题**获取结构化题目**并入题库（复用 quiz 链路）
- 全程**版权可控**：区分「商用 / 个人使用」两种模式，可在设置页切换
- 学科**覆盖全面可审计**：以权威学科目录为骨架，能看出哪些板块已采集、哪些遗漏

### 非目标（本期不做）
- 不做通用无差别爬虫（不抓超星/学习通/网盘等灰产题库接口）
- 不做 PDF/Word 内嵌图片复杂排版还原（已有解析器，够用）
- 不做全自动无人工确认的批量灌库（每个候选入库前可见可勾选）

---

## 2. 关键前提：入库链路已存在，本模块只做「找 + 下载 + 识别」

| 资产 | 现有落地通道 | 复用什么 |
|------|------------|---------|
| 资料(文本/PDF/MD) | `kb_manager.upload_and_index(user_id, filename, content, parent_id)` | 解析→分块→向量化→BM25→目录树，全自动 |
| 结构化题目 | `quiz_store.save_questions(questions, subject, difficulty)` | 5 类题型 + 作答/判分/统计 |
| 资料被对话引用 | RAG pipeline 自动检索 | 入库即生效，零额外工作 |
| 学科图谱生成 | `/kb/graph/generate` | 采集的资料可直接喂给图谱生成器 |

> 推论：模块核心工作量 = **来源适配层（SourceAdapter）+ 学科目录 + 版权分级 + 任务编排**。

## 3. 版权合规：双模式设计（核心议题）

### 3.1 法律背景调研
- 中国《著作权法》第 24 条：**个人学习、研究/欣赏**（第 1 项）、学校课堂教学（第 6 项）属合理使用，可不经许可不付酬，**但必须指明作者/作品名称，且不得影响正常使用/损害权利人合法权益**。
- 合理使用为**封闭式列举**，"三步检验法"，**不得扩大解释**——商用/公开发布场景不能适用"个人学习"豁免。
- 知识共享 CC 协议对**商用（Commercial）有明确限制**：
  - `CC BY / CC BY-SA`：可商用（SA 要求同协议共享）
  - `CC BY-NC / CC BY-NC-SA`：**禁止商用**
  - `CC0 / Public Domain`：可任意使用
- 竞赛/商业发布场景须规避 NC 源；个人学习场景（合理使用）范围可放宽，但仍需署名留痕。

### 3.2 来源授权分级（license 分级）
每类来源按"商业可用性"打标签，作为双模式的**过滤依据**：

| 授权等级 | 含义 | 示例 | 个人模式 | 商用模式 |
|---------|------|------|:-------:|:-------:|
| L0 | 公有领域/CC0/开放授权 | 维基百科(CC BY-SA)、OI-wiki(CC BY-SA)、公有领域教材 | ✅ | ✅ |
| L1 | 作者明确授权转载/仅注明出处 | 特定开源教材站点 | ✅ | ⚠️ 需白名单核验 |
| L2 | 合理使用（个人学习） | 一般网页正文、公开题目页 | ✅ | ❌ |
| L3 | 版权不明/明确禁止 | 付费题库、网盘资料、超星类 | ❌ | ❌ |

### 3.3 双模式定义（2026-09-05 用户确认方向）

| | 个人使用模式（personal） | 发布/商用模式（commercial，内部即"阉割版"） |
|---|---|---|
| **适用场景** | 个人自学（绝大多数使用） | 商业产品、**比赛公开展示/发布** |
| **可采授权等级** | L0 + L1 + L2 **尽量全量爬取一切资料**（合理使用边界内） | **阉割版**：仅 L0（+人工核验的 L1） |
| **设计取向** | **全面优先**：宁多勿漏 | **安全优先**：授权不明确的源全部不可采 |
| **入库资料标注** | 记录来源 URL + 授权等级 + "个人学习用途" | 强制标注 License + 作者 + 来源 |
| **界面提示** | 采集前轻提示「个人学习用途」 | 强约束：L1/L2 源灰化不可选 |
| **用途角标** | 资料/题目卡片显示「个人」徽标 | 显示授权图标（如 CC-BY-SA） |

### 3.4 落地位置
- **设置入口**：`SettingsView.vue` 新增「资源与版权」分组，单选切换 personal / commercial
- **存储**：账号级设置，复用用户画像 `preferences.usage_mode`（勿新建表，零迁移）
- **默认值**：`personal`
- **演示策略（已确认）**：比赛/演示用**空白账号 + 个人模式**现场采集，无需第三态"演示模式"

### 3.5 历史数据策略（已确认简化版）
- 模式切换**只影响后续采集行为**，不清除历史数据
- 若从个人模式切到商用模式：界面提示"此前按个人模式采集的内容仅限本地个人使用，请勿对外传播"——**仅提示，不动数据**
- 比赛演示账号为空白账号 → 无历史数据包袱

## 4. 学科全面覆盖（核心议题）

### 4.1 学科目录选型（保证"不遗漏"的骨架）
候选基准：
| 体系 | 规模 | 适用 | 备注 |
|------|------|------|------|
| 教育部《研究生教育学科专业目录》 | 14 门类 / 117 一级学科 | 大学自学 | 覆盖考研/本科高年级 |
| 教育部《普通高等学校本科专业目录》 | 12 门类 / 93 专业类 | 本科低年级 | 专业粒度更细 |
| GB/T 13745 学科分类与代码 | 5 门类 / 62 一级 | 科研 | 偏研究 |
| K12 课程体系（部编版/人教/新课标） | 语数英物化生史地政等 + 学段 | 中小学 | 按课程标准分册/章 |
| 职业资格考试名录 | 软考/一建/法考/教资等 | 考核类 | 按考试大纲 |

> **2026-09-05 用户确认**：**全部包含**（大学 14 门类 + K12 中学 + 考核类），不设范围限制。
> 目录树 = `学段(stage: k12/university/professional) → 门类/大类 → 一级学科/科目 → 板块`。
> 具体目录数据文件待细化（见 4.4）。

### 4.2 「资源形态」差异维度（用户提出的关键洞察）

不同学段的资源形态**差异极大**，采集策略不能一刀切：

| 学段/类别 | 知识资料密度 | 题型/练习量 | 采集侧重 | 说明 |
|-----------|:----------:|:----------:|---------|------|
| **K12（中学）** | 低（知识点少而固定） | **极高（题海，需大量训练）** | 资料少量 + **题库优先、海量** | 一个知识点衍生几十种题型，训练量大 |
| **大学本科** | 高（概念/理论密度大） | 中（题型相对收敛） | 资料优先 + 适量题库 | 理论讲解比刷题重要 |
| **考核类（软考/一建等）** | 中（大纲固定） | **高（真题反复练、体量大）** | **真题/题库优先** | 内容分散于各培训机构，且高度重复考 |

> **推论**：目录中每个学段/学科节点需挂「资源配比画像」，即采集时**按知识资料与题库的权重配比**去发现资源，
> 而非每科都平均抓。这也决定前端「采集推荐」的默认勾选策略。

### 4.3 覆盖机制（可审计）
- **种子目录文件**：`data/collector/subjects.json`
  - 学段树 + 每学科：知识种子词 + **资源配比画像(knowledge:quiz)** + 权威来源锚点（Wikipedia 分类页 / 考试大纲 / 教材目录）
  - K12：按「科目 → 教材章节」锚定（如 高中数学 → 人教 A 版 章节树）
  - 考核类：按「考试大纲 → 考点」锚定（软考中级 → 各科目大纲考点）
- **采集状态表**：记录 `subject / board / source / license / status(未采/采集中/已完成/失败) / 资源数 / 资料数 / 题数`
- **覆盖率视图**：前端展示「学段 → 学科 → 板块采集雷达」，缺口一目了然（直击"不遗漏"诉求）
- 自动扩面：Wikipedia `categorymembers` 递归拉某学科分类下全部条目 → 生成待采候选清单（可选深度）

### 4.5 分场景采集策略（2026-09-05 调研，核心议题）

核心追问：**"怎么才能拿到最重要、最全面的资料" → 决定搜索策略。**
调研结论：不同学习场景的"最重要资料"类型、权威源集中度、获取难度差异极大，**不能一套搜索策略通吃**，需按场景定制。

| 场景 | 代表用户 | 最重要资料 | 权威源/集中度 | 获取难度 | 授权 | 策略要点 |
|------|---------|-----------|--------------|---------|------|---------|
| **K12 同步学** | 中小学生 | 电子课本(知识骨架) + 章节习题 | **国家中小学智慧教育平台(smartedu)**，官方单一源**集中** | 中(有开源下载器 smartedu-dl，解析PDF) | 官方教育公共服务，个人学习✅ | 教材目录静态内置 + 按学段/科目/册抓电子课本 |
| **K12 应试(中考/高考)** | 中学生 | **历年真题海量** + 教辅 | **分散**于各机构站(组卷网/真题吧/机构站) | 高(站点多、有登录墙) | 真题版权模糊，个人合理使用✅ 商用❌ | 个人模式 web_page 白名单抓取 + 用户自查；真题→AI 出变式 |
| **大学本科/考研** | 大学生 | 教材/讲义 + 大纲 + 公共课真题 | 中文出版教材版权严；MOOC(icourse/xuetangx)**需登录视频为主难抓**；考研真题机构站集中(启航/中公/eol 免费公开) | 中高 | 开放教材(OpenStax CC)✅；中文教材仅合理使用 | 知识主体走 Wikipedia/OI-wiki 等 L0；讲义/真题 web_page |
| **职业资格考核** | 软考/一建/法考/注会考生 | **考试大纲(唯一结构权威)** + 历年真题(反复考) | 大纲=**官方单一源集中**(如软考 ruankao.org.cn)；真题=**分散**于培训机构(希赛/各题库站) | 低(大纲) / 高(真题) | 大纲官方免费✅；真题机构公开部分✅ | **大纲必抓(决定目录结构)** + 若干年真题 + AI 生成变式(呼应 quiz 模块) |
| **语言考试** | 四六级/雅思/托福 | 官方样题 + 真题 | 官方样题限量；真题机构整理分散 | 高 | 样题官方✅ | 题型固定→AI 生成变式为主，真题为辅 |
| **竞赛编程** | OI/ICPC 选手 | 算法/数据结构知识 + OJ 题 | **OI-wiki 整站 CC BY-SA 开放**(集中) | 低(按目录抓即可) | L0 ✅ | **L0 全量可采**，最优场景 |
| **通识/自学** | 泛用户 | 概念性知识 | Wikipedia/Wikibooks 分类树 | 低(API) | L0 ✅ | 全学科知识骨架 + 出题素材 |

**三条通用策略法则（从矩阵提炼）：**
1. **官方单一源 = 直通车**：大纲/教材类先抓（结构权威、URL 集中、可全量），决定目录骨架（软考大纲、K12 教材、OI-wiki 目录）
2. **L0 开放源做知识主体**：Wikipedia/Wikibooks/OI-wiki 是唯一可全量自动采集的知识来源，覆盖全学科概念层
3. **分散型习题/真题 = 漏斗策略**：无集中源 → ① 个人模式 web_page 白名单抓公开机构页 ② **真题/样题 → AI 生成变式题**（绕开版权依赖 + 呼应"题海训练量"诉求），商用模式只走 ②

**待讨论**：以上 7 类场景分类是否覆盖你的预期？有无遗漏场景？

## 6. 技术架构草案

### 6.1 采集流程
```
用户: 选择 学科/板块 + 模式 + 触发采集
  → collector.search(subject, mode)   # 各 adapter 并行发现候选
  → 候选列表(标题/来源/授权/大小/预览) → 用户勾选
  → collector.fetch(item)             # 下载
  → 复用 parsers 解析 / dataset loader 转 Question
  → upload_and_index() / save_questions() 入库(带 source/license 元数据)
  → 更新采集状态表 → 前端覆盖率刷新
```

### 6.2 关键技术点（已调研部分结论）
- **HTTP**：复用项目已有 `httpx`
- **网页正文抽取**：调研结论 → **主用 `trafilatura`，`readability-lxml` 作后备**
  - trafilatura：现代、轻量、输出干净 Markdown/纯文本，自带元数据+日期+许可字段提取，社区口碑最稳（"最稳的开源正文提取器"）
  - readability-lxml：经典 Mozilla 算法，部分 trafilatura 失败的页面可兜底
  - 两者失败/效果差的页面 → 弃用该候选（不做多级复杂兜底，YAGNI）
- **异步任务**：采集耗时长，需任务机制。当前 FastAPI 无任务队列。候选：进程内 `asyncio.create_task` + 状态轮询（uvicorn 单 worker 约束下可行，最简单）vs 引入 arq。**倾向先做进程内任务表（内存 dict + SQLite 持久化状态）**
- **元数据落点**：
  - 资料 → KB `nodes` 是否加列存 source/license？倾向 **不迁移**：用目录树表达（`自动采集/{授权等级}/{学科}/...`）+ 正文头部 YAML front-matter 注来源
  - 题目 → `questions.source` 字段已存在，直接复用

### 6.3 来源发现策略（学科全覆盖的技术手段）
- MediaWiki API 三件套（全部免费、结构化、无 key）：
  - `search`：按学科种子词全文搜索
  - `categorymembers`：**给定学科分类 → 递归拉取该分类下全部条目**（这是"学科板块全覆盖"的关键 API，可生成待采候选清单）
  - `parse/extracts`：拉条目正文
- Wikibooks 与 Wikipedia 同栈（MediaWiki），姊妹计划，**同一套 API 代码可复用**（URL 换 host + 项目名即可）
- OI-wiki 站点自带完整目录树（`/ds/`、`/math/` 等板块），锚定 CS 板块可直接按目录清单抓取
- 中文维基/维基教科书是 L0（CC BY-SA），是双模式下唯一可全量自动采集的来源，优先做主链路

### 6.4 新议题：权威目录源「需要时去查」（用户 2026-09-05 提出）

用户想法：学科目录本身不必全部内置维护，而是**对接权威来源，需要某个学科时实时查询**。
- 适用对象：K12 科目章节（教材目录）、考核类大纲（软考/一建等）这类**动态且分散**的目录
- 潜在权威源：教育部/考试院公开大纲、教材出版社目录、Wikipedia 分类树（作为学科入口）
- **待讨论**：
  - 这套"目录按需查询"与"内容采集入库"的关系——是两级联动（先查目录→再采内容）还是并行两条？
  - 目录源是否有稳定的 API/页面可解析？K12 教材目录在官网常以静态页/PDF 存在，抽取成本不一
  - ponytail 视角：**先把内置静态目录（大学+K12主干+考核类名录）做成 v1 是否已够用？** "按需查目录"可作为 v2 增强，避免首版同时啃两块硬骨头

### 6.5 需登录网站的采集策略（2026-09-05 讨论）

用户提出：zlibrary 类全量开源网站需要账号登录，能否"用户登录后我们再抓"？

**技术方案（通用、可行）：Cookie 会话复用，两级落地**
1. **浏览器辅助登录（推荐）**：采集器内嵌浏览器（复用项目已有 agent-browser / playwright 生态），用户在弹窗中正常登录目标站一次 → 导出登录 Cookie（持久化在**用户本机/用户级数据目录**）→ 后续 `httpx`（或继续 playwright）以该会话抓取下载
2. **手动粘贴 Cookie**：用户在浏览器 DevTools 复制 Cookie 粘贴进采集配置，适合无头环境/纯 API 抓取
- 关键设计：凭据**只属于该用户**，隔离存储、不跨用户共享、不落日志、明文仅存本地配置

**合规红线（必须明确，尤其比赛"原创无纠纷"）**
- 需登录 ≠ 授权下载。**站方 ToS 禁止抓取 / 会员付费墙**的站点，即使用户登录抓取也违约，且可能属侵权（如 zlib 类盗版书库，本身是未授权分发源）
- **分类处理**：
  - 合法但需登录的资料站（如部分机构免费资料、需登录才可见的官方大纲附件）→ 会话抓取，标注 L2 个人用途
  - 盗版/未授权分发库（zlib 类）→ **不内置适配器**；即便个人模式也置灰，避免合规与封号风险；建议提示用户走正版/官方渠道
  - 商业付费会员站 → 会话抓取违约风险高，默认置灰（个人模式可留"用户自行承担"的强提示入口？——待决 #15）

### 6.6 资料组织存放与细化整理（2026-09-05 讨论，地基设计）

用户诉求：资料存进来后要**细化、递归地组织**——最细粒度到「高中的某一个知识点的某一个题型集」；对书籍/课本要能**拆分切片 → 理解 → 整合**。

**现状约束**
- KB 目录树 `nodes`：folder/file 两级以上（资源管理器式，支持多级），文件→chunks 向量化
- 资料有 `path` 溯源（目录路径动态拼）；quiz 题目有 `subject / knowledge_point` 字段
- 缺：**知识点级（非文件级）的组织单元**、**跨来源的题型集合**

**细化层级设计（目录树表达，不迁表）**
```
学段(k12/university/professional)
└─ 门类/大类
   └─ 学科/科目（含 resource 配比画像）
      └─ 板块/教材（如 人教版高中数学必修一 / 软考软设大纲）
         └─ 章/模块（如 函数 / 结构化开发）
            └─ 知识点文件夹（如 函数的单调性）
               ├─ 知识卡片.md（讲解，来自教材切片/L0 开放源）
               └─ 题型集.md 或 quiz 关联（如 单调性证明 题型）
```
- **"最细 = 知识点 × 题型集"** 在现有模型里的落法：KB 里建「知识点」目录（文件级），quiz 题目用 `knowledge_point` 精确关联；或 KB 建「题型集」文件夹内放题目解析 md
- **教材/整书 → 切片流程**：
  1. 抓整书（PDF/电子课本/开放教材）→ 复用现有 PDF 解析
  2. **章节识别切片**（按目录/页码/标题规则）→ 每章独立文件
  3. **LLM 理解整合**：对每章提取知识点、生成 `知识卡片.md`（复用 graph_generator 提示词思路），并可回填图谱
  4. 关联习题到知识点 → 支持「学完知识点 → 自动调该知识点题型集练习」
- 归位机制：采集的文件如何落进正确目录 → **标题/元数据规则匹配为主，LLM 兜底分类**（个人模式可自动，商用/演示可人工确认）

**待讨论**
- [ ] 知识点文件夹粒度是否会过碎导致 KB 目录爆炸？（大数据量下的检索/浏览体验）
- [ ] "题型集"以 KB 文件组织 还是 quiz 的题目标签分组？两处如何联动？
- [ ] 整书切片 v1 用规则（目录/页码）还是 LLM 智能切？成本与准确度权衡

### 6.7 资料组织/查询技术选型调研（2026-09-05）

用户诉求："怎么组织存放 + 怎么查询最快"，点名比较传统 DB vs 现代 RAG，找开源参考。
调研到 3 个高相关参考，**恰好对应三种组织哲学**：

| 参考项目 | 核心思路 | 对我们最有价值的一点 |
|---------|---------|---------------------|
| **BookBoomer**（Apache-2.0） | PDF 教材 → 解析目录 toc.yml → 用户确认 → 按目录生成层级文件夹 → **LLM 逐章抽取原子知识点 Markdown 卡片**（卢曼卡片法），适配 Obsidian | **目录搭骨架 + LLM 抽知识点** = 我们的"整书切片→知识卡片"管线几乎一一对应，可作流程蓝图 |
| **TreeSearch**（shibing624） | **结构感知检索**：不依赖向量模型，用 SQLite 的树/索引先做结构化导航 + 关键词定位，毫秒级(<50ms)，零依赖 | 支持"目录树导航优先"派——先靠结构缩小范围再查细节，而非上来全库向量 |
| **OpenKB** | LLM 把原始文档编译成互链的 wiki 式知识库，vectorless 推理式检索 | 知识间的链接组织，呼应图谱 |

**查询速度结论（结合我们现状）**：
- 我们**已有**现代混合检索（向量 + whoosh BM25 → RRF 融合，见 kb_manager.search），且 **kb.search 已支持 node_ids 目录范围过滤**
- "最快查询"应拆两层、不是二选一：
  1. **结构化导航层**（确定位置，毫秒级）：目录树 + 元数据过滤 → 先收窄到知识点文件夹（TreeSearch 思路）
  2. **语义召回层**（模糊找内容）：现有混合检索在已收窄范围内跑
- **结论**：不引入新检索引擎。v1 沿用现有混合检索 + node_ids 范围过滤（已支持"在某知识点文件夹内检索"），目录导航只是前置于检索的选择器。真正要新做的是"切片 + LLM 理解组织"管线（BookBoomer 流程），而非查询引擎

### 6.8 接入现有 RAG 中间件（rag_pipeline，去耦合）

用户明确要求：新模块接入已有 RAG 中间件，减少耦合（用户记忆中的"中间件" = `app/core/rag_pipeline/`）。

**现状确认**：
- `RagSource` 协议（name/should_query/retrieve）已定义，sources.py 注释里本就预留"未来网页检索"
- pipeline 已注册 graph、kb 两源；chat_service 只调 `pipeline.run()` 一次，按 `source` 分组渲染区块，消费层不知道具体源
- rag 检索已是 Agent function calling 工具（rag_search, source=graph|kb|all）

**接入设计（零耦合新文件 = 新增一个 source 实现 + 注册）**：
1. 采集资料**入库后**（落 KB）→ 天然走现有 `KbRagSource`，无新代码
2. 采集模块若需"入库前的线上源检索 / 采集候选相关性排序"→ 新增 `CollectorRagSource(RagSource)`（name="collector"）实现 retrieve 调 collector 的候选源发现接口，`pipeline.register()` 一行注册
   - 对话中如把"线上采集资料"纳入引用 → collector source 会出现在既有 rag_search / _build_retrieval_context 流程里，消费层零改动
3. **采集任务管理自身不进 RAG 管道**（不是检索问题），走独立 api/collector 路由，只在"检索/引用"层汇入中间件

**待讨论**：采集候选源是否真要进对话引用（线上检索有延迟/质量风险），还是只在采集页使用？

## 11. 里程碑与批次规划（roadmap，2026-09-05 定）

### 11.1 V1 最小闭环（验收标准）
一条完整链路可演示：
```
选学科（如 数据结构）→ 候选源列表(Wikipedia L0) → 勾选 → 下载 → 入库 KB → 对话 RAG 引用 → 采集状态可查
```
- 验收：弱网下也能用**离线种子**走通；点击一次采集到引用 ≤ 3 步内看到效果
- 原则（用户强调）：**去耦合、带测试、复用已有组件**（SourceAdapter 仿 kb/parsers；入库走 upload_and_index；检索走 rag_pipeline）

### 11.2 批次划分
| 批次 | 范围 | 内容 |
|------|------|------|
| **Batch 1（V1）** | 最小闭环（L0 知识主体） | 学科目录 JSON（首期 2-3 学科全链路）；wikipedia/wikibooks adapter；collector 服务 + 采集记录表（含去重 hash）；采集 API；前端最小采集页；离线种子 |
| **Batch 2** | 切片整理 | OI-wiki adapter；整书/长文规则切章入库；LLM 知识卡片整合（BookBoomer 思路）；doc_chunks embedding 可空迁移（支撑"短文档 BM25-only"） |
| **Batch 3** | 题库与 web_page | dataset_quiz 题库导入（复用 save_questions）；web_page adapter（trafilatura）；来源使用统计（溯源表扩展） |
| **Batch 4（v1.5+）** | 登录站与引用增强 | Cookie 会话复用（浏览器辅助登录）；CollectorRagSource 入对话引用评估；本地 sentence-transformers 正式启用 |
| **v2** | 高级 | 权威目录按需查询（§6.4）；整书 LLM 智能切章；多学科目录数据批量内置 |

### 11.3 混合存储落地要点（T1）
- 短知识点卡片/题目（尤其 K12 题海）：**只建 whoosh BM25 / 结构化索引，不做 embedding**
- 长教材/讲义全文：现有向量 + BM25 混合链路不变
- quiz 题本身就存 SQLite（subject/knowledge_point 索引），天然不走向量
- 需要迁移点：`doc_chunks.embedding` 允许为空（Batch 2 做，Batch 1 不动现有表）

### 11.4 溯源与去重（T2）
- 采集记录表必含：`source_url(unique) / content_hash / license / mode / status / times_referenced`
- content_hash 防重复抓取：同 URL 或同内容不重复入库（省 embedding 钱）
- times_referenced 为来源质量统计预留（评估哪个网站资料最有用，后置 Batch 3）

## 13. 第三方审查核对（2026-09-05，逐条对照代码验证）

DeepSeek 对本文档审查提了 8 条（4 致命 + 4 工程雷区）。以下为**逐条对照代码库**后的核对结论——采纳的、采纳但改方案的、拒绝的，都写清理由。

### ✅ 采纳（真缺陷，V1 必须处理）
**① 断点续传（cursor）** — 成立。任务表需 `cursor/checkpoint` 字段（维基递归分页有 `continue` 游标）。**决策**：采集任务表加 `cursor TEXT` + `processed_count`，重启后从断点续。工作量小，Batch1 就做。

**② 取消 = 协作式取消** — 成立。`asyncio.create_task` 不能外部强杀。**决策**：任务对象持 `asyncio.Event`，Adapter 每轮循环检查；取消时优雅收尾（提交已处理、回滚未完成），而非强 cancel。Batch1 做。

**⑤ 维基速率限制** — 成立且 V1 就必须处理（否则演示当场被封）。MediaWiki 要求合法 `User-Agent` + 礼貌限速。**决策**：采集 HTTP 客户端统一设 UA；用 `asyncio.Semaphore` 限并发 + 简单间隔控制（aiolimiter 太重，YAGNI；维基官方建议遵守 maxlag/限速即可）。Batch1 做。

**⑦ LLM 知识卡片幻觉 → 减负** — 成立且**帮我们砍工作量**。**决策修正**：Batch2 砍掉"LLM 生成知识卡片"步骤，**只规则切章保留原文切片**；需要"总结讲解"时让现有 RAG + LLM 在对话时动态生成（这本来就是系统架构）。避免错误知识永久固化进 KB。✅ 这条让 Batch2 更简单。

### ⚠️ 部分成立（采纳但改方案 / 论证有误）
**③ V1 首科选择** — 结论部分对（首科可选"数据结构与算法"，L0 源充足、知识结构化），**但论证有技术错误**：Wikipedia 内容抓取走 MediaWiki API（返回纯文本/维基文本），**不经过 trafilatura**，所以"高数词条太长导致 trafilatura 崩"不成立。真实理由是：高数/物理词条含大量 LaTeX 公式，转 Markdown 复杂；数据结构/算法词条公式少、更规整。**决策**：V1 首科 = 数据结构与算法（走 Wikipedia 主链路 + OI-wiki 参考），第二科选一个公式少的（如 线性代数 或 K12 数学）。

**④ 商用模式检索层过滤** — 缺漏成立（文档 §3.5 只说了采集层），**但"nodes 加列"不是唯一方案**。核实代码：`nodes`/`documents`/`doc_chunks` 表无 license 字段，`kb.search` 无过滤参数。**决策（零迁移方案）**：采集资料按目录落 `自动采集/L{level}/{学科}/...`（文档 §6.2 已设计），商用模式下 RAG 检索前先收集 node 白名单 = 排除 `自动采集/L2` 前缀的节点集合，再传入现有 `kb.search(node_ids=...)`——**复用已存在的范围过滤能力，不加列**。手动上传内容归用户自持（默认不自动传播标注）。Batch1 带此过滤。

### ❌ 不成立 / 对 V1 无影响
**⑥ PDF 扫描件静默失败** — **基本不成立**。核实 `parsers/pdf.py`：已有扫描版 OCR 回退（`SCAN_TEXT_THRESHOLD=20` + RapidOCR），且 `upload_and_index` 已有"解析为空抛 ValueError"防线。增量仅在：OCR 依赖 RapidOCR 未装 + 超大扫描件超 `MAX_OCR_PAGES=60` 时会退回少量文本——属边缘。**决策**：可把入库文本量下限提高到 ~200 字符并 warning（低成本，Batch2 顺手），不阻塞 V1。

**⑧ 磁盘无限膨胀** — 对 K12 百万题场景成立，但 **V1 完全不需要**（2-3 学科 + 离线种子，量级 MB）。storage_quota/TTL 属于 Batch3 开启题库批量导入**之前**的预研项，现在做是过度设计（YAGNI）。

### 总结
- 采纳进 V1：① 断点续传、② 协作取消、④ 检索层商用过滤（零迁移版）、⑤ 限速/UA
- 采纳并简化 Batch2：⑦ 砍 LLM 卡片，只切章保留原文
- 首科建议：数据结构与算法（理由已修正）
- 拒绝：#6 已有防护（仅边缘增强）、#8 V1 不做（YAGNI）
